# Implementation Plan — chat-integration-app

> umbrella spec: [chat-integration](../chat-integration/)。要件は umbrella の `requirements.md` が持つ。
> **本 spec が担当する要件 ID は 50 件**（85 件は 3 つの sub-spec で分担する）。

**`chat-integration-protocol` の完了が前提。** 本 spec は `@growi/chat` の型と関数に依存する。

**Gen 1（`apps/slackbot-proxy` と `packages/slack`）には手を入れない。** 読むだけ。

**feature の外を触るタスクは 7 つある** — 1.1（依存と build の順序）、第 2 章（全体に掛かる 3 つの仕組み）、
3.5（受け口を既存の経路に登録する）、6.1（承認画面の経路）、6.2（個人設定のタブ）、
8.2（定期実行の起動）、9.1（管理画面の受け皿と案内の一覧）。
**それ以外は `features/chat-integration/` の中だけで完結する。**

**各タスクは自分のファイルから直接出す。層の入口はその層の最後のタスクが作る。**
そうしないと、同じ層で並行して進むタスクが 1 つの入口ファイルを取り合う。

---

- [ ] 1. feature の土台を作る
- [x] 1.1 feature の骨組みと依存を用意する
  - `apps/app/src/features/chat-integration/` を作り、`@growi/chat` を依存に足す
  - **build の順序を宣言する**（同じリポジトリ内の build を作る依存が増えたら書き足す決まり）
  - **feature の入口を作り、そこから起動時に辿れるようにする**（次のタスクで置く model が
    読み込まれる経路になる）
  - 型検査と build が通り、feature の入口が起動経路から辿れる
  - _Requirements: 1.3_

- [x] 1.2 新しいデータの置き場所を作る
  - **11 個のコレクション**を宣言する — 関係・紐付け・鍵・通知の控え・処理済みの記録・
    使い捨ての値・保留中のペアリング・一度きりのリンク・所有確認の回数・
    チャンネル権限・通知の宛先
  - **関係の識別子は単独で一意にする**（相手が採番する値だが、届くリクエストがこれだけで
    関係を名乗るので、引き当てが一意にならない形にはできない）
  - 紐付けは関係・サービス・アカウントの組で**複合ユニーク**にする（要件 7.4 の実現手段）
  - 送信待ちの控えには**奪った時刻**の列と、2 つの索引（奪うときに引く組・結果を書き戻すときに引く組）
  - **model は feature の入口から静的に読み込む**（読み込まれた瞬間に索引が作られるので、
    辿れない置き方だと機能を最初に使うまで索引ができない）
  - 起動すると 11 個のコレクションと索引が実際に作られる
  - _Requirements: 7.4, 10.4_
  - _Depends: 1.1_

- [x] 1.3 秘密鍵を暗号化して保存する仕組みを作る
  - **GROWI に前例が無いので、仕組みごと作る**（設定を伏せ字にする既存の仕組みは暗号化ではない）
  - 暗号化に使う鍵は**環境変数から読む**。設定画面からは入れられないようにする
    （保存に入れると、保存を取られた人が暗号化した鍵も一緒に取れて意味が無くなる）
  - **未設定ならペアリングを始められない。平文で保存に落とさない**
  - 復号は署名する関数の中だけで行い、他の層へは復号した値を渡さない
  - 入れ替えのために、行に**どの世代の鍵で暗号化したか**を持たせる
  - 暗号化した列が保存の上では読めず、環境変数が無いとペアリングが始められないことが試験で示される
  - _Requirements: 10.6_
  - _Depends: 1.2_

- [ ] 2. 全体に掛かる仕組みに手を入れる
- [x] 2.1 proxy から届く口だけ、本文を生のバイト列で受ける
  - **全体の JSON 解析より前に**、proxy 向けの口の接頭辞だけ生のバイト列で受ける
  - **掛ける範囲を接頭辞で絞る。**同じ feature の中には管理画面が叩く口もあり、
    そちらまで生のバイト列になると入力検査ごと動かなくなる
  - **`Buffer` のまま扱う**（文字列に足し込むと、複数バイトの文字が塊の境目で壊れる）
  - 種類が JSON でなければ、署名の検証に入る前に断る
  - 日本語を含む本文を送って、口に届いた時点でバイト列が送信時と一致し、
    **同じ接頭辞の下の管理画面用の口は解析済みのまま**であることが試験で示される
  - _Requirements: 10.1_
  - _Depends: 1.1_

- [x] 2.2 proxy 向けの口を、消毒と session の仕組みから外す
  - **保存の値を消毒する仕組みから外す。** その仕組みは `Buffer` を素の object とみなすので、
    全バイトぶんの添字を列挙して 1 件ずつ判定を回す（実測で 1 MiB あたり 0.13 秒、
    上限に決めた大きさでは 1 秒を超える）。**`Buffer` に保存の演算子は入りようがないので、掛ける意味も無い**
  - **session を張る仕組みから外す。** 全体の設定は「一度も触られていない session も保存する」形なので、
    要求 1 本ごとに保存へ文書が 1 件書かれる。とくに**署名の要らない所有確認の口**では、
    回数の上限に達して断る要求も、断る前に文書を 1 件書く
  - 消毒の仕組みは条件無しで登録されているので、包む形で外す
  - proxy 向けの口へ大きな本文を送っても消毒に時間を取られず、session の文書が増えないことが試験で示される
  - _Requirements: 10.1_
  - _Depends: 2.1_

- [x] 2.3 Gen 2 の通知の宛先を、既存の送信処理の外に足す
  - 既存の 2 つの宛先の呼び方には**手を入れない**。Gen 2 の宛先を外側に足す
  - **種類で分岐しない形にするのは Gen 2 側だけ。** 宛先の集合を回す形にする
  - ページの保存時に宛先を指定する経路で、Gen 1 の項目を残したまま Gen 2 の宛先を別項目で受ける
  - パス条件の突き合わせに使う既存の処理を外へ出して共有する。**振る舞いは変えない**
  - Slack が未設定でも Gen 2 の宛先だけで成立するようにする
  - **完了の条件は「Gen 2 の宛先が集合として呼ばれること」まで**（受け側は仮のものでよい）。
    実際に両方へ通知が出ることは 8.1 で確かめる
  - _Requirements: 12.1, 12.2, 12.3_
  - _Depends: 1.1_

- [ ] 3. proxy から届くリクエストを受ける
- [x] 3.1 鍵を保持する
  - 自分の鍵と相手の公開鍵を保持する。**鍵の識別子は関係・側・鍵名の組**で扱う
  - 引くときは**相手側の鍵だけを返す**（自分の鍵を引くと、自分が署名した要求を
    自分の口へ差し戻す形が通る）。失効済みとまだ有効でない鍵は引けない
  - **ペアリングの途中の鍵は保留の行に持つ**（関係がまだ無いので、鍵の置き場所が先に要らない形にする）
  - 署名するときは、**復号した値ではなく署名する手段**を上の層へ渡す
  - 関係と鍵名の組で正しい鍵が引け、自分の鍵が相手側として引けないことが試験で示される
  - _Requirements: 9.5, 10.6_
  - _Depends: 1.3_
  - _Boundary: KeyStore_

- [x] 3.2 届くリクエストの署名を検証し、封筒を突き合わせる
  - **口を作る作業より先に置く**（後にすると口ごとに実装者が各自で決めることになる）
  - **本文は生のバイト列のまま検証に渡す。**解析した値から組み立て直したものを渡さない
    （鍵の並び順が送信時と一致する保証が無く、正しい相手が弾かれる）
  - **使い捨ての値に渡す期限は受ける側が上限で切った値**にし、**検証に成功した後にだけ**消費する
  - **検証の後、契約側の検査関数で本文の形を確かめ、さらに本体の関係の識別子と
    口の名前を突き合わせてから処理へ渡す。** 落としても正常な使い方はそのまま動くので、
    後から気づけない
  - 失敗の種類を記録する。**署名そのものと本文は記録しない**
  - **鍵の並び順だけが違う同じ内容を送ると通らない**こと、**別の口へ宛てた要求が断られる**ことが
    試験で示される
  - _Requirements: 10.1, 10.2, 10.3, 10.4, 10.7_
  - _Depends: 2.1, 3.1_
  - _Boundary: SignatureGuard_

- [x] 3.3 操作した人を解決する
  - チャットのアカウントから GROWI ユーザーと所属グループを引く。**関係も鍵に含める**
    （チャットのアカウントの識別子だけでは workspace の軸が無い）
  - **利用者の状態が「有効」でなければ、紐付いていない扱いにする。**
    停止・削除扱い・承認待ちの人が、画面からは何もできないのにチャットからだけ操作できる状態を作らない
  - **読み取り専用の利用者は、本人として検索は通し、書き込みだけ断る**
  - **ログインしていない相手に何も見せない設定の GROWI では、紐付いていない利用者に
    公開ページも返さない**（外へ本文を出す口では、既存の実装もこの設定を必ず見ている）
  - 断る理由を 3 つに書き分ける（紐付いていない・読み取り専用・利用者が使えない）。
    **利用者が使えない場合に「紐付けが要る」と返さない**（その人は既に紐付けており、リンクを開いても変わらない）
  - 状態が有効でない 4 種と読み取り専用について、正しい分岐に入ることが試験で示される
  - _Requirements: 3.6, 3.7, 4.3, 4.4, 4.5, 7.5, 7.6_
  - _Depends: 1.2_
  - _Boundary: ResolveActor_

- [x] 3.4 所有確認に答える
  - 保留中の登録コードと一致するときにだけ答える
  - **署名するのは用途を示す接頭辞を連結した文字列**であって、受け取った値そのものではない
    （そのままだと、本番の署名に使う同じ鍵で任意の文字列に署名して返す窓口になる）
  - **保留が生きている間はどの問いかけにも答える。**答えた内容を覚えて次から断る形にしない
    （登録コードを見た第三者が本物より先に叩くだけで、その登録コードでは二度と成立しなくなる）
  - 回数の上限は**送り元ごと**に数える。送り元の決め方は契約側の決まりに従い、
    **区別できない設定のときはその旨を運用者に見せる**
  - 上限に当たったことを運用者が見られる形で残す（**取り直せば直ると気づけるようにするため**）
  - 別の送り元が上限に当たっていても本物の問いかけが通ることが試験で示される
  - _Requirements: 9.2, 9.3_
  - _Depends: 3.1, 3.2_
  - _Boundary: PairingEndpoint_

- [x] 3.5 proxy から届く 6 つの口を既存の経路に登録する
  - コマンド・紐付けの開始・**設定の取り出し**・鍵の追加・鍵の失効・所有の確認
  - **既存の apiv3 の経路一覧に、この feature の router を 1 か所で登録する**
    （他の feature も同じ形で配線されている）。中身は後続のタスクが埋める
  - **設定の取り出しは、押し込みが届かなかったときに proxy が取りに来る保険**である。
    版と設定を返す
  - 署名の要る 5 つが署名の検証を通り、所有の確認だけが通らないことが試験で示される
  - _Requirements: 11.4_
  - _Depends: 3.2, 3.4_
  - _Boundary: routes_

- [ ] 4. GROWI が送り出す中身を組み立てる
- [x] 4.1 (P) この利用者が見てよいページだけを残す
  - **既存の絞り込みの条件を組み立てる処理を、引数 2 つで呼ぶ**
    （既定値のままだと、リンクを知っている人だけが読めるページが混じる）
  - **本文の抜粋を消すだけの既存の処理を写さない。両方向に間違っている** —
    特定ユーザー限定は素通りし、グループ限定は形の取り違えでメンバー本人でも落ちる
  - 判定にはページ本体が要る（検索結果には公開範囲の項目が含まれない）。
    当たった識別子をまとめて 1 回問い合わせる。**共有の関数に絞り込みを足さない**
    （本体の検索結果まで変わる）
  - 求められた件数の 3 倍を取ってから落とし、落とした後に順位を振り直す
  - 5 種類の公開範囲について、紐付いている場合といない場合で落ちるものが正しいことが試験で示される
  - _Requirements: 3.6, 3.7_
  - _Depends: 3.3_
  - _Boundary: ViewerPageFilter_

- [x] 4.2 (P) 誰でも見られるページかを判定する
  - **相手によらない判定**。入力も戻り値も 4.1 とは違うので、部品を分けてある
  - ログインしていない相手に何も見せない設定の GROWI では、
    通知はそのまま出し（宛先は管理者が設定したもの）、**URL の要約はパスだけにする**
  - 5 種類の公開範囲について、相手によらず「誰でも見られる」ものだけが残ることが試験で示される
  - _Requirements: 2.3, 6.3_
  - _Depends: 1.2_
  - _Boundary: PublicPageFilter_

- [x] 4.3 発言の列をページの本文へ組み立てる
  - **投稿者は発言ごとに解決する**（操作した人を解決する処理は 1 人ぶんしか返さない）
  - **まとめて 1 回引く**（発言の数だけ問い合わせると、100 件の取り込みで 100 回引くことになる）
  - 紐付いていない投稿者は、チャット上の表示名をそのまま書く
    （「不明」と書くと、誰の発言か分かるという条件を満たさない）
  - **ページを作る人と、発言の投稿者は別である**。作成者は取り込みを打った人
  - 紐付いている投稿者は GROWI ユーザー名、いない投稿者は表示名になることが試験で示される
  - _Requirements: 5.2, 5.3_
  - _Depends: 3.3_
  - _Boundary: ConversationPage_

- [x] 4.4 検索結果・ページの要約・ヘルプを組み立てる
  - 検索結果を構造化データへ（**整形済みの表示物ではない**。日時は決めた表記で）
  - ページを要約へ（本文の冒頭・更新日時・コメント数）
  - このバージョンが提供するコマンドの一覧を組み立てる
  - 検索結果に非公開ページが混じらず、要約が公開範囲に応じて中身を落とすことが試験で示される
  - _Requirements: 3.9, 6.2, 6.3, 14.2_
  - _Depends: 4.1, 4.2_
  - _Boundary: content_

- [x] 4.5 通知の文面を組み立て、この層の入口をまとめる
  - 6 つの出来事ぶんの文面。**非公開ページを含むかどうかの判断もここで行う**
  - 本文の埋め込みと、更新時の差分の作り方は既存の振る舞いをそのまま残す
  - **この層の入口もここでまとめる**
  - 6 つの出来事それぞれで文面が作られ、非公開ページの本文が落ちることが試験で示される
  - _Requirements: 2.1, 2.2, 2.3_
  - _Depends: 4.2, 4.3, 4.4_
  - _Boundary: NotificationContent_

- [ ] 5. proxy から届くコマンドを処理する
- [x] 5.1 読み取りのコマンドを処理する
  - 検索・URL の要約・ヘルプの 3 種類。**例外を投げず必ず応答を返す**
  - **冒頭でチャンネル権限を判定する**（契約側の関数を呼ぶ）
  - 処理済みの要求には**1 回目の応答をそのまま返す**
  - 3 種類が通しで動き、同じ要求の 2 回目に 1 回目の応答が返ることが試験で示される
  - _Requirements: 3.6, 3.7, 6.2, 6.3, 10.4, 11.3, 14.2_
  - _Depends: 3.5, 3.3, 4.4_
  - _Boundary: CommandEndpoint_

- [x] 5.2 書き込みのコマンドを、権限と重複まで含めて処理する
  - ページの作成と発言の取り込みの 2 種類
  - **「この人がここに書いてよいか」を判定する**（既存のページ作成の処理はそれを見ていない）
  - パスの重複を事前に確かめ、**「パスが重複」と「権限が無い」を区別して返す**
    （既存の例外は汎用のもので、他の失敗と区別できない）
  - 取り込みも書き込みなので、同じ 3 つ（権限・重複・再送）がそのまま要る
  - **取り込む範囲に発言が 1 件も無いときは proxy 側で打ち切られる**ので、ここには届かない
  - 2 種類が通しで動き、権限が無い場合と重複した場合が別の理由で返ることが試験で示される
  - _Requirements: 4.2, 4.5, 4.6, 5.2_
  - _Depends: 5.1, 4.3_
  - _Boundary: CommandEndpoint_

- [x] 5.3 書き込みを監査ログに残す
  - **リクエストの到着時に文脈を組み立てる既存の仕組みは使えない** — その仕組みは到着時に
    操作した人を読むが、この口では操作した人が署名付きの本体の中にあり、その時点では空である。
    そのまま置くと、**行はできるが操作した人の列が空**になる（動かして眺めても壊れて見えない）
  - **操作した人が決まった後に、自分で文脈を組み立てて記録を始める。**
    到着時刻は入口で 1 度取って持ち回る（記録を始める時刻ではない）
  - **記録を始めたら、必ず後始末で終わる。**成功して出来事を出せば消えるが、
    それ以外のすべての道で自分で消す（時間で消える仕組みも古い順に捨てる仕組みも意図的に無いので、
    漏らすとプロセスを再起動するまで戻らない）
  - **断った要求は記録しない。**失敗した書き込みは「試みた」記録として残す
    （応答が成功の形で返るので、既存の失敗検知はこの口では一度も働かない）
  - 書き込みの後に記録が 1 件でき、**操作した人と発言元のチャンネルが残る**ことが試験で示される
  - _Requirements: 4.3_
  - _Depends: 5.2_
  - _Boundary: CommandEndpoint_

- [ ] 6. チャットの利用者と GROWI ユーザーを紐付ける
- [x] 6.1 一度きりのリンクを発行して承認を受ける
  - **既存の同じ形の仕組みに倣う**（乱数で作った値を短時間で失効させ、使ったら失効させる形が 3 つある）
  - **承認画面の経路を既存の経路一覧に登録する。ログイン必須にする**
    （登録しないと末尾の受け皿に拾われ、そこで使われるのはゲストの閲覧を許す緩いほうの確認になる。
    パスワードの再設定の画面は専用の経路を登録してこれを満たしている）
  - **どのチャットアカウントを、どの GROWI ユーザーに結び付けるのかを画面に出す**
    （出さないと利用者が取り違えたまま承認する）。複数の GROWI が紐づくときは workspace も添える
  - 承認したら紐付けを書き、**同じトランザクションで値を失効させる**
  - 既に別の利用者に紐付いていれば複合ユニークが弾き、その旨を返す
  - **再送のたびに新しいリンクを作らない**（保留中のものがあればそれを返す）
  - リンクが 1 度しか使えず、期限を過ぎると使えないことが試験で示される
