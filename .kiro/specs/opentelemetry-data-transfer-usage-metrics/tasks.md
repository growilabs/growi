# Implementation Plan

- [ ] 1. 利用回数の記録基盤
- [ ] 1.1 データアーカイブとお引越しの利用回数を記録するメトリクスモジュールを作る
  - アーカイブ用とお引越し用の 2 つの単調増加カウンターを、設計で定めたメトリクス名・単位・属性語彙（操作種別・役割・結果）で定義する
  - 記録関数は列挙値のみを受け付け、カウンター未生成のあいだは何もしない
  - カウンターへの加算で例外が起きても呼び出し元へ伝えず、diag ロガーに記録する
  - 実際の MeterProvider と InMemoryMetricExporter を使ったテストで、記録回数どおりの系列が属性別に出ること、2 つのメトリクスが混ざらないこと、初期化前の記録が送信されないこと、属性キーが設計どおりに限られること、加算の例外が外に出ないことが確認できる
  - _Requirements: 2.6, 3.3, 3.4, 3.5, 4.1, 4.2_
- [ ] 1.2 記録モジュールをテレメトリの起動処理と公開窓口に組み込む
  - SDK 開始後に実行される独自メトリクスの初期化処理から、カウンターの生成を呼び出す
  - テレメトリ機能の公開窓口から、記録関数と列挙型だけを外部に公開する（内部ファイルは公開しない）
  - テレメトリ有効時はカウンターが生成されて記録が送信対象になり、無効時は生成されず記録が no-op になることがテストで確認できる
  - _Requirements: 3.1, 3.2_

- [ ] 2. データアーカイブ操作の計測
- [ ] 2.1 (P) アーカイブ作成の成否を記録する
  - 作成要求の受付後、バックグラウンドで進む作成処理の完了・失敗を待って記録する。応答は従来どおり処理完了を待たずに返す
  - 作成結果が得られた場合は成功、結果なし・失敗（実行中の重複要求による失敗を含む）は失敗として 1 回記録する
  - 作成処理の失敗は記録後に再送出せず、従来グローバルで出ていた相当のエラーログを残す
  - 監査ログの設定に関係なく記録されること、入力検証で弾かれた要求は記録されないことをテストで確認できる
  - _Requirements: 1.1, 1.2, 1.8, 1.9, 1.11, 4.3_
  - _Boundary: export route_
  - _Depends: 1.2_
- [ ] 2.2 (P) アーカイブのダウンロードを記録する
  - 指定ファイルの取得に成功した時点でダウンロードを 1 回記録する。パス不正や取得失敗では記録しない
  - 監査ログの設定に関係なく記録されることをテストで確認できる
  - _Requirements: 1.3, 1.8, 1.11_
  - _Boundary: admin download route_
  - _Depends: 1.2_
- [ ] 2.3 (P) アーカイブのアップロードの成否を記録する
  - 受け取ったファイルの検証通過を成功、解析失敗・バージョン不一致を失敗として記録する。ファイルが添付されていない要求は記録しない
  - 各分岐で記録が 1 回だけ行われることをテストで確認できる
  - _Requirements: 1.4, 1.5, 1.8, 1.9, 1.11_
  - _Boundary: import route (upload)_
  - _Depends: 1.2_
- [ ] 2.4 インポートの成否を 1 か所で記録する
  - インポート実行処理が成功・失敗の結果を返すようにし、部分失敗（取り込めなかったコレクションがある）と例外は失敗を返す。実行処理自体は記録しない
  - インポート要求の受付後のバックグラウンド処理で結果を 1 つ保持し、実行前に管理画面へエラー通知して終わる経路も含めて、処理の最後に 1 回だけ記録する
  - 実行処理のテストは戻り値で、受付後の処理のテストは「結果どおりに 1 回だけ記録される」ことで確認できる
  - 2.3 と同じルートファイルを変更するため 2.3 の後に行う
  - _Requirements: 1.6, 1.7, 1.8, 1.9, 1.10, 1.11_
  - _Depends: 1.2, 2.3_

- [ ] 3. お引越し（GROWI 間転送）の計測
- [ ] 3.1 (P) 取り込み完了判定を共通化し、転送処理が結果を返すようにする
  - 送信側の既存の「取り込みが不完全か」の判定を純関数として切り出し、送信側の判定をそれに置き換える
  - 転送処理が、転送先の取り込みが不完全だったかを結果として返すようにする（既存の失敗時の例外送出・画面通知は変えない）
  - 判定関数の各条件が単独で不完全判定になること、正常時は不完全でないこと、救済が計画されていない場合は不完全扱いしないことをテストで確認できる。既存の転送処理のテストが通る
  - _Requirements: 2.7_
  - _Boundary: G2G transfer service_
- [ ] 3.2 お引越し送信側の成否を記録する
  - 転送開始要求で、バックグラウンドの転送処理の完了・失敗を待って記録する。応答は従来どおり即時に返す
  - 取り込み完了なら成功、不完全・失敗なら失敗として 1 回記録する。転送開始前の確認（接続確認・転送可否判定）で中止した要求は記録しない
  - 転送処理の失敗は記録後に再送出しない（処理内でログと画面通知は済んでいる）
  - 各ケースの記録内容と、開始前の中止で記録されないことをテストで確認できる
  - _Requirements: 2.1, 2.2, 2.5, 2.7, 2.8, 4.3_
  - _Depends: 1.2, 3.1_
- [ ] 3.3 お引越し受信側の成否を記録する
  - 受信処理がエラー応答時には結果なし、成功応答時には取り込み結果を返すようにする
  - 受信処理の結果に共通判定を適用し、成功・不完全・エラー応答・予期しない例外のそれぞれで、受信側として 1 回記録する
  - 各ケースの記録内容をテストで確認できる。3.2 と同じルートファイルを変更するため 3.2 の後に行う
  - _Requirements: 2.3, 2.4, 2.7, 2.8_
  - _Depends: 1.2, 3.1, 3.2_

- [ ] 4. 結合確認
- [ ] 4.1 二重計上がないことと全体の健全性を確認する
  - お引越し 1 回の実行（送信側・受信側）で、アーカイブの利用回数が記録されないことを、お引越しの既存結合テスト（`apps/app/src/server/routes/apiv3/g2g-transfer.integ.ts`）に記録関数をモックしたケースを追加して確認する
  - apps/app の lint・テスト・ビルドがすべて通る
  - _Requirements: 1.9, 2.6_
- [ ] 4.2 devコンテナでローカルのコレクターへの実送信を確認する
  - 前提: ホスト側で opentelemetry-collector-dev-setup を起動し、devコンテナをそのネットワークに接続する。お引越しの確認には GROWI を 2 インスタンス起動する
  - ローカルの OTel コレクターに接続し、テレメトリ有効の状態でアーカイブ作成・インポート・お引越しを実行して、2 つのメトリクスが期待どおりの属性で届くことを確認する
  - テレメトリ無効の状態で同じ操作を行い、何も送信されず操作結果も変わらないことを確認する
  - 確認結果（届いた系列）を PR の説明に記載する（本 spec のディレクトリは 5.2 で削除されるため、spec 内には残さない）
  - 新しいメトリクス名と属性を受信側（コレクター・ダッシュボード）の担当者に共有し、リリース前に受信側の準備が整っていることを確認する（opentelemetry spec の Revalidation Trigger「受信側ダッシュボード／クエリの参照更新」に該当）
  - _Requirements: 3.1, 3.2, 4.3_
