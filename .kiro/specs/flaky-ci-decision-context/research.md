# Research & Design Decisions

## Summary
- **Feature**: `flaky-ci-decision-context`
- **Discovery Scope**: Extension（既存の `bin/flaky-ci/` パイプラインへの軽量な追加）
- **Key Findings**:
  - ダッシュボード（`bin/flaky-ci/lib/dashboard.ts`）は既に「First seen / Last seen / Occurrences」を issue の body・コメントから計算しているが、この計算ロジック（`observationDates` / `countOccurrences` / `toTableRow`）は `dashboard.ts` 内の非公開関数で、他から呼べない。
  - `flaky/suspected` の issue が「再現測定を一度も受けていない」ことを検知するマーカーは既に存在する（`COMMENT_HEADINGS.reproResult = '### Repro result'`）。この文字列を持つコメントが1件もなければ、その issue はまだ測定されていない。
  - `--stale-days`（既定14日）は既に `flaky-ci-routine.md` の CLI 引数として存在し、Step 4 の `flaky/observing` 自動クローズに使われている。新しい閾値フラグを増やさず、この既存の値をそのまま「suspected 滞留」の判定にも使い回せる。
  - `.claude/skills/investigate-flaky-test/SKILL.md` の「Pausing for a human decision」節は、スキル内の全ての一時停止箇所が参照する**唯一の定義**（単一の型番方式）。ここに1箇所追加すれば、全ての停止経路に自動で反映される。
  - `- Recommendation:` 行は「コメントの最後の非空行」という契約をダッシュボードが検証している（`flaky-ci-routine.md` Shared constants → Recommendation line）。新しい頻度の行は、この行より**前**に置かなければ契約を壊す。

## Research Log

### 既存の頻度計算ロジックの所在
- **Context**: Requirement 1 は「ダッシュボードと同じ計算結果を再利用する」ことを求めている。実装が本当に再利用可能な形になっているか確認が必要だった。
- **Sources Consulted**: `bin/flaky-ci/lib/dashboard.ts`（488行）
- **Findings**:
  - `DashboardIssue`型（`number`, `title`, `labels`, `body`, `comments`）が入力。
  - `observationDates(issue)` が body の初回観測日＋`### Additional observation`/`### Backfilled observation`コメントの`Date:`行を集めて日付配列を返す（純粋関数）。
  - `countOccurrences(issue)` がその配列の長さを返す。
  - `toTableRow(issue)` がこれらを束ねて `{firstSeen, lastSeen, occurrences}` を含む行を作る。
  - これら全て `dashboard.ts` の非公開（`export`なし）関数。
- **Implications**: 新しいロジックを書く必要はない。この計算部分を独立した公開関数として切り出し、`dashboard.ts`自身もそれを呼ぶ形にすれば、二重管理を避けつつ再利用できる。

### 「未測定」をどう判定するか
- **Context**: Requirement 2 は「再現測定の記録が一度も無い」suspected issue を検知する必要がある。
- **Sources Consulted**: `bin/flaky-ci/lib/constants.ts`（`COMMENT_HEADINGS`）、`investigate-flaky-test/SKILL.md`（Step 2-E, confirmation measurement）
- **Findings**: 再現測定が行われると、必ず `### Repro result` という見出しを持つコメントが投稿される（`.github/scripts/flaky-repro/run-repro.sh` が書き込む）。この見出しを持つコメントが1件も無い open な `flaky/suspected` issue が「未測定」。
- **Implications**: `fetch-flaky-issues.ts` が返す `comments[].body` に対して単純な文字列検索で判定できる。新しい状態やラベルは不要。

### 頻度データの挿入位置と既存契約との整合
- **Context**: pause コメントの最後の非空行は `- Recommendation:` でなければならないという既存の契約（ダッシュボードの Awaiting セクションがこれを読む）。
- **Sources Consulted**: `flaky-ci-routine.md` Shared constants → Recommendation line、Pause ordering
- **Findings**: 新しい頻度の行を `- Recommendation:` の後に置くと、ダッシュボードの「最後の非空行を推奨として読む」ロジックを壊す。
- **Implications**: 頻度の行は署名（`_Generated by [Claude Code]...`）より前、コメント本文の中に置く。順序の契約（何が最後の行か）を壊さないことを design.md の Revalidation Trigger に明記する。

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| dashboard.tsから計算ロジックを抽出し新規libファイルへ | `observationDates`/`countOccurrences`/`toTableRow`の日付処理部分を`bin/flaky-ci/lib/occurrence-summary.ts`へ移し、`dashboard.ts`はそれをimportする | 単一の計算源。既存のテストも移設すれば重複が残らない | 既存ファイルの分割で差分がやや広がる | 採用 |
| dashboard.ts内の関数をそのままexportするだけ | 移動せず`export`を付けるだけ | 差分最小 | `dashboard.ts`という「ダッシュボード描画」の関心事に、無関係な「頻度計算の公開API」という責務が混ざる（coding-style.mdの単一責任原則に反する） | 不採用 |
| pauseコメント側で頻度を独自に再計算 | 既存ロジックを見ずに投稿コメント作成側で日付を拾い直す | 変更範囲が投稿側だけで閉じる | 計算ロジックの二重管理・ドリフトのリスク（Requirement 1.2が明示的に禁止） | 不採用 |

## Design Decisions

### Decision: 頻度計算ロジックを `occurrence-summary.ts` として独立させる
- **Context**: Requirement 1.2（既存計算の再利用、新規実装の禁止）
- **Alternatives Considered**:
  1. `dashboard.ts`内に残したまま`export`だけ付ける
  2. pauseコメント生成スクリプト側に計算をコピーする
- **Selected Approach**: `bin/flaky-ci/lib/occurrence-summary.ts` を新設し、`computeOccurrenceSummary(issue: DashboardIssue): OccurrenceSummary` を公開する。`dashboard.ts`はこれをimportし、自身の`toTableRow`から呼ぶ形に書き換える。
- **Rationale**: 「ダッシュボード描画」と「観測頻度の計算」は別の関心事であり、後者はダッシュボード以外（pauseコメント、将来のレポート）からも呼ばれる。既存の`lib/`ディレクトリの構成（`gh.ts`, `time.ts`, `constants.ts`等、各ファイルが一つの関心事を持つ）にも合致する。
- **Trade-offs**: `dashboard.ts`の差分が計算ロジック抽出の分だけ増える。既存のテスト（`dashboard.spec.ts`の該当部分）も`occurrence-summary.spec.ts`へ移す必要がある。
- **Follow-up**: 実装時に`dashboard.spec.ts`が計算ロジックのテストケースを重複して持っていないか確認する。

### Decision: 「未測定滞留」の閾値は新しいフラグを作らず既存の `--stale-days` を再利用する
- **Context**: Requirement 2.1 は日数の閾値を必要とするが、新しい設定値を増やすと`flaky-ci-routine.md`のCLI引数が肥大化する。
- **Alternatives Considered**:
  1. 新しい `--stale-suspected-days` フラグを追加する
  2. 既存の `--stale-days`（既定14日、Step 4の観測自動クローズに使用）をそのまま流用する
- **Selected Approach**: 既存の `--stale-days` をそのまま使う。
- **Rationale**: 「どれくらい放置されたら注意を促すか」という意味論はどちらも同じ（14日）で、閾値を分ける明確な理由が無い。既存の値を再利用する方が、設定項目を増やさず理解しやすい。
- **Trade-offs**: 将来「suspectedの滞留はobservingより早く気づきたい」というニーズが出た場合は、この決定を見直して分離する必要がある。
- **Follow-up**: なし（必要になれば別のamend specで分離する）。

## Risks & Mitigations
- 頻度計算ロジックの抽出（`dashboard.ts`の変更）が既存のダッシュボード出力を意図せず変えてしまうリスク — 既存の`dashboard.spec.ts`のゴールデン出力テストをそのまま通すことで検知する（抽出前後で出力が一字一句変わらないことを確認）。
- pauseコメントの頻度行を`- Recommendation:`より後ろに置いてしまい、ダッシュボードの「最後の非空行」契約を壊すリスク — design.mdのRevalidation Triggersに明記し、実装タスクのBoundaryで挿入位置を固定する。
