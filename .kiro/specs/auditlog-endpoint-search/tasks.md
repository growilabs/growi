# Implementation Plan

- [ ] 1. 一覧 API で URL による絞り込みができる
- [ ] 1.1 絞り込み条件の組み立てが、URL をパス部分の完全一致の条件に変換できる
  - 共有の一覧の絞り込み条件の型（`ISearchFilter`）に、URL（パス部分）の配列の項目を足す。この型の拡張はこのタスクが担当する
  - 選んだパスのいずれかと等しい値、または「パスの直後に `?` が続く値」に一致する条件を組み立てる。前方一致に使う値は、正規表現の記号をエスケープしてから `?` を付ける
  - URL の条件は、ユーザー名・アクション・期間の条件と AND で結合し、トップレベルの OR は使わない
  - ユーザー名と URL の条件は、配列で、空でなく、要素がすべて文字列のときだけ付ける。既存のユーザー名の判定も同じ形に直し、文字列が来ても例外を投げないようにする
  - 単体テストで、OR の形・エスケープ・大文字小文字の区別・AND での結合・不正な値（空、未指定、文字列、文字列以外の要素）を無視することが確かめられ、通る
  - _Requirements: 1.3, 2.1, 2.2, 2.3, 2.4, 3.8, 5.2_
- [ ] 1.2 一覧 API の 2 経路が URL の条件を受け取り、実際のデータベースで正しく絞り込める
  - GET と POST の両経路で、検索条件の URL の項目を絞り込み条件の組み立てに受け渡す
  - OpenAPI の検索条件の説明に URL の項目を足す
  - 実際の MongoDB を使う integ テストで、`/_api/v3/page` を選ぶと `/_api/v3/page` と `/_api/v3/page?x=1` が返り、`/_api/v3/pages` と `/_API/v3/page` は返らないこと、`(` や `.` を含むパスも一致することが確かめられ、通る（Prisma の `startsWith` がエスケープしない振る舞いを固定する）
  - _Requirements: 1.3, 2.1, 2.2, 2.3, 2.4_

- [ ] 2. 検索欄の判断ロジックと文言がそろっている
- [ ] 2.1 (P) 検索対象の種類の表と、候補を出すかの判定・候補一覧の組み立てができる
  - 検索対象の種類（すべて・ユーザー・URL）と、それぞれが候補を取る種類・文言キーを 1 か所の表で宣言する。表の順序が選択肢と候補のグループの順序になる。文言キーの名前は 2.2 のキー一覧に合わせる
  - 古い応答の判定を 1 つの関数にまとめ、候補ごとの除外（古い候補と選択済みの値を除く）と、候補一覧のグループの組み立て（失敗のグループは新しいときだけ出す）の両方がこの判定を使う
  - 単体テストで、古い候補・選択済みの値の除外、種類が違えば同じ値でも出すこと、種類の順のグループ、0 件の種類はグループにならないこと、失敗したときは失敗のグループ 1 つだけになること、古い入力に対する失敗のグループは出さないことが確かめられ、通る
  - 1.x とは独立して進められる（型を共有しない）
  - _Requirements: 1.1, 1.5, 3.2, 3.3, 3.4, 3.7, 4.1_
  - _Boundary: search-scopes, search-suggestion-options_
- [ ] 2.2 (P) 検索欄の文言が 5 ロケールすべてで表示できる
  - 次のキーを、5 ロケールの `admin` の翻訳ファイルの `audit_log_management.search` の下に足す。このキー一覧が、検索欄で使う文言キーの唯一の取り決めになる
    - `placeholder`（検索欄のプレースホルダ）
    - `scope_selector`（「絞り込みを選択」）
    - `scope.all` / `scope.username` / `scope.endpoint`（選択肢）
    - `header.username` / `header.endpoint`（候補の種類ごとの見出し）
    - `fetch_failed`（候補を取得できなかったことの表示）
  - 追加したキーがすべてのロケールにあることを確かめる locale drift のテストが通る
  - _Requirements: 6.1_
  - _Boundary: admin.json, search-labels-locale-drift.spec_

- [ ] 3. 検索欄でユーザーと URL を検索して選べる
  - 前提（3.x のすべて）: 候補 API が URL（`field=endpoint`）に対応している（候補の種類の型 `AuditlogSuggestionField` に `endpoint` が含まれ、`search-auditlog-suggestions.ts` がある）
- [ ] 3.1 候補 API の `q` の上限を、画面とサーバーで同じ定数として使える
  - 候補 API の `q` の上限（100 文字）を、画面とサーバーで共有する定数にし、候補 API の validator がその定数を使うようにする。上限の値は変えない
  - validator が共有の定数を使い、既存のテストと型チェックが通る
  - _Requirements: 1.7_
- [ ] 3.2 候補の取得のフックが、複数の種類を 1 回のリクエストで取得できる
  - 候補 API を呼ぶ既存の SWR フックが、種類を 1 つだけでなく種類の配列も受け取れるようにする。配列のときは 1 回のリクエストにすべての種類を載せる
  - 種類を 1 つだけ渡す既存の呼び出し（エクスポートのモーダルのユーザー名の入力欄）は、引数もリクエストも変えない
  - テストで、配列を渡すと 1 回のリクエストに全種類が載ること、種類を 1 つ渡したときのリクエストが変わらないことが確かめられ、通る
  - _Requirements: 3.4, 3.5_
  - _Boundary: stores/activity.ts_
- [ ] 3.3 検索対象に応じて、候補をまとめて取得できる
  - 検索対象に含まれる種類をまとめて 1 回のリクエストで取得し、空の入力ではリクエストしない。件数の上限は種類ごとに 5 件
  - 前後の空白を除いた入力が共有の上限を超えるときもリクエストせず、候補 0 件・失敗なしとして返す
  - ユーザーの結果は Active / Inactive の区別付きの候補に、URL の結果は URL の候補に変換し、失敗と読み込み中を返す
  - テストで、「すべて」なら 1 回のリクエストで 2 種類を、「URL」なら URL だけをリクエストすること、空の入力ではリクエストしないこと、101 文字以上ではリクエストせず失敗も返さないこと（100 文字ちょうどならリクエストすること）、リクエストの失敗が失敗として返ることが確かめられ、通る
  - _Depends: 2.1, 3.1, 3.2_
  - _Requirements: 1.1, 1.6, 1.7, 3.4, 3.5, 4.1_
- [ ] 3.4 検索欄が、見出し付きの候補一覧と失敗の表示を描ける
  - この時点では検索対象の状態を持たず、「すべて」で固定して候補を取得する（切り替えは 3.6）
  - 入力欄は複数選択で、自由入力はできない。古い候補と選択済みの値は候補ごとの除外で取り除き、候補一覧は見出し付きのグループか失敗の表示で描く。結果が 0 件でも失敗の表示は出す
  - ユーザーの候補に Active / Inactive のバッジを付ける。取得中は読み込み中を表示する
  - 出すグループが 1 つもないときは、候補一覧を描かず何も表示しない（ライブラリの既定の英語の文言を出さない）
  - コンポーネントテストで、見出しとバッジ、取得の失敗で失敗表示が 1 つ出ること、古い候補を出さないこと、古い候補の上で Tab・→・Enter を押しても選ばれないこと、入力を止めた直後・空の入力欄へのフォーカス・101 文字の入力で候補一覧も既定の英語の文言も出ないことが確かめられ、通る
  - _Depends: 2.2, 3.3_
  - _Requirements: 1.1, 1.5, 1.6, 1.7, 3.1, 3.3, 3.7, 4.1, 6.1_
- [ ] 3.5 検索欄で候補を選び、選択済みの値を外し、その結果を親へ通知できる
  - 選択済みの値を、種類が分かるトークンで表示する
  - 選択の変化を、ユーザー名と URL に分けて親へ通知する。候補を選ばずに Enter を押しても通知しない。候補の取得に失敗しても、選択と通知は変えない
  - 検索欄のディレクトリの `index.ts` で、検索欄とその型だけを公開する
  - コンポーネントテストで、URL の選択と解除が通知されること、候補を選ばずに Enter を押しても通知されないこと、取得の失敗で選択済みのトークンが残ることが確かめられ、通る
  - _Requirements: 1.2, 1.4, 1.5, 4.2_
- [ ] 3.6 「絞り込みを選択」で検索対象を切り替え、検索欄を初期状態に戻せる
  - 入力欄の右に、検索対象の種類の表から選択肢を作るドロップダウンを置き、初期値は「すべて」
  - 検索対象を切り替えても選択済みの値は保ち、以降の候補の種類だけを変える
  - 外から初期化すると、選択と入力が空になり、検索対象が「すべて」に戻る
  - コンポーネントテストで、切り替えてもトークンが残ること、初期化でトークンが消えて「すべて」に戻ることが確かめられ、通る
  - _Requirements: 3.2, 3.9, 5.3_

- [ ] 4. 監査ログ画面が、検索欄で選んだユーザーと URL で一覧を絞り込める
  - 画面の絞り込み条件の組み立てが URL を受け取れるようにし、単体テストを足す
  - 監査ログ画面のユーザー名の入力欄を新しい検索欄に置き換え、選んだユーザーと URL を一覧の条件に渡す。選択や解除で 1 ページ目に戻す
  - リセットで、選んだユーザーと URL を空にし、検索欄を初期状態に戻す。エクスポートのモーダルには今までどおりユーザー名だけを渡す
  - 画面の絞り込み条件の組み立ての単体テストが通る。画面での絞り込み（URL の選択で一覧が絞り込まれ、ユーザー・期間・アクションと組み合わせてもすべての条件を満たす記録だけが出ること）は、6 の開発サーバーでの確認で確かめる
  - _Depends: 1.2, 3.5, 3.6_
