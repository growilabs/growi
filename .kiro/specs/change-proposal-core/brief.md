# Brief: change-proposal-core

**Parent**: umbrella spec `change-proposal`（[roadmap.md](../change-proposal/roadmap.md)、判断の理由とコード上の事実は [research.md](../change-proposal/research.md)）

## Problem

GROWI には、AI や外部の仕組みが複数のページをまとめて書き換えるための、安全な書き込みの仕組みが無い。

- 今の保存の処理は、人がエディタや画面から1ページずつ保存することを前提にしている。上書き防止の確認・activity・通知・yjs の同期は API の処理（route）の中にあり、他の処理から呼び出せない。
- 確認と書き込みが別々なので、外から書き込むと人の保存とぶつかり、どちらかが上書きされる。
- REST で保存すると、編集中の yjs の文書が置き換わり、共同編集者の未保存の入力が消える。今の MCP からの書き込みにも同じ問題がある。
- 複数のページへの変更を1つにまとめて記録する仕組みも、版を戻す機能も無い。

## Current State

- 書き込みは、エディタの保存、ページの作成・更新・移動の API、外部の `@growi/mcp-server`（API トークンで REST を呼ぶ）だけ。
- `Revision.origin`（`view` / `editor`）は上書き防止の確認に使われていて、書き込みの出どころを記録する用途には使えない。
- activity は同じ人の5分以内の更新を1つにまとめ、30 日で消える。

## Desired Outcome

- 複数ページへの操作（編集・新規作成・移動）を1つにまとめた Change Proposal を保存できる。
- Change Proposal を、LLM を使わずにサーバー側で反映できる。反映では、人の保存とぶつからず、共同編集中の人の入力を消さず、権限をその時点で確かめる。
- 管理者の設定に応じて自動で反映するか、依頼した本人がページ単位で承認してから反映する。
- 反映した Change Proposal を、取り消し用の Change Proposal を作ることで取り消せる。戻してよい条件に合わない操作は断る。
- どのリビジョンとページがどの Change Proposal で作られたかを記録し、Change Proposal そのものを消えない記録として残す。

## Approach

- 新しいコレクションに Change Proposal を保存する。持つもの:
  - 依頼した人、入口（AI チャット／Vault／MCP／取り消し）、状態、作成日時
  - 並び順のある操作の一覧。操作ごとに状態（待ち／反映済み／失敗／古い／飛ばした／取り消し済み／取り消しを断られた）を持つ
  - 編集: 対象ページ、元のリビジョン ID、変更後の本文全体
  - 新規作成: パス、本文（閲覧範囲は親ページから引き継ぐ）
  - 移動: 移動元と移動先
  - 削除は持たない
- 保存まわりの処理を route から切り出し、人の保存・Change Proposal の反映・取り消しが同じ処理を通るようにする。
- 反映の処理:
  - 書き込みは「ページがまだ元のリビジョンを指していれば書く」を1回の操作で行う。指していなければ、その操作は「古い」にする。
  - AI が反映するリビジョンの `origin` は空にする。反映の前から開いていたエディタの次の保存で、上書き防止の確認が働くようにするため。
  - 接続している編集者がいる、または yjs に未保存の入力があるページには反映しない。その操作は承認待ちのまま残す。
  - 移動は1つの Change Proposal につき1つまでとし、最後に実行する。
  - リビジョンに `proposalId` と操作の key（ランダムな識別子）を記録する。ページには記録しない。やり直しのときはこの印を先に探し、二重に書かない。
  - すでに反映した操作は、後の操作が失敗しても巻き戻さない。
  - ページごとの通知（購読している人へのアプリ内通知と、グローバル通知の Slack・メール）は、管理者の設定（初期値: 出さない）と Change Proposal ごとの指定（初期値: 出す。依頼した人が承認待ちの間に変えられる）の両方が有効なときだけ出す。Change Proposal ごとに1つの通知にまとめたものは、いつも出す。受け取る人が閲覧できるページの分だけで中身を作る。
- 取り消しは、種類が「取り消し」の Change Proposal を作り、同じ反映の処理で適用する。元の操作には、戻した Change Proposal の ID を記録する。全体の状態は操作ごとの状態から計算する。
- 管理者の設定:
  - 書き込み機能の有効化（初期値: 無効）
  - 操作ごとの有効化（編集・作成・移動）
  - 自動反映の方針（しない／自分が作ったページだけ／すべて、初期値: しない）
  - 上限: 1回の操作数（初期値: 50）、1日あたりの件数（初期値: 上限なし）
  - 反映でページごとの通知を出すか（初期値: 出さない）
  - 書き込み機能を無効にしたら、承認待ちの Change Proposal を取り下げる

## Scope

- **In**:
  - Change Proposal のデータ、状態の移り変わり、期限切れ
  - 保存まわりの処理の切り出しと、サーバー側の反映
  - 反映時の確認（元のリビジョン、編集中の人、権限、読み取り専用ユーザー）
  - ページ単位の承認と、自動反映の方針
  - 取り消しと、戻してよい条件の判定。移動を戻すときに逆向きのリダイレクトを消す
  - `proposalId` の記録
  - 通知のまとめ、activity への記録（新しい action）
  - 管理者の設定画面
  - Change Proposal を作り、取得し、承認し、取り消す API。API は、見る人が閲覧できるページの分だけを返す
- **Out**:
  - AI に Change Proposal を作らせる道具 → `change-proposal-ai-agent`
  - 詳細ページ、ページ履歴と Recent Changes の印 → `change-proposal-viewer`
  - Vault・MCP の入口（将来）
  - 差分の塊ごとの承認、元の版が変わった案の自動の合わせ込み

## Boundary Candidates

- データと状態の移り変わり
- 保存まわりの処理の切り出し（人の保存と共通にする部分）
- 反映と取り消しの実行（確認と書き込みを1回の操作で行う部分、編集中の人の確認）
- 通知のまとめ
- 管理者の設定

## Out of Boundary

- どこから Change Proposal が来たか（AI チャット・Vault・MCP）によって反映の処理を変えない。入口ごとの違いは、入口の側が案を作るときに吸収する。
- 画面での表示は持たない（管理者の設定画面を除く）。

## Upstream / Downstream

- **Upstream**:
  - ページの作成・更新・移動の処理（`apps/app/src/server/service/page/`、`apps/app/src/server/routes/apiv3/page/`）
  - yjs のサービス（`apps/app/src/server/service/yjs/`）
  - activity とアプリ内通知、グローバル通知
- **Downstream**:
  - `change-proposal-ai-agent`、`change-proposal-viewer`
  - 将来の Vault の push、`change-proposal-mcp`

## Existing Spec Touchpoints

- **Extends**: なし（新しい境界）
- **Adjacent**:
  - `collaborative-editor`（yjs の扱い）
  - `activity-log` / `activity-log-snapshot`（新しい action の記録）
  - `revision-diff-api`（差分の取得）

## Constraints

- 反映と取り消しに LLM を使わない。
- `Revision.origin` に新しい値を足さない。
- 新しいコレクションの索引は Mongoose 側で宣言する（`.claude/rules/model.md`）。
- 見えないページについては、API のエラーで存在を区別させない（同じ 404 を返す）。
- 複数台のサーバーで動かしている場合、編集中の人の確認は今の数え方（プロセスごと）では漏れる。分かっている制約として設計に書く。
- 最初に確かめること:
  - `origin` の扱いと上書き防止の確認の関係を、結合テストで固定する
  - 人の保存と反映が同時に起きたときの動き
  - 移動を戻したときのリダイレクトの残り方
