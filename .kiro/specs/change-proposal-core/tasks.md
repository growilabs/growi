# Implementation Plan

> 本計画の語（操作・元のリビジョン・依頼した人・入口・見る人・編集中の人がいるページ・操作の状態）は requirements.md の「本要件で使う言い方」と同じ。部品の名前は design.md の Components and Interfaces に合わせる。
>
> **未決の初期値について**: 承認待ちの期限（design の OQ-1）と、操作数・1 日の件数の上限（OQ-2）の初期値は未決である。これを入れるのはタスク 8.1 だけで、グループ 1〜7 はこの値を待たずに進められる。8.1 を始める前に、決まった値を人に確かめる。決まっていなければ 8.1 から先を止める。

- [ ] 1. 土台: 型・データ・設定・action の宣言
- [ ] 1.1 Change Proposal の型と決まった値を宣言し、純関数の barrel を用意する
  - 入口の種類、操作の種類（作成で受ける 3 種類と、取り消しだけの「ごみ箱へ移す」「ごみ箱から戻す」）、Change Proposal の段階（open / 破棄 / 期限切れ / 取り下げ）、操作の 7 つの状態、全体の状態、理由の値（待ち・失敗・古い・飛ばした・取り消しを断られたの各理由）、戻せるかの判定結果、印（Change Proposal の ID と操作の `key`）を、design の Logical Data Model のとおりに型で宣言する。本文の合計の上限 `MAX_TOTAL_BODY_BYTES`（8 MiB）を `interfaces/change-proposal.ts` に宣言する
  - REST の応答の形（操作の表示、Change Proposal の表示と要約、リビジョンの印）と、`ApplyTrigger` / `ApplyResult` / `RevertResult`（design の Data Contracts のとおり。操作は `key` で指す）を `interfaces/api.ts` に、まとめた通知の snapshot の形、設定の形を宣言する
  - `interfaces/index.ts` を barrel にし、上の型と `MAX_TOTAL_BODY_BYTES` をすべて export する（兄弟の spec は `features/change-proposal/interfaces` から import する）
  - 純関数を置くディレクトリに、design の Domain の 8 つのファイルを、関数の形（引数と戻り値の型）だけを持ち中身は「未実装」の例外を投げる仮のファイルとして作り、barrel からすべて export する（グループ 3 のタスクが同じ barrel を同時に書き換えないようにするため。中身はグループ 3 で書く）
  - 型の検査が通り、server と client の両方から型と `MAX_TOTAL_BODY_BYTES` を import できる状態になっている
  - _Requirements: 1.2, 1.3, 1.4, 1.16, 2.1, 2.7, 9.1_
- [ ] 1.2 設定キーを宣言し、設定を読み書きする処理を作る
  - design の「設定キー」の表の 9 つのキーを、型と環境変数つきで宣言する。初期値が未決の 3 つ（期限と 2 つの上限）は、作った値を置かず、初期値を `null`（値が無い）として宣言する。値が無い間は、上限は確かめず、期限切れにもしない。決まった値はタスク 8.1 で入れる。テストでは値を明示して使う
  - 設定を型付きの値として読む処理と、管理者の API から書く処理を作る。読むたびに設定の仕組みから取り、他のサーバーでの変更も次の読み込みで使われる
  - 設定キーの宣言の既存のテストに新しいキーを足し、決まっている初期値（書き込み機能は無効、操作ごとの有効化は有効、自動反映は「しない」）がテストで確かめられている
  - _Requirements: 1.9, 8.1, 8.2, 8.3, 8.4_
- [ ] 1.3 リビジョンに、作った Change Proposal の印の項目を足す
  - `@growi/core` のリビジョンの型（`IRevision`）に、任意の `proposalId` と `proposalOperationKey`（操作の `key`）を足し、changeset を作る。ページの型（`IPage`）は変えない。apps/app は `@growi/core` を `dist` から読むので、apps/app の型の検査と結合テストの前に `@growi/core` を build し直す
  - Prisma の schema のリビジョンに同じ項目を足す。Mongoose のリビジョンの schema にも項目と、値を持つ文書だけが入る疎な索引 `{ proposalId: 1, proposalOperationKey: 1 }` を宣言する（索引は Mongoose 側で宣言する規則に従う）。ページの schema には項目を足さない
  - リビジョンを作るための入力を組み立てる処理が、任意の印を受け取ってリビジョンに入れる
  - 印を渡さずに作ったリビジョンには項目が無く、渡したときは値が保存されることを結合テストで確かめている。既存の「ページに TTL 索引が無い」テストも通る
  - _Requirements: 6.1, 6.2, 6.3, 6.6_
- [ ] 1.4 Change Proposal のコレクションを Mongoose で宣言する
  - 依頼した人、入口の種類、表示用のモデル名（100 文字まで）、取り消しの元、段階、操作の配列（操作ごとに並び順の番号と乱数の key）、反映で触れたページの一覧、最後に反映した日時、反映の権利（lease）、期限、作成日時を持つ
  - design の Physical Data Model の 5 つの索引を宣言し、TTL 索引は持たない
  - 保存と読み出しの結合テストで、操作の配列の 1 つの要素だけを条件付きで更新できることを確かめている
  - _Requirements: 1.1, 1.15, 2.6, 2.8, 6.5_
- [ ] 1.5 新しい activity の action と、通知の対象の種類を宣言する
  - 作成・反映・取り消し・管理者の設定の更新の 4 つの action を足す。反映と取り消しは、監査ログの設定にかかわらず記録される組に入れ、作成は監査ログの組の設定に従う組に入れる
  - 通知と activity の対象の種類に「Change Proposal」を足す。監査ログの分類に Change Proposal を足し、分類の正規表現は `^CHANGE_PROPOSAL_` を直接書く
  - 監査ログの action の名前と分類の名前を 5 言語の `admin.json` に足す
  - 監査ログの絞り込みの一覧に新しい分類と 4 つの action が出ること、activity の既存のテストが通ること、5 言語の翻訳キーの検査が通ることを確かめている（baseline は引き上げない）
  - _Requirements: 7.5, 7.7, 8.7_
- [ ] 1.6 兄弟の spec の画面で共通に使う client の部品を作る
  - `features/change-proposal/client/shared/` に、操作の種類・操作の状態・全体の状態・理由・戻せない理由の 5 つの「値 → 翻訳キー」の表を、design の Client Shared の名前で作る。どの表も `satisfies Record<値の型, string>` で宣言する。入口の種類の表は作らない
  - 5 つの表が指すキー（`change_proposal.operation_type.*` など）を、5 言語の `translation.json` に足す。`i18next.config.ts` の `extract.preservePatterns` に 5 つの接頭辞のワイルドカードを足す（`change_proposal.` で始まる静的な `t('…')` の呼び出しは作らない）
  - `RevisionDiff.tsx` の diff2html の設定と色の決め方を `diff2html-options.ts`（`buildDiff2HtmlOptions`・`useDiff2HtmlColorScheme`）に移し、`RevisionDiff` もそれを使う。`RevisionDiff.vendor-styles.ts` を `client/shared/diff2html.vendor-styles.ts` に移し、`RevisionDiff` は移した先の prebuilt を読み込む
  - barrel（`client/shared/index.ts`）から、5 つの表と diff2html の部品を export する
  - 表のすべてのキーが 5 言語にあること（`label-keys.spec.ts`）、同じ差分と同じ色の指定から移す前の `RevisionDiff` と同じ HTML ができること（`diff2html-options.spec.ts`）を確かめ、5 言語の翻訳キーの検査が通っている（baseline は引き上げない）
  - `change-proposal-viewer` と `change-proposal-ai-agent` の画面のタスクより先に終える
  - _Requirements: 11.1, 11.2, 11.3_
  - _Depends: 1.1_

- [ ] 2. 確認と書き込みを 1 回の更新にし、人の保存と共通にする
- [ ] 2.1 今の上書き防止の確認の動きを、結合テストで先に固定する
  - `origin` が空のリビジョンが最新のとき、`origin: editor` で `revisionId` を送らない保存が 409 `conflict` になること
  - 最新のリビジョンの `origin` が `editor` か `view` のとき、`origin: editor` の保存が確認を飛ばして通ること
  - 切り出しの前のコードでこれらのテストが成功していることを確かめている（以後の変更で動きが変わらないことの基準にする）
  - _Requirements: 3.11, 10.1_
- [ ] 2.2 ページの書き込みを「期待するリビジョンのままなら書く」にできるようにする
  - リビジョンを積む処理に、任意の「期待するリビジョンの ID」を足す。渡されたときは、ページの今のリビジョンがその ID であることを条件に 1 回の更新で書く
  - 一致しなかったときは、作ったリビジョンを消し、リビジョンの衝突を表す例外を投げる。渡されなかったときの動きは今と同じ
  - 一致しない場合にページが変わらず、作ったリビジョンが残らないことを結合テストで確かめている
  - _Requirements: 3.3, 3.4_
- [ ] 2.3 ページのサービスに、印・期待するリビジョン・通知を止める指定を通す
  - 更新の options に印と期待するリビジョンを足し、リビジョンを積む処理まで渡す
  - 作成の options に印を足し、最初のリビジョンにだけ印を書く（ページには書かない）
  - 移動・ごみ箱への移動・ごみ箱から戻す（`revertDeletedPage`）の options に「アプリ内通知を出さない」指定を足す。指定したときは、アプリ内通知のための知らせを出さず（`revertDeletedPage` では `emit` に対象のページと通知の準備の関数を渡さない）、activity の記録は今のまま行う
  - 作成で渡した印が最初のリビジョンに保存され、ページに印の項目が無いこと、3 つの処理のそれぞれで、通知を止める指定のときにアプリ内通知が増えず、指定しないときは今と同じ数だけ増えることを結合テストで確かめている
  - _Requirements: 6.1, 6.2, 7.1_
- [ ] 2.4 上書き防止の確認と書き込みを、人の保存と共通の処理に切り出す
  - 人の保存の方法: `isUpdatable` で確認を飛ばすかを決め、ページを読んだ時点のリビジョンを期待して書く。負けたときはページを読み直して確認をやり直し、決めた回数まで書き直す。確認が通らなければ今と同じ 409 `conflict` の結果を返す
  - 反映の方法: 元のリビジョンを期待して書き、`origin` を空にし、印を付ける。負けたら書き直さずに衝突の結果を返す
  - ページの更新の route を、この処理を呼ぶ形に直す。middleware の順と、応答の前に activity を記録する位置は変えない
  - 既存のページの更新の結合テスト（更新・前のリビジョン・共同編集の文書の同期）を変更せずに通し、2.1 のテストも通っている
  - _Requirements: 3.3, 3.4, 6.3, 6.4, 10.1, 10.2_
  - _Depends: 2.1, 2.2, 2.3_
- [ ] 2.5 人の保存のあとの処理（通知・共同編集の文書の同期）を、route から共通の場所へ移す
  - 更新の route と作成の route の、応答のあとの処理（グローバル通知、Slack 通知、購読の作成、`origin` が `view` か空のときの共同編集の文書の置き換え）を、順序と条件を変えずに移す
  - 既存の作成と更新の結合テストを変更せずに通している。書き込み機能が無効でも有効でも、人の保存の通知の数が変わらないことを確かめている
  - _Requirements: 7.6, 10.1, 10.2, 10.3_
  - _Depends: 1.2_
- [ ] 2.6 人の保存と反映が同時に起きたときの動きを、結合テストで確かめる
  - 同じページに、人の保存（エディタからの保存と、API からの保存）と反映の方法の書き込みを同時に走らせる
  - どちらの順になっても、最新のリビジョンが相手の内容を確認なしに上書きしていないこと、反映の側が負けたときは衝突の結果になることを確かめている
  - エディタどうしの保存が同時に起きても、今までどおり両方が通ること（負けた側が書き直しで通ること）を確かめている
  - _Requirements: 3.16, 10.1_
- [ ] 2.7 リダイレクトをまとめて消す処理と、共同編集の接続数を返す処理を足す
  - 指定したパスと、その下のパスを起点とするリダイレクトを消す処理を、リダイレクトの Prisma の拡張に足す
  - 共同編集のサービスに、そのページのこのプロセスでの接続数を返す処理を足す
  - それぞれの結合テストで、指定外のパスのリダイレクトが残ること、接続している間は 1 以上・切断後は 0 になることを確かめている
  - _Requirements: 3.5, 5.7_

- [ ] 3. 判断の純関数（グループ 1 の 1.1 だけに依存し、1.2 以降を待たない）
- [ ] 3.1 (P) 入力の検査と、全体の状態を決める純関数を作る
  - 作成の入力の検査: 操作が無い、知らない種類、移動が 2 つ以上、操作数の上限、本文の合計の大きさ（8 MiB）、無効にされた種類、ページのパスとして使えない形、を理由の値つきで断る
  - 全体の状態: design の 6 つの規則を上から当てはめる
  - 各規則と各理由を単体テストで確かめ、見える操作だけを渡したときに見えない操作の状態が結果に出ないこと、依頼した人以外に見える操作（反映済み・取り消し済み・取り消しを断られた）だけを渡したときに `pending` と `partially-applied` にならないことも確かめている
  - 1.1 で作った仮のファイルの中身を書く。barrel は書き換えない
  - _Requirements: 1.5, 1.6, 1.7, 1.13, 1.14, 1.16, 2.1, 2.2, 9.2, 9.4_
  - _Boundary: Domain Pure Functions_
  - _Depends: 1.1_
- [ ] 3.2 (P) 反映の順序・承認の広げ方・自動反映の対象を決める純関数を作る
  - 反映の順序: 保存した並び順を保ち、移動だけを最後にする
  - 承認の広げ方: 選ばれた操作を、同じページ（編集と移動はページ ID、新規作成はパス）への「待ち」の操作に広げる。全体の承認はすべての「待ち」にする
  - 自動反映の対象: 3 つの方針ごとに選ぶ。「自分が作ったページだけ」の判定は 1 つの関数にまとめ、決まるまでは作成者で判定する仮の実装であることを関数の中に書く。新規作成は対象にし、移動は移動元のページで判定する
  - それぞれを単体テストで確かめている
  - 1.1 で作った仮のファイルの中身を書く。barrel は書き換えない
  - _Requirements: 3.2, 4.1, 4.2, 4.3, 4.4, 4.5_
  - _Boundary: Domain Pure Functions_
  - _Depends: 1.1_
- [ ] 3.3 (P) 戻せるかの判定と、取り消しの操作を作る純関数を作る
  - design の `judgeRevertability` の規則（状態、ページが無い、反映後の編集、子のページ、反映後の移動、移動元のパスの使用、ごみ箱へ移した操作ではごみ箱に無い・元のパスに空でないページがある・最新のリビジョンが変わった、ごみ箱から戻した操作は新規作成と同じ規則）を理由の値つきで判定する。元のパスに空のページだけがあるときは、使われているとみなさない
  - 戻せる操作から、取り消しの操作（編集は元の本文に戻す編集、新規作成はごみ箱へ移す操作、移動は元のパスへの移動と消すリダイレクトの起点、ごみ箱へ移した操作はごみ箱から戻す操作、ごみ箱から戻した操作はもう一度ごみ箱へ移す操作）を作り、それぞれに戻す相手（Change Proposal の ID と操作の `key`）を持たせる
  - 理由ごとと、取り消しの取り消し（編集と移動は同じ形で戻せる、ごみ箱へ移した操作は条件を満たせばごみ箱から戻す、ごみ箱から戻した操作はもう一度ごみ箱へ移す）を単体テストで確かめている
  - 1.1 で作った仮のファイルの中身を書く。barrel は書き換えない
  - _Requirements: 5.5, 5.6, 5.7, 5.8, 5.12, 5.15, 5.16_
  - _Boundary: Domain Pure Functions_
  - _Depends: 1.1_
- [ ] 3.4 (P) 見る人に返す操作を選ぶ純関数を作る
  - 閲覧できるページの操作だけを残す。依頼した人以外には、状態が反映済み・取り消し済み・取り消しを断られたの操作だけを残し、リンクを知る人だけが見られるページの操作を残さない。Change Proposal の段階（open かどうか）は判断に使わない。まだページが無い新規作成の操作は依頼した人にだけ残す
  - 依頼した人・他の人・リンクを知る人だけが見られるページ・まだページが無い操作・操作の 7 つの状態の組み合わせを単体テストで確かめ、依頼した人以外には「待ち」「失敗」「古い」「飛ばした」が残らないことを確かめている
  - 1.1 で作った仮のファイルの中身を書く。barrel は書き換えない

- [ ] 4. 反映の実行
- [ ] 4.1 編集中の人がいるかを確かめる処理を作る
  - このプロセスでの接続数が 1 以上、または共同編集の文書に未保存の入力（`draft`）があれば、編集中とする
  - 接続数はこのプロセスの分しか見えないことを、処理の説明として残す（design の分かっている制約）
  - 接続中・`draft`・どちらでもない、の 3 つの場合を結合テストで確かめている
  - _Requirements: 3.5, 5.11_
  - _Depends: 2.7_
- [ ] 4.2 操作の書き込みの決まった形と、編集と新規作成の書き込みを作る
  - 操作の書き込みの決まった形（前の実行の書き込みを探す処理と、書き込む処理）と、操作の種類をキーにした表を作り、編集と新規作成を登録する
  - 編集: 依頼した人が閲覧できなければ失敗（対象が使えない）。共通の処理の反映の方法で書き、衝突なら「古い」
  - 新規作成: 近い祖先を依頼した人が閲覧できなければ失敗。パスが使われていれば失敗。閲覧範囲を指定せずに作り、祖先から引き継がせる。閲覧範囲を割り当てられずに断られたら失敗。WIP は指定しない
  - どちらも、前の実行の書き込み（同じ `proposalId` と `proposalOperationKey` を持つリビジョン。新規作成では、そのリビジョンの `pageId` が作ったページ）があれば、それを結果として返す
  - 結合テストで次を確かめている: 作者が依頼した人であること、閲覧範囲が親と同じであること、リビジョンの `origin` が空で印を持つこと、新規作成では最初のリビジョンが印を持ち、ページには印の項目が無いこと、ページごとのアプリ内通知とグローバル通知が出ないこと、ページの作成・更新の event（`crowi.events.page`）が出ること、反映のあとに共同編集の文書を開くと反映後の本文になること
  - _Requirements: 3.3, 3.4, 3.6, 3.8, 3.9, 3.10, 3.12, 3.17, 6.1, 6.2, 6.4, 7.1_
- [ ] 4.3 移動・ごみ箱へ移す・ごみ箱から戻すの操作の書き込みを作る
  - 4.2 で作った表に、移動・ごみ箱へ移す・ごみ箱から戻すを登録する（表と決まった形は変えない）
  - 移動: 移動元を依頼した人が閲覧できなければ失敗。移動先が使われていれば失敗。アプリ内通知を止める指定と、リダイレクトを作る指定で移動する。取り消しの移動では、リダイレクトを作らず、移動のあとで元のパスとその下を起点とするリダイレクトを消す
  - ごみ箱へ移す（取り消しだけ）: 最新のリビジョンが期待どおりで子のページが無いときだけ、アプリ内通知を止めてごみ箱へ移す
  - ごみ箱から戻す（取り消しだけ）: ページを閲覧できること、ページがまだごみ箱にあること、最新のリビジョンが期待どおりであることを確かめ、アプリ内通知を止めて既存の `revertDeletedPage` で戻す（子のページを含めない）。元のパスに空でないページがあって断られたら失敗（`original-path-occupied`）。戻したあとで、元のパスを起点とするリダイレクトを消す
  - 前の実行の書き込み（すでに移動先にある、すでにごみ箱にある、すでにごみ箱から戻って元のパスにある）を結果として返す
  - 移動・ごみ箱へ移す・ごみ箱から戻すでアプリ内通知とグローバル通知（移動・削除・戻す）が出ないことを結合テストで確かめている（グローバル通知が route から出ていることを先に確かめ、ページのサービスの中から出ている場合は 2.3 の指定で止める）
  - ごみ箱から戻したあと、元のパスがページそのものを表示し、元のパスを起点とするリダイレクトが残っていないこと、元のパスに空でないページがあるときは書き込まずに失敗になることを結合テストで確かめている
  - 子のページを持つページの移動と取り消しの移動のあと、元のパスがページそのものを表示し、元のパスとその下を起点とするリダイレクトが残っていないことを結合テストで確かめている（brief の「移動を戻したときのリダイレクトの残り方」）
  - _Requirements: 3.6, 3.8, 3.10, 5.6, 5.7, 5.15, 5.16, 7.1_
- [ ] 4.4 反映の activity と、まとめたアプリ内通知を作る
  - activity: route から呼ばれたときは route が作った activity に、応答の前に記録する。裏で動くときは自分で文脈を作って記録し、失敗したら文脈を消す
  - 通知: 反映済みの編集と移動のページ（取り消しの Change Proposal では、ごみ箱へ移した・ごみ箱から戻したページも）を購読している人と、取り消しの Change Proposal では元の Change Proposal の依頼した人を受け取る人にし、そこから依頼した人（取り消しでは取り消した人）を除く。受け取る人ごとに閲覧できるページ（リンクを知る人だけが見られるページを除く）だけで中身を作って 1 件ずつ入れ、Socket.IO で知らせる。1 つも閲覧できない人には作らない。作るのに失敗したらログに残すだけにする
  - アプリ内通知の一覧の API が、Change Proposal を対象にした通知の `target` を `_id` だけにして返すようにする
  - 通知の一覧の API の応答に、受け取る人の snapshot 以外の Change Proposal の中身（他の操作、パス、本文）が入らないこと、受け取る人ごとの中身に閲覧できないページのパスと件数が入らないこと、閲覧できない人に通知が作られないこと、取り消しでは元の依頼した人に届き、ごみ箱へ移した・戻したページが中身に入ること、activity の操作者が依頼した人（取り消しでは取り消した人）であることを結合テストで確かめている
  - _Requirements: 7.2, 7.3, 7.4, 7.5, 7.8_
- [ ] 4.5 反映の権利の取り方・操作の順の実行・結果の記録を作る
  - lease が空か期限切れのときだけ取り、取れなければ「反映中」を返す。操作を 1 つ反映するたびに lease を延ばし、最後に手放す
  - 承認された「待ち」の操作を決めた順に 4.2・4.3 の表で実行し、1 周したあとで対象を読み直して、まだ試していない承認があれば続ける
  - 各操作を書き込む前に、表の「前の実行の書き込みを探す処理」を呼び、見つかったときは書き込まずにその結果を記録する（反映し直しても二度書かない役目はこの処理が持つ）
  - 結果（状態・理由・日時・作ったページとリビジョン）をその場で記録する。反映済みになったときは、同じ更新で、反映で触れたページの一覧にそのページを足し、最後に反映した日時を更新する。前に反映した操作は戻さない
  - lease を手放したあと、反映済みが 1 つ以上あれば 4.4 の activity と通知を呼ぶ
  - 同じ Change Proposal を同時に 2 回反映しても、途中で止めた（lease を期限切れにした）あとでもう一度反映しても、同じ操作のリビジョンが 1 つだけで、その操作の状態が「反映済み」であること、反映で触れたページの一覧と最後に反映した日時が記録されていること、通知が 1 回だけ作られることを結合テストで確かめている
  - _Requirements: 2.6, 2.7, 3.1, 3.2, 3.13, 3.14, 3.15_
  - _Depends: 3.2, 4.2, 4.3, 4.4_
- [ ] 4.6 反映の前の確認と、取り消しの結果を元の操作に書く処理を作る
  - 各操作の前に、設定（取り消しの Change Proposal では確かめない）、依頼した人がまだ有効で読み取り専用でないこと、編集中の人、重なるページの処理（決めた時間まで間を空けて確かめ直す）を、この順に確かめる
  - 編集中や重なる処理が残るときは、通常の操作は「待ち」に戻して承認を消し、理由を記録する。取り消しの操作は「飛ばした」にする
  - 取り消しの Change Proposal では、操作の結果に応じて元の操作を「取り消し済み」（取り消した Change Proposal の ID つき）か「取り消しを断られた」にする。「取り消しを断られた」の理由は、design の取り消しの流れの表で決める（古い → 反映後の編集、パスが使われている → 元のパスの使用、重なる処理が残った → `page-operation-in-progress`、その他の失敗 → `apply-failed`）。編集中で飛ばした場合は元の操作を「反映済み」のまま残す。重なる処理が決めた時間を過ぎても残ったときは、取り消しの操作は「待ち」に戻さず失敗にする
  - 確認のそれぞれで、書き込まれないこと、状態と理由が正しいこと、承認が消えることを結合テストで確かめている
  - 取り消しが反映されたときに元の操作が「取り消し済み」になり取り消した Change Proposal の ID を持つこと、取り消しの操作が「古い」か「失敗」になったときに元の操作が「取り消しを断られた」になり、表のとおりの理由を持つこと、編集中で飛ばしたときに元の操作が「反映済み」のまま残ることを結合テストで確かめている
  - _Requirements: 3.5, 3.6, 3.7, 4.8, 5.9, 5.11, 5.13_
  - _Depends: 4.1, 4.5_

- [ ] 5. Change Proposal のサービス
- [ ] 5.1 Change Proposal の作成と、作成直後の自動反映を作る
  - ゲスト・読み取り専用ユーザーを断る。入力の検査、1 日の件数（サーバーの日付の 0 時から、取り消しを除く）、書き込み機能と操作の種類の有効化、対象のページを依頼した人が閲覧できること、元のリビジョンが対象のページのものであることを確かめる。閲覧できない場合と存在しない場合は同じ結果を返す
  - 承認待ちの期限の設定に値があるときだけ、作成日時にその秒数を足した日時を期限として保存する。値が無いときは期限を保存しない
  - 保存したあと、作成の activity を記録し、自動反映の方針の対象に承認を付けて反映する。作成の関数は任意の `trigger: ApplyTrigger` を受け取る。`trigger` が request なら、その activity を作成の activity として結果を返す前に記録し、作成直後の反映は `background` として自分で activity を作る。`trigger` が無ければ、作成の activity も `background` と同じ方法で記録する
  - 入口（`change-proposal-ai-agent`）が使えるよう、機能の server の barrel から作成の関数と `readChangeProposalSettings` を export する（承認は 5.2、取得は 6.1 が、それぞれ自分で export を足す）。`interfaces` の barrel から `MAX_TOTAL_BODY_BYTES` が import できることも確かめる（宣言は 1.1）。AI の SDK を読み込まない
  - 断る場合のそれぞれ、3 つの方針での作成直後の反映、期限の設定に値がある場合と無い場合の期限の保存を結合テストで確かめている
  - `trigger` に request の activity を渡したとき、その activity が作成の activity として記録され、記録されないままの activity（`ACTION_UNSETTLED`）が別に残らず、作成直後の反映の activity が別の行として記録されることを結合テストで確かめている

- [ ] 5.2 承認・飛ばす・破棄を作る
  - 依頼した人でなければ「見つからない」を返す。段階が open でなければ「反映できない状態」を返す
  - 承認は、選んだ操作を同じページへの「待ち」の操作に広げて承認を付け、反映する。飛ばすと破棄は「待ち」の操作を「飛ばした」にする
  - 機能の server の barrel から承認の関数を export する

- [ ] 5.3 取り消しと、戻せるかの判定に使うページの状態の読み込みを作る
  - 判定に要るページの状態（ページがあるか、今のパス、最新のリビジョン、子のページがあるか、使われているパス）を、まとめて少ない問い合わせで読む共通の処理を作る（6.1 でも使う）
  - 取り消しを求めた人が閲覧できる、指定された操作（指定が無ければ閲覧できる反映済みの操作すべて）を選び、戻せるかを判定する。戻せない操作は元の Change Proposal の中で「取り消しを断られた」にする
  - 戻せる操作から入口の種類が「取り消し」の Change Proposal を作り、自動反映の方針と承認を通さずにすぐ反映する。設定の有効化と件数の上限は確かめない
  - 結果は design の `RevertResult` の形で返す（操作を `key` で指し、`reverted` / `revert-refused` と理由 / `skipped` と `page-being-edited`。取り消しの Change Proposal を作ったときはその ID）
  - 閲覧できない操作と存在しない key を区別せずに対象から外し、結果にも出さない
  - 依頼した人による全体の取り消し、他の人による一部の取り消し、書き込み機能が無効なときの取り消し、断られる場合を結合テストで確かめている
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.8, 5.10, 5.13_
- [ ] 5.4 期限切れ・取り下げ・止まった反映の再開と、保守用の cron を作る

  - lease が期限切れで、承認された「待ち」の操作が残る Change Proposal を、裏で動く形で反映し直す
  - 決まった間隔で動く cron を作る（複数台の間でずらす待ち、保守モードでは動かない）。起動時の cron の設定の中で、書き込み機能の有効・無効にかかわらず起動し、実行の間隔の設定が空のときだけ起動しない
