## 1. 決定事項

### 1.1 形式ごとの抽出方法

| 対象 | 抽出方法 | 返す単位 (`pages[]`) |
|---|---|---|
| DOCX / RTF / EPUB / CSV | `@firecrawl/anydoc` | 1 要素 |
| XLSX | `xl/workbook.xml` の中でシート名を一意な目印に置き換え、全シートを表示状態にしてから anydoc を 1 回だけ呼び、出力を目印の見出しで切る (全シートのセル数が 7 万を超えるものは変換の前に上限超過のエラーにする) | シートごと |
| PPTX | スライドごとに 1 枚だけの PPTX パッケージに分けてから、それぞれを anydoc に渡す | スライドごと |
| 旧形式 PPT | 分けられない (ZIP ではない) ので、丸ごと anydoc に渡す | 1 要素 |
| 旧形式 DOC / XLS、OpenDocument (ODT / ODS / ODP) | anydoc (XLS は anydoc の形式名 `xlsx` を明示して渡す) | 1 要素 |
| PDF | `@embedpdf/pdfium` (PDFium の WASM) でページごとに取り出す。開くのにパスワードが要らない (オーナーパスワードのみの) PDF は抽出する | ページごと |
| CSV / TSV | 文字コードを判定して UTF-8 にしてから、anydoc に形式 `csv` を明示して渡す (区切り文字は anydoc が判定する)。8MiB (`MAX_CSV_BYTES`) を超えるものは、子プロセスを作る前に上限超過にする | 1 要素 |
| HTML | サービス自身で処理する。`htmlparser2` の `Tokenizer` でタグを切り出し、script / style などを除いてテキストにする。20MiB (`MAX_HTML_BYTES`) を超えるものは、子プロセスを作る前に上限超過にする | 1 要素 |
| TXT / MD / LOG / JSON / YAML | サービス自身で処理する。文字コードを判定してデコードしたテキストをそのまま返す (JSON / YAML は解析しない) | 1 要素 |
| XML | サービス自身で処理する。DOCTYPE を取り除き、タグを取り除いたテキストを返す (エンティティは展開しない) | 1 要素 |
| ipynb | サービス自身で処理する。セルの source と、テキストの出力 (stream、text/plain) を取り出す。画像の base64 は捨て、出力ごとに文字数の上限を設ける | 1 要素 |
| Outlook MSG | 対象外。サポート対象外のエラーを返す | — |

- 改行コードを LF に揃える処理は、すべての経路の最後にかける。
- 日本語の文字 (ひらがな・カタカナ・漢字) の間に入った 1 文字分の半角空白・改行を取り除く処理は、PDF の経路だけにかける (Req 1.9)。語の途中の切れが見つかったのは PDF の抽出だけで、TXT や DOCX などの改行・空白は書き手が入れたものだから。全角空白と段落の区切り (2 つ以上続く改行) は残す。
- どちらの後処理も、入出力が文字列だけの純粋関数にする。
- 後処理の後に中身が空になった要素は `pages[]` から除く。ただし `pages[]` は最低 1 要素を必ず返す (全部が空なら中身が空の 1 要素)。下流の indexing は `pages[]` の要素ごとに検索文書を作り、ファイル名だけの文書は失敗したときにしか作らないため、空の配列を返すと画像だけの PDF や空のブックがファイル名でも見つからなくなる。
- 文字コードの判定は、BOM → 宣言 → UTF-8 (厳密) → 自前の判定 (候補は Shift_JIS 系・EUC-JP・ISO-2022-JP・windows-1252) → cp932 → windows-1252 の順に試す。HTML は先頭の `<meta charset>` を優先する (§4.6)。

### 1.2 部品ごとの使い方の条件

**anydoc (`@firecrawl/anydoc` 0.2.4)**

- 版を固定する。0.x 系で公開から日が浅く、PPTX の分割は文書化されていない挙動に頼るため。
- 形式は中身から判定させず、呼び出し側で明示して渡す。
- OCR は既定の `reject` のまま使う。`hosted` を指定すると文書全体を外部の Firecrawl Parse に送ってしまう。
- エラーは `ConvertErrorCode` を持つ `Error` として投げられる。値と失敗の種類の対応は、版を固定した契約テストで固定する。
- anydoc は変換できない部分が 1 か所でもあると、文書全体をエラーにする (暗号化されたファイル、壊れたファイルなど)。部分的な結果は返らない。
- anydoc には処理時間の上限を指定する手段がない。時間切れの打ち切りは、子プロセスごと止めることで実現する (§1.3)。
- `toMarkdownBytes` は Promise を返し、変換は Node の裏のスレッドで動く。中のスレッドの数は子の `env` の `RAYON_NUM_THREADS=1` で 1 本にする。
- Rust のスレッドの中の panic と、大きな XML の部品 (64MiB 級) でのメモリの確保の失敗は、子を abort させる (`crashed`)。
- bzip2・LZMA で圧縮した ZIP の部品は読めない (`compression method not supported`)。

**PPTX の分割 (分けてから anydoc に渡す方式)**

- `presentation.xml` のスライド一覧を、対象の 1 枚だけに書き換えたパッケージを作る。書き換えは正規表現ではなく、XML として解析して行う (名前空間の接頭辞や Strict OOXML の違いに左右されないようにするため)。
- パッケージには、対象スライドと、そのスライドが参照する XML 部品だけを入れ、無圧縮で包む。文字の抽出に要らない画像などは入れない。他のスライドの XML まで入れると、処理量が「スライド数 × XML 全体」に膨らむ。
- XML 部品を展開するときは、部品ごとと合計の両方について、実際に展開したバイト数に上限を設ける。
- 契約テストを置く。「スライドごとに分けて変換した結果をつなぎ直すと、丸ごと anydoc に渡した結果と一致する」ことを確かめる。参照から外したスライドや画像の抜けたパッケージを anydoc が受け付けるのは文書化されていない挙動なので、anydoc の版を上げるたびにこのテストで変化を検知する。
- anydoc が出力する PowerPoint の自動生成の代替テキスト (「AI 生成コンテンツは誤りを含む可能性があります」など) と、改行の印として出る `\` を後処理で取り除く。
- 旧形式の .ppt は ZIP ではないため分けられない。丸ごと anydoc で変換し、1 要素として返す。

**PDFium (`@embedpdf/pdfium` 2.15.1)**

- PDFium の C の関数をそのまま呼ぶ。使う関数は `PDFiumExt_Init`、`FPDF_LoadMemDocument`、`FPDF_GetLastError`、`FPDF_GetPageCount`、`FPDF_LoadPage`、`FPDFText_LoadPage`、`FPDFText_CountChars`、`FPDFText_GetText`、`FPDFText_ClosePage`、`FPDF_ClosePage`、`FPDF_CloseDocument` と、WASM の `malloc` / `free`。入力の PDF を写した WASM のメモリは、文書を閉じるまで解放してはいけない (`FPDF_LoadMemDocument` はそのメモリを読み続ける)。
- WASM の本体は package の中の `pdfium.wasm` を読んで `init({ wasmBinary })` に必ず渡す。渡さない場合の読み方に外へ取りに行く経路が無いことは、ネットワークを止めて確かめていない。
- 開くのにパスワードが要る PDF は `FPDF_GetLastError` が 4 (パスワード) か 5 (セキュリティ) になる。これを暗号化として扱う。オーナーパスワードだけの PDF は普通に開けるので抽出する (Req 1.12)。それ以外の失敗は壊れた PDF として扱う。PDFium が修復して読める場合はそのまま抽出する。
- WASM の PDFium は、ページの無い PDF を 0 ページとして開く (ネイティブの PDFium は開くこと自体を拒む)。ページの無い PDF は壊れた PDF として扱う。
- `malloc` は失敗すると 0 を返す (例外にならない)。必ず 0 を確かめて `internal` にする。PDFium の中の `abort` は `RuntimeError` として投げられ、これも `internal` になる。
- 文字列は `FPDFText_GetText` が返した長さで WASM のメモリを切り、`TextDecoder('utf-16le')` で復号する (NUL で読むのをやめる関数は使わない)。ページの文字列の先頭の BOM を残し、対になっていないサロゲートを取り除き、本物の U+FFFD は残す。
- 画像だけの PDF は例外にならず、全ページで文字数が 0 になる。空の結果として扱う (上の「最低 1 要素」の規則に従う)。
- 同期の WASM なので、1 ページ 400 万字の変換は約 1 秒メインのスレッドを止める。親を見張る処理は worker thread で行う (§4.3)。

**XLSX のシート分割**

- `xl/workbook.xml` の中で、各シートの名前を `ZZ<リクエストごとの乱数><連番>ZZ` に置き換え、非表示のシートを表示状態に戻してから、anydoc を 1 回だけ呼ぶ。出力を `## 目印` の行で切り、目印から元のシート名に戻す。
- 元のシート名は、XML の文字参照 (`&lt;` など) を元に戻してから使う。
- `pageNumber` は workbook.xml に並んでいる順番 (1 始まり、非表示・空・グラフのシートも数える) にし、`label` は元のシート名にする。空のシートは返さないので番号が飛ぶことがある。非表示のシートは、ファイルを開いた人なら誰でも表示に戻せるので対象に含める。
- シートが 1 枚だけのブックでは anydoc は見出しを出さないので、出力全体を 1 要素とし、`pageNumber=1`、`label` を workbook.xml のシート名にする。空のシートとグラフだけのシートは目印が現れないが、返さないシートなので問題にしない。
- 置き換えていない目印が出てくる、目印の順番が食い違う、最初の目印より前に空でないテキストがある、のどれかに当たるときだけ、XLSX 全体を 1 要素として返す (別のシート分割処理を持たない)。
- セル数の事前の検査は、DOM を作らずに部品を 64KiB ずつ走査して `<c` を数える。書き直しは、workbook.xml だけを差し替え、ほかの部品を元の圧縮の方式のまま流しながら写す (§4.8)。
- anydoc の版を固定した比較テストを置く。

**ZIP を書き換える経路の前提**

- PPTX と XLSX は、ZIP として一覧でき、必要な部品 (`ppt/presentation.xml` / `xl/workbook.xml`) がちょうど 1 つあるときだけ書き換えの経路に入れる。ZIP の終わりの記録がファイルのどこにも見つからないもの (暗号化された OOXML や旧形式。中身は CFB 形式) だけを、書き換えずに形式を明示して anydoc にそのまま渡す。こうすると anydoc から型の付いたエラーが返る。終わりの記録があるのに一覧を読み切れない ZIP、必要な部品が無い・2 つ以上ある ZIP は `malformed` で断る (検査を通らずに anydoc に渡ると、上限を回避できるため。§9.3)。
- ZIP の終わりの記録はファイル全体から探す。最後の 64KiB の中は CPython の `zipfile` と同じ手順で読み (前後の余分なバイト、注釈の長さ、要素の数の食い違い、ディスク番号の扱い)、それより前の候補は検証してから使う (§9.3.2)。エントリ数と、申告された展開後のサイズの合計を確かめる。yauzl の大きさの検査は切り、部品を読むときに自分で確かめる (申告を超えるバイトが来たらその場で壊れたファイル、終わりに CRC-32 を確かめる。申告より短く終わっても CRC-32 が合えば通す)。

**テキスト系の部品**

- HTML は `htmlparser2` 12.0.0 の `Tokenizer` だけを使う (`Parser` は使わない。§4.6)。版は固定する。内部の値 (`recognizeSelfClosing` と `index`) を 2 か所書き換えているので、版を上げるときは見張りのテストを通す。
- XML の解析は `@xmldom/xmldom` 0.9.12 以上 (それより古い版は使わない) の上に自前の検査を重ねる (§4.6)。
- ZIP の読みは `yauzl`、書きは `yazl`。yazl は要素の数の 2 乗の時間で書く (4 万個で 3 秒) ので、要素の数の上限で先に断る。
- 文字コードの判定とデコードには部品を使わない (§4.6)。

### 1.3 サービスの構成

- **動かす場所**: apps/app のプロセスの中では動かさない。独立したコンテナとして動かし、apps/app からは HTTP (multipart) で呼ぶ。
- **配布**: GROWI.cloud では k8s の共有 Deployment + 自動スケールとして、テナント間で共有する。OSS 版は Docker image を使う。サービスは状態を持たない。k8s の manifest の例は持たず、守る条件を `docker/README.md` に文章で書く (§5.8)。
- **言語と実行環境**: Node.js 24 + TypeScript。HTTP は Hono (`@hono/node-server`)。monorepo のほかの部分と同じ言語と道具 (pnpm / turbo / vitest / biome) で保守する。
- **置き場所**: `apps/attachment-text-extractor/` (`@growi/attachment-text-extractor`)。`apps/pdf-converter` と同じく pnpm workspace の一員で、package ごとの `turbo.json` を持つ。`pnpm-workspace.yaml`、ルートの `turbo.json`、`vitest.workspace.mts` は変えずに済む (`apps/*` がすでに対象)。
- **変換の実行**: 変換は、リクエストごとに 1 つの子プロセスで実行する。子は `/usr/bin/prlimit` で包んだ `child_process.spawn` で起動する (§4.3)。
  - 時間切れのときは親が子に SIGKILL を送る。これで変換そのものが止まり、同時実行の枠とメモリが解放される (Req 2.5)。
  - 1 件の異常終了は、その子の中で閉じる (Req 2.7)。
  - メモリの主な守りは、親が子の RSS (プロセスが実際に使っている物理メモリの量) を 50ms ごとに見張り、上限を超えたら止める方式にする。OS の仮想メモリ上限 (`RLIMIT_AS`) は最後の歯止めとして、RSS の上限より大きく設定する (§4.7)。
  - 親と子のやり取りは管 (パイプ) だけで行い、子から親へは JSON を 1 回送る。親はそれをコードとして解釈しない。共有メモリ (`/dev/shm`) は使わない。
  - 親が先に終わったときに子が残らないよう、子の中の見張り専用の worker thread が、親だけが書き込み側を持つ管を見張り、それが閉じたら子が自分に SIGKILL を送る。
  - 同時実行の上限は 1 つのプロセスの `MAX_CONCURRENCY` で、それがコンテナ全体の上限になる。スケールはレプリカを増やして行う。
  - 呼び出し側が変換中に接続を切ったら、変換を止めて枠とメモリを返す (Req 2.9)。
  - 呼び出しは「状態を持たない同期の HTTP 呼び出し」のままにする。非同期の受け付け方式は採らない (§3.8、2026-11-02 ユーザー判断)。
- **Dockerfile**: `node:24.x-bookworm-slim` を元にした multi-stage。build の段で pnpm の workspace から build し、`pnpm deploy --prod` で本番の依存だけを取り出す。実行の段で `/usr/bin/prlimit --version` を実行し、無ければビルドを失敗させる。ffmpeg や exiftool などの外部バイナリは入れない。
- **実行ユーザー**: 非 root (uid 10001)。read-only rootfs、capabilities をすべて外す、権限を上げない、seccomp `RuntimeDefault` で動く。書き込める `/tmp` は要らない。
- **image の大きさ**: 400MB 以下 (CI が検査する。§4.13)。
- **CI**: このサービス専用の GitHub Actions workflow (`.github/workflows/ci-attachment-text-extractor.yml`)。lint とテストのジョブと、image の確認のジョブを持つ。ほかの app の workflow と同じ `ci-<app>.yml` の名前にした。
- **OpenAPI → 生成クライアント**: 経路の定義の横に書いた zod のスキーマから `hono-openapi` で文書を作る (§4.5)。`scripts/export-openapi.ts` で `packages/attachment-text-extractor-client/openapi.json` に書き出し、orval で生成クライアントを作る。名前は道具の既定に従う。
- **compose ファイルは同梱しない**: どこからも使われておらず、運用の条件は `docker/README.md` にある。ユーザーの決定 2026-11-16。

### 1.4 外部とのつながりとライセンス

- **OCR と LLM は使わない**。画像の文字認識も、LLM による補助もしない。
- **外向き通信 (egress) なしで動く**。k8s では NetworkPolicy で外向き通信を遮断する。anydoc の `hosted` の OCR を使わないのはこのため (§1.2)。anydoc の経路で、`fetch`・`net`・`child_process` の呼び出しと環境変数の読み取りが 0 回であることを、335 件の変換を差し替えと `strace` で見て確かめた。
- **外部バイナリを使わない**。依存は npm から入る部品 (ビルド済みのネイティブ部品と WASM を含む) だけにする。例外は util-linux の `prlimit` で、Req 1.7 が防ぎたかったのは ffmpeg や exiftool のような変換用の外部ツールを image に足すことなので、`prlimit` はこれに当たらない (ユーザー判断、2026-11-04)。`prlimit` が元の image に入っていることは、ビルド・CI・起動時の `/readyz` の 3 か所で確かめる。
- **install のときにファイルを取りに行く部品は使わない**。`pnpm-workspace.yaml` の `allowBuilds` は install のときの処理を許可制にしている。許可を足すと、開発者全員の `pnpm install` と CI が外部のサイトに依存する。
- **ライセンスは MIT / Apache-2.0 / BSD / ISC などの許容的なライセンスのものだけ**を採用する。GPL / AGPL / LGPL は使わない。

## 2. 採用理由と根拠

### 2.1 計測の方法 (Office 系のライブラリの比較)

§2.2〜§2.8 の数字のうち、ライブラリの比較は 2026-10 に、それ以前の実装の言語 (Python 3.12) の部品で測ったものである。anydoc の Rust の核は npm 版と同じで、70,000 セルの XLSX で出力が文字数まで同じ (964,002 字) ことを確かめたので、anydoc を選んだ理由はそのまま成り立つ。Node.js 版で測り直した数字は §4 にある。

- **環境**: 16 コアの開発コンテナ 1 台。
- **メモリと速度**: 1 回の変換ごとに新しいプロセスを起動して測った (各 3 回、メモリは最大値、時間は中央値)。メモリは RSS で見た。
- **サンプル**: デジタル庁の公開資料 6 件 (PDF 3 件: 116 / 47 / 41 ページ、PPTX 1 件: 61 スライド、XLSX 2 件) と、生成したファイル (日本語の DOCX 2 件: 40 段落 / 6,000 段落 + 表 40 個、PPTX 1 件: 300 スライド、XLSX 1 件: 5 シート × 2 万行 × 10 列、6MB)。これとは別に、実ファイル 29 件 (DOCX 12 / PPTX 8 / XLSX 9)、実物の PDF 5 件 (1〜116 ページ)、実物の PPTX 8 件 (2〜112 スライド) でも比べた。
- **日本語の品質**: 別の手段で取り出したテキストを基準にした。NFKC 正規化をかけたうえで日本語 (ひらがな・カタカナ・漢字) だけを抜き出し、4 文字の並びがどれだけ一致するかを見た。

### 2.2 Office 系に anydoc を使う理由

比べた相手は、それまで採用していた markitdown (`[pdf,docx,xlsx,pptx]`) である。

**待機時のメモリ** (ライブラリを読み込んだだけの状態):

| 構成 | 待機時 |
|---|---|
| markitdown + PDF のページ分割用の pdfminer | 148.7MB |
| anydoc + pdfminer | 35.3MB |

- markitdown は読み込んだ時点で、ファイル種別を判定する機械学習モデル (magika / onnxruntime) と pandas / numpy まで読み込むため重い。
- 変換を子プロセスで動かす (§1.3) と、子プロセスを作るたびに読み込みの費用がかかるので、軽いほうが有利になる。
- 依存の大きさは anydoc 8.4MB に対し markitdown 286MB。依存パッケージの数は anydoc 0 個に対し markitdown 36 個。

**変換中の最大メモリと時間**:

| ファイル | 大きさ | markitdown | anydoc |
|---|---|---|---|
| PDF 116 ページ | 2.3MB | 158MB / 3.1 秒 | 44MB / 7.7 秒 |
| PPTX 61 スライド | 5.6MB | 192MB / 0.29 秒 | 49MB / 0.04 秒 |
| XLSX 小 (2 件) | 20KB | 152MB / 0.04 秒 | 25MB / 0.002 秒 |
| DOCX 大 (生成) | 0.4MB | 202MB / 1.7 秒 | 59MB / 0.05 秒 |
| PPTX 300 スライド (生成) | 0.4MB | 154MB / 0.59 秒 | 28MB / 0.01 秒 |
| XLSX 5 シート × 2 万行 (生成) | 6MB | 617MB / 36.5 秒 | 623MB / 2.1 秒 |

- Office 系では anydoc が 10〜30 倍速い。実ファイル 29 件 (DOCX / PPTX / XLSX) では 20〜40 倍速く、メモリは約 6 分の 1 だった。
- markitdown は内部のファイル種別判定が、変換のたびに約 10 コア分のスレッドを空回りさせる。共有サービスでは他の変換の CPU を奪う。
- PDF は anydoc のほうが遅いが、PDF は anydoc に任せず PDFium で取り出す (§2.5) ので、判断に影響しない。

**細工したファイルへの耐性**:

| 入力 | markitdown | anydoc |
|---|---|---|
| 750KB の DOCX (展開すると 300MB) | メモリが 1.5GB を超え、強制終了された | 0.01 秒で上限エラー |
| 47KB の DOCX (10 万段の入れ子) | CPU を 90 秒以上占有 | 0.01 秒で上限エラー |

- anydoc は Rust 製でメモリ安全であり、fuzz テストを行っている。展開後のサイズ・入れ子の深さ・ノード数に固定の上限がある。
- anydoc は失敗の種類ごとにエラーが分かれている (暗号化・壊れた・部品が無い・上限・未対応) ので、エラーコードに対応づけやすい。

**出力の質**: XLSX の雑音 (`NaN`、`Unnamed: N` という列名など) は markitdown のほうが多い。markitdown は PPTX の改行コード (垂直タブ) を残す。anydoc は PPTX の一部で行の順番を入れ替える (表紙の日付と組織名が逆になった)。anydoc は、シートが 1 枚だけのブックではシート名を出さず、非表示のシートと空のシートは出力しない (§1.2 の「XLSX のシート分割」で扱う)。

**機能の違い**: anydoc は旧形式 Office (DOC / XLS / PPT) と OpenDocument も扱えるので、対象形式を増やせた (Req 1.8)。HTML / JSON / TXT / MSG は扱えない。PPTX のスライド区切りも PDF のページ区切りも出さない。

### 2.3 テキスト系をサービス自身で処理する理由

- anydoc は HTML / JSON / TXT を扱えない。
- HTML から検索用の文字を取り出すだけなら、タグを切り出す部品と、読み飛ばす要素と改行の入れ方を決める小さな自前の層で足りる。markitdown のような変換ライブラリを HTML のためだけに残すと、待機時のメモリが重い構成の水準に戻ってしまう。
- TXT / JSON / XML / YAML / MD / LOG / ipynb は、文字コードを判定してそのまま返せばよく、変換ライブラリは要らない。

### 2.4 子プロセスで変換する理由

- 変換を同じプロセスのスレッドや非同期の処理に逃がしても、外から確実に止められない。Req 2.5 (処理そのものを止めて、枠とメモリを解放する) を満たすには、kill できる子プロセスに分けるしかない。これは言語と部品の選択に関係なく必要になる。
- Node の worker_threads では、ネイティブ部品の abort や segfault でプロセスごと落ち、メモリの上限もスレッドごとには掛けられない。
- PDFium は C++ で書かれていて、細工した PDF でメモリが壊れる種類の不具合が起きうる。想定外の異常終了を他のリクエストに波及させないため、子プロセスで隔離する。
- 子ごとに上限 (仮想メモリ、CPU 時間、コアダンプ) を掛けられる。Node には `setrlimit` が無いので、`prlimit` で包んで起動する (§4.3)。

### 2.5 PDF に `@embedpdf/pdfium` を使う理由

PDFium (Chromium の PDF エンジン) を選んだ理由: 2026-10 に実物の PDF 5 件 (1〜116 ページ) で比べ、速さ (116 ページで 0.19 秒)・メモリ (34MB)・取りこぼしの無さのすべてで最上位にいて、ライセンスの条件も満たした (比べた相手は §3.3)。Node で使える PDFium の包み方の中から `@embedpdf/pdfium` を選んだ理由は §4.2 にある。要点は次のとおり。

- ベンチマークの PDF と、Req 1.4 / 1.9 / 1.10 / 1.11 / 1.12 のテストで、それ以前の実装と同じ結果だった。
- install のときの処理が無い (WASM が package に入っているだけ)。CPU を選ばない (x64 と arm64 で同じファイル)。
- WASM の中で動くので、PDFium の中のメモリの破壊が子のプロセスのほかの部分に届かない。
- 公開の関数でエラーの番号 (4 と 5) を取れる。
- 測った候補の中で最も小さい (7.2MB)。
- PDF をページ単位の別経路で取り出す方針は、外部の評価 (markitdown の PDF は表と見出しが弱い、§7.2) とも合う。

### 2.6 PPTX をスライドごとに分けてから anydoc に渡す理由

anydoc の出力にはスライドの区切りが無い。見出しを手がかりに区切ろうとすると、本文の約 23% が隣のスライドに入ってしまい、スライド番号を確実に戻せない。そのため、スライド単位で取り出す方法を別に比べた (2026-10、実物の PPTX 8 件 (2〜112 スライド) と生成 1 件)。

| 方式 | スライド数 | 取り出した文字 | 112 スライドの時間 / 最大メモリ | 備考 |
|---|---|---|---|---|
| **スライドごとに 1 枚の PPTX に分けて anydoc に渡す** | 全件正しい | つなぎ直すと、丸ごと anydoc に渡した結果と 1 文字も違わない | 0.53 秒 / 56MB | **採用** |
| PPTX 専用のライブラリ (python-pptx) | 全件正しい | 基準 | 0.22 秒 / 110MB | 垂直タブが残る。結合で隠れたセルの重複文字も拾う |
| 自前の読み取り (約 50 行) | 全件正しい | 上と全 9 件で 1 文字も違わない | 0.08 秒 / 28MB | 不採用 (§3.3) |

採用した方式の利点: 追加の依存が要らない。結合セルの文字を 1 回だけ出す。表は Markdown で出るので、他の Office 形式と書式が揃う。文字の出方が、丸ごと anydoc で変換した場合と完全に同じになる。

分割した変換は、共有部品 (マスター・レイアウト・テーマ) をスライドごとのパッケージに写すので、処理量は「スライド数 × 共有部品の大きさ」に比例する (2026-10 の計測で 2,000 枚・マスター 200KB で約 6 秒)。上限は `TIMEOUT_S` と RSS の上限が受け持つ。

Node.js 版の分割は、スライドごとの包みを無圧縮で `yazl` で書く。4,000 スライドの分割は 4.7 秒で、時間はスライド数に比例する。メモリは §4.11。

### 2.7 日本語の正規化をかける理由と範囲

- **文字化けは見つからなかった**。U+FFFD (置き換え文字)、`(cid:N)`、私用領域の文字、康煕部首、Latin-1 として読み違えた崩れのいずれも、比べたライブラリ・全ファイルで 0 件だった。
- **PDF では、単語の途中で文字列が切れる問題がどの抽出方法にもある**。PDF の折り返し位置で、ある方法は日本語の間に空白を入れ (116 ページの PDF で 2,558 か所)、ある方法は改行を残す (同 1,904 か所)。
- 語の途中に入った空白は、kuromoji (Elasticsearch で使っている日本語の単語区切りの仕組み) が語を 2 つに割る原因になる。116 ページの PDF で検索語の出現数を数えると、基準より 5〜10% ほど少なかった (例: 「情報システム」は基準 478 件に対し 443 件)。
- 日本語の間の 1 文字分の空白・改行を詰める後処理をかけると、116 ページの PDF での語の一致率は 0.878〜0.966 から 0.981〜0.997 に上がった。

ライブラリを替えても PDF の語の途中の切れ目は残るので、後処理はライブラリの選択と関係なく必要になる。一方、DOCX / XLSX / PPTX の anydoc の出力には、抽出で入った切れ目は見つからなかった (日本語の間の空白の数が基準のテキストと同じだった)。そこで、詰める処理は PDF の経路だけにかけ、書き手が入れた改行や空白を消さないようにした。

### 2.8 大きな XLSX のメモリとセル数の上限

- 6MB の XLSX (5 シート × 2 万行) で、anydoc は約 620MB まで膨らむ。アップロードの上限 (`maxFileSizeBytes`、既定 50MB) ではこのメモリを抑えられない。
- 対策として、形式ごとのサイズ上限ではなく、子プロセスの RSS の上限で止める方式にした。入力の大きさとメモリの関係は形式や中身でばらつくため、実際に使ったメモリで止めるほうが確実だから。既定の上限は 320MB (2026-10-28 ユーザー判断)。
- XLSX は anydoc がセル数に比例してメモリを使う (1 セルあたり約 2.5KB)。1 シート 50 万セル以上は anydoc の `max_xml_nodes` の上限でエラーになる。そこで、anydoc に渡す前に全シートのセル数を数え、7 万セルを超えるものは上限超過のエラーにする (2026-10-28 ユーザー判断)。Node.js 版で 7 万セル 1 シートの子の最大 RSS は 289〜294MB (image の中で 291MB) で、320MB に収まる (§4.8)。大きな XLSX は検索の対象にならない。
- 2026-10 の計測の「7 万行 × 1 列 285MB」「10 万行 × 1 列 328〜357MB」は、それ以前の実装で、計測のスクリプトの一番外側でテスト用の生成器を読み込んでいたために子の土台が約 40〜45MB 重くなった値である (本番と同じ起動では 7 万セルで 242MB)。Node.js 版の値と直接は比べない。
- 同時実行は 3 件にし、コンテナのメモリを節約する (2026-10-28 ユーザー判断)。メモリの予算は §4.9。

### 2.9 サービスの構成を選んだ理由

**apps/app の外で、別コンテナで動かす**

- apps/app のイベントループの上で重い変換をすると、他のリクエストが止まる。メモリ不足で落ちたときに apps/app も巻き込まれる。
- 別コンテナにすると、テナント間のリソースの境界を保てる。クラッシュしても apps/app は生き残る。
- anydoc は Node から使えるが、apps/app のプロセスの中では動かさないことをユーザーが決めた (2026-10-27)。抽出サービスを Node.js で書いても、この判断は変わらない (同じ言語で書くことと、同じプロセスで動かすことは別である)。
- 入力は添付のバイト列、出力は短いテキストという短いリクエストなので、HTTP multipart で完結する。
- `apps/pdf-converter` で確立した「マイクロサービス + OpenAPI から自動生成するクライアント」の型をそのまま使える。

**テナントごとのサイドカーではなく、共有 Deployment + 自動スケールにする**

- サイドカー方式 (テナントの Pod ごとに抽出コンテナを 1 つずつ付ける方式) だと、待機中のメモリがテナントの数だけかかる。umbrella の試算 (2026-04) では、100 テナント × 待機時 約 120MB = 12GB に対し、共有で 2 レプリカ × 約 500MB ≈ 1GB で済む。いまの構成の待機時は image の中で 34〜35MiB と小さいが、テナントの数だけ積み上がる点は変わらない。

**Node.js + Hono で書き、`apps/` に置く (ユーザー判断、2026-11-04)**

- 目的は言語の統一による保守のしやすさである。monorepo のほかの部分はすべて Node / TypeScript で、このサービスだけ別の言語・別の道具・別の CI を保守し続けることを避ける。性能や抽出の質を上げることは目的にしない (性能が少し落ちることも、それだけで不採用の理由にはしない)。検索の品質は、ベンチマークで下回らないことで守った (§4.1)。
- Hono は `@hono/node-server` で標準の `Request` と Node の要求のストリームの両方に触れられ、本文の受け取りを自分で制御できる (§4.4)。
- `apps/pdf-converter` が同じ形の前例になる (workspace の中の Node のマイクロサービスで、専用の CI と `pnpm deploy --prod` の Dockerfile を持ち、生成クライアントを orval で作る)。この形に揃えると、CI・Dockerfile・vitest・turbo の扱いを新しく考えずに済む。
- 代わりに、開発者全員の `pnpm install` に anydoc のネイティブ部品 (linux x64 で 7.9MB) と PDFium の WASM (7.2MB) が入る。
- Bun は挙動が不安定で、Deno は仮想メモリの上限 5GB でも動かなかったので採らない (Req 5.7)。

**既製の image を使わず自前でビルドする**

- 要件 (余計な機能を含まない軽い構成、health の確認口、認証、ビルド済みの配布) をすべて満たす既製の image は無かった (§3.6)。

### 2.10 この根拠の限界

- 実物は 6 件で、実物の DOCX は無い (再検証の 29 件を除く)。大きなファイルはすべて生成したもの。
- 品質は文字の一致と、小さなベンチマーク (23 文書。§4.1) で見ており、表の構造や読み順が正しいかは、目で少し確かめただけ。ベンチマークはほぼ満点の水準にあり、良くなった点は点数に出ない。
- Node.js 版の計測は、開発コンテナと CI の image の中で行った。本番のクラスタでの値ではない。CPU の上限の下では測っていない。
- 遅い側の処理時間 (p95) は測っていない。

## 3. 不採用にした選択肢

「出典」は、その理由を確かめた場所を示す。§3.1〜§3.8 の多くは 2026-10 までの検討で、そのときの実装の言語 (Python) の部品を物差しにしている。いまの設計と食い違う行には、その旨を書いた。Node.js で書くことを決めた後の検討は §3.9 にある。

### 3.1 抽出をどこで動かすか

| 選択肢 | 不採用の理由 | 出典 |
|---|---|---|
| Elasticsearch の ingest-attachment (Apache Tika) | GROWI.cloud は Elasticsearch のクラスタをテナント間で共有している。ingest ノードに Tika の CPU・メモリの負荷が集中し、他テナントの検索やインデックス更新に影響する。Java ランタイムと Tika サーバのプロセスを k8s に足すことにもなる。Req 4.1 (共有 ES の ingest ノードでは抽出しない) にも反する | umbrella |
| apps/app の中で Node のライブラリ (unpdf + officeparser など) を使う | 重い変換が apps/app のイベントループを占有し、他のリクエストに影響する。メモリ不足で落ちると apps/app も巻き込まれる。Office 系、特に PPTX / XLSX の構造を保った抽出の品質も劣っていた (旧比較)。当時あった「Python のほうがテキスト抽出のライブラリが豊富」という理由は、anydoc が npm にもあり、いまは成り立たない。残る理由は、apps/app のプロセスの外で動かすこと | umbrella |
| markitdown の TypeScript 移植版 (markitdown-ts など) | いずれも個人のメンテナンスで、PPTX に対応していないものや更新が止まったものばかり。本番には向かない | umbrella |
| anydoc を apps/app のプロセス内で (Node から) 使う | ユーザーが不採用と決めた (2026-10-27)。重い処理と異常終了を apps/app から切り離すため | 本 spec |

### 3.8 変換の実行方式と細かな処理方法 (design の調査で見送ったもの)

言語に依存しない理由で見送ったものと、いまも判断の材料になるものだけを残す。

| 選択肢 | 不採用の理由 |
|---|---|
| 変換を同じプロセスのスレッドで実行する | スレッドは外から止められず、Req 2.5 を満たせない (§2.4) |
| 常駐ワーカーのプール | 大きな XLSX の変換後、ワーカーが 609MB を持ったまま返さない。CPU 時間の上限が仕事ごとではなく累積で効く。1 件の異常や悪意あるファイルの影響が次の要求に残る |
| ワーカーが 1 つ落ちると実行中の他の仕事まで失敗するプール | Req 2.7 を満たさない |
| `RLIMIT_AS` (仮想メモリの上限) を主なメモリの守りにする | anydoc (Rust) は確保に失敗すると abort し、親からは異常終了と区別できない。Node.js と WASM は仮想メモリを大きく予約するので、RSS の上限に近い値にもできない (§4.7)。最後の歯止めにとどめる |
| XLSX: anydoc の `## シート名` の見出しをそのまま突き合わせる | 見出しを出す規則が一定しない (2 枚でも片方が非表示だと出ない、グラフシートだと出る)。シート名の先頭の空白が削られ、`<` は `\<` になる。非表示と空のシートは出力されない |
| XLSX: シートごとに 1 枚だけのブックに分けて変換する | 正確だが、共有文字列をシートごとに読み直すため遅い (30 シートで 0.17 秒 → 1.3 秒)。グラフシートだけのパッケージは壊れたファイルのエラーになる |
| XLSX: anydoc の構造データ (`to_document()` など) を受け取る | 非表示のシートは同じように落ちる。Markdown への変換を自前で書く必要がある |
| 文字コード: UTF-8 → cp932 → latin-1 の順に試すだけ | EUC-JP と cp1252 が文字化けしたまま通ってしまう |
| 文字コード: 候補を絞らずに判定する | 短い Shift_JIS が big5 と誤判定された |
| JSON / YAML を解析して値だけ取り出す | 深い入れ子でエラーになり、YAML はエイリアスの展開で膨らむ。デコードしたテキストをそのまま使えば検索には十分 |
| オーナーパスワードだけの PDF を暗号化として拒否する | 開くのにパスワードが要らず、誰でも読める内容なので、拒否すると検索できる文書が減るだけになる (Req 1.12 として要件に明記した) |
| XLSX を少しずつ読む自前の処理 (シートの XML を先頭から順に読み、セルの文字を取り出す。約 100 行) | 実測ではメモリが小さく (100 万セルで 54MB)、日本語の文字数も一致した (ふりがな `<rPh>` を除く処理が要る)。ユーザー判断 (2026-10-28) で、anydoc とセル数の上限で扱う案 (大きな XLSX は検索の対象外) を選んだ。大きな XLSX も検索したくなったときの第一候補 |
| XLSX を対象外にする | Excel の添付が一切検索できなくなる |
| 1 件のメモリ上限を 768MB にする | 大きすぎる。XLSX 以外は 320MB で足りる |
| 同時実行を 2 件にする / 4 件にする | 2 件 (上限 768MB) では約 2.2GB、4 件 (上限 320MB) では約 2.4GB になる見積もりだった。2 件にすると全体の処理量が 3 分の 2 になる |
| 非同期の受け付け方式 (依頼 ID を返し、後で結果を取りに来る) | 呼び出し元は画面を待たせない裏の索引作成処理なので、同期で足りる。非同期にすると、依頼 ID・結果の保存場所・期限切れの掃除・Pod の再起動で消えた依頼への対処が要る (2026-11-02 ユーザー判断。代わりに apps/app 側の待ち時間の既定を 90 秒にした) |
| CSV のセル数を変換の前に数える | 効果が小さい。バイト数の上限 (8MiB) と RSS の監視で足りる |
| image に init のプロセス (tini など) を入れる | 子は親の直接の子で、親がいなくなると自分で終わるので要らない (§4.3) |

| 選択肢 | 不採用の理由 | 詳細 |
|---|---|---|

### 4.3 子プロセスの作り方と、親の見張り

2026-11-05、`/usr/bin/prlimit` (util-linux 2.41.3。image の中は 2.38.1)。

**採った形**: `spawn('/usr/bin/prlimit', ['--as=…', '--cpu=<soft>:<hard>', '--core=1', '--', process.execPath, …node の引数, <子の入口>], { stdio: ['pipe', 'pipe', 'pipe', 'pipe', 'pipe'], env: <明示した 2 つ> })`。fd 3 を結果の専用の管、fd 4 を親を見張る管にする。

- `prlimit` は自分に上限を掛けてから node を exec する (同じ PID) ので、上限は node の起動の前に必ず掛かる。子の `/proc/self/limits` は設定どおりで、soft と hard を分けられる (`--cpu=60:65`)。`prlimit` を挟んでも起動の時間はほとんど変わらない (中央値 21.8ms 対 22.6ms)。
- `--as=300000000` (300MB) では、Node は起動できずに SIGTRAP で終わる (§4.7)。
- 親の側のソケットの fd には `O_CLOEXEC` が付いていて、ある子の見張りの管の書き込み側を別の子が受け継ぐことは無い。子の fd は 0〜4 だけ。

**コアダンプの上限は 1 (ユーザー判断、2026-11-05)**: 開発コンテナの `/proc/sys/kernel/core_pattern` は `|/usr/share/apport/apport …` (コアをプログラムに渡す設定) だった。この設定では `RLIMIT_CORE` の 0 は無視され、コアは渡し先のプログラムに送られる (man7.org の core(5))。実測では、`--core=0` の子に SIGABRT / SIGSEGV / SIGXCPU を送ると回収まで 73〜77ms かかった (コアを書いている)。`--core=1` では 2.7〜3.2ms で、SIGTERM と同じだった。カーネル (Linux v3.10〜v6.12 の `fs/coredump.c` の `do_coredump`) は、渡し先がプログラムのとき `cprm.limit == 1` を「再帰したクラッシュを止めるための特別な値」として扱い、警告を 2 行ログに出してコアを作らずに終わる。man には無く、ソースのコメントだけの挙動である。ファイルに書く設定のときは、上限が ELF の最小 (4,096 バイト) より小さいので書かない (ソースを読んだ。実測していない)。上限 0 だけでは、利用者のファイルの中身を含むコアがホスト側に渡りうる。

**親の見張り (worker thread とソケット)**: 子の中に見張り専用の worker thread を 1 つ立て、その worker 自身のイベントループで fd 4 を `net.Socket` として読み、`'end'` / `'close'` / `'error'` で `process.kill(process.pid, 'SIGKILL')` を呼ぶ。

| 方法 | 親を SIGKILL してから子が終わるまで |
|---|---|
| 子のメインのスレッドで fd 4 を読む | 子が同期の処理をしている間は終わらない (3 秒待っても動き続けた) |
| 見張りなし | 終わらない |
| worker の中で止まる読み方 (`fs.readSync`) | 3〜10ms。ただし下の問題で採らない |
| **worker の中でソケットとして読む** | **3〜7ms** (同期の処理で止まっている子 3 つ、PDFium を回し続ける子、`RLIMIT_AS` 1,600MiB の下でも同じ) |

- 止まる読み方の worker では、worker が読み取りに入った後に子が `process.exit()` を呼ぶと、子が終わらなくなる。Node の `process.exit()` は worker の終了を待つ (`stop_sub_worker_contexts`) が、カーネルの中の読み取りで止まっているスレッドは起こせないためである (スレッドの状態は、メインが `futex_wait_queue`、worker が `unix_stream_data_wait`)。その結果、結果なしで終わる子がすべて期限まで待ってから `timeout` に誤って分類された。ソケットの worker では、どの終わり方も約 330〜390ms で `crashed` に正しく分類される。
- worker の分だけ、子の RSS が約 12〜14MB、必要な仮想メモリが約 64MiB 増える。worker の `resourceLimits.codeRangeSizeMb: 4` を渡さないと、PDF の部品を読み込んだ子で必要な仮想メモリが約 576MiB 増える。worker の分を減らす作り (`resourceLimits` を外す、`codeRangeSizeMb: 1` (子が SIGTRAP で落ちる)、fd 4 を main で読む) は、どれも使えなかった。
- worker には `execArgv: []` を渡す。渡さないと親の node の引数を受け継ぎ、親が `--input-type=module` で起動していると worker が起動に失敗した。
- 親が消えたことを検知できるのは worker の準備完了 (起動から約 23ms) の後からで、それより前に親が消えた場合は、準備完了したときに EOF を受け取ってすぐ止まる。メインのスレッドが同期の処理で止まっている間は、worker のメモリ不足を検知できない (worker は起動した後に何も確保しないので、起きる見込みは低い)。

**終わり方と失敗の種類**: 分類の順は (1) 結果を最後まで受け取った → 結果のとおり、(2) 親が決めて止めた → その種類、(3) 結果なしで終わった → SIGXCPU なら `timeout`、それ以外は `crashed`。`RLIMIT_AS` に当たったとき、`Buffer` や WASM のメモリを増やせない場合は例外 (`RangeError`) で `internal`、JavaScript のヒープや V8 の内部の予約が失敗した場合は SIGABRT / SIGTRAP で `crashed` になる。どちらも応答は 500 `extraction_failed`。

**起動の時間**: 小さな TXT 1 件の起動から回収まで、中央値 84ms (`prlimit` の起動、node の起動、worker の起動、`convert` の読み込み、PDF なら PDFium の初期化 +17MB・30ms を含む)。

### 4.4 本文の受け取りと multipart の分解

**採った形**: Node の要求のストリーム `c.env.incoming` を `'data'` の受け手で直接読み、届いた断片をその場で自前の解析器 1 つに渡す。

- 本文全体の上限 (`MAX_FILE_SIZE_MB` + 64KiB) は、届いたバイト数で数える。期限 (`UPLOAD_TIMEOUT_S`) は受け取り全体に 1 つだけ掛ける。
- 切断は、本文の途中なら要求のストリームが `complete` にならないまま閉じたことで、本文を受け取り終えた後なら `c.req.raw.signal` の `abort` で分かる (Hono で確かめた)。
- 解析器は同期的に動き、失敗は同期的な例外だけになる。部品の中身は、小さな断片を 64KiB の塊にまとめて持ち、断片のまま子へ渡す (連結しない)。
- 文法と部品のヘッダーの引数の読み方は、python-multipart 0.0.27 と Starlette 1.0.0 (それ以前の実装の受け口) のソースから移した。そのため、それ以前の実装と直接突き合わせられた: 生の要求 273 通り中 260 通りが同じで、違いは理由の分かっているものだけ (§5.4)。引数の解析は 80 万件で違い 0。部品のヘッダーは 1 行 4,224 バイトまで、1 つの部品につき 8 行まで。
- **固定データ**: テストの手本のデータ `multipart-oracle.json` と `header-param-oracle.json` は、移行の前の実装の振る舞いを記録したもので、その実装を撤去したので作り直せない。解析器を変えるときは、このデータとの違いを、意図した違いかどうか確かめてから受け入れる。

**メモリ**: 50MiB × 3 件の親の最大 RSS は、断片のまま渡す形で 244〜258MiB (それ以前の実装は 263MiB)。連結する形は 376〜379MiB だった。1 バイトずつ届く本文でも、塊にまとめる持ち方で親の増え方は 12〜16MiB (まとめない形は 781MiB)。

**応答の後に閉じる接続への早めのエラー応答** (`src/http/early-answer.ts`):

Node は、応答の後に接続を閉じる要求 (HTTP/1.0 で keep-alive を頼んでいない要求と、`Connection: close` の要求) に、本文を読み終える前のエラー応答 (宣言が上限超の 413、受け取り途中の 413、認証の 401 など) を返すと、応答を書いた直後に、読み残しのある接続を閉じる (`socket.destroySoon`)。このとき接続のリセットが起き、クライアントがまだ読んでいない応答が捨てられる、と考えると結果に合う (パケットは見ていない)。次の案を比べた。

- 0: 何もしない (Node の既定)
- 1: `c.env.outgoing.shouldKeepAlive = true` を立てる
- 2: 1 に加えて、`Connection: close` の要求なら、応答の後で読み残しを読み捨ててから `socket.end()`
- 3: 要求の `Connection` ヘッダーを正規表現で見て `close` なら、このソケットの `destroySoon` を「読み残しを読み捨ててから `socket.end()`」に差し替える
- 4: **`c.env.outgoing.shouldKeepAlive === false` なら、`destroySoon` を「読み残しを読み捨ててから、元の `destroySoon` を呼ぶ」に差し替える (採用)**。Node が「応答の後に閉じる」と決めた要求を、Node 自身の判定で選ぶ。差し替えた関数は 1 つのソケットで 1 回だけ動く

30 回送って 413 が届いた回数 (3 組):

| 要求 | 移行の前の実装 | 案 0 | 案 3 | **案 4 (採用)** |
|---|---|---|---|---|
| HTTP/1.0 (`Connection` ヘッダーなし)、宣言が上限超の 2MiB | 30 / 30 / 30 | 28 / 27 / 26 | 15 / 1 / 1 | **30 / 30 / 30** |
| HTTP/1.1 + `Connection: close`、宣言が上限超の 2MiB | 30 / 30 / 30 | 20 / 13 / 23 | 30 / 30 / 30 | 30 / 30 / 30 |
| 同、宣言が上限超の 2MiB を 1 回で書く | 30 | 17 | 30 | 30 |
| 同、宣言なし (chunked) 20MiB で受け取り途中の 413 | 30 | 22 | 30 | 30 |
| keep-alive の chunked 20MiB | 30 | 30 | 30 | 30 |

- 案 0 で届かなかった回は、すべて `EPIPE` (クライアントが書いている途中で接続が切られた) だった。案 0 はばらつきが大きい (別の計測では HTTP/1.0 で 25 / 19 / 18、`Connection: close` で 25 / 3 / 8)。
- 案 3 は、HTTP/1.0 の要求に `Connection` ヘッダーが無いので正規表現に当たらず、差し替えが働かない (HTTP/1.0 の値は案 0 のばらつきの範囲)。案 4 は、Node が閉じると決めたすべての要求を対象にする。
- 案 1 と 2 は、要求が `close` と言っているのに応答に `keep-alive` と返す副作用があった。案 4 では、HTTP/1.0 と `Connection: close` の要求には `Connection: close`、keep-alive の要求には `keep-alive` が返る。
- **読み捨ての後に `socket.end()` だけを呼ぶ形は採らない**: Node の普通の閉じ方 (送信を終え、送り終えたらソケットを壊す) のうち「壊す」をしないので、FIN を送らない相手のソケットが残る。FIN を送らないクライアント 20 本で、fd が 19 → 39 に増えたまま 15 秒たっても戻らなかった (5 本が 90 秒後まで残った回もある)。fd が尽きると、`/healthz` を含むすべての接続を受け付けられなくなり、これはトークンなしで起こせる。読み捨ての後に元の `destroySoon` を呼ぶ形では、fd は 19 のままだった。
- **案 4 の弱点**: `shouldKeepAlive` と `destroySoon` は `@types/node` の型定義にあるが、「応答の後に `shouldKeepAlive` を見て `destroySoon` を呼ぶ」という流れは Node の文書が約束するものではない。将来の Node で流れが変わると、黙って案 0 に戻る。`src/http/early-answer.integ.ts` が、HTTP/1.0 と `Connection: close` の要求への 413 (宣言のものと受け取り途中のもの) を 30 回ずつ送り、すべて届くことと応答の `Connection` を確かめて見張る。クライアントは別のプロセス (`src/http/spec-support/repeat-upload-client.mjs`) で動かす。サーバーと同じプロセスでは、案 0 に戻しても 413 が先に読み取られ、後戻りを見つけられなかったため。
- 同じ接続に続けて送った 2 件目: `Connection: close` の要求への 413 の後の 2 件目には 400 (`Connection: close`) が返る (`close` と言った後に送られた要求なので妥当)。keep-alive なら 413 の後の 2 件目は 200。
- apps/app (axios。Node 24 の既定のエージェントは keep-alive) は `Connection: close` を付けず、HTTP/1.0 も使わないので、どの案でも影響は無い (axios で計 240 回すべて届いた)。

**選ばなかった形**: §3.9 の表のとおり (`formData()`、検査 + `@fastify/busboy`、`busboy`、`c.req.raw.body`)。

### 4.5 OpenAPI の作り方

2026-11-10、`hono` 4.13.16、`hono-openapi` 1.5.0、`zod` 4.6.7、`orval` 7.2.0、`ajv` 8.18.0。

**採った形**: `hono-openapi` の `describeRoute` で、経路の定義の横に zod のスキーマを書き、`generateSpecs` で文書を作る (ユーザー判断、2026-11-10)。

- 名前を合わせる指定と、作った文書を書き換える後処理は 1 つも書かない。文書のために書いた設定は `info` の題名・説明・版と、OpenAPI が必須にしている応答の `description` (`'OK'`、`'Not ready'`、エラーはそのステータスのコードをつないだもの) だけである。操作の名前は自動で `postExtract`・`getHealthz`・`getReadyz` になる。スキーマに名前を付けたい所 (`ErrorCode`・`ErrorResponse`・`PageInfo`・`ExtractResponse`) だけ `.meta({ id })` で付ける (付けないと、応答ごとに同じ形が展開される)。
- `describeRoute` は `await next()` だけの中間処理で、本文にも応答にも触らない (ハンドラーに届いた時点で `c.req.raw.bodyUsed` が false だった)。`@hono/zod-openapi` は本文を先に読むので採らない。要求を検査する `validator` は使わない。
- `ErrorCode` のスキーマは `z.enum(ERROR_CODES)` で作り、`contract/` は zod を読み込まない。`PageInfo` のスキーマが `contract/` の型と同じ型であることを型の検査で確かめる。`/extract` のエラーのステータスは `ERROR_TABLE` と `REFUSAL_TABLE` から作る (400・408・413・422・500・503。401 は文書に無い)。
- `/healthz` と `/readyz` は `describeResponse` で書き、値の間違い、文書に無いステータス、`as const` の書き忘れが `tsgo` で型のエラーになる。文書に無い項目を足しても型のエラーにはならず、`ajv` のテストが見つける。`/extract` は応答を少しずつ書くので型では確かめられず、`ajv` で実際の応答を文書と照合する。
- 文書はアプリごとに 1 回だけ作って覚える。`generateSpecs` の結果には値が `undefined` のキーが入るので、文書どうしは JSON にしてから比べる。
- 親の RSS は、文書を作る部品を足して約 9MB 増えた。`zod` は約 8MB。変換の層と子が zod と `hono-openapi` を読み込まないことを、読み込みを止めた状態で確かめるテストがある。
- **drift の検査**: `test/openapi/export-openapi.integ.ts` が書き出しの手順をプロセスとして動かし、出力を commit 済みの `openapi.json` と完全に比べる。commit 済みの文書を 3 通りに変えて (`required` を空にする、説明に空白を 1 つ足す、enum に値を足す)、どれも違いの場所が出ることを確かめた。CI の image の確認は、コンテナの `/openapi.json` を書き出しの手順の文書と比べる。
- 生成クライアントの名前の対応は §5.6。

### 4.6 テキスト系の部品

2026-11-05〜09。それ以前の実装の単体テストから写した検査 (HTML 33、文字コード 46、ZIP の読み 27、ZIP の書き 5、XML 23) がすべて通り、ベンチマークで PDF を除く 20 文書の `pages[]` が文字単位で同じだった。

| 分野 | 採ったもの | 一言で |
|---|---|---|
| HTML | `htmlparser2` 12.0.0 の `Tokenizer` | タグの切り出しだけに使う。読み飛ばす要素・改行・セルの空白・空白のまとめ方は自前の層で行う。`recognizeSelfClosing: true` を渡す (無いと `<script src="a.js"/>` の後ろの本文が消える) |
| 文字コード | 部品を使わない | デコードは Node 標準の `TextDecoder` (full ICU)。判定は自前の関数 (空行を除いて 44 行)。UTF-32 も自前。Shift_JIS は、単独の 0x80・0xA0・0xFD〜0xFF も読む自前の関数で読む |
| ZIP の読み | `yauzl` 3.4.0 | CRC-32 は yauzl が確かめないので、自前で `zlib.crc32` で確かめる |
| ZIP の書き | `yazl` 3.3.1 | yauzl の読みを yazl に直接つなぎ、200MiB の要素をピークの RSS +21MiB で書き直せた |
| XML の解析 | `@xmldom/xmldom` 0.9.12 以上 | xmldom の誤りの報告は `warning` も含めて例外にする。壊れた XML を拒む検査、`<!ENTITY` を拒む検査、書き戻しの処理、バイト列から文字列への変換は自前 |

- **エンティティ・DTD・XXE の線**: DTD そのものは通し、エンティティの宣言は使われていなくても拒み、外部の資源を読みに行かない。ZIP 爆弾と XXE は、それ以前の実装と同じ線で止まった。
- **悪意のある入力での時間**: XML の解析を 30 種類、HTML・文字コード・ZIP・XML の部品ごとに 39 種類の悪意のある形で、N・2N・4N の大きさで測り、時間が入力にほぼ比例することを確かめた。直したもの: `htmlparser2` の `Parser` (閉じない要素で 2 乗)、名前空間の数え方の正規表現 (`xmlns:` 10 万回で 29 秒 → 比例する走査で 40 万回 27〜54ms)、部品の見出しの末尾の空白を削る正規表現 (タブ 4,150 個の見出し 1,000 個で 11.4 秒 → 8ms)、`LineJoiner` の折りたたみ (`replaceBatched` に替えた)。yazl の書きだけは要素の数の 2 乗 (4 万個で 3 秒) なので、要素の数の上限で先に断る。
- **悪意のある入力でのメモリ**: xmldom の DOM は、入力の 100〜600 倍のメモリを使うことがある (閉じていない開始タグ 0.6MB で +361MiB)。子の RSS の上限で止まる。
- **文字コードの判定の精度**: 日本語の文字コードの判定の集まり 4 つで、自前の判定は (i) 184 (それ以前の実装 182)、(ii) 7,069 (7,023)、(iii) 15,575 (15,086)、(iv) 半角カナ 800 件中 736 (666)。新しい入力 3,189 件で、悪くなった入力は 0 件、良くなった入力は 125 件。半角カナの点数は候補ごとに変えた (EUC-JP は +3、Shift_JIS は半角カナが続く 2 字目から +0.5、1 字だけなら −2)。
- 宣言が `shift_jis`・`sjis`・`csshiftjis` のときは、狭い Shift_JIS が拒むバイト (先頭のバイトが 0x87・0xED・0xEE・0xF0〜0xFC) があれば、宣言を使わずに判定へ進む。これで、`<meta charset="shift_jis">` が付いて中身が EUC-JP の HTML を正しく読む (1,500 件で、それ以前の実装より悪い件が 142 → 1)。

### 4.7 仮想メモリの上限 (`RLIMIT_AS`)

**決定**: `RLIMIT_AS` = `MAX_CHILD_RSS_MB` + 2,304MiB (既定で 2,624MiB)。「RSS の上限 + コードの定数」の形で、新しい環境変数は足さない。親は、この値を自分の hard の上限で切り詰めてから `prlimit` に渡す。子の `env` に `MALLOC_ARENA_MAX=2` を入れる。

- Node は、何もしない状態で約 1,200MiB、anydoc の XLSX で約 2,000MiB、PDFium の WASM でさらに多くの仮想メモリの予約を要る。実メモリではなく、確保だけしているアドレスの範囲である。
- glibc の malloc はスレッドごとに 64MiB の予約 (arena) を作る。Node の子は 10 前後のスレッドを持つので、予約が 6〜10 個でき、必要な仮想メモリが 300〜800MiB 増え、実行ごとに揺れた (同じ PPTX で 1,600 / 2,240 / 1,856MiB)。`MALLOC_ARENA_MAX=2` で、出力 (81 入力のハッシュ)・子の最大 RSS・変換の時間は変わらず、必要量が下がって揺れがほぼ消えた。
- **すべての正常な変換が、この値で失敗しない**: 子の最大 RSS が 320MB 以下の 71 入力を各 5 回 (計 355 回)、上限なしと同じ結果になった。正常な入力で必要量が最も大きかったのは 1,984MiB (7 万セル 1 シートの XLSX) で、640MiB の余地がある。
- **RSS の監視が主な守りで、`RLIMIT_AS` は最後の歯止め**: 2,624MiB の下で、触れながらメモリを増やす 6 つの合成の形と、上限を超える 9 つの本物の入力が、各 3 回すべて RSS の監視で止まった (止めた時点の RSS 321〜442MB)。`RLIMIT_AS` が先に効くのは「予約するが触らない」確保で、1.5GiB / 3GiB の `Buffer.allocUnsafeSlow` は上限なしなら RSS を増やさずに成功し、2,624MiB の下では `RangeError` (`internal`) になった。
- **k8s のメモリの上限には影響しない**: PDF の部品まで読み込んだ子 3 つを止めておいたとき、cgroup v2 の `memory.current` の増え方は、上限なしで VmSize の合計 28,128MiB のときも、2,624MiB で 5,088MiB のときも、約 169MiB で同じだった。
- 上限を掛けると、変換が 7〜12% 遅くなる。期限で切るので合計の時間は変わらない。
- `MALLOC_ARENA_MAX=2` を採らない場合の値は `MAX_CHILD_RSS_MB` + 3,072MiB になる (同じ決め方)。

### 4.8 子の最大 RSS と既定値

**決定 (2026-11-09)**: 既定値は変えない (`MAX_CHILD_RSS_MB` 320、`MAX_XLSX_CELLS` 70,000、`MAX_HTML_BYTES` 20MiB)。そのために子の形を次のように決めた。どれも子の中のことで、環境変数の契約の外にある。

1. **部品は経路ごとに読み込む**: PDF の子は PDFium と共通の正規化だけを読み込む。DOCX・ODT・RTF・DOC と CSV/TSV は anydoc、TXT・MD・JSON・XML・ipynb・HTML は anydoc も PDFium も読まず、XLSX / PPTX は自分の経路の `ooxml/` の部品と anydoc だけを読む。全部を読み込むと、7 万セル 1 シートの XLSX が 302〜310MB、画像 12 枚の 48MB の DOCX が 297〜311MB になり、0.95 倍 (304MB) を超えた。1 ページ 200 万字の PDF では、PDFium だけ 302〜303MB、anydoc + PDFium 306MB、全部 315〜316MB。
2. **子の node に `--max-semi-space-size=4` を付ける** (`--wasm-max-mem-pages=8192` と並べる): 20MiB の HTML が 308〜309MB → 220〜240MB、3,000 スライドの PPTX が 320〜326MB → 219〜233MB に下がった。XLSX・DOCX・PDF は変わらない。
3. **子は受け取った入力を写さない** (写すと 48MB の DOCX で約 +50MB)。
4. **XLSX は、DOM を作らないセル数の検査と、流し込みの書き直しで渡す**: 150MiB の pivot cache の XLSX が 401〜402MB → 105〜107MB に下がった。

- 出力は変わらない (79 入力で、子の形を変えても結果の JSON のハッシュがすべて同じ)。
- **基準のファイル** (Req 2 の上限の余裕を見るもの): 7 万セル 1 シートの XLSX と、画像 12 枚の 48MB の DOCX。子が自分で読んだ `VmHWM` で、開発コンテナでは XLSX 289〜294MB、DOCX 262〜297MB (余裕 7〜42MB)。50ms ごとの見回りの値は、終わる直前の山を取り逃がし、DOCX で最大約 50MB 少なく出る。image の中の値は §4.13。

- 子の待機時は 62〜63MB (何も読まない node 41MB + `convert` の静的 import +4MB + 見張りの worker 約 +12〜14MB)。
- 子が読む `/readyz` の確認用の入力は、経路ごとの読み込みとは別に、PDF・PPTX・HTML を 1 件ずつ変換して、PDFium と anydoc とテキスト系の部品のすべてを通る。

### 4.9 メモリの予算 (コンテナ 2Gi)

**決定 (ユーザー、2026-11-09)**: 親の作りを軽くする (契約も既定値も変えない)。

- 親は、子からの結果を、先頭の長さが分かった時点でその長さの入れ物を 1 つ確保して受け取る (届いた断片を持ち続けて最後に連結しない)。
- 親は、応答の JSON を 1 つの文字列に組まず、ページごと・本文の一定の字数ごとに少しずつ書く (送るバイト列は同じ。サロゲートの対の途中で切らない)。

**根拠**:

- 最も重い負荷 (S1: 制御文字だけの 5.5MB の TXT を 3 件同時に 3 回。結果は JSON で約 33MB。S2: S1 の TXT 3 件と、上限まで伸びて止められる 8MiB の CSV 3 件を交互に 4 回) の実測 (cgroup の増え方 + 待機時) は、開発コンテナで 1,135〜1,285MiB、image の中で 918〜1,095MiB (§4.13)。移行の前の実装は同じ負荷で 1,230MiB、親の作りを軽くする前の Node.js 版は 1,402MiB だった。
- 最悪の値を足し合わせる見積もりは、`親の待機時 + MAX_CONCURRENCY × (MAX_CHILD_RSS_MB + 監視の遅れ + 親の 1 件あたり)`。監視の遅れ 148MiB は、RSS の監視が止めた時点の RSS の最大 468MB − 320。親の 1 件あたり 157MiB は、(親の最大 540 − 待機時 69) ÷ 3。既定で 69 + 3 × (320 + 148 + 157) = 1,944MiB。書き込める `/tmp` を付けるならその分を足す (64MiB で 2,008MiB)。本物の変換の値を入れると約 2,025〜2,070MiB (`/tmp` を足すと 2,089〜2,131MiB) で、2Gi とほぼ同じか少し超える。移行の前の実装は同じ式で 1,987MiB だった。
- **2Gi を守る根拠は、見積もりではなく実測にする** (ユーザーが承認した)。見積もりは、3 つの子が同時に監視の遅れいっぱいまで伸び、同時に 3 件の最大の結果の写しが残る、という同時には起きにくい場合を足している。
- 親の 1 件あたりの重さの内訳: 約 33MB の結果の JSON を 3 件同時に受け取ったときの親の最大 RSS は 276〜349MB (1 件あたり約 100MB)。親が最も膨らむのは、3 件の大きな結果を同時に受け取って JSON を解き、応答を作るときである。
- 却下した選択肢: 今の形のまま実測を根拠にする (移行の前より見積もりで約 200MiB、実測で約 170MiB 悪いまま)、結果の受け取りの上限を下げる、`MAX_CONCURRENCY` を 2 にする (§3.9)。
- k8s の requests は 512Mi (待機時が約 35MiB で、ほとんどの変換は最悪の場合よりずっと少ないため)。

| 区間 | 値 |
|---|---|

### 4.11 RSS の上限で止まる入力の範囲

対象 spec の AC は「上限を超えたら止めて `resource_limit_exceeded` を返す」ことを求めるだけで、次の入力を通すことは約束していない。移行の前の実装は通していたが Node.js 版は止めるものとして、検索の対象が狭まる範囲を記録する (ユーザー判断は要らない、と判断した)。

| 入力 | 移行の前の実装 | Node.js 版 | 範囲 |

## 5. 契約と既定の振る舞いの記録

このサービスは 2026-11 に、Python 3.12 + FastAPI の実装から Node.js + Hono の実装に書き換えた (§7)。書き換えでは、API・エラー・設定の契約を変えないことを既定の方針とし、守るとかえって複雑になる場合は、何を変えるか・守ると何がどう複雑になるか・下流の変更の範囲を記録して変えてよい、とユーザーが決めた (2026-11-04)。判断の基準はシンプルさ (保守性) である。崩さない不変条件は、セキュリティ上の性質、メモリの予算 2Gi、対応形式と位置情報つきの抽出だった。

この節は、その手続きで決めたことの記録である。いまの振る舞いの説明は design.md の Revalidation Triggers にあり、ここには「なぜそうしたか」を残す。各項目の (c) で、下流 (apps/app、生成クライアント、下流 spec) への影響を書く。

### 5.1 `WORKERS` の廃止 (ユーザー判断、2026-11-04)

- **何を変えたか**: Web サーバーのワーカーの数を指す環境変数 `WORKERS` (既定 1)。サービスはこの環境変数を読まない。設定されていても起動は失敗しない。
- **守ると何が複雑になるか**: Node には同じ仕組みが無い。同じ意味を保つには cluster で親を N 個に分け、それぞれが枠と子の監視を持つ形になり、プロセスの管理が 1 段増える。ワーカーが 2 つ以上だと OS の接続の振り分けが偏り、空きがあっても 503 が返る弱点も引き継ぐ。スケールはレプリカを増やすのが本来の方法である。
- **下流**: compose から消した。メモリの予算の式からワーカー数の項が消えた。apps/app、生成クライアント、下流 spec は変わらない。2 以上を設定していた運用者は、同時実行の全体の上限が `MAX_CONCURRENCY` だけになるので、必要なら `MAX_CONCURRENCY` を上げるかレプリカを増やす。

### 5.2 `/docs` と `/redoc` の廃止 (ユーザー判断、2026-11-04)

- **何を変えたか**: 以前の Web フレームワークが既定で出していた API の説明画面 (どちらも認証が要るパス)。いまはトークンなしで 401、トークンありで 404。`/openapi.json` は残す。
- **守ると何が複雑になるか**: 画面を配る部品 (Swagger UI、ReDoc) を本番の依存に足す必要がある。apps/app は使っておらず、テストも無い。画面が要る人は `/openapi.json` を手元の道具で開ける。
- **下流**: なし (apps/app と生成クライアントのコードを検索し、呼ぶ箇所が無いことを確かめた)。

### 5.3 `/readyz` の `dependencies` の名前 (ユーザー判断、2026-11-04)

- **何を変えたか**: キーを、実際に使う部品の npm の名前 (`@firecrawl/anydoc`、`@embedpdf/pdfium`) と `prlimit`、内部のモジュールをまとめた `converter` にした。以前は以前の部品の名前 (`anydoc`・`pypdfium2`・`charset-normalizer`・`converter`) だった。503 の本文は `{"status":"not_ready"}` だけで、`dependencies` を出さない (`readiness()` は `ready` だけを返し、部品ごとに確かめたかのような一覧を作らない)。
- **守ると何が複雑になるか**: 以前の名前のままだと、使っていない部品の名前で、別の部品が読み込めたかどうかを表すことになり、見た人を誤らせる。役割の名前 (`pdf` など) にする案もあったが、ユーザーは実名を選んだ。
- **下流**: OpenAPI の文書は `dependencies` を「名前から `ok` への対応」としてだけ型を付けるので、名前を変えても生成クライアントは変わらない。apps/app は `/readyz` を呼ばない。k8s と compose の確認はステータスだけを見る。運用者が本文を見たときの表示が変わる。
- `converter` の意味: 確認用の子は PDF・PPTX・HTML を変換して外部の部品 7 つを通るが、自分たちの内部のモジュール (XLSX・ipynb・XML・DOCX の経路の `dist/` のファイル) が欠けた場合は準備完了のままになる。以前の実装の `converter` (変換の層全体を読み込む) と同じ意味ではない。

### 5.4 本文の形の例外 (ユーザー判断、2026-11-05)

multipart の解析器を以前の実装の文法から移したうえで、次の 3 つは合わせないことにした。どれも apps/app (axios) は送らない形で、下流の変更は無い (axios は `Content-Length` を本文から計算し、boundary を英数字と `-`・`_` だけで作り、`Content-Type` に `charset` を付けず、ファイル名を UTF-8 で送る)。

| # | 要求 | 以前の実装 | いま | 合わせない理由 |
|---|---|---|---|---|
| 1 | `Content-Length` が実際の本文より短い | `code` の無い 400 (`Connection: close` を付けたときは 422) | `code` の無い 400 | Node の HTTP の解析器が余りを次の要求として読み、まだ書いていない応答を捨てて 400 を返す。合わせるには Node の内部の状態 (`socket._httpMessage`) に頼る必要がある。`Connection: close` を付けない要求では差は無かった (当初「以前は 422」と見ていたのは測り違いで、測り直して訂正した) |
| 2 | boundary に CR が入っている (`boundary*=UTF-8''a%0D%0Ab` の形でだけ作れる) | 200 | 422 | RFC 2046 が禁じる形。合わせると、断片の切れ目をまたぐ区切りの候補を「最後の CR から後ろ」だけで持ち越す単純な判定を失う。LF だけを含む boundary は受け付ける |
| 3 | 要求の `Content-Type` の `charset` | 部品の名前・ファイル名・`mimeType` を `charset` で読む | 使わない (UTF-8 として正しければ UTF-8、そうでなければ latin-1) | 使うには以前の言語の文字コードの表を移す必要があり、Node の `TextDecoder` の名前と一致しない (ユーザーの指示は「シンプルでコード量が少なく済む解に」)。宣言どおりに符号化してくる送り手では以前の実装のほうが役に立ち、宣言だけの送り手では逆になる |

- 合わせないことを決めたほかの形: `filename*=` と `filename*0=` を混ぜた要求は、以前の実装が捕まえていない例外で `code` の無い 500 を返していた。いまは表どおりの 422 `extraction_failed`。ASCII でない文字を足したトークンも、以前の実装は `code` の無い 500、いまは表どおりの 401。
- 黒箱のテストの理由の id: `7.5-2` (#2)、`7.5-3` (#3)、`16.1` (`filename*` の混在などの、表に合わせた件)。

| 200 の応答 | `Content-Length` つき | chunked (応答を少しずつ書くため。axios が解く) |
| 404 の本文 | JSON | Hono の既定の文字列 |
| 401 の本文 | 空白つきの JSON | 詰めた JSON (読めば同じ) |
| `Server` ヘッダー | あり | なし |
| `Expect: 100-continue` と `Expect: foo` の 2 行 | 100 の後に 200 | 同じ (本文を読むと決めた時点で、HTTP/1.1 で値に `100-continue` を含めば `100 Continue` を返す)。`Expect: foo, 100-continue` を 1 行で送ると、いまは 100 を返す。HTTP/1.0 の `Expect: 100-continue` には返さない |

### 5.6 OpenAPI の文書と生成クライアントの名前 (ユーザー判断、2026-11-10)

- **何を変えたか**: 以前の Web フレームワーク (FastAPI) が自動で付けた名前も含めて同じ文書を出し、生成クライアントの型・関数・引数と apps/app のファイルを変えない、という方針。文書は経路の定義から作り、名前は作る道具の既定に従うことにした。
- **守ると何が複雑になるか**: 名前を守ったまま文書をコードから作ると、名前を書き写す指定と後処理が 31 個要る。それを避けて文書を手で持つファイルにすると、258 行の文書をコードとは別に持ち、経路・`ErrorCode`・エラーのステータスが食い違わないことを確かめるテストを持つことになる。
- **下流**: 生成クライアントの関数名と型名が変わった。apps/app で変えたのは `apps/app/src/features/search-attachments/server/services/attachment-text-extractor.ts` とそのテストの 2 つだけで、関数名の置き換えと、`file` の型の書き方 (`buffer as unknown as string` → `buffer as unknown as Blob`) である。実行時に送られる本文は、変える前と後で同じだった (境界の文字列のほかは完全に同じ。受け口のサーバーで本文を取って確かめた)。`.kiro/specs` の中で以前の名前を書いた下流 spec は無い。

**名前の対応** (Req 7.5。orval 7.2.0 で作り直した結果):

| 変わる前 | 変わった後 |
|---|---|
| `postExtractExtractPost` | `postExtract` |
| `healthzHealthzGet` | `getHealthz` |
| `readyzReadyzGet` | `getReadyz` |
| `BodyPostExtractExtractPost` | `PostExtractBody` |
| `BodyPostExtractExtractPostMimeType` | 無くなる (`mimeType?: string`) |
| `PostExtractExtractPostResult` | `PostExtractResult` |
| `HealthzHealthzGet200` | `GetHealthz200` |
| `HealthzHealthzGetResult`・`ReadyzReadyzGetResult` | `GetHealthzResult`・`GetReadyzResult` |

| `ErrorCode`・`ErrorResponse`・`ExtractResponse`・`PageInfo`・`PageInfoPageNumber`・`PageInfoLabel` | 変わらない |

- 変わらないもの: `file` が必須で `mimeType` が任意であること、`/extract` のステータス (200・400・408・413・422・500・503)、`ErrorCode` の 8 つの値とその順。
- 変わった形: `file` の型が `string` から `Blob` に (zod の `z.file()` は `format: binary` を出す。以前の文書は `contentMediaType` だけを書いていたので orval は `string` にしていた)、`mimeType` が null 可でなくなった (multipart では null を送れないので、送れる値は同じ)、`/healthz` の応答が `{status: 'ok'}` の型に、`/readyz` の応答に型が付いた。応答のオブジェクトに `additionalProperties: false`、整数に最小と最大が付く。操作の `summary` とスキーマの説明文は無い。
- orval (7.2.0) は、文書のヘッダーの parameter から、関数の引数も型も作らない (実験。§9.2.2)。`POST /extract` の任意のヘッダー `X-Growi-App-Id` は文書には載るが、生成クライアントの関数と型は変わらず、apps/app は axios の `options.headers` で渡す。ヘッダーの引数を作らせる orval の設定 (`headers: true`) は、文書のための指定を書かない方針 (AC 7.6) に合わせて足さない。そのため AC 7.2 (生成クライアントは文書のとおりに項目を持つ) は、ヘッダーについては成り立たない。

### 5.7 ログ (ユーザー判断、2026-11-11)

実装のレビューで、以前の実装にあって今の実装に無いログが記録されていないと分かり、ユーザーに 3 つの選択肢で諮った: (ア) このまま受け入れる、(イ) 親が書く診断の行を戻し、子の警告もサービスのログに通す、(ウ) (イ) に加えて `/extract` 以外の要求のログも戻す。**決定は (イ)**。

- **戻したもの**: 子を起動できない、子が結果なしで終わった、シグナルで止まった、結果が決まった形でない、SIGKILL の後も終わらない、の診断の行。子の警告 (`oom_score_adj` を上げられない、入力が不正、結果を送れない、想定外の失敗) と、見覚えのない出力の 1 行。準備の確認の失敗 (理由が変わったときだけ) と回復の行。
- **戻さなかったもの**: `/extract` 以外の要求ごとの行と、Web サーバー自身のアクセスログ。以前の実装は、認証を通った要求ごとに JSON の行を 1 行出し、Web サーバーのアクセスログも 401 を含むすべての要求に出していた。いまは 401 の要求、存在しないパス、probe の呼び出し、`/metrics` の呼び出しが、ログに 1 行も残らない。ただし応答の数は、経路とステータスごとに `/metrics` (`attachment_extractor_http_responses_total`) で数える (§9.8.1)。
- **行の先頭の書式**: 以前は「地方時の時刻、重要度、ロガーの名前」、いまは「ISO 8601 の UTC の時刻、重要度」。`extract format=… size=… duration_ms=… result=… child_peak_rss_mb=…` の部分は同じで、その後ろ (行の最後) に呼び出し元の app を示す `app=…` が付く (§9.2)。
- **想定外の失敗の例外の種類の名前は、ログに出さない** (以前の実装は出していた)。部品が自由に決める文字列で、親が決まった一覧と照らせないため。
- **準備未完了の理由**: 「最初に失敗した確認と、その失敗のしかた」を言う。以前の実装のように、読み込めなかった部品の一覧は出さない。
- **子の警告の伝え方** (子は信頼しない前提): 子は標準エラーに決まった 4 つの符号のどれかを 1 行で書き、親は行の全体が符号と完全に同じときだけ認め、親が持つ固定の文を出す。親が子 1 つから保持するのは 256 バイトまでで、それより後は読んで捨てる。乗っ取られた子をまねた偽の子 (約 45 通り。1GiB を標準エラーに書く子を含む) で、ログが決まった形から外れないこと、親の RSS が量に比例しないことを確かめた。終了の直前に書かれた警告は届かないことがありうる (実測では 300 件中 300 件、8 件同時で 320 件中 320 件が届いた)。
- **`/readyz` でログを溢れさせられないこと**: 準備完了のまま 180 回呼んで 0 行、準備未完了のまま 3 秒に 5 万回以上呼んで 0 行。状態が毎回本当に入れ替わる最悪の場合で 1 秒あたり 5.7 行。
- **下流**: 無い。

### 5.8 k8s の manifest の例をやめた (ユーザーの決定、2026-11-11)

- **何を変えたか**: 成果物の「k8s manifest 例 (Deployment + Service + HPA + NetworkPolicy + securityContext)」と、その中身を確かめるテスト (29 件)。Req 3.3 の推奨設定を「提供する」先を、manifest の例から運用者向けの文書 `docker/README.md` に変えた (番号は同じ)。守る条件そのものは要件のまま残る。
- **守ると何が複雑になるか** (ユーザーが挙げた理由): `apps/` のほかの app は Dockerfile だけを持ち、k8s の出力を持たない。例は本物のクラスタに一度も適用していない。実際の配備は別の場所で管理されていて、例を置くと合わせ続ける手間が残り、合わなくなっても気づく仕組みが無い。運用の条件は文章で残せば足りる。
- **下流**: apps/app、生成クライアント、下流 spec は変わらない。運用者は、そのまま写して使える manifest の出発点を失う代わりに、`docker/README.md` で条件と理由を読む。
- **文書に書いた条件と、manifest から変えた点**: メモリの requests 512Mi と limits 2Gi、権限の設定、3 つの確認 (startup・liveness・readiness) の間隔・期限・回数、停止の猶予 85 秒、通信の制限、レプリカの数と自動スケールの値、環境変数は、消した manifest から 1 行ずつ移したことをレビューで確かめた。変えた点: 書き込める `/tmp` は要らないと書き、メモリの式から 64MiB の項を外した (サービスが書き込むのは `/proc/self/oom_score_adj` だけで、CI も tmpfs なしで起動する)。CPU (500m / 2) と自動スケール (2〜10、CPU 70%、縮小の待ち 300 秒) は、以前の実装の例から引き継いだ測っていない値で、「出発点」と明記した。サービスに固有でない注意 (image の版を固定する、PodDisruptionBudget、`maxSurge` など) は外した。
- 確認の期限 15 秒と間隔 20 秒は、確認用の子の制限 10 秒から決めた。

### 5.9 そのほかの、以前の実装と違う振る舞い

どれも作業者の判断で採り、API・エラー・設定の契約には触れないと判断したもの。apps/app は送らない形か、意味の無い設定値か、壊れた・珍しい形のファイルである。

**設定の読み方**

- 環境変数の名前は大文字だけで読み、作業ディレクトリの `.env` は読まない (以前の実装は大文字・小文字を区別せず、`.env` も読んだ)。設定を読むのは `main.ts` が渡した値だけで、`process.env` を読むのは `main.ts` だけである。
- 整数は 10 進の数字だけを受け付ける。以前の実装が受け付けた `1_000`・`1.0`・2^53 以上の整数では起動しない (黙って誤った値で動くより、起動しないほうを選んだ)。
- 前後の空白の取り除き方: 以前の実装は `\x1c`〜`\x1f` と NEL (`\x85`) を取り除き BOM を残した。JavaScript の `trim()` はその逆である。形式の表・整数・`LOG_LEVEL`・トークンの 4 か所に出る。
- 運用者が設定した `RAYON_NUM_THREADS` を使わない。子は常に 1 と `MALLOC_ARENA_MAX=2` で動く。
- 負の `MAX_CONCURRENCY` で起動し、すべての要求に 503 を返す (以前の実装は起動時に止まる見込み。推論)。`LOG_LEVEL=NOTSET` で、いまはすべての行を書く (以前の実装は `extract` の行を出さない見込み。推論)。
- 秒の値はタイマーが扱える最大 (2^31 − 1 ミリ秒、約 24.8 日) に丸める。丸める前は、`TIMEOUT_S=3000000` のような値で期限が 1 ミリ秒になり、毎回 408 になった。`UPLOAD_TIMEOUT_S` が約 9.0e12 秒以上だと起動もできなかった。起動のときに値を拒む形は、以前の実装が受け付けていた値を新しく拒むことになるので採らない。`prlimit` の `--cpu` は丸めない (大きな値でも `prlimit` は動く)。
- `requestTimeout` は設定から決める (`max(300 秒, 60 + UPLOAD_TIMEOUT_S + 30 秒)`)。300 秒に固定すると、`UPLOAD_TIMEOUT_S` が長いときに Node が先に 408 を返すため。

**停止**

- 停止の合図 (SIGTERM / SIGINT) の 1 回目で待ち受けをやめ、応答を返し終えていない要求を待ってから終了コード 0 で終わる。2 回目ですぐ終了コード 1 で終わる (2 回目は変換中の子を止めない。コンテナの中では PID 1 の終了で一緒に消える)。待つ時間に上限は無い (以前の実装も同じ)。
- 応答を返し終えていない要求の数を数え、0 になった時点ですべての接続を閉じる。最初の実装は「接続がすべて無くなるまで待つ」形で、ヘッダーを途中まで送った接続が 1 本あると、Node が「要求の途中」と数えて閉じず、`server.close()` が `headersTimeout` の見張りも止めるので、停止が終わらなかった (トークンなしで起こせた)。
- 応答を読まない相手がいると、トークンなしでも停止が猶予時間まで延びうる。オーケストレーターの猶予の後の SIGKILL で終わるので受け入れた。

**変換の結果**

- **文字コード**: デコードの表の違い (`〜` が `～` になるなど 6 字)。宣言された `iso-8859-1` / `latin1` / `ascii` を WHATWG の決まりどおり windows-1252 として扱う (ブラウザと同じ)。`replacement` のラベルの宣言は無視する。宣言の無い壊れたバイト列は最後に windows-1252 で読む (以前の実装は latin-1)。BOM は 1 つだけ取り除く。判定は先頭 64KiB だけを見る。残る違い: 偶数の長さの半角カナだけの並び (EUC-JP の漢字としても読める)、半角カナが 1 字だけ ASCII の中にある cp932 の文書、NEC の特殊文字だけの短い cp932、以前の言語に codec の無いラベルの嘘の宣言、UTF-8 の文書に `euc-jp` が宣言されたとき (Node の ICU の euc-jp がゆるく読む)。
- **XML・HTML・ipynb**: XML の ASCII でない数字の数値の文字参照 (`&#６５;`) は字のまま残す (XML の決まりではこちらが正しい)。ipynb の `NaN`・`Infinity` を読む。HTML の末尾の閉じていない開始タグ、`<!-->` などの細部。
- **OOXML の XML**: 展開した名前が同じ属性を持つ壊れた XML、WHATWG にだけある文字コードの名前、`encoding="utf8"` の宣言 (いまは読む) で、通す / 拒むが違う。
- **ZIP**: bzip2・LZMA で圧縮した部品を持つ PPTX は、以前は 200 (スライドごとに無圧縮で包み直したため)、いまは 422 `malformed`。暗号化の印 (bit 0) とローカルの見出しの破損が重なると、以前は `malformed`、いまは `encrypted`。要素が 65,536 個を超えるのに zip64 でない ZIP は、以前は `limit_exceeded`、いまは 200 か `malformed` (一覧に入らない要素は書き直した package に入らないので、上限の抜け道にはならない)。印の付いたディレクトリ要素を持つ XLSX は、以前は失敗、いまはページを返す。中央ディレクトリの最後の記録の中だけが欠けた ZIP の 44 件 (2,223 通り中) は、いまだけ 422 になる (直すとセル数の検査の抜け道が広がるので直さない)。ZIP の名前に `../` が入る XLSX の要素は読み飛ばす (以前と同じ)。
- **PDF**: 作った PDF の約 7%、壊した PDF 3,000 件のうち 40〜47 件で、以前の実装は `malformed` (422) か空、いまは文字を返す (PDFium の版の違い。いまの実装が拒み以前の実装が通す入力は 0 件)。縦書きの全角の空白を残す。以前の実装には、同じプロセスで続けて変換すると前の件のエラー番号が残る性質があったが、いまは無い。
- **大きな入力**: §4.11 の表。
- **閉じない開始タグを持つ PPTX** は、回によって `memory_exceeded` か `malformed` になる (どちらも 422)。申告の大きさを偽った ZIP 爆弾は `limit_exceeded` と `malformed` のどちらもありうる。病的な HTML の 3 件は、以前の実装の `memory_exceeded` から「子の中で収まり、次の変換が成功する」に変わった。
- **結果の検査**: 片割れのサロゲートを含む結果は子の側で拒む。`pageNumber` が小数や指数の形の結果は `JSON.parse` が整数と区別しないので受け付ける。結果が `MAX_RESULT_BYTES` を超えたときの種類は `result_too_large` (以前と同じ)。
- **変換の層はログを出さない**ので、XLSX の分割で目印が説明できない出力のときに出していた警告は無い。

**子と実行管理**

- 親が消えたとき、以前の子は終了コード 3、いまの子は自分に SIGKILL。想定外の例外のとき、いまの子は `internal` の結果 (detail はクラス名だけ) を送ってから終了コード 1。どちらも応答は同じ。
- 確認用の子は、運用者の変換の上限ではなく固定の上限で動く (以前の確認は部品を読み込めたかだけを見ていた)。`readiness()` は、確認を終えた時点から 10 秒間、準備完了と準備未完了のどちらの結果も覚える (以前の実装は準備完了だけを覚えていた。§5.3、§9.4、design.md §HealthRoutes)。
- 中止の合図で止めた実行は `crashed` (detail `conversion was cancelled`) で返り、ログでは `client_disconnected` と書く (以前と同じ)。
- 子の終わり方の detail は、シグナル番号ではなくシグナルの名前。detail は応答にもログにも出ない。

**apps/app からファイルが届いていなかった件** (2026-11-12 に直した。直した commit `b1e3adb4a5`): 生成クライアントは Node の組み込みの `FormData` に `file` を入れ、組み込みの `FormData` は `Blob` でない値を文字列に変えるので、apps/app が渡していた `Buffer` は UTF-8 の文字列になり、ファイル名も部品の `Content-Type` も無いテキストの項目として送られていた (422 `extraction_failed`)。以前の実装のときから同じで (生成クライアントが `file` を `string` と書いていたので型の検査では見つからなかった)、書き換えで入った不具合ではない。送る内容の決まり (ファイル名は `file.<拡張子>`、部品の `Content-Type` は付けない、保存してある MIME type は拡張子が使えないときだけ送る) は、`attachment-search-indexing` の design.md と research.md に書いた。

## 6. 実装で分かったこと

実装と検証で初めて分かった、部品と実行環境の挙動。設計への反映は design.md にある。

**Node.js と Hono**

- Hono (`@hono/node-server` 2.1.6) では、`Content-Length` を見て本文を読む前に 413 を返せる。`c.req.raw.signal` は、本文を送り終えた後の切断で `abort` を出す。本文の途中の切断では、要求のストリームが `complete` にならないまま閉じる。
- `@hono/node-server` は `c.req.raw.body` を `Readable.toWeb` で作り、断片ごとに 1 回写す。
- `c.req.header()` は Web の `Headers` を読むので、同じ名前のヘッダーが 2 行ある要求では値を `, ` でつないで返す (`Content-Type` や `Authorization` が 2 行ある要求で状態が変わった)。要求のヘッダー (`authorization`・`content-length`・`expect`・`content-type`) は `c.env.incoming.headers` から読む。
- `@hono/node-server` の `autoCleanupIncoming` (既定で有効) は切らない。
- Node は、応答の後に閉じる要求 (HTTP/1.0 と `Connection: close`) に本文を読み終える前のエラー応答を返すと、`socket.destroySoon` で読み残しのある接続を閉じ、クライアントが読む前の応答が捨てられうる。対処は §4.4 の「応答の後に閉じる接続への早めのエラー応答」。
- Node の HTTP の解析器は、`Content-Length` より後ろの余ったバイトをすぐ次の要求として読み、壊れていれば 400 を返して接続を閉じる (以前の実装の httptools も同じ)。`Host` の無い HTTP/1.1 の要求を拒むのは公開の設定では変えられない。
- `server.close()` は、Node が内部で行う `headersTimeout` と `requestTimeout` の見張りも止める。ヘッダーを途中まで送った接続を Node は「要求の途中」と数え、`closeIdleConnections()` では閉じない。
- `setTimeout` は約 24.8 日を超える値を 1 ミリ秒に置き換え、`TimeoutOverflowWarning` を出す。
- Node 24.22.2 は、子の起動が EMFILE / ENFILE で失敗すると `child.stdio` を作らずに抜ける。`stdio` を走査する処理を書くと TypeError で親ごと落ちる (`prlimit --nofile=80` で 40 件同時に起動して再現)。起動の直後に `child.pid === undefined` なら、次の tick の `'error'` を待つ。
- `process.stdin` に触ると fd 0 が O_NONBLOCK に変わる。子の入力は `readSync` で読む。
- worker thread は `execArgv` を渡さないと親の node の引数を受け継ぐ。`process.exit()` は worker の終了を待つ (§4.3)。
- `import.meta.main` は Node 24 ではまだ実験的な機能である (道具の `scripts/check-openapi-drift.ts` だけが使っている)。
- `JSON.parse` には入れ子の深さの上限が無く、33MiB の枠に収まる深い入れ子で親のメモリが約 1.8GB まで増える。平らな巨大な配列 (`[{},{},…]`) でも 1.3GB・2 秒かかる。そのため、`JSON.parse` の前に構造を検査して拒む (検査の後は 145MB・14ms)。正しい形の結果 (空のページ 75 万個) はまだ約 +170MB・0.5 秒かかるが、正当な結果と区別できない。

**`prlimit` とカーネル**

- `prlimit --cpu=soft:hard` で soft と hard を分けられる。同じ値だと SIGXCPU より先に SIGKILL が届く。
- コアダンプの渡し先がプログラムの環境では、`RLIMIT_CORE` の 0 は無視され、1 は「コアを作らない」(§4.3)。
- k8s (cgroup v2) の `memory.oom.group` は既定で有効で、`oom_score_adj` を付けてもコンテナが上限に達すると親ごと止まる。
- cgroup v2 の `memory.peak` は kernel 5.19 以降にある。cgroup の値は node の実行ファイルなどの共有のページを一度しか数えないので、子の RSS の合計より小さく出る (推論)。

**部品**

- anydoc の XLSX: シートは `workbook.xml.rels` のリンク先で探す (パス名で絞ったセル数の検査はすり抜けられる)。空の `<row>` を大量に並べた入力 (50 万行で約 268MB) はセル数の指標に現れない。ピボットキャッシュなどの大きな部品を丸ごと読むと、メモリが入力の何十倍にもなる。
- anydoc の CSV: メモリはバイト数ではなくセル数で決まる (約 100 万セルで 320MB を超える。1 文字のセルだけなら 2MiB で超える)。
- PowerPoint の自動代替テキスト: anydoc の出力では「説明 + 半角空白 2 つ + 決まり文」の 1 行になる。作者が同じ形で打った行は見分けられない。
- `@embedpdf/pdfium` は本来ブラウザ向けで、Node では WASM のファイルを読んで `init({ wasmBinary })` に渡す形で動く。PDFium の初期化は +17MB・30ms。
- `htmlparser2` の `Parser` は開いた要素の一覧を持ち、閉じない要素で 2 乗の時間になる。`Tokenizer` の内部の値を書き換えないと、以前の実装の HTML の読み方と 4 か所で違う (`<x / >`、`<title>` の中の `<&` など)。
- `@xmldom/xmldom` は、警告として報告するだけで通してしまう壊れた XML がある (裸の `&` など)。DOM は入力の 100〜600 倍のメモリを使うことがある。
- yauzl は CRC-32 を確かめない。yazl は要素の数の 2 乗の時間で書く。ZIP の読みから書きへ流してつなぐとき、元の流れが途中で失敗すると受け手が無ければプロセスが落ちる。
- V8 は `RLIMIT_AS` に合わせて予約の大きさを変えるので、仮想メモリのピークで上限の余裕を見る検査は移せない。

**ビルド**

- package の `build` は `rimraf dist && tsc -p tsconfig.build.json && node scripts/add-js-extensions.ts dist`。`tsc` と `rimraf` はルートの devDependencies から使う。`dist/` は 118 ファイル。
- `test/global-setup.ts` は vitest を始めるたびに `dist/` を消して作り直すので、同じ package で vitest を 2 つ同時に動かすと互いを壊す。CI は `turbo run test` を 1 本流すだけなので害は無い。
- Docker の build の context はリポジトリのルートで、dockerignore は最後に合った行が勝つ。`apps/**` と `!apps/attachment-text-extractor` を先頭に置き、その後に `**/node_modules` と `**/dist` を置く (逆の順だと、この app 自身の `node_modules` と古い `dist` が context に入る)。

### 9.1 `/metrics` の部品: `@prometheus-io/client` を使う

- **背景**: Req 9 は、gauge・ラベル付きのカウンタ・ヒストグラムと、プロセスの CPU・メモリ・イベントループの遅れを、Prometheus のテキスト形式で出すことを求める。
- **比べた案**:
  1. Prometheus の公式の JavaScript のクライアント `@prometheus-io/client` を使う (リポジトリは prometheus/client_js。旧名の `prom-client` の後継)
  2. `prom-client` を使う (採らない。npm で「`@prometheus-io/client` に置き換えられた」と非推奨の表示が出ている。最新は 15.1.3 で 2024-06 のまま)
  3. テキスト形式を自分で書く (`process.cpuUsage()`、`process.memoryUsage()`、`perf_hooks.monitorEventLoopDelay()` を読み、形式の決まり (エスケープ、`# HELP`・`# TYPE` の行、ヒストグラムの `_bucket`・`_sum`・`_count` と `le="+Inf"`) を自分で守る)
  4. OpenTelemetry の SDK と Prometheus の exporter (apps/app は `@opentelemetry/exporter-prometheus` を使っている)
- **決定**: 1。
- **理由**:
  - プロセスの既定の指標の名前 (`process_cpu_seconds_total`、`process_resident_memory_bytes`、`nodejs_eventloop_lag_seconds` など) は、Node のサービスで広く使われている名前で、運用者の既存のダッシュボードと警報の設定がそのまま使える。3 で同じ名前と意味を再現すると、保守するコードが増え、意味のずれを確かめる手段も無い
  - 3 は依存を増やさないが、形式の決まりを守るコードとテストを自分で持つことになる。小さくはならない
  - 4 は部品が多く、このサービスの小さな image と少ない依存の方針に合わない
- **引き換えにしたこと**: 本番の依存が 1 つ増えた (12 個。§1.4)。`@prometheus-io/client` は HTTP の層だけで使い、変換の子は読み込まない (`test/layers/layer-rules.ts` の規則で守る)。
- **npm で確かめたこと**: `@prometheus-io/client` 0.16.1 (最初の公開は 2026-08-21)。ライセンスは Apache-2.0。依存は `@opentelemetry/api` (Apache-2.0) と `tdigest` (MIT。さらに `bintrees` MIT)。Node は ^22 || ^24 || >=26 で、このサービスの >=24 に合う。`prom-client` 15.1.3 も Apache-2.0 で依存は同じ。版は 0.x なので、`^0.16.1` は 0.16.x の範囲に限られる。最初の公開から日が浅く、API が今後変わりうるので、依存の版を上げるときに確かめる。
- **`pnpm-lock.yaml` に入った実際の内容で確かめたこと**:
  - `@prometheus-io/client` 0.16.1 の依存は `@opentelemetry/api` 1.9.0 (Apache-2.0)、`tdigest` 0.1.3 (MIT)、`tdigest` の依存 `bintrees` 1.0.2 (MIT) の 3 つ。どれも install のときのスクリプト (preinstall / install / postinstall) を持たない (`bintrees` の scripts は test だけ)。`pnpm-workspace.yaml` の `allowBuilds` は広げていない
  - 使う API (`Registry`、`Gauge`、`Counter`、`Histogram`、`collectDefaultMetrics`) は、そのままの名前で在る。`registry.contentType` は `text/plain; version=0.0.4; charset=utf-8` (Prometheus のテキスト形式)
  - `pnpm-lock.yaml` の差分は `@prometheus-io/client`・`bintrees`・`tdigest` の追加だけにした。無関係な peer の再解決の差分は除いた
- **image の大きさ**: docker の無い環境では測れないので、CI の image の確認で確かめる (§1.6)。1.0.0 の値は、展開して amd64 で 259,258,880 バイト、arm64 で 277,116,416 バイト (上限 400,000,000 バイト)。

**本番の依存を増やすときに一緒に直す場所** (確かめた):

- `test/deploy/production-dependencies.spec.ts`: 本番の依存の一覧を完全一致で固定している。一覧に足し、テスト名とコメントの個数を直す
- `test/layers/layer-rules.ts` の `PACKAGE_RULES`: 部品ごとに、読み込んでよい層を決めている。HTTP の層だけで使う部品はここに足す
- `docker/Dockerfile`: 変えなくてよい。build の段の `pnpm deploy out --prod --legacy` が本番の依存を取り出すので、`package.json` と `pnpm-lock.yaml` を直せば image に入る
- `pnpm-lock.yaml`: `pnpm install` で更新する (ほかの pnpm の実行と同時に動かさない。`.claude/rules/devcontainer.md`)。`ci-attachment-text-extractor.yml` は `pnpm-lock.yaml` の変更でも動く

### 9.2 呼び出し元の app の ID (`X-Growi-App-Id`)

#### 9.2.1 ヘッダーの名前と形 (ユーザーと取りまとめ役の決定)

- 名前は `X-Growi-App-Id`。値は apps/app の設定 `app:growiAppIdForCloud` (環境変数 `GROWI_APP_ID_FOR_GROWI_CLOUD`) の値。
- 形は `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`。ログの行は空白で区切った `key=value` の並びなので、空白・`=`・改行などを通さない。英数字で始めるので、`-` と `(invalid)` は本物の値と取り違えない。
- 値は自己申告で認証されていない。負荷の内訳を見るためだけに使い、認可・上限・判断には使わない。悪い値で要求を失敗させない (負荷の内訳のためのラベルにすぎないため)。形に合わない値は、ログの行には出さず `(invalid)` と書く。
- メトリクスのラベルには使わない。自己申告の値は種類が際限なく増えうる (ラベルの値の種類が増えると、監視システムの記憶と計算の量が増える)。

#### 9.2.2 orval はヘッダーの parameter から何も作らない (実験)

- **やったこと**: `packages/attachment-text-extractor-client` の `openapi.json` を作業用のディレクトリに写し、`POST /extract` に `{"in":"header","name":"X-Growi-App-Id","required":false,"schema":{"type":"string","pattern":"^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$"}}` を足した文書と、足さない文書から、それぞれ orval (`v7.2.0`、設定は `input` と `output.target` だけ) でクライアントを作り、`diff` で比べた。
- **結果**: 2 つの出力は 1 バイトも違わなかった。`postExtract(postExtractBody, options?: AxiosRequestConfig)` のままで、ヘッダーの型も作られない。
- **意味**: OpenAPI の文書にはヘッダーが載るが、生成クライアントは変わらない。apps/app は axios の `options.headers` で渡す。AC 7.2 (生成クライアントは文書のとおりに項目を持つ) は、ヘッダーについては成り立たない。これは orval の既定 (ヘッダーの引数は `headers: true` を指定したときだけ作る) によるもので、AC 7.6 (文書のための指定を書かない) を守るために、この設定は足さない。この事実は §5.6 にも書いた。
- **`info.version` を 1.1.0 にしたとき**: 生成クライアントの先頭のコメントに `OpenAPI spec version: …` の行があり、この行だけが変わる。`ci-app.yml` は生成クライアントを作り直して commit 済みのものと比べるので、作り直したものを commit する。
- **`describeRoute` が `parameters` を受け付けること**: `hono-openapi` の型 (`DescribeRouteOptions` は OpenAPI 3.1 の `OperationObject` から `requestBody`・`responses`・`operationId` を除いたもの) で確かめ、書き出しの手順の出力に `parameters` が載ることを確かめた。

#### 9.2.3 ヘッダーを読む場所

- 認証の後、route の最初 (宣言された `Content-Length` の確かめと、枠を取るより前) で読む。ヘッダーは本文より先に届いているので、本文を読む前に断る行 (`service_busy`、`file_too_large`、`upload_timeout`、`invalid_upload`、`client_disconnected`) にも値を出せる。
- 認証より前には読まない。401 の要求は行を出さない (§5.7) ので、読んでも使い道が無い。
- Node は、同じ名前の未知のヘッダーが 2 つ以上あると、`, ` でつないだ 1 つの値にする (`c.env.incoming.headers`)。その値は形に合わないので `(invalid)` になる。2 つのうちどちらかを選ぶ規則を足さない。

| 同じものの前に 100 バイト足す | 成功 (1,077,794 字) | `malformed` |
| 小さい正常な XLSX / PPTX の後ろに 70,000 バイト | 成功 (anydoc がファイル全体を読み、ページ番号の無い 1 要素) | 成功 (検査を通り、後ろに何も足さないときと同じ結果) |
| 10 万セルの XLSX の中央の一覧を終わりの記録の後ろへ移し (オフセットの値は移した先に直す)、後ろに 70,000 バイト | `malformed` (anydoc も開けない) | 変わらない (`inspectArchive` は `null`。記録より前に中央の一覧の印が無いため) |

- 後ろに足した形で上限を通り抜けたのは、変更前の `zip-extent.ts` が終わりの記録を最後の 64KiB の中でしか探さず、見つからなければ「ZIP でない」としてファイル全体を anydoc に渡していたためである。anydoc は、それより前にある終わりの記録も見つけて開く。
- anydoc は、終わりの記録の「中央の一覧の大きさ」の値を使わずに中央の一覧を見つける。前に 100 バイト足し、大きさの値を 3 減らす、3 増やす、100 減らすのどれでも、後ろに 70,000 バイト足した XLSX を開いた (変更前のコードで、この経路は検査を通らずに anydoc に渡っていた)。オフセットの値を 7 増やしたものは開けなかった (`malformed`)。
- **読み取れること**: 1.0.0 の `inspectArchive` が `null` を返す 4 つの場合のうち、
  - **ZIP でない**: 正しく通す必要がある (暗号化された OOXML が `encrypted` になり、旧形式の XLS が読める)。
  - **一覧を読み切れない**: 3 つの上限 (エントリ数、展開後の大きさ、セル数) をすべて通らない。
  - **必要な部品が 2 つ以上**: エントリ数と展開後の大きさは確かめた後なので、セル数の上限だけを通らない。
  - **必要な部品が無い**: 試したどの形でも、anydoc は何も取り出さないか `malformed` を返した。上限を通らずに中身が変換される形は見つからなかった。
  - なお、「ZIP でない」の `null` には、ZIP の終わりの記録が見つからない場合と、見つかったのに yauzl が開けない場合の 2 つが含まれていた。後者は「ZIP なのに読めない」側に入れた (§9.3.2)。
- anydoc には組み込みの展開量の上限 (512MiB) があるが、エントリ数の上限は試した範囲では無かった (12,000 エントリが通った)。セル数の上限は anydoc に無い。

#### 9.3.2 決定: ファイル全体を anydoc に渡すのは「ZIP でない」ときだけにする

- **決定**: `inspectArchive` の `null` を「ZIP の終わりの記録がファイルのどこにも見つからない (検証に通る終わりの記録が無い)」だけの意味にする (探す範囲と検証は下の「終わりの記録を探す範囲」)。終わりの記録が見つかったのに yauzl が開けない、一覧を読み切れない、必要な部品が無い、2 つ以上ある、の 4 つはすべて `malformed` にする。
- **理由**:
  - 実際に上限を回避できたのは 2 つの場合だが、「ZIP なのに検査を通せない」形をまとめて断るほうが規則が単純で、`null` の意味が 1 つになり、分岐が減る。別の検査を並べて足す形より、穴をふさぐ場所が 1 か所で済む。
  - 必要な部品が無い場合と yauzl が開けない場合は、実験では anydoc も `malformed` か 0 字だった。断っても、呼び出し側から見た結果はほぼ同じである (0 字の成功が `extraction_failed` に変わる形はある)。
  - ZIP でない形 (暗号化された OOXML、旧形式) の扱いは変わらない。
  - 終わりの記録が言う位置に中央の一覧が無い ZIP (記録の「中央の一覧の大きさ」の値が実際と合わないもの) も、「ZIP でない」とは扱わず、yauzl に判断させる。これを `null` にすると、10 万セルの XLSX で大きさの値を 3 減らすだけでセル数の上限を通る (§9.3.1 の 2 つ目の表)。yauzl は大きさの値を見ないので、正常なファイルは断らない。`null` の意味が「終わりの記録が無い」だけになり、分岐も 1 つ減る。
- **終わりの記録を探す範囲: ファイル全体**。判定は 2 段になっている (最後の 64KiB の中と、それより前)。
  - 最後の 64KiB (CPython の `zipfile` と yauzl が探す範囲) だけを探すと、ZIP の後ろに 64KiB より長いバイトを足すだけで「ZIP でない」になり、検査を通らずに anydoc に渡る。anydoc はそれより前の終わりの記録も開くので、エントリ数とセル数の上限を通り抜けられる (§9.3.1 の 3 つ目の表)。CPython に合わせて 64KiB に絞る理由は要件に無く、上限を守ることを優先する。
  - **1 段目 (最後の 64KiB の中)**: いちばん後ろの完全な終わりの記録を、確かめずにそのまま使う (大きさを偽った ZIP は yauzl に判断させる、という上の扱いのまま)。ファイルの最後の 21 バイトで途中で切れた印は読み飛ばし、その手前の完全な記録を使う。以前はこの場合に「ZIP でない」になり、正しい XLSX の後ろに印を含む 4〜21 バイトを足すだけで上限を通り抜けられた。
  - **2 段目 (それより前)**: ここで見つかった候補は、暗号化された OOXML や旧形式の中身に偶然 `PK\x05\x06` が入っているだけのこともあるので、検証してから使う。検証の条件は 2 つある。1 つ目の条件に通るのは、記録の「中央の一覧の大きさ」の値から計算した位置 (記録の位置から大きさを引いた位置) に、中央の一覧の印 `PK\x01\x02` がある候補と、すぐ前に zip64 の locator の印がある候補である。後ろから順に候補をたどり、1 つ目の条件に通らない候補は読み飛ばして手前を探す。そのため、後ろにダミーの終わりの記録を置いても、手前の本物が見つかる。
  - 1 つ目の条件に通る候補が無くても、いちばん後ろの候補より前のどこかに `PK\x01\x02` があれば、その候補を終わりの記録として扱う。これが検証の 2 つ目の条件で、この節で「検証に通る」と言うときはこの条件も含む (結果は yauzl が開けず `malformed`)。anydoc は大きさの値を使わずに中央の一覧を見つけるので (§9.3.1 の 3 つ目の表の後の注)、記録の値だけで確かめると、前にバイトを足して大きさの値をずらした ZIP を「ZIP でない」として anydoc に渡してしまうためである。暗号化された OOXML がこれに当たるには、`PK\x01\x02` と、その後ろの `PK\x05\x06` の両方が偶然入っている必要があり、まず起きない。
  - どちらの段でも、CFB の印 (`D0 CF 11 E0`) を見て旧形式や暗号化ファイルを通す検査はしない (下の「採らなかった案」と同じ理由)。
  - 候補をたどるときは `lastIndexOf` の開始位置を前へずらしながら探すので、ファイル全体を一度読む程度の手間で済む。4 バイトおきに `PK\x05\x06` で埋まり、最後の 70,000 バイトだけが 0x00 という最悪の形で測ると、50MB (`MAX_FILE_SIZE_MB` の既定値) で約 0.9 秒、100MB で約 1.9 秒だった。
  - 記録の「オフセット」の値 (ファイルの先頭から数えた中央の一覧の位置) が指す位置を見る検証は入れない。それだけで通る候補は、大きさの値が合わないので、結局 yauzl が開けず `malformed` になる。2 つ目の条件と結果が同じなので、分岐を増やさない。
- **応答**: `malformed` は既存の `extraction_failed` (422)。`ErrorCode`、ステータス、OpenAPI の文書は変わらない。
- **影響の範囲**: 名前か MIME が `.xlsx` / `.pptx` のファイルだけである。`.xls` / `.ppt` と `office` の経路 (DOCX など) は `inspectArchive` を使わない (§9.3.4)。動きが変わる形は §9.3.3。
- **残る心配**: yauzl が開けない ZIP は、実験では 1 つの形 (一覧の位置のずれ) しか試していない。zip64 の形のうち yauzl が開けないものがあれば、それまで anydoc が読めていたものが断られる。「zip64 の大きさで書いた部品を受け付ける」テストは残してある。
- **採らなかった案 (旧形式を CFB の印で通す)**: 旧形式 (PPT / XLS) や暗号化された OOXML は、ZIP の埋め込みや偶然の印のために、それまで読めたものが `malformed` になりうる (§9.3.1 の 2 つ目の表)。最後の 64KiB の中に終わりの記録の印があるとき、またはファイルのどこかに中央の一覧へつながる終わりの記録 (埋め込まれた ZIP のもの) があるときである。影響は、名前か MIME が `.xlsx` / `.pptx` になっている場合だけである。CFB の印 (`D0 CF 11 E0`) を見て旧形式を通す検査は入れない。入れると `null` に 2 つ目の意味ができ、AC 2.10 の書き方を変えることになる一方、取り戻せるのは「名前が違い、かつ ZIP を埋め込んだ旧形式」という狭い場合だけである。CFB の印の後ろに ZIP を付けたものを anydoc に渡しても、抜け道にはならないことを確かめた (`malformed`、または外側の文書だけが読まれる)。
- **見直す条件**: 名前の違う旧形式や暗号化ファイルが、この変更のために `malformed` になった例がログ (`result=malformed`) から見つかったとき。

#### 9.3.3 以前の動きとの違い (§5.4 と同じ形の記録)

- **以前 (1.0.0 まで) の動き**: CPython の `zipfile` が開けない ZIP (扱えない版の印、UTF-8 の印と合わない名前) と、必要な部品が無いか 2 つある ZIP は、ファイル全体を anydoc に渡していた。以前の Python の実装と同じ扱いで、`archive-guard.spec.ts` の「passes … through」のテストがこれを固定していた。
- **いまの動き**: 上のどれも `malformed` (422 `extraction_failed`) で断る。
- **合わせない理由**: 以前の扱いでは、ZIP の上限とセル数の上限が回避できる (§9.3.1)。上限は細工したファイルから子を守るためのもので、以前の実装に合わせることより優先する。
- **同じ変更で動きが変わるもの**: (a) 終わりの記録の大きさの値が実際と合わない ZIP は、以前は全体を anydoc に渡して変換していたが、いまは上限を確かめる (超えれば `limit_exceeded`、yauzl が開けなければ `malformed`)。(b) 名前か MIME が `.xlsx` / `.pptx` の旧形式や暗号化ファイルで、ZIP の終わりの記録を持つもの (最後の約 64KiB の中の印、またはファイルのどこかにある、埋め込まれた ZIP の終わりの記録) は、以前は読めたり `encrypted` になったりしたが、いまは `malformed`。理由は上と同じで、ZIP の終わりの記録を持つファイルを、検査を通さずに anydoc へ渡さないため。(b) を避ける CFB の印による検査を採らない理由と見直す条件は §9.3.2。
- **下流**: apps/app、生成クライアント、下流 spec は変わらない。`malformed` は既存の 422 `extraction_failed` である。

#### 9.3.4 扱わないもの

- `office` の経路 (DOCX、ODT など) は、もともと `inspectArchive` を通らない。エントリ数の上限は anydoc 任せで、守りの境界は RSS の上限である。PPTX / XLSX の経路の外なので、変えなかった。

### 9.4 `/readyz` の結果を覚える期間: 10 秒

- **背景**: 1.0.0 では、`/readyz` を呼ぶたびに確認用の子を起動していた (1 回約 0.24〜0.4 秒の CPU)。同時の呼び出しは 1 回の確認を共有するが、終わった後は覚えないので、トークンなしで休みなく呼ばれると最大で約 1 コアを使った。覚えなかったのは、固まった部品を検知できなくならないため、準備未完了から戻れるようにするため、だった。
- **前提**: `docker/README.md` が勧める確認の設定は、間隔 20 秒、期限 15 秒、3 回の失敗。確認用の子の期限は 10 秒。
- **決定**: 確認を終えた時点から 10 秒間、結果を覚える。準備完了と未完了のどちらも覚える (確認が例外で終わった場合も同じ)。確認の実行中に届いた呼び出しは、その 1 回の確認を共有する。
- **理由**:
  - 10 秒は確認の間隔 (20 秒) より短い。kubelet の確認の前の確認は、普通は 20 秒前に終わっているので、kubelet は毎回新しい確認の結果を受け取る。kubelet から見た振る舞いは、普段は変わらない。
  - トークンなしの呼び出しで起動される確認は、10 秒 (+ 確認そのものの時間) に 1 回までになる。CPU は最大で 0.4 秒 / 10 秒、1 コアの約 4% に下がる。
  - 部品が固まってから気づくまでの時間: 確認の結果が最大 10 秒古いので、「3 回の失敗 × 20 秒」に最大 10 秒足した、約 70 秒以内になる。
  - 準備未完了から戻るまでの時間: 覚えた未完了の結果は 10 秒で消えるので、部品が直ってから最大で「10 秒 + 次の確認の間隔」で戻る。
  - 未完了も覚えるのは、未完了の結果だけを覚えないと、固まった部品のある Pod で、トークンなしの呼び出しが 10 秒の期限の確認を続けて起こせるからである。
- **終えた時点から数える理由**: 確認は最大 10 秒かかる。始めた時点から数えると、遅い確認の結果は覚えた瞬間に古くなり、覚える意味が無くなる。
- **環境変数にしない理由**: 運用者が変える値ではなく、確認の間隔との関係 (間隔より短いこと) をコードの側で守るため。`docker/README.md` には、値と、readiness の確認の間隔を 10 秒より十分長く (例の 20 秒のように) 取ることを書いた。
- **採らなかった案**: 準備完了だけを長く覚える (固まった部品を見落とす時間が延びる)。トークンなしの `/readyz` を断る (k8s の確認はトークンを送れない)。
- **下流**: 応答の形は変わらない。確認の結果が最大 10 秒古いことがある。運用者が決める確認の間隔と期限 (20 秒と 15 秒) は変えなくてよい。

#### 9.5.4 ここから言えること (文書に書く強さ)

- 言えること: 抽出サービスと同じ形で起動した子は、同じ uid の親の環境変数を `/proc` から読める。少なくとも Yama の `ptrace_scope` が 1 の Linux 6.8 では読めた。作業者の理解では、`/proc/<pid>/environ` を読む許可は「同じ uid で、相手が dump できるプロセスである」ことで決まり、Yama の制限 (ptrace で取り付くことへの制限) の対象ではない。この理解はカーネルの資料での知識で、この実験では確かめていない (確かめたのは `ptrace_scope` が 1 の 1 つの環境だけ)。そのため、ほかのノードでも読める見込みが高いと考えるが、試してはいない。
- 言えないこと: GROWI.cloud のノードで読めること。親のメモリ (処理中のほかの要求のファイルを含む) が読めないこと。`ptrace_scope` が 0 のノードでは、同じ uid のプロセスのメモリを読める可能性があるが、試していない。
- `docker/README.md` には、この範囲で書いた。「子は親と同じ uid で動き、トークンは子に渡さないが、乗っ取られた子は親の環境変数をトークンを含めて `/proc` から読める (Linux 6.8、`ptrace_scope` 1 の環境で確かめた。GROWI.cloud のノードと image の中では試していない)。親のメモリが読めるかはノードの ptrace の設定による (試していない)。対策は決めていない」。置き場所は「Conditions the service is designed for」の中の「Non-root, read-only, no privileges.」の段落の後の、独立した段落である (`docker/README.md` に「security」という名前の節は無い)。
- 子自身の環境にトークンが無いことを確かめるテスト (`/proc/<pid>/environ` を読むもの) は正しいが、確かめているのは子の環境で、親の環境が子から読めることとは別の事実である。
- この事実を文書に書くと攻撃の手がかりを示すことになるが、事実はコードと Linux の仕組みから分かることで、運用者が判断するために要る。そのため書くことにした。
- 対策 (`MAX_CONCURRENCY=1`、顧客ごとのサービス、OS による隔離) は決めていない。umbrella の [roadmap.md](../attachment-search/roadmap.md) の (h) で扱う。

### 9.7 結果の大きさの数え方

- `assemblePages` は、改行を LF に揃えた `content` の UTF-8 のバイト数を足し、`MAX_RESULT_BYTES` を超えたら `result_too_large` を投げる。`label` は数えない。
- PPTX の `content` は、anydoc の出力の掃除 (`cleanSlideText`) の後で、まだ CR を含みうる。揃える前のバイト数で数えると、最後の確かめでは通る結果を途中で止めてしまう。
- **決定**: 数え方を `result-budget.ts` の 1 か所に置き、PDF の繰り返し、PPTX の繰り返し、`assemblePages` が同じものを使う。数える関数は改行を揃えず、揃えた後の文字列だけを型 (`LfText`。`normalize.ts` の関数だけが作る) で受け取る。各呼び出し元は自分で 1 回だけ揃える。PPTX は掃除の後に揃える (掃除の行末の判定は Python 版と同じく LF だけを見るので、先に揃えると消すものが変わる)。`PageInfo.content` は普通の文字列なので、`assemblePages` は経路を問わずもう 1 回揃える。揃える処理は文字列を写し直すので、上限に近い大きな PDF で同じ文字列に何度もかけると、CPU と一時的なメモリを無駄に使うためである。
- 空の要素は 0 バイトなので、数えても数えなくても同じになる。
- 親の受け取りの上限 (`2 × MAX_RESULT_BYTES + 約 1MiB`) は変えない。

### 9.8 `/metrics` の数え方と、公開の手順

#### 9.8.1 応答をどこで数えるか

- **比べた案**:
  1. Hono の middleware (`app.use('*', …)`) を `bearerAuth` より前に置き、`await next()` の後の `c.res.status` を数える
  2. Node の `server.on('request')` と `response.once('close')` (`start-server.ts` の `trackRequests` と同じ場所) で数える
- **決定**: 1。
- **理由**: HTTP の層の中で完結し、`app.request()` でテストできる。`trackRequests` は停止のための仕組みで、指標を混ぜると責務が 2 つになる。2 にしても、Node が自分で返す答え (400、408、417、431) は `'request'` の前に返されるので数えられず、違いは「読み手のいない答え」の扱いくらいである。
- **数えないもの**: Node の HTTP の層が自分で返す答え (壊れた要求と `Host` の無い要求の 400、431、`Expect` が `100-continue` 以外の 417、ヘッダーと要求の期限切れの 408)、答える前に閉じた接続、`100 Continue`。
- **401 と 404 はログの行を出さない** (§5.7 の決定のまま)。数は `/metrics` で分かる。
- **`/metrics` はトークンなしで開いている**: 中身に利用者のデータは無い (`X-Growi-App-Id` の値もラベルに使わない。§9.2.1)。内向きの通信の制限で守る。

#### 9.8.2 registry を 2 つに分けた理由

- サービスの 5 つの指標 (応答の数、枠の使用中の数と上限、`/extract` の結果ごとの件数と所要時間) はアプリごとの registry に置く。プロセスの既定の指標 (`collectDefaultMetrics`) は、モジュールで 1 回だけ作る registry に置く。`/metrics` は `Registry.merge` で 2 つを合わせたものを返す。
- **理由**: `collectDefaultMetrics` は、止められない `setInterval`、GC の `PerformanceObserver`、イベントループの遅れの計測を起動する。テストでアプリを数百個作ると、これらが溜まる。また、既定の指標はアプリではなくプロセスの値である。本番ではアプリは 1 つなので、出力は並び順のほかは変わらない。
- **注意**: `Registry.merge` は、呼んだ時点の指標を写し取る。後からどちらかの registry に指標を足しても、合わせた registry の出力には出ない。指標を足すときは、合わせる前に足す。

#### 9.8.3 版と公開

- `apps/attachment-text-extractor/package.json` は `"private": true`。1.0.0 までは、この package の changeset は 1 つも無かった (`git log` で確かめた)。
- `.changeset/config.json` の `ignore` に `@growi/attachment-text-extractor` は無い。`private: true` の app が changesets で版を上げる前例は `apps/growi-vault-manager` (`CHANGELOG.md` があり、版は 1.1.7)。
- ルートの `package.json` の `version-subpackages` は `changeset version && pnpm update "@growi/*" -r && pnpm dedupe`、`release-subpackages` は `@growi/core` と `@growi/pluginkit` を build して `changeset publish` (private の package は npm に出さない)。`release-subpackages.yml` の `changesets/action` が「Release Subpackages」の PR を作り、それを master にマージすると `apps/attachment-text-extractor/package.json` の版が変わり、`release-attachment-text-extractor.yml` が image を公開する。
- 生成クライアントの package (`@growi/attachment-text-extractor-client`、`private: true`) は changeset を書かない。npm に出さず、apps/app は workspace の中で使うので、版を上げて伝える相手がいない。生成コードの変化は先頭のコメントの版の行だけである (§9.2.2)。
- メモリの計測 (`ci-attachment-text-extractor.yml` の `Measure memory in the image`) は `workflow_dispatch` のときだけ動く。計測の道具は、ログの `/extract` の行を `\bextract format=(\S+) .*\bresult=(\S+) child_peak_rss_mb=(\S+)` で読む (`scripts/image-check/memory/report.ts`)。`app=` を行の最後に足しても、この正規表現は読める (`child_peak_rss_mb=` の値の後ろの空白で `\S+` が止まる)。ただし、計測は手で起動しないと動かないので、公開の前に手で起動する (§1.6)。
