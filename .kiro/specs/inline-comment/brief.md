# Brief: inline-comment

## Problem

閲覧者・編集者が、ページ本文の**特定の範囲**に対してコメントを付けたい。現状のコメント機能（`apps/app/src/features/comment/`）はページ末尾に積む1本のスレッドのみで、本文のどの部分について話しているのかが文脈から失われる。

この需要とドキュメント（dev wiki「資料/外部仕様/インラインコメント機能.md」「資料/内部仕様/インラインコメント機能.md」）は2023年当時から存在し、現在も有効。

## Current State

- 2023年11月〜12月に `feat/inline-comment` ブランチ（PR #8313、未マージ、実装途中で放棄）で一度試作された。DOMのXPath＋innerHTML diffパッチで選択範囲をクライアント側だけで特定・復元する方式だったが、コメント送信は決め打ち文字列を送るダミー実装のまま止まっており、サーバー側のマージ・検証ロジックも空だった。
- 当時のdev wiki設計ドキュメントは、上記の試作コードとは異なる方式（本文中に`<selected>`タグを埋め込んだ`Revision.markedBody`という別フィールドを持たせ、diffパッチで新リビジョンに引き継ぐ）を描いていたが、これも実装はされていない。
- 現在のコードベースはこの2023年当時から構造的に大きく変わっている：
  - `Comment`（`comments`コレクション）は既にPrisma化済み（`apps/app/prisma/schema.prisma`、`provider = "mongodb"`）。ただし `apps/app/src/features/comment/server/models/comment.ts` の Mongoose スキーマは「コレクション・インデックス作成のためだけに」残っており（`.claude/rules/model.md` の移行ルール通り）、新しいフィールドを足す場合は Mongoose スキーマと `prisma/schema.prisma` の**両方**を揃える必要がある。
  - `commentPosition`（Int、常に`-1`）という当時の「位置」フィールドは事実上未使用のまま残っており、新しい位置情報の土台にはならない（別フィールドとして設計し直す）。
  - ページ本文は現在 Yjs による共同編集（[collaborative-editor](../collaborative-editor/) / [collaborative-editor-awareness](../collaborative-editor-awareness/)）の対象になっている。ただしこれは「エディタでの編集セッション」の話であり、インラインコメントを付ける対象は「レンダリング済みの読み取り専用ページビュー」（`PageView.tsx` → `RevisionRenderer.tsx` → react-markdown）であるため、直接の依存にはならない（後述の Out of Boundary 参照）。
  - ブロック単位（段落・見出し等）でmarkdown上の開始行をDOMに埋め込む仕組み（`add-line-number-attribute.ts` rehypeプラグイン、`data-line`属性）が既に存在し、エディタのプレビュー・スクロール同期用途で本番運用されている。ただし現在は通常の読み取りページビュー（`generateViewOptions`）には組み込まれておらず、行番号までの粒度しか持たない（文字オフセットは持たない）。

## Desired Outcome

- 閲覧者が本文中の任意のテキスト範囲を選択し、その場でコメントを作成できる。
- 作成したインラインコメントは、選択したテキスト範囲の近傍に紐付いた形で表示される。
- 対象範囲がのちの本文編集で変わってしまっても、システムは可能な範囲でコメントの位置を追跡し直す（ベストエフォート）。追跡できなくなった場合は、コメント自体は残るが本文中のハイライトは失われてよい。

## Approach

**採用: レンダリング後テキスト空間でのクオート＋前後文脈アンカリング（ベストエフォート再アンカー）**

> この方針は、opusサブエージェント2体に対案（B案：markdownソース文字オフセット方式、`data-line`機構を文字粒度まで拡張して取得）を検討・討論させた上で確定した。討論はB案側が2ラウンド目で全面的に譲歩し、A案（本方針）をベースに2点の設計要求を追加する形で収束している。詳細は以下に統合済み。

- コメント作成時に保存する位置情報は、**markdownソースの文字オフセットでもDOM XPathでもなく**、レンダリングされたページのプレーンテキスト表現に対する「選択文字列（exact quote、正規化前の原文のまま保存）＋前後文脈（prefix/suffix）＋テキスト全体中でのおおよそのオフセット」（W3C Web Annotation Data Model の TextQuoteSelector / TextPositionSelector に相当する、hypothes.is 等で実績のあるモデル）。
- 表示時は、その時点でレンダリングされているページの本文テキストに対して同じクオート＋文脈で検索し直し、一致すればハイライトを復元する。完全一致しない場合はあいまい一致（fuzzy re-anchor）を試み、それでも見つからなければハイライトなしでコメント自体は一覧に残す。
- 選定理由：
  - markdownソース側の文字オフセットで持つ案は、`**太字**` や `[リンク](url)` を跨ぐ選択がレンダリング後テキストとソース文字列で一致しなくなる（マークダウン記法自体が選択範囲に含まれてしまう）ため、文字精度を求めるなら整合性の取れた設計にならない。
  - 2023年当時の設計ドキュメントが描いていた「`Revision.markedBody` に注釈を埋め込む」方式は、本文が変わるたびにサーバー側で再計算・保持するコストが今回採用する方式と同等以上にかかる一方、得られるメリット（クライアント側再アンカーが不要になる）は薄い。
  - `data-line` 機構は現在 `generateViewOptions`（通常の読み取りページビュー）には組み込まれておらず、プレビュー・スクロール同期用途（`generatePresentationViewOptions`/`generatePreviewOptions`）限定である。これを文字オフセットまで拡張する対案（B案）も検討したが、(a) 読み取りパス全体へのレンダリングパイプライン変更が必要、(b) sanitizeより前の段階に新しいhastウォーカーを差し込む必要があり本文レンダリングの他機能にも影響しうる、(c) 段落の並び替え・移動（cut&paste）に対してはオフセットベースの再アンカーも結局あいまい一致にフォールバックせざるを得ない、という理由でB案は不採用となった。`data-line` は将来「編集中に対象範囲をハイライトする」（別スペック）を作る際の参考実装として残す。

### 討論で確定した設計要求（設計フェーズでの具体化が必須）

1. **あいまい照合（fuzzy re-anchor）マッチャーの仕様**：
   - 比較時のみ NFC 正規化を行う（保存するクオート自体は選択されたままの原文を保持し、正規化しない — 表示・エディタでの再選択に正規化後の文字列を使うと情報が失われるため）
   - 単語境界・空白によるトークン化を前提にしない実装を選ぶ（CJKには単語境界が無いため）
   - 前後文脈の窓（prefix/suffix）は**書記素クラスタ境界**（`Intl.Segmenter` の `granularity: 'grapheme'`）にスナップした固定長とする。コードポイント単位だけでは合成文字（結合分音記号）やZWJ絵字文字シーケンスが分断されうる。スナップは**内側に縮める**方向で行い、窓サイズの妥当性チェックはスナップ**後**に行うこと。
   - diff-match-patchのBitapベース`match_main`を使う場合、パターン長の上限（`Match_MaxBits = 32`）が窓サイズの制約になることを設計時に明記する。
   - 比較がNFC正規化後の文字列に対して行われるため、マッチ結果のオフセットは正規化後の文字列上のインデックスになる。正規化前（原文）の文字列とは長さが異なりうるため、**正規化後オフセット→原文オフセットの逆変換**（または原文上での再特定）を設計に含めること。ここを怠るとハイライト位置がずれる。

2. **アンカーの起点リビジョンを示す専用フィールド**：既存の `Comment.revisionId`（「投稿時点で表示されていたリビジョン」という情報的な意味で今も使われている）とは**別に**、アンカー計算の起点となったリビジョンIDを保持するフィールドを追加する。
   - 目的はオフセット計算ではなく、「このアンカーはどの本文に対して作られたものか」を diff を行わずに判定できるようにすること（孤立化判定・検証を軽くする）
   - このフィールドは**作成時に一度だけ設定される不変の来歴情報**とし、再アンカーが成功しても書き換えない（書き換えると「どの本文に対して作られたアンカーか」という本来の目的が答えられなくなる）
   - 再アンカーに成功した場合の解決済みオフセット（キャッシュ）は、この不変フィールドとは別の場所に保持し、毎回のレンダリングであいまい一致をやり直さずに済むようにする

## Scope

- **In**（今回のv1で設計・実装する範囲。ユーザーの選択に基づく）:
  - 本文中のテキスト範囲を選択してインラインコメントを作成する
  - 作成したインラインコメントを閲覧する（ページ表示時にハイライト・一覧表示）
  - `@メンション`対応（[comment-mention](../comment-mention/) の remark ハイライト・通知経路を、インラインコメント本文にもそのまま適用する。メンション機能自体の再設計はしない）
  - 解決/未解決トグル（当時のドキュメントにあった `resolvedBy` / `resolvedAt` 相当の状態管理）
- **Out**（v1では扱わない）:
  - コメントの編集・削除（既存の通常コメント機構が持つ機能を、インラインコメントにも将来展開するかは後続タスク）
  - 共有リンク経由でのインラインコメント閲覧（[share-link-comments](../share-link-comments/) の対象範囲拡張）

## Boundary Candidates

- **アンカリングの計算とデータモデル**（選択範囲→クオート/文脈/オフセットへの変換、保存、再アンカーのロジック）— 最も技術的不確実性が高い部分で、独立して検証・実装できる
- **UI（範囲選択ツール・吹き出しフォーム・ハイライト表示・一覧）** — 2023年試作の `TextSelectionTools` 系コンポーネントを土台として再利用しやすい層
- **サーバー側の永続化とAPI**（`Comment`/`InlineComment` のPrisma/Mongooseスキーマ拡張、`comments.add`等のルート）— 既存の通常コメントAPIとどこまで共有し、どこから分けるかが設計判断のしどころ
- **解決/未解決トグル** — アンカリングとは独立して着手可能な、小さな状態管理機能

## Out of Boundary

- **エディタ（Yjs共同編集セッション）内でのインラインコメント作成・表示。** インラインコメントは読み取り専用のレンダリング済みページビューに対して付けるものとし、CodeMirror／Yjsのドキュメントモデルやカーソル・awareness機構には一切触れない。将来「編集中に対象範囲をハイライトする」「Y.RelativePositionでリアルタイムに追従させる」といった拡張が欲しくなった場合は、別スペックとして扱う。
- **共有リンク経由の閲覧**（上記Scope参照）。ただし `/comments.get` は既に `share-link-comments` によって共有リンク閲覧者にも開放されているため、**このスペックの実装で、インラインコメント行（アンカーのクオート文字列等を含む）が共有リンク閲覧者に意図せず返らないようにする**（UIを出さないだけでなく、レスポンスからも除外する）ことは本スペックのスコープに含める。単なるUI非表示では防げないデータ露出の問題のため。
- **通常コメント（ページ末尾スレッド）の編集・削除・通知まわりの仕様変更。** 既存のまま。
- **`@メンション`機能自体の追加要件**（自動補完の仕組み変更など）。[comment-mention](../comment-mention/) の既存実装を利用するのみ。

## Upstream / Downstream

- **Upstream**:
  - `Comment`（Prisma/`comments`コレクション、`apps/app/prisma/schema.prisma`）と、それを補助する legacy Mongoose スキーマ（インデックス作成用）
  - ページレンダリングパイプライン（`RevisionRenderer.tsx`、react-markdown、rehypeプラグイン群）
  - [comment-mention](../comment-mention/) のメンションハイライト・通知経路（利用するのみ、変更しない）
- **Downstream**:
  - [share-link-comments](../share-link-comments/)（将来、共有リンク閲覧者へのインラインコメント公開を検討する場合の拡張先）
  - 「エディタ内でのインラインコメント表示」（将来、必要になれば新規スペックとして着手）

## Existing Spec Touchpoints

- **Extends**: なし（新規スペック）
- **Adjacent**:
  - [comment-mention](../comment-mention/) — メンションハイライト・通知の依存先。本文中の位置指定という関心事は重複しない。
  - [share-link-comments](../share-link-comments/) — 共有リンク閲覧時のコメントアクセス制御の確立パターン（`certify-shared-page.js`・`isSharedPage`）。v1では露出を防ぐ側で触れるのみ。
  - [collaborative-editor](../collaborative-editor/) / [collaborative-editor-awareness](../collaborative-editor-awareness/) — Yjs共同編集。本スペックは意図的に非依存（Out of Boundary参照）。

## Constraints

- ユーザーの選択により確定した前提：
  - アンカー精度は**文字単位**が必要（ブロック/行単位では不十分）
  - 対象範囲が共同編集で書き換わった場合は**ベストエフォート**（追従できなければハイライトが外れるだけでよい。厳密なリアルタイム追従は不要）
- 設計フェーズで具体化・検証する事項（[Approach](#approach) の「討論で確定した設計要求」を参照。opusサブエージェント同士の討論で、単なる「要検証」から具体的な契約に格上げ済み）:
  - あいまい照合マッチャーは、NFC比較・非トークン化・書記素クラスタ境界スナップ・固定窓サイズ（Bitap採用時は32文字上限を考慮）・正規化後オフセットの原文への逆変換、を満たすものを選定・実装する。
- 新フィールド追加時、Mongooseスキーマ（`apps/app/src/features/comment/server/models/comment.ts`）と `prisma/schema.prisma` の**両方**を同期させる必要がある（`.claude/rules/model.md` 参照）。今回追加するフィールドは「アンカーのクオート/前後文脈/オフセット」に加え、討論の結果「アンカー起点リビジョンID（不変・`Comment.revisionId`とは別）」も対象になる。
