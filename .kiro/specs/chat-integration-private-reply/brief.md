# Brief: chat-integration-private-reply

チャットで、依頼した本人にだけ答えを届ける仕組みを proxy に作る amend spec。
本人にだけ見えるメッセージを出せる場所ではそれを使い、出せない場所では本人への DM で届ける。
どんな失敗でも、チャンネルの全員に見える形には戻らない。

最初の利用者は `search` の結果（出荷済みのコードの漏れを直す）と、出荷済みの本人にだけ返すメッセージ（`tell`）。
後から作る `chat-integration-agent` の答えも、この仕組みを使う。

## Amend target

| 対象の spec | 変わる契約 |
|---|---|
| `chat-integration`（umbrella） | 要件 3.2「1 本のリストとして投稿する」— 結果を誰に見せるかを定める受け入れ条件を、要件 3 の末尾に足す。本人にだけ届ける手段がサービスごとにどう違うか（要件 1.2 の代わりの手段）も足す。既存の番号は振り直さない |
| `chat-integration-proxy` | 本人にだけ届ける手段（今は `platform/outbound.ts` の `postEphemeral`。DM への切り替えは、アダプタに本人だけのメッセージの機能が無いときだけ働く）。`search` の結果の届け方（今は「いったん投稿して差し替える」段取りでチャンネルに出す）。能力表の `ephemeralMessage` の評価（Mattermost は管理者の権限が要る） |

- `chat-integration-protocol` と `chat-integration-app` の契約は変わらない見込み。GROWI が返す検索結果の中身（要件 3.9）はそのままで、変わるのは proxy がそれを誰にどう届けるかだけ。
- Revalidation Triggers（下流の spec を確かめ直す必要が出る条件）への影響: 無い見込み。requirements の段階で確かめる。

## Problem

- 出荷済みの `search` は、検索した本人の閲覧権限で調べる（要件 3.6）。それなのに、その結果をチャンネルの全員に見える形で投稿している。そのため、本人にしか見えないページの題名とパスが、チャンネルの参加者全員に見える。社外の人が入るチャンネルでは、社外にも見える。
- 本人にだけ返すつもりのメッセージ（登録コード、紐付けの URL、エラー、引数の聞き返し）が、サービスや場所によって届かないおそれがある。
- 後から作る `agent` も本人にだけ答える必要があり、同じ問題を抱える。

## Current State

- **`search`**: proxy の `orchestration/command-flow.ts` は、`search` を受けると、まずチャンネルに「「…」を検索しています…」と投稿する。結果が揃ったら、その投稿を一覧で差し替える（`platform.post` → `platform.replace`）。仮の投稿に失敗したときだけ、本人にだけ見えるメッセージで返す。
- **本人にだけ返すもの**: 紐付けが要るという案内、エラー、登録コード、`link` の URL、引数の聞き返しは、`platform.postEphemeral` で返している。`platform/outbound.ts` は Chat SDK に `fallbackToDM: true` を渡しているが、これはアダプタに本人だけのメッセージの機能が無いとき（Discord）にしか働かない。
- **サービスごとの制約**（`chat-integration-agent` の brief の「実現性の確認の結果」で確かめた）:
  - **Slack**: 本人だけのメッセージは、あとから書き換えられない。届くことの保証も無く、再読み込みで消える。返事の無いメッセージのスレッドに出すと、表示されないことがある（https://docs.slack.dev/reference/methods/chat.postEphemeral ）。実機試験では、メンションへの本人だけの返事（登録コード、紐付けの URL）は届いている。
  - **Mattermost**: 本人だけのメッセージを出すには、システム管理者の権限（`create_post_ephemeral`）が要る。コミュニティ製のアダプタはこの API を直接呼び、DM に切り替えない。普通の bot ではエラーになり、今の本人宛ての返事が届いていない疑いがある（実機では未確認）。
  - **Discord**: メンションへの返事を本人だけに見せる手段は無い。アダプタ側で DM に切り替わる。
  - **Teams**（未確認）: 本人だけのメッセージ（targeted message）がスレッドの中に出るかは確かめていない。

## Desired Outcome

- proxy に「本人にだけ届ける」部品が 1 つあり、本人にだけ返すものはすべてそこを通る。
- その部品は、本人だけのメッセージを出せる場所ではそれを使い、出せない場所や失敗したときは本人への DM で届ける。どの失敗でも、チャンネルの全員に見える形にはならない。
- `search` の結果の一覧は、検索した本人にだけ届く。本人は、検索を受け付けたことを待ち時間の間に知ることができる。
- チャンネルに共有したいときは、本人が結果のページの URL をチャンネルに貼る。何を誰に見せるかは、要件 6（URL の展開）の規則がそのまま決める。
- 運用者は、各サービスで本人にだけ返すものがどう届くか（その場か DM か）を能力表と導入ドキュメントで知ることができる。

## Approach

**本人にだけ返し、共有は URL を貼る形に任せる**（2026-10-26 の discovery で決定）。

- 新しい共有の仕組み（「共有する」ボタンなど）を作らない。Mattermost はボタン操作を受け取れないので、ボタンに頼ると 4 サービスで同じに動かない。
- URL を貼れば、何を誰に見せるかを要件 6 の規則が決める。`search` と `agent` に同じ規則を使える。
- **届け方の部品を 1 つにまとめる。** サービスと場所ごとの事情（Slack のスレッドの有無、Mattermost の権限、Discord）は部品の中で吸収し、呼ぶ側は「この人に届けて」とだけ言う。DM に切り替えた場合は、元の場所で何の依頼への答えかが分かるようにする（どう分からせるかは design で決める）。
- **待ち時間の表示**は、書き換えの要らない形にする（例: 本人にだけ「検索しています…」を出し、結果は別のメッセージで届ける。または元のメッセージにリアクションを付ける）。どれにするかは design で決める。

検討して採らなかった案:
- 誰でも見られるページだけで調べた結果をチャンネルに出し、本人の権限でしか見えない分は本人にだけ返す — 返事が 2 通に分かれる。ゲストの閲覧を許さない GROWI では、チャンネルに出せる結果がほぼ無くなる。
- 今のままチャンネルに出す（管理者がチャンネルごとに許可していることを、参加者を信頼する根拠とみなす）— 社外の人が入るチャンネルで漏れる。
- いつも DM で届ける — 仕組みは一番単純だが、チャンネルで頼んだ人がチャンネルを離れることになる。本人だけのメッセージが使える場所では使う。

## Scope

- **In**:
  - proxy の「本人にだけ届ける」部品（本人だけのメッセージ → 使えなければ DM、チャンネルには戻さない）
  - 今ある本人宛ての返事（`tell`、登録コード、`link` の URL、引数の聞き返し）をこの部品に通す
  - `search` の結果・検索中の表示・結果の注記（応答しなかった GROWI など）を本人にだけ届ける
  - 能力表と導入ドキュメントの関係する記述（Mattermost で管理者の権限を与えるかどうかの案内を含む）
  - 実機試験の手順（`docs/manual-e2e-slack.md`）の該当する行
- **Out**:
  - イベントの処理の外から、あとで届けること（`agent` の答え。`chat-integration-agent` が、この部品の上に足す）
  - `help` の届け方（GROWI が提供するコマンドの一覧で、閲覧権限に左右される内容を含まない）
  - `create-page` の成功の知らせ、URL の展開
  - 結果をチャンネルに共有する専用の仕組み

## Boundary Candidates

- **届け方の部品**（`platform/outbound.ts` の `postEphemeral` まわり）: サービスと場所ごとの手段の選択と、DM への切り替え
- **`search` の段取り**（`orchestration/command-flow.ts`）: 「いったん投稿して差し替える」から、本人にだけ届ける形への変更

## Out of Boundary

- GROWI 側の検索と権限の適用（要件 3.6・3.7）— 変えない
- 結果をチャンネルに共有したときに何を見せるか — 要件 6 と、backlog の「要件 6 の見直し」が扱う

## Upstream / Downstream

- **Upstream**: `chat-integration-proxy`（実装済み）の送信の層と、Chat SDK のアダプタ（Slack・Discord・Teams・Mattermost）
- **Downstream**: `chat-integration-agent` が、この部品を使って `agent` の答えを届ける（あとで届ける部分は `agent` 側で足す）

## Existing Spec Touchpoints

- **Extends**: `chat-integration`（要件 1・3）、`chat-integration-proxy`（送信の層、検索の段取り、能力表）
- **Adjacent**: `chat-integration-agent`（この部品を使う）。backlog の「要件 6 の見直し」（共有したときに何を見せるか）

## Constraints

- 要件 ID を振り直さない。足す受け入れ条件は各要件の末尾に付ける。
- この spec は amend spec なので、最後のタスクを「変更を対象の spec に書き戻し、この spec を削除する」にする（`.claude/rules/spec-lifecycle.md`）。
- 実装中は、対象の spec の本文に「後で変わる」といった注記を書き込まない。
- Chat SDK に触れてよいのは proxy の platform 層だけ（umbrella の決定 2）。
