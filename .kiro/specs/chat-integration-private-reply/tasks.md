# Implementation Plan

> amend spec。最後のタスク（7）は「変更を対象の spec に書き戻し、この spec を削除する」（`.claude/rules/spec-lifecycle.md`）。実装中は、対象の spec（umbrella・`chat-integration-proxy`）の本文に注記を書き込まない。
>
> 各タスクの終わりで、proxy の型の検査（spec ファイルを含む）が通る状態を保つ。

- [ ] 1. 土台: 共有の型と保存の形
- [ ] 1.1 本人宛ての返事の仕組みが使う結果の型と、依頼のメッセージの id をそろえる
  - 本人だけのメッセージ専用の結果（既存の投稿の結果に「このサービスには無い」を足したもの）、DM の結果（送れたなら DM のチャンネル）、リアクションの結果、使う絵文字の名前（受け付け・DM に届いた）の型を足す。既存の投稿の結果の型は変えない
  - 依頼の情報に、依頼のメッセージの id を省略可で足す（保存済みの行に無くても型が合う）
  - 完了の状態: 型の検査と既存の単体テストが通り、既存の投稿・差し替え・URL の展開の呼び出し側に変更が要らない
  - _Requirements: 1.2, 1.3, 1.5, 3.3_

- [ ] 1.2 聞き返しへの答えを DM でも受け付けられるよう、保留中の入力に「答えを受け付けるチャンネル」を持たせる
  - 保留中の入力の表に、答えを受け付けるチャンネル（null 可）と、(サービス, そのチャンネル, 本人) の索引を足す migration を作る
  - 「この入力への答えはこの DM でも受け付ける」と記録する操作を足す。同じサービス・同じ本人・同じ DM の別の保留中の入力からは、その経路を外す（新しい聞き返しが勝つ）。外すことと書くことは 1 つの transaction で行う
  - 保留中の入力を探す操作が、元のチャンネルに加えて「答えを受け付けるチャンネル」でも見つける。両方に当たるときは元のチャンネルの行を優先する
  - 保存済みの依頼の情報に、依頼のメッセージの id が無い行も読める
  - 完了の状態: 結合テストで、経路の記録・古い行の経路の解除・2 通りの探し方・元のチャンネルの優先・id の無い既存の行の読み込みがすべて確かめられ、既存の保存の結合テストも通る
  - _Requirements: 2.3_

- [ ] 2. platform 層の仕組み
- [ ] 2.1 本人だけのメッセージを、Chat SDK の共通の処理を通さずアダプタへ直接出す
  - チャンネルの id から、差し替えや URL の展開と同じ方法でスレッドの形の id を作り、それを宛先にしてアダプタの「本人だけのメッセージ」を呼ぶ（Mattermost で素のチャンネル id のせいで必ず失敗していた問題を直す）
  - アダプタにその機能が無いとき（Discord）は、DM に切り替えず「このサービスには無い」を返す
  - installation の指定（scope）を受け取り、その installation の接続から出す。例外を投げず、失敗は既存の分類で返す
  - 戻り値の型が変わるので、聞き返しの部品の 2 か所（値の聞き返しと GROWI の選択）で「無い」を「聞き返せない」として扱う。これは 3.4 で消える一時的な対応
  - 完了の状態: 単体テストで、Discord 相当のアダプタでは何も送らず「無い」が返ること、Mattermost 相当のアダプタにスレッドの形の id が渡ること、scope を渡せばその installation の接続が使われることが確かめられ、型の検査が通る
  - _Requirements: 1.2, 1.3_

- [ ] 2.2 本人への DM と、依頼のメッセージへのリアクションの仕組みを足す
  - 依頼が来たチャンネルからサービスと接続（scope があればその installation）を選び、本人との 1 対 1 の会話を開いて投稿する。送れたら DM のチャンネルを返す
  - 依頼のメッセージにリアクションを付ける。同じリアクションが既に付いている（Slack の already_reacted など）ときは成功として返す
  - どちらも例外を投げない。本人だけのメッセージ・DM・リアクションの 3 つを、platform 層の入口から使えるようにする
  - 試験用の偽のチャットサービスにも DM とリアクションを足し、送った DM と付けたリアクションを記録する
  - 完了の状態: 単体テストで、DM のチャンネルが返ること、DM を開けないときに失敗の理由が返ること、既に付いているリアクションが成功になることが確かめられ、platform 層の公開の一覧の試験と型の検査が通る
  - _Requirements: 1.3, 1.4, 1.5_

- [ ] 2.3 (P) mention のイベントに「DM の中か」と依頼のメッセージの id を載せる
  - mention のイベントの型に、「DM の中か」と「依頼のメッセージの id」を必須の項目として足す
  - Chat SDK のメッセージから mention を作るとき、スレッドが DM かと、メッセージの id を写す
  - 試験用の mention の部品と、mention を組み立てている各単体テストを新しい項目に合わせる
  - 完了の状態: 対応付けの単体テストで、DM のメッセージでは「DM の中」が真、チャンネルでは偽になり、どちらにもメッセージの id が載る。型の検査と既存の単体テストが通る
  - _Requirements: 2.3, 3.3_
  - _Boundary: event-mapping, platform-event types, testing chat-events_

- [ ] 2.4 本物のアダプタで、DM・リアクション・本文の形を確かめる結合テストを作る
  - 4 サービスの本物のアダプタを使い、送信先の HTTP だけを置き換える
  - Discord で本人だけのメッセージが「無い」になり、Chat SDK の自動の DM を通らない
  - Mattermost に proxy のチャンネル id を渡すと、本人だけのメッセージの API への要求が実際に出る。そのうえで API が 403 を返すと、DM の API に送られる
  - Mattermost で installation が 2 つ開いていても、scope を渡せばその installation の接続から出る
  - 4 サービスそれぞれで、DM を開いたときに返るチャンネルの id と、利用者がその DM に書いたときのイベントのチャンネルの id が一致し、保存の検査がその id を受け付ける
  - 同じリアクションを 2 回付けても成功が返る。Teams でリアクションを付けられるかを記録する
  - 各サービスの DM のイベントで「DM の中」が真になり、本文の先頭に bot への呼びかけがどう表れるかを記録する（3.1 の規則の根拠にする）
  - 完了の状態: 結合テストがすべて通り、Teams のリアクションの可否と DM の本文の先頭の形が試験の中に事実として残る。id が一致しないサービスがあれば、その時点で止めて design の見直しに戻す
  - _Depends: 2.1, 2.2, 2.3_
  - _Requirements: 1.2, 1.3, 1.4, 1.5, 2.3_

- [ ] 3. command 層: 本人宛ての返事の判断と、聞き返し
- [ ] 3.1 DM で打たれた文の先頭の語を、呼びかけとして落とさない
  - コマンドの解釈と聞き返しへの答えの取り出しで、DM の中では先頭の語を残す。DM でも先頭が bot への呼びかけ（2.4 で確かめた形）なら落とす
  - 依頼のメッセージの id を依頼の情報に写す（slash command では無し）
  - 完了の状態: 単体テストで、DM の「search foo」はコマンド名 search として読まれ、DM での答え「foo bar」が欠けずに取り出され、チャンネルの mention の扱いは変わらないことが確かめられる
  - _Requirements: 2.3_

- [ ] 3.2 (P) 本人宛ての返事の届け方を決める部品を作る
  - 本人だけのメッセージ → 失敗または「無い」なら本人への DM → DM が届いたら依頼のメッセージに封筒のリアクション（付けられなければ内容を含まない短い文）の順で届ける
  - DM の本文は「<場所> での「<依頼>」への返事です」という見出しと、元の返事そのもの。場所の名前は渡された関数で引き、引けなければ「元のチャンネル」
  - DM も送れなければ、内容を含まない「届けられなかった」知らせ（本人の表示名と、DM を受け取れる設定かを確かめ、だめなら運用者に連絡してほしいという案内）をその場に出し、サービス名・チャンネルの id・2 つの失敗の理由だけを運用者向けに報告する。知らせの投稿も失敗したら報告だけ残す
  - 受け付けの知らせ: 依頼のメッセージに目のリアクションを付け、付けられない・メッセージが無いときは、呼び出し元が渡した文を本人宛ての返事として届ける
  - installation は依頼の情報にあればそれを、無ければ渡された関数で依頼のチャンネルから引き、すべての platform の呼び出しに同じ scope として渡す
  - 例外を投げない。返事の内容を全員に見える投稿に渡さない
  - command 層の公開の入口から部品の作成関数と型を公開し、公開の一覧の試験を更新する
  - 完了の状態: 単体テストで、失敗の組み合わせ（本人だけのメッセージ 成功・失敗・無い × DM 成功・失敗 × 知らせ 成功・失敗 × 依頼のメッセージ 有り・無し）のすべてについて、返事の内容が全員に見える投稿に一度も渡らず、見出し・知らせ・報告・scope が設計どおりであることが確かめられる。同じ依頼から 2 通目が DM に届いても短い文が出ないことも確かめられる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7, 1.8, 2.2, 3.3, 3.4_
  - _Boundary: PrivateReplier, command index_
  - _Depends: 2.2_

- [ ] 3.3 本人宛ての返事の部品を、実行時の組み立てで作る
  - 実行時の組み立てで部品を作る。場所の名前は、既存の installation の引き当てと保存済みのチャンネル一覧の行のチャンネル名から引く（新しい repository は作らない）。運用者への報告は既存の報告の関数に渡す
  - 場所の名前の引き当ては、installation の一覧とチャンネルの一覧を引数で受け取る小さな関数として切り出し、単体テストの対象にする
  - この時点では、まだどの流れにも渡さない（3.4・4.1・4.3 がそれぞれ自分の流れに渡す）。3.4 で使われるまでの間、使われていない値として lint の警告が出るのは許容する
  - 完了の状態: 場所の名前の引き当ての単体テストで、保存済みのチャンネル一覧から名前が引け、一覧に無いチャンネルでは名前が無いと返ることが確かめられ、型の検査が通る
  - _Requirements: 1.7, 1.8_

- [ ] 3.4 引数の聞き返しを本人宛ての返事の部品で出し、DM での答えを受け付ける
  - 値の聞き返し・答えの検証の失敗・GROWI の選択・前の入力を取り消した知らせの 4 か所を、本人宛ての返事の部品で出す（2.1 の一時的な対応はここで消える）
  - 「本人だけのメッセージが使えないサービスでは聞き返せない」という事前の断りをやめ、部品が「届けられなかった」を返したときだけ聞き返せないで終える
  - 聞き返しが DM に届いたら、その DM を答えを受け付けるチャンネルとして記録する。答えは元のチャンネルでも DM でも受け付け、DM の文は先頭の語を残して読む
  - 聞き返しの部品が受け取る platform の操作をモーダルを開くことだけに絞り、実行時の組み立てで本人宛ての返事の部品を渡す
  - 完了の状態: 単体テストで、DM で聞き返したら答えの経路が記録され、DM での答えで元の依頼が進み、同じ DM に 2 つ目の聞き返しが届いたら DM での答えは新しいほうに渡ることが確かめられる。型の検査が通る
  - _Depends: 1.2, 3.1, 3.3_
  - _Requirements: 2.1, 2.3_

- [ ] 4. orchestration 層と能力表
- [ ] 4.1 コマンドの流れの本人宛ての返事を、本人宛ての返事の部品に寄せる
  - 本人宛ての返事（紐付けの案内、許可されていないことの案内、エラー、URL の展開で GROWI を選べなかった説明、入力の期限切れの知らせ、ヘルプの仮の投稿に失敗したときの経路）を部品で出す
  - 依頼の要約は「コマンド名 + 引数の 1 行目」を 80 文字で切ったもの。installation は既に引いた値を渡し、まだ引けていない段階では無しで渡す
  - 実行時の組み立てで、コマンドの流れに本人宛ての返事の部品を渡す
  - 完了の状態: 単体テストで、これらの返事が部品を通り、依頼の要約が 80 文字で切られ、ヘルプ・ページ作成の成功の知らせ・URL の展開が今どおりチャンネルに出ることが確かめられる。型の検査が通る
  - _Requirements: 2.1, 5.1_
  - _Depends: 3.3_

- [ ] 4.2 検索の結果を本人にだけ届ける
  - チャンネルへの「検索しています…」の投稿と差し替えをやめ、受け付けの知らせ（目のリアクション、付けられなければ本人宛ての「「…」を検索しています…」）を出す
  - 結果か「結果は得られませんでした」と注記を、1 通の本人宛ての返事で届ける。並べ方と注記の文は変えない
  - コマンドの流れが受け取る platform の操作から、本人だけのメッセージを外す
  - 完了の状態: 単体テストで、検索がチャンネルへの投稿も差し替えも一度も呼ばず、結果と注記が本人宛ての返事 1 通で届き、その中身が変更前と同じ並べ方・注記であることが確かめられる
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5_

- [ ] 4.3 管理コマンドの本人宛ての返事を、本人宛ての返事の部品に寄せる
  - 本人宛てに返している管理コマンドの返事（登録コードなど）を部品で出す。チャンネルに出している返事（unregister・weight・rotate-key）は今どおり
  - 管理コマンドの流れが受け取る platform の操作をチャンネルへの投稿だけに絞り、実行時の組み立てで部品を渡す（4.1・4.2 と同じ実行時の組み立てのファイルを変えるので、並行させない）
  - 完了の状態: 単体テストで、本人宛ての返事は部品を通り、チャンネル向けの返事は今どおりチャンネルに出ることが確かめられる。型の検査が通る
  - _Requirements: 2.1, 5.1_

- [ ] 4.4 (P) 能力表に、本人宛ての返事の届き方を書く

  - 本人への DM の行を足す（4 サービスとも使える）
  - 完了の状態: 能力表の単体テストが新しい行と値で通り、GROWI へ送る能力の報告に DM の行が含まれる

- [ ] 6. 運用者向けの説明
- [ ] 6.1 (P) Slack の導入の説明と実機試験の手順を直す
  - マニフェストに DM を開く権限（im:write）と、利用者が bot との DM に書き込める設定（App Home の Messages タブ）を足す。導入済みの workspace は導入し直す必要があることを書く
  - 「Slack の DM に書いてもコマンドは起動しない」を、DM での聞き返しへの答えは受け付け、DM で打ったコマンドは「workspace が登録されていない」と返る、という今の振る舞いに書き換える
  - 実機試験の表に、検索の結果が本人にだけ見えること、DM に落ちる場合（封筒のリアクション）、DM の聞き返しに DM で答えて元の依頼が進むこと、im:write の無い導入では内容を含まない知らせになることを足す
  - 完了の状態: 2 つの文書のマニフェストと説明が design と一致し、手順どおりに導入すれば DM の権限と設定がそろう

  - _Boundary: docs Slack_

- [ ] 6.2 (P) Mattermost・Discord・Teams の導入の説明を直す

  - Teams: 本人だけのメッセージは 24 時間で消えること、DM には利用者が一度 bot に呼びかけている必要があること、1 対 1 の会話で答えるのに personal の範囲が要るかは未確認であること
  - 完了の状態: 3 つの文書に、本人宛ての返事がどこに届くかと、そのために用意するものが書かれている
