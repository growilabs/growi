# Research: g2g-transfer-migration-mode

対象: `.kiro/specs/g2g-transfer-migration-mode/requirements.md`
実施日: 2026-08-04(gap 分析)〜2026-08-05(design のレビュー)。Discovery の種別: **Extension（light）**。既存の G2G 転送パイプラインへの拡張であり、新しい外部依存も新しいライブラリも導入しない。

---

## 1. 現状の調査で判明した事実(設計判断に直結するもの)

- **取り込み方法のサーバ側検証は `configs` だけ。** `users` の置き換えを禁じているのはクライアントの `MODE_RESTRICTED_COLLECTION` だけで、サーバは受け取った指定をそのまま実行する。押す側は任意の指定を送れてしまう。
- **転送対象コレクションのサーバ側検証も実質無い。** ルートのバリデータは `body('collections').isArray()` のみ。除外リストはクライアント側の定数で、`transferkeys` はそこにも入っていなかった。
- **転送前チェックの置き場所は既にあるが、確認 UI には一段足りない。** `getTransferability` は POST `/g2g-transfer/transfer` の内側で走るため、「確認するまで生成も送信もしない」を満たすには押す前に取得する経路が要る。
- **可否は 2 値で、警告のチャネルが無い。** `Transferability` は `{canTransfer:true} | {canTransfer:false, reason}`。「警告するが続行できる」を表せない。既存の `reason` は未 i18n(`// TODO: i18n for reason` が 7 箇所)。
- **保守モードは G2G の受信経路を塞がない。** `unavailableWhenMaintenanceModeForApi` は `apiV3Router` にのみ適用され、`/g2g-transfer/*` は `apiV3AdminRouter` 配下なので保守モード中でも受信できる。
- **取り込みは実際には並行（コメントは逆のことを書いている）。** `import.ts` は `// process serially so as not to waste memory` とコメントしながら `collections.map(...)` で全コレクションの取り込みを同時に起動し、`for await` は待つだけ。この読み直しが、後述の D2(直列化しない)で gap 分析の当初の想定（要件 4.8 は並行取り込みと噛むので設計の山）を上書きした。`import()` はコレクション単位の例外を内部で捕捉して正常終了するため、救済の再投入を `import()` の後に必ず実行する位置に置けば順序制御は不要と分かった。
- **置き換えは `deleteMany({})`（`drop` ではない）。** 索引は残るので、置き換え後も一意制約はそのまま効く。
- **救済に使える素材は揃っている。** `admin` フラグと `apiToken`、`User.findAdmins()`、パスワードは `sha256(PASSWORD_SEED + password)` で種は環境変数(設定の置き換えでは変わらない)、移行元 username 抽出は `detect-unique-conflicts.ts` に実装済み。
- **セッションは既定で MongoDB(connect-mongo)。** 転送対象からは除外済みだが、移行先の古いセッションは転送後も残るため明示的な削除が要る。
- **衝突検知は取り込み設定を受け取らない。** `detectImportConflicts(innerFileStats)` のみで、置き換え対象集合を渡す拡張が要る。
- **`configs` の一部を移行先の値に戻す枠が既にある。** `importCollections` が `UPLOAD_CONFIG_KEYS` を退避・復元しており、サイト URL はこの枠に鍵を 1 つ足す形で実現できた。

## 2. 実装方針の選択と却下案

`service/g2g-transfer.ts` は着手時点で既に 858 行あり、coding-style の 800 行上限を超過していた。救済・保守モード・キー保護をそのまま同じファイルに足す(Option A)と単体試験がしにくく肥大が進むため、**純関数として切り出す(Option C: ハイブリッド)を採用**した。

- **純関数として切り出す**: preset の組み立て、救済後のドキュメント算出、警告の算出、置き換え対象集合の算出。
- **既存を拡張する**: `answerGROWIInfo`、`getTransferability`、`importCollections`、検知(置き換え集合を引数で受ける)。
- 2 段階(モードに依らない修正が先、preset 本体が後)に分けたのも、単独で出荷できる価値の単位を切るための判断。

**転送前の確認をどう実現するかの却下案**: POST `/transfer` を「確認フラグの有無で 2 つの意味を持たせる」形は、同じ URL が 2 つの意味を持ち要件 3.3(確認しなければ無変更)の検証も分かりにくくなるため却下し、押す側に独立した preflight エンドポイントを足す案を採った。

## 3. レビューで決着した設計判断と却下した代替案

design のレビューは 11 巡(sonnet 3 巡・opus 8 巡)を要した。骨格(D1〜D10)への反証は 3 巡目以降 1 件も出ておらず、4 巡目以降に出た指摘はすべて「設計が新しく作る値・状態が、既存コードや通信経路の実行時の前提と噛み合うか」という一貫した種類だった。ここでは決着した判断と、それぞれで実際に却下した代替案を記録する(採用した最終形は design.md に反映済みなので重複させない)。

### 引っ越しモードから選択肢を取り除く

コレクションごとの取り込み方法だけを preset で決め、対象選択は操作者に任せる案を最初に検討したが、`users` を対象から外して `usergrouprelations` だけを置き換える指定が残ってしまい、要件 2.2(グループ公開ページの閲覧)が壊れる。「依存するコレクションは一括で選ぶ」規則を足して塞ぐ案も検討したが、**規則を積むほど操作者に理解を要求することになる**ため、ユーザー判断で「引っ越しモードから自由度そのものを取り除く」方向へ切り替えた(design.md D1)。

### 取り込み中の保護の仕組み

当初は「取り込み中の保護をプロセス内の状態で持ち、middleware がそれを見る」独自モジュール(`service/serving-suspension.ts`)を新設する案を作ったが、次の 2 点でユーザーに却下された。

1. 利用者が G2G しかないのに汎用の口を作っていた(単純化の原則に反する)。
2. 独自概念でトリッキーであり、既存の概念(保守モード)で済むならそのほうがよい。

採用した形は、既存の保守モードを流用し、設定コレクションの取り込み直後に立て直す方式(design.md D5)。判定の仕組み(`isMaintenanceMode()` と middleware)は一切変更しない。`AppService` に取り込み固有の変数を置く案も、置き場所として誤りだったため破棄した。

### 転送キーの寿命(D10)

転送キーは作成時刻から 30 分で TTL 失効し、延長する処理がどこにも無かった(この事実自体は 7 巡目まで気づかれず、6 巡目までの GO 判定はここを見落としていた)。試験方法として「`expireAt` を直接過去へ寄せる」案を検討したが、寄せた文書は TTL の掃除(約 60 秒周期)で消え、消えた文書は延長できないため守りたい場面を一度も通らないと分かり、却下。**「寿命より長くかかる取り込みを作り、その間にキーが生き残ることを見る」形を採用した。**

### セッション無効化の手段

「store API(`all`/`destroy`)だけを使う。Redis 構成でも動く」という当初案は誤りで、`connect-mongo` の `all()` はセッション ID を返さないため既定構成でこそ動かなかった。`{ store, sessionsCollection? }` という 1 つの型に両対応を詰める案も検討したが、Redis 構成で `sessionsCollection == null` になり判定が二重化するため却下し、種類で分けた判別可能な型(`SessionAccess`)を採用した。

### レビューで見つかった実害の要点

11 巡のレビューを通じて、次の実害が段階的に見つかり、設計に反映済み(詳細は design.md)。**転送キーが作成から 30 分の TTL で失効し延長処理が無かった**こと、**保守モードの起動条件が置き換え対象集合の空でなさだけだと従来モードでも常に真になってしまう**こと、**セッション無効化を store API だけで実装すると既定構成(MongoDB)でこそ動かない**こと、**救済の一意フィールドに `slackMemberId` が漏れていた**こと、**保守モードの解除判断が救済の失敗を見ていなかった**こと。いずれも「同じ状態(旗・キーの寿命・一意フィールドの集合)に触る経路のうち 1 本しか直っていない」という共通の失敗パターンだったため、design.md に「状態ごとの経路の棚卸し」の表を追加して以後の再発を防いだ。

## リスクと未確定事項(設計時点)

- 既存の中断事由の文言が未翻訳(`// TODO: i18n for reason` が 7 箇所)。新しい警告を英語で追加し、体裁を揃える方針とした。他言語は後続タスク。
- `_id` の衝突(移行先の管理者と移行元のユーザー)は極めて低い確率だが、重複挿入は失敗する。新しい `_id` で救済し、セッションが失われることを通知する方針とした。
- 移行先のストレージに残る旧添付は参照されない状態で残る(要件の対象外)。
- 設定を空にしてから書き戻すまでの窓、取り込み中のプロセス停止、複数プロセス構成での同時実行の拒否漏れは、上限を設ける手段が無いリスクとして受け入れた(design.md の該当節を参照)。
