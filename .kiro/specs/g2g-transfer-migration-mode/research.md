### 規約と依存の向き

- 受信側は転送キーだけで認証する（`validateTransferKey`）。ユーザーセッションを必要としない。
- 検知の中核は I/O を持たない純関数、その外周に薄いアダプタという構成が既に入っている（`g2g-import-conflict-detection` で確立）。本 spec もこの向きを踏襲できる。
- coding-style の「モード名で分岐しない」「実行する側は対象集合を引数で受け取る」に沿う形が、要件 1 の「受信側にモードの概念を持たせない」と一致する。
- 結合試験は実 DB（レプリカセット rs0）。`detect-unique-conflicts.integ.ts` / `g2g-transfer.integ.ts` が手本。

### 統合面（今回効いてくる既存の接点）

- **押す側には既に転送前チェックがある**。`routes/apiv3/g2g-transfer.ts:802-822` が `askGROWIInfo(tk)` → `getTransferability(destGROWIInfo)` を実行し、不可なら `growi_incompatible_to_transfer` で**アーカイブ生成前に**中断する。`startTransfer` はその後に fire-and-forget で走る。
- `answerGROWIInfo()`（受信側）は version / userUpperLimit / fileUpload 関連 / attachmentInfo を返す。
- `importCollections()` は取り込みの前後でファイルアップロード設定を退避・復元している（`service/g2g-transfer.ts:861-881`）。
- 保守モードは `middlewares/unavailable-when-maintenance-mode.ts`、切り替えは `service/app.ts` の `startMaintenanceMode` / `endMaintenanceMode`。

## 2. 調査で判明した事実（設計判断に直結するもの）

### F1. 取り込み方法のサーバ側検証は `configs` だけ

`import.ts` の `validateImportSettings` は `configs` に置き換えを強制する分岐しか持たない。**`users` の置き換えを禁じているのはクライアントの `MODE_RESTRICTED_COLLECTION`（`users: ['insert','upsert']`）だけ**で、サーバは受け取った指定をそのまま実行する。

- 要件 2 にとっては朗報で、置き換えを可能にするのにサーバ側の解禁は要らない。
- 同時にリスクでもある。現状、押す側は任意の指定を送れる（サーバ側のガードが無い）。

### F2. 転送対象コレクションのサーバ側検証も実質無い

ルートのバリデータは `body('collections').isArray()` のみ。`IGNORED_COLLECTION_NAMES`（`sessions` / `rlflx` / `activities` / `attachmentFiles.*`）は**クライアント側の定数**で、`transferkeys` はそこにも入っていない。

→ 要件 5.1（転送キーを失わせない）は、クライアントの除外リストに 1 行足すだけでは満たせない。**受信側で拒否する**必要がある。

### F3. 転送前チェックの置き場所は既にあるが、確認 UI には一段足りない

`getTransferability` は POST `/g2g-transfer/transfer` の**内側**で走る。要件 3 は「操作者が確認するまで生成も送信もしない」なので、確認のための情報を**押す前に**取得する経路が要る。選択肢は 2 つ（後述の Option 参照）。

### F4. 可否は 2 値で、警告のチャネルが無い

`Transferability` は `{canTransfer:true} | {canTransfer:false, reason}`。要件 3.4 / 3.5 は「警告するが続行できる」なので、`canTransfer:false` を流用すると転送が止まってしまう。**警告の配列を返す形への拡張が必要**。既存の reason は i18n されていない（`// TODO: i18n for reason` が 7 箇所）ので、新しい警告を i18n するなら既存との不整合が見える。

### F5. 保守モードは G2G の受信経路を塞がない

`unavailableWhenMaintenanceModeForApi` が適用されているのは `apiV3Router`（`routes/index.js:207`）だけ。`/g2g-transfer/*` は `apiV3AdminRouter`（同 88 行）に載っており、**保守モード中でも受信できる**。

→ 要件 2.4 は既存機構で実現でき、保守モードを入れても転送自体は止まらない。

### F6. 取り込みは実際には並行（コメントは逆のことを書いている）

`import.ts:152-171`:

```ts
// process serially so as not to waste memory
const promises = collections.map((collectionName) => { ... return this.importCollection(...); });
for await (const promise of promises) { ... }
```

`.map()` の時点で全コレクションの取り込みが**起動する**。`for await` は待つだけなので直列にならない。

→ 要件 2.1（取り除いてから取り込む）自体はコレクション単位で閉じるので並行でも成立するが、要件 4.8（途中で失敗しても管理者が残る）は順序保証を必要とする。ここが本 spec で唯一「既存の取り込み挙動に触れる」候補。

### F7. 置き換えは `deleteMany({})`（drop ではない）

`import.ts:219-220`。索引は残るので、置き換え後も一意制約はそのまま効く。

### F8. 救済に使える素材は揃っている

- `admin: { type: Boolean, default: 0, index: true }`、`apiToken: { type: String, index: true }`
- `userSchema.statics.findAdmins`（`find({ admin: true, status: {...} })`）
- パスワードは `sha256(crowi.env.PASSWORD_SEED + password)`（`generatePassword`）。種は**環境変数**なので設定の置き換えで変わらない → 要件 4.2 はハッシュをそのまま持ち越すだけで満たせる。
- 移行元アーカイブの username 抽出は `detect-unique-conflicts.ts` に実装済み → 要件 4.4 の「移行元に存在しない名前」を保証付きで選べる。

### F9. セッションは MongoDB（connect-mongo）

`crowi/index.ts:433-434` で `MongoStore.create(...)`。`sessions` は G2G の転送対象から除外済みだが、**移行先の古いセッションは転送後も残る**。要件 5.5 は明示的な削除が要る。同時に、要件 4.3（救済アカウントのセッションが生きる）と両立させるため、削除は「救済対象以外」に限定する必要がある。

### F10. 衝突検知は取り込み設定を受け取らない

`detectImportConflicts(innerFileStats)` のみ。要件 2.3（置き換え対象では中断しない）を満たすには、**置き換えられるコレクションの集合を引数で渡す**形への拡張が要る。これは coding-style の「実行する側は対象集合を引数で受け取る」に沿う変更で、純関数の設計とも整合する。

### F11. `configs` の一部を移行先の値に戻す枠が既にある

`importCollections` が `UPLOAD_CONFIG_KEYS` を退避 → 取り込み → 復元している。要件 5.4（サイト URL を移行先の値に保つ）は、この枠に鍵を 1 つ足す形で実現でき、新しい仕組みを作らずに済む。

## 4. 実装方針の選択肢

### Option A: 既存コンポーネントの拡張のみ

`G2GDataTransferExportForm` に preset、`getTransferability` に警告、`importCollections` に救済と保守モードを足す。

- ✅ 新規ファイルが少なく、既存の流れに沿う
- ✅ 受信側の入口が 1 つのままで追いやすい
- ❌ `service/g2g-transfer.ts` は既に 858 行で、coding-style の 800 行上限を超過済み。救済・保守モード・キー保護を足すとさらに膨らむ
- ❌ 救済（退避・付け替え・再投入）は独立した関心で、取り込みの orchestration に混ぜると試験しにくい

### Option B: 新規モジュールに切り出す

`preset を組み立てる純関数`・`救済（rescue-destination-admins）`・`転送前の点検（preflight）` をそれぞれ独立モジュールにし、既存は呼び出しに徹する。

- ✅ 救済を純粋な入出力（既存管理者 + 移行元 username 集合 → 救済後のドキュメント）として単体試験できる
- ✅ `g2g-transfer.ts` の肥大を止められる
- ❌ ファイルが増え、受信フローの全体像が 1 ファイルで読めなくなる
- ❌ 保守モードの入切は結局サービス層に残るので、完全な分離にはならない

### Option C: ハイブリッド（推奨）

- **純関数として切り出す**: preset の組み立て（選択 → optionsMap）、救済後のドキュメント算出（付け替え・email 除去の決定）、警告の算出（種の一致・SSO 管理者の有無 → 警告一覧）
- **既存を拡張する**: `answerGROWIInfo`（件数と種の指紋を追加）、`getTransferability`（警告を返す形へ）、`importCollections`（救済と保守モードの呼び出し）、検知（置き換え集合を引数で受ける）
- **新規に足す**: 受信側の転送対象ガード（転送キーの拒否）、セッション無効化

段階は 2 つに割れる。**第 1 段（モードに関係なく必要な 3 件＝検知の置き換え対応・転送キーのガード・種の警告）**は引っ越しモードの有無と独立に価値があり、先に出せる。**第 2 段（preset・置き換え・救済・保守モード・確認 UI）**が本体。

## 5. 転送前の確認をどう実現するか（要件 3 の分岐点）

| 案 | 内容 | 評価 |
|---|---|---|
| 案 1: preflight エンドポイントを足す | 押す側に「転送キーを渡すと、移行先の件数と警告一覧を返す」API を追加。クライアントが確認モーダルを出し、承知後に既存の POST `/transfer` を呼ぶ | 既存 POST の意味を変えない。`askGROWIInfo` をそのまま再利用できる。エンドポイントが 1 本増える |
| 案 2: POST `/transfer` を 2 段階にする | 確認フラグが無い呼び出しでは開始せず要約を返し、フラグ付きで実行 | エンドポイントは増えないが、同じ URL が 2 つの意味を持つ。要件 3.3（確認しなければ無変更）の検証も分かりにくくなる |

案 1 を推奨する。押す側は既に `askGROWIInfo` を持っており、`getTransferability` を「可否 + 警告 + 移行先の状態」を返す形に拡張すれば、POST `/transfer` 側は最終確認として同じ判定を再実行するだけで済む（クライアントの表示と実行の間に移行先が変わっていても、実行時の判定が効く）。

## 6. 複雑さとリスク

| 項目 | 規模 | 備考 |
|---|---|---|
| 第 1 段（検知の置き換え対応・キーのガード・種の警告） | S（1〜3 日） | 既存パターンの延長。単独で出せる |
| preset と UI の出し分け | S〜M | 混在を到達不能にする範囲をどこまでサーバで担保するかで変わる |
| 置き換え + 保守モード | M（3〜7 日） | 失敗時に保守モードが解除されない状態を作らないこと |
| 管理者の救済 | M | 要件 4.8（失敗時保証）が F6（並行取り込み）と噛む。ここが設計の山 |
| 実 DB 検証 | M | 作業量の本体。ログイン可否の検証は新規 |

### 主なリスク

1. **要件 4.8 と並行取り込みの噛み合わせ**（F6）。全コレクションが同時に走るため、`users` の取り込み完了を待って救済を再投入する制御が要る。取り込み全体を直列化するか、`users` だけ順序を保証するかは design の判断。直列化は所要時間に影響する。
2. **保守モードの解除漏れ**。転送が異常終了したときに移行先が保守モードのまま残ると、管理者が救済アカウントで入っても解除操作が要る。解除が保守モードの影響を受けない経路であることの確認が必要（`app-settings` 側は `apiV3Router` 配下＝保守モードで塞がる可能性がある。要調査）。
3. **サーバ側ガードの不在**（F1 / F2）。今は押す側の指定を受信側が信用している。preset を導入しても、受信側で「置き換えと追加の混在」「転送キーの上書き」を拒否しないと要件 1.3 / 5.1 は形骸化する。
4. **`getTransferability` の既存 reason が未 i18n**。新しい警告を i18n すると、同じ画面に訳された文と英語の生文字列が混在する。既存 spec でも同種の退行（見出しだけ翻訳され本文が英語）を踏んでいるので、表示の作り方は揃えたい。

## 7. Research Needed（design で決めること）

- 取り込みを直列化するか、`users` の完了だけを待つか。直列化した場合の所要時間への影響。
- 救済の再投入をどの層で行うか（`importCollections` の中 / 受信ルート）と、取り込みが失敗しても必ず走らせる方法。
- 保守モードの解除経路が保守モード自身に塞がれないか（`app-settings` のマウント先を確認する）。
- 種の指紋の作り方（そのまま比較しないための一方向変換）と、それを `growi-info` に載せることの妥当性。
- `email` の `required` 指定の有無（外した状態で救済できるか）。
- 移行先に残すべき `configs` の鍵が `app:siteUrl` 以外にもあるか（`UPLOAD_CONFIG_KEYS` の隣に置く形で足せる）。
- 混在の禁止をサーバ側でどこまで検証するか（preset 名を送らない方針との両立）。

# Discovery & Synthesis（design フェーズ、2026-08-05）

Discovery の種別: **Extension（light）**。既存の G2G 転送パイプラインへの拡張であり、新しい外部依存も新しいライブラリも導入しない。

## gap 分析で「要調査」としていた項目の決着

| 項目 | 結果 |
|---|---|
| 保守モードの解除経路が保守モード自身に塞がれないか | **塞がれない**。`app-settings` は `routes/apiv3/index.js:102` で `routerForAdmin` に載り、`routerForAdmin` は `routes/index.js:88` で保守モードの middleware を通さずマウントされる。`/g2g-transfer/*` も同じ側。したがって保守モード中でも転送を受けられ、解除もできる |
| `email` の `required` 指定 | **無い**。`email: { type: String, unique: true, sparse: true }`。外した状態で救済できる。一方 `username: { type: String, required: true, unique: true }` なので、付け替えは必須で空にはできない |
| 移行先に残す設定キーの置き場所 | 既存 `UPLOAD_CONFIG_KEYS`（`service/g2g-transfer.ts:51`）と同じ形で宣言する。ただしアップロード設定は `app:fileUploadType !== 'none'` の条件付きで復元されるのに対し、サイト URL は無条件で残すため、同じ定数に混ぜず別の宣言にする |
| 取り込みの直列化 | **不要と結論**（下記 D2） |
| 救済の再投入をどの層で行うか | 受信サービスの `importCollections` の内部。純粋な算出は `service/import/rescue-admins.ts` に分離する |
| 種の指紋の作り方 | Node 標準 `crypto` の sha256。既存 `generatePassword` と同じ標準ライブラリで、追加依存なし |
| 混在の禁止をサーバ側でどこまで検証するか | 押す側と受信側が**同じ純関数**で検証する（`isCoherentOptionsMap`）。preset 名は wire に乗せない |

## Synthesis

### 1. 一般化

- 要件 3.1 / 3.4 / 3.5 は「転送を始める前に移行先を点検して、止める・警告する・知らせる」という 1 つの能力の 3 つの現れ。既存の `getTransferability` が「止める」だけを扱っているので、**中断事由と警告の 2 段を返す判定**に一般化した。
- 要件 5.3 / 5.4 は「移行先固有の設定は置き換えの対象外」という 1 つのルールの 2 例。既存のアップロード設定の退避・復元を、**移行先の値を保つ設定キーの宣言**として一般化した。
- 要件 1.3 / 2.3 / 4.1 はいずれも「どのコレクションが置き換えられるか」という 1 つの事実から導かれる。**置き換え対象集合を単一の入力**として渡す形にした（受信側にモードを持たせない設計の核）。

### 2. 採用 vs 自作

| 関心 | 判断 |
|---|---|
| 保守モード | 既存の `app:isMaintenanceMode` + `AppService` を採用。自作しない |
| 管理者の列挙 | 既存の `User.findAdmins` を採用 |
| 救済後のログイン検証 | 既存の `isPasswordValid` を採用（結合試験で使う） |
| 移行元 username の抽出 | 既存 `detect-unique-conflicts.ts` の抽出を再利用。再実装しない |
| セッションの破棄 | express-session の store API（`all` / `destroy`）を採用。MongoDB の `sessions` を直接触る実装は却下（移行先が Redis 構成のとき動かないため） |
| 種の指紋 | Node 標準 `crypto`。専用ライブラリは不要 |

### 3. 単純化

- 受信側に「モード」の型を持ち込まない（型が 1 つ減り、分岐が生まれない）。
- 点検は新規エンドポイント 1 本（押す側の preflight）に留め、受信側は既存 `growi-info` の拡張だけにする。2 段階 POST 案は却下（同じ URL が 2 つの意味を持ち、要件 3.3 の検証も分かりにくくなる）。
- ロールバック用アーカイブは作らない（要件になく、救済で目的が満たされる）。

## 設計判断（design.md の D1〜D5 の根拠）

- **D2（直列化しない）が gap 分析の結論を上書きした。** research の前半では「要件 4.8 は並行取り込みと噛むので設計の山」と書いたが、`import.ts:152-171` を読み直すと `import()` は**コレクション単位の例外を内部で捕捉して続行し、正常終了する**。したがって救済の再投入を `import()` の後に必ず実行する位置に置けば、個々のコレクションの失敗では管理者が失われない。順序制御も直列化も不要で、所要時間も変わらない。
  - 残る穴: プロセスが落ちた場合は救済が走らない。転送キーが残るため転送の再実行で復旧できる。
  - 注意: `import()` の catch は `err.collectionProgress` を前提にしているため、それ以外の例外は外へ抜ける。救済と保守モード解除は「例外が抜けた場合も実行される位置」に置く必要がある。
- **D1（preset を wire に乗せない）** は coding-style の「モード名で分岐せず宣言されたメタデータで判断する」に対応する。
- **D4（store API 経由）** は、セッションストアが Redis と MongoDB の 2 系統ある（`crowi/index.ts:425-437`）ことから決まった。`store.all` を提供しないストアでは破棄を行わずログに残す。
- 削除済みユーザーのセッションを残すと `deserializeUser` が例外になり（`service/passport.ts:1195-1207`）、そのブラウザは匿名に落ちずリクエストが失敗し続ける。破棄する方が体験として良い、という判断でセッション破棄を要件どおり実装する。

## リスクと未確定事項

- 既存の中断事由の文言が未翻訳（`// TODO: i18n for reason` が 7 箇所）。新しい警告を英語で追加し、体裁を揃える。他言語は後続タスク。
- `_id` の衝突（移行先の管理者と移行元のユーザー）は極めて低い確率だが、重複挿入は失敗する。新しい `_id` で救済し、セッションが失われることを通知する方針とした。
- 移行先のストレージに残る旧添付は参照されない状態で残る（要件の対象外）。

# レビュー後の方針変更（2026-08-05）

サブエージェント 2 体（アーキテクチャの裏取り / 要件網羅）によるレビューで、要件を満たせない箇所 2 つと既存の転送を壊す箇所 1 つが出た。設計を次の 3 点で作り直した。

## 変更 1: 引っ越しモードから選択肢を取り除く（ユーザー判断）

**当初**: コレクションごとの取り込み方法だけを preset で決め、どのコレクションを転送するかは操作者の選択に任せていた。

**問題**: 取り込み方法だけを縛っても、`users` を選択から外して `usergrouprelations` だけを置き換える選択が残る。置き換え後の関係が存在しないユーザーを指し、要件 2.2（グループ公開ページが閲覧できる）が破れる。`externalaccounts` を外せば「引っ越しなら SSO の衝突は原理的に発生しない」という Out of Boundary の根拠も崩れる。当初はこれを「依存するコレクションは一括で選ぶ」規則を足して塞ごうとした。

**ユーザーの判断**: 規則を積むと、規則の数だけ操作者に理解を要求することになり、機能の挙動が掴めなくなる。**引っ越しモードから自由度を取り除く**方向で解く。

**結果**: 引っ越しは「転送可能なコレクションすべてを置き換える」1 通りに固定し、対象選択も方法選択も操作者に見せない。依存グループの規則も混在の規則も操作者からは消える（システムが常に満たす）。従来モードは今の自由度をそのまま残し、新しい規則を適用しない。失うのは「引っ越しで一部だけ移す」ことだけで、必要なら従来モードを使う。

## 変更 2: 整合条件から強制モードのコレクションを除く

「すべて置き換え」か「置き換えを含まない」の 2 形しか許さない当初の規則は、自分の別の不変条件（`configs` は常に置き換え）と両立していなかった。従来モードの通常の転送（`configs`=置き換え ＋ `users`=追加）はどちらの形でもないので、受信側の検証で 400 になり、要件 6.1（従来モードの挙動を変えない）を正面から破る。取り込み方法がシステム側で強制されるコレクション（`configs` は置き換えのみ、`pages` は追加不可）を判定の対象から除く。

## 変更 3: 停止判定を保守モードの旗から切り離す

**問題 1**: `app:isMaintenanceMode` は `configs` コレクションの値で、`configs` は転送で必ず置き換えられる。さらに取り込みの最後に `configManager.loadConfigs()` が走るので、旗を立てても取り込みの途中で消える（`import.ts:176`, `import.ts:219-220`, `config-definition.ts:429-431`）。判定は都度その場読みなので、消えた瞬間から素通りになる。

**問題 2**: `isMaintenanceMode()` に OR で足す案も却下した。呼び出し元のうち `routes/apiv3/import.ts:284` と `app-settings/index.ts:1120` は、保守モードを「破壊的な管理操作をしてよい合図」として使っている。転送中に真を返すと、**転送のさなかに手動取り込みや v5 正規化を開始できてしまう**。

**結果**: `service/serving-suspension.ts` を新設し、プロセス内の状態として停止理由を持つ。判定を足すのは保守モード middleware の 2 か所だけで、`isMaintenanceMode()` と他の 4 箇所は無変更。モジュールは「取り込み」を知らず、受け取るのはラベル文字列のみ。`AppService` に取り込み固有の変数を置く案は、置き場所として誤りだったので破棄した（ユーザーの指摘）。

複数ノード構成ではそのプロセスだけが止まる。`s2sMessagingService` で配る拡張は将来の課題として設計に残し、本 spec は単一ノードを前提にする。

## その他の反映（レビューの二次的指摘）

- **アクセストークンの救済**: `users.apiToken` とは別に `accesstokens` コレクション（`AccessToken` モデル、`user` / `tokenHash` / `expiredAt` / `scopes`）が主系として存在し、除外リストにも入っていないので置き換えられる。救済対象の管理者に紐づくトークンも退避・再投入する。識別子を再割り当てした場合はトークンの `user` 参照も合わせる。
- **通知の経路**: 押す側は受信側の応答本体を読んでいない（`service/g2g-transfer.ts:615-619`）。進捗の型も `{ mongo, attachments }` の 2 状態だけで文字列を運べない。応答本体に救済結果を載せ、押す側が読んで通知に載せる契約を明記した。
- **後処理の失敗が添付転送を止める**: 押す側は POST が成功しないと `transferAttachments` に到達しない（`service/g2g-transfer.ts:600-636`）。`finally` の 4 つ（救済・セッション破棄・設定復元・停止判定の解除）が失敗しても応答は成功として返す設計にした。
- **サイト URL の復元は独立ステップ**: 既存のアップロード設定の復元は `app:fileUploadType !== 'none'` という無関係な条件で分岐している（`g2g-transfer.ts:862-881`）。同じ枠に混ぜず、無条件の別ステップにする。
- **D3 の書き方**: `import()` はコレクション単位の例外を捕捉するが、取り込み後の `normalizeAllPublicPages()` は捕捉していない（`import.ts:183-184`）。「`import()` は必ず正常終了する」に依存せず、本物の `try/finally` を要請として書いた。
- **要件側の修正**: 1.2（対象選択も提示しない）、1.3（強制モードを除外）、2.6（依存コレクションを常に一緒に含める）、3.7（セッションを無効化できない場合の警告）、4.3（識別子衝突時を除く）、4.9（アクセストークン）、4.10（識別子の再割り当てと通知）、5.5（列挙に対応する場合）。受け入れ基準は 35 → 39 項目。

# 保守モードの扱いの決着（2026-08-05、ユーザー判断）

## 経緯

当初は「取り込み中の保護をプロセス内の状態で持ち、middleware がそれを見る」案（`service/serving-suspension.ts` の新設）を書いたが、これは**相談せずに決めた設計**で、次の 2 点で否定された。

1. 利用者が G2G しかないのに汎用の口を作っていた（単純化の原則に反する）。
2. トリッキーである。既存の概念（保守モード）で済むならそのほうがよい。

## 採用した形

**取り込み前に保守モードを立て、設定（`configs`）の取り込みが終わった直後に立て直し、取り込み後に失敗の有無で解除するか残すかを決める。**

- 旗は設定コレクションの中にあり、そのコレクションは必ず置き換えられるので取り込みの途中で消える。立て直しを**設定の取り込み直後**に置けば、保護が外れるのは設定の挿入が終わるまでの一瞬だけになる。当初「立て直し案は窓が大きい」と判断したのは、`import()` 全体の終了後に立て直す前提で考えていたためで、誤りだった。
- 立て直しは**取り込みの共通処理（`ImportService`）に置く**。受信側からは「設定の取り込みが終わった瞬間」が分からない（全コレクションを同時に取り込むため）。分かるようにするには取り込みを 2 回に分けて呼ぶ必要があり、進捗の管理が 2 回始まって 2 回終わる形になって表示が壊れる。
- 共通処理に置く副産物として、**管理画面からの zip 取り込みの既存の不具合も直る**。あちらは「保守モードを先に立てろ」と管理者に要求しておきながら、設定の取り込みでその旗を消している。
- 判定の仕組み（`isMaintenanceMode()` と 2 つの middleware）は**一切変更しない**。新しい概念もモジュールも増えない。
- DB の値なので、プロセスが落ちても保護が残る（プロセス内フラグ案はここが弱かった）。

`ImportService` は design で「変更しない」と宣言していたが、この 1 点（と下記の同時実行の拒否）のために Out of Boundary をゆるめた。どちらも G2G 固有ではない一般の修正だという理由で、ユーザーが承認済み。

## 副作用とその始末

転送中は `isMaintenanceMode()` が真になるので、「保守モードなら実行してよい」という合図も立つ（`routes/apiv3/import.ts:284` の手動取り込みと `app-settings/index.ts:1120` の v5 正規化）。つまり転送のさなかにそれらを開始できてしまう。

ただし**同時実行はすでに壊れている**（`import()` に同時実行のガードが無く、`importService.baseDir` に固定名で JSON を書くので相互に上書きする）。新しい穴ではなく、既存の穴が踏みやすくなるだけ。`import()` の入口にガードを 1 つ足して塞ぐ（要件 2.7）。v5 正規化は取り込みの外なのでガードでは防げず、運用の案内で対応する。

## 要件の追加

- **2.7**: 取り込みが実行されている間に別の取り込みを開始しようとしたら拒否する。
- **2.8**: 取り込み完了時、失敗したコレクションが 1 つも無ければ通常の状態へ戻し、1 つ以上あれば通常利用者を通さない状態を保ったまま通知する。

受け入れ基準は 39 → 41 項目。

# 敵対的レビュー 1 巡目の反映（2026-08-05）

サブエージェント 3 体（敵対的な裏取り / 型とテスト / 要件網羅）の指摘のうち、Critical 3 件と二次的指摘を反映した。

## 訂正 1: 保守モードが落ちる機構の理解が誤っていた

`getConfig()` は**メモリに読み込んだ値を返すだけ**で、呼び出しごとに DB を読まない（`config-manager.ts:65-91`）。取り込みは `mongoose.connection.collection()` の生ドライバで書く（`import.ts:206`）ので、設定コレクションを空にした時点では旗は落ちない。**落ちるのは次に `loadConfigs()` が走ったとき**で、それは取り込み末尾（`import.ts:176`）と、他の管理操作が `updateConfig` 系を呼んだとき（同 113-137）である。

したがって書き戻しの役目は「DB に true を書き戻し、以後のあらゆる再読込が true を読む状態にすること」。置き場所（設定の取り込みの後）は結果的に正しく、v5 正規化の時間帯もアップロード設定の復元による再読込も保護される。ただし次の 2 点を足した。

- **設定の取り込みが失敗した場合も書き戻す**（`try/finally`）。空にした後に失敗すると DB に旗が無い状態で残り、以後の再読込で保護が外れる。
- **書き戻しの完了を `await` し、末尾の `loadConfigs()` より先に走ることを保証する**（横で走らせない）。

残る窓（設定を空にしてから書き戻すまでの間に他の管理操作が設定を書く）は、上限を設ける手段が無いので受け入れるリスクとして記録した。

## 訂正 2: 失敗したコレクションを知る手段が無かった

要件 2.8 の判定に使う `failedCollections` を作る経路が存在しなかった。`import()` は `Promise<void>` を返し、コレクション単位の例外をループ内で握ってログとイベント通知だけ行う（`import.ts:159-171`）。実装すると常に空になり、2.8 は必ず「解除する」側に落ちていた。

`import()` の戻り値を失敗コレクション名の一覧にする（`Out of Boundary` の変更点を 2 → 3 に広げた）。管理イベントを購読して集計する案は、依存が増え購読漏れが起きやすいので採らなかった。**エラーを握って続行する方針そのものは変えない**（返すのは事実だけ）。

## 訂正 3: 「転送可能なコレクション」の定義が空白だった

引っ越しから選択肢を取り除いた結果、「何を転送するか」の判断がシステム側に移ったのに、その定義が無かった。実データベースを調べると 58 コレクションあり、`migrations`（migrate-mongo が適用済みスクリプトを記録する台帳）や `changestream_resume_tokens` はどちらの除外リストにも入っていない。

さらに重要な事実: **今の G2G は既定で全コレクションを選択済み**にしている（`G2GDataTransfer.tsx` の `setSelectedCollections(new Set(filteredCollections))`）。`/mongo/collections` はサーバ側で何も絞っていない（全件返す）。従来モードは `insert` なので帳簿系も「行が増えるだけ」で済んでいたが、**引っ越しは置き換えなので消える**。`migrations` が移行元の古い内容になると、移行先は次回起動時に適用済みの移行スクリプトを再実行する。

対応: `service/import/non-transferable-collections.ts` に唯一の宣言を置き、基準（GROWI のコンテンツではなく、その環境の運用状態を持つか）を明記した。`/mongo/collections` がその宣言で絞った一覧を返し、クライアント側の 2 つの定数（中身が食い違っている）を削除する。実データベースの一覧と宣言の差分を検出する試験を要件 7.5 として足した。分類が分かれうるもの（`vault_instructions` / `growiplugins`）は実装タスクで確認する。

## 二次的指摘の反映

- **救済対象に `status` の条件を足した**。有効でない管理者を救済しても `loginRequiredStrictly` で弾かれ、「ログインできる管理者が残る」ことにならない。要件 3.5 の警告条件も「パスワード無し」から「ログインできる状態でない」に広げた（`no_loginable_admin`）。
- **アーカイブ側の集合を返す公開関数**を `detect-unique-conflicts.ts` に追加する旨を File Structure Plan に明記した（抽出処理は非公開で、公開 API の戻り値には衝突した組しか現れないため、救済の付け替え名を保証できなかった）。
- **同時実行の拒否を 2 段構えにした**。`import()` の入口だけでは、2 本目が退避まで進み、拒否後に自分の `finally` を走らせて 1 本目の結果を汚す。受信側の入口でも拒否し、`finally` は「取り込みを開始できたか」を見る。
- **型 2 件**: `RescuedAdmin.accessTokens` を `IAccessTokenDocument`（Mongoose の実ドキュメント）から `IAccessToken & HasObjectId` に直した（`user` 側は既にプレーン型で不統一だった）。`TransferBlocker` / `TransferWarning` を文字列化する `describeBlocker` / `describeWarning` を契約として明記し、既存の `reason: string` を使う呼び出し元との接続を決めた。
- **テスト戦略**: 置き換え系の試験は per-worker 共有 DB の他ファイルの fixture を消すので、専用ファイルに切り出して worker を専有させる（`pool: 'forks'` / `singleFork`）。契約の固定方法を具体化した（DB から読み直して `isPasswordValid`、平文トークンを事前確保して `findUserIdByToken`、`store.get` で確認、`snapshotDestination()` で 3.3、保守モードは完了後でなく**取り込み中**に確認）。
- **試験で固定できない事項**を 3 件明記した（書き戻しまでの窓・プロセス停止・複数プロセスでの同時実行）。

受け入れ基準は 41 → 44 項目（5.6 / 5.7 / 7.5 を追加、4.1 と 3.5 を修正）。

# 敵対的レビュー 2 巡目の反映（2026-08-05）

## 訂正 4: `/mongo/collections` をサーバ側で絞る計画が、無関係なバックアップ機能を壊していた

1 巡目の反映で「コレクション一覧の応答をサーバ側で絞り、クライアントの 2 つの除外リストを削除する」と書いたが、これは誤りだった。この API はバックアップ用のエクスポート画面からも呼ばれており（`stores/admin/export.ts` の `useSWRxExportCollections`）、あちらは自前の 4 件だけを除いた一覧を出して、`migrations` や `activities` や `vault_*` までバックアップ zip に含められるようにしている。G2G の宣言で絞ると、この選択肢が 16 件減る。要件が Out of scope としている手動 zip 画面の劣化そのものだった。

対応:
- **`/mongo/collections` は変更しない**。エクスポート画面は据え置く。
- G2G 画面に出す一覧は、押す側に足す G2G 専用の口（`GET /g2g-transfer/transferable-collections`）から取る。
- 除外の目的が 2 つある（G2G は「移行先で意味を持たない環境固有の状態」、エクスポートは「バックアップに含めて安全なもの全部」）ことを設計として認めた。

あわせて、**押す側が送る前に宣言のコレクションを必ず除く**形にした（要件 5.8 を追加）。受信側の拒否は安全網に降格。こうしないと、既定で全コレクションが選択されている従来モードの転送が 400 で止まり、要件 6.1 を破る（既定選択は `setSelectedCollections(new Set(filteredCollections))`）。

## 訂正 5: `import()` の戻り値変更は既存の呼び出し元を壊す

「戻り値を無視しても壊れない（追加のみ）」と書いたのは誤り。`routes/apiv3/import-executor.ts:12-17` が `interface ImportRunner { import(...): Promise<void> }` という最小限の型を自前で定義しており、`Promise<ImportResult>` を返すクラスは代入できない（`Promise<X>` は `Promise<void>` に代入できない）。この型の更新を Modified Files に明記した。

# 敵対的レビュー 4 巡目の反映（2026-08-05）

3 巡目が GO だったので収束確認のために回した 4 巡目で、**設計の骨格ではなく受信側の既存コードとの接続部分に実害のある欠落**が見つかった。骨格は変えずに塞いだ。

## 欠落: 引っ越しの `optionsMap` に `pages` / `revisions` の追加オプションが無く、転送が必ず失敗する

受信側の取り込み設定の生成は、コレクションが `pages` / `revisions` のとき `isImportOptionForPages(option)` を通す。この判定は **`'isOverwriteAuthorWithCurrentUser' in opt` というキーの存在チェック**で、無ければ `Invalid option for pages` を投げる（`overwrite-params/index.ts:18-27`、`import-option-for-pages.ts:39-43`）。

設計では引っ越しの `optionsMap` の型を `{ [collectionName]: { mode } }` としていた。`mode` しか持たないので、この判定を通らない。しかも要件 1.2 で操作者にオプションの画面を出さないので、値を補う手段がどこにも無かった。**引っ越しの転送は `pages` の取り込み設定を作る段階で必ず失敗する**（DB 書き込みの前なので移行先は壊れないが、転送が一度も成立しない）。

見落とした理由: `optionsMap` が**二重の役割**を持つことを設計に書いていなかった。整合条件（D2）の判定には `mode` しか要らないので、その文脈では `{ mode }` で十分に見える。しかし同じ値がそのまま wire に乗って受信側の取り込みオプションになる。

対応: `ImportOptionsMap` の型を `pages` / `revisions` の追加オプションを含む形に広げ、`buildMigrationTransferPlan` が既存の既定値（すべて `false`。各 `DEFAULT_PROPS`）を補うと明記した。値の選択（グループ制限のページを公開に変えない）は要件 2.2 と整合する。単体試験に「preset の出力をそのまま受信側の取り込み設定の生成に通して例外が出ない」ことを固定する項目を足した（キーの有無を見るガードなので型の確認だけでは守れない）。

なお、このガードがキーの存在で判定する形になっているのは意図的で、`declare` によるフィールドの型のみ宣言と合わせて **#11341 のインポート不具合の修正で load-bearing になった**箇所である（`import-option-for-pages.ts` のコメントがその経緯を残している）。`undefined` を入れても通らない。

## 補足: 型変更に追随する試験ファイルの範囲を絞った

3 巡目で「`import-executor.spec.ts:24-25,54-55` と `import-executor.integ.ts:116` を直す」と書いたが、実際に修正が要るのは `spec.ts:25` の `mockResolvedValue(undefined)` だけ。同 54-55 行は `mockRejectedValue`（拒否理由の型は戻り値の型と無関係）、`integ.ts:116` は型引数なしの `vi.fn()`（戻り値が `any` に推論される）なので、戻り値の型が変わっても代入可能性は崩れない。記述を絞った。

- 1 巡目: 要件を満たせない箇所 2 件＋既存を壊す箇所 1 件（NO-GO）
- 2 巡目: 反映の過程で無関係な既存機能を壊していた 1 件（NO-GO）
- 3 巡目: GO。記述の精度 2 件

# 敵対的レビュー 5 巡目の反映（2026-08-05）

## 抜け 1: 取り込みの失敗が移行元の管理者に届く経路が無かった

# 敵対的レビュー 7 巡目（opus、2026-08-05）— 6 巡目の GO は妥当でなかった

6 巡目の GO を出したのは小さいモデルで、見落としが疑われたため opus で 2 視点（広範な敵対的検証 / 実装可能性・型・テスト）を回した。**結果は NO-GO で、着手前に直すべき実害が 5 件出た。** ユーザーの疑いが正しかった。

## 6 巡目が見落としていたもの

6 巡目は「既存コードの実行時の前提と噛み合うか」に観点を絞り、その 4 点は正しく検証していた。しかし見ていたのは**値と型の噛み合い**だけで、次の 2 種類を点検していなかった。

- **時間の前提**: 転送キーの寿命が転送の所要時間を上回るか
- **区間の前提**: 判定に使う状態が、守りたい区間と一致しているか

観点を絞ったことが収束を早めた反面、絞った外側が点検されないまま GO になった。

## 重大（着手前に直した）5 件

### 1. 転送キーは作成から 30 分で消える（要件 5.1 / 5.2 が実装しても満たせなかった）

`models/transfer-key.ts:18` が `expireAt: { default: () => new Date(), expires: '30m' }`。**作成時刻からの TTL で、延長する処理はどこにも無い**（受信側の検証は読み取りだけ）。この 30 分の枠に「エクスポート＋zip 生成＋送信＋全コレクションの取り込み＋v5 正規化」が入り、**そのあとに添付ファイルの転送が同じキーで始まる**。引っ越しは対象が全コレクションになり `pages` が必ず入るので `normalizeAllPublicPages()` が毎回走り、枠を構造的に伸ばす。

失効すると `GET /files` と全ての `POST /attachment` が 403 になり、**DB は置き換わったのに添付が 1 件も入らない移行先**が残る。ページの画像切れとして後から発覚する——この spec が消そうとした体験そのもの。要件 5.1 は「転送が進行している間キーを失わせない」と書いてあるのに、設計はコレクションを転送しないことだけを担保にしていて、時間による失効に 1 行も触れていなかった。

D10 として「受信側のキー検証で要求のたびに `expireAt` を延ばす（無操作 30 分で失効の意味は保つ）」を追加。要件 5.1 と 7.4 に「時間の経過も含む」を明記した。

### 2. 保守モードの起動条件が常に真で、従来モードの転送が保守モードに入る（要件 6.1 違反）

「置き換えを含む取り込みでは保守モードを立てる」の判断材料を素の置き換え対象集合にしていた。`configs` は取り込み方法が置き換えに強制されるので、**この集合はどの転送でも必ず `configs` を含み、条件が常に真**。従来モードの転送でも移行先が保守モードに入り、コレクションが 1 つでも失敗すれば立ったまま残る。移行先の管理者は転送を見ていないので放置される。

判断に使う集合を 2 つに書き分けた。**検知を外す用**（素の集合、`configs` を含んでよい）と**保護・救済を起こす用**（強制モードを除いた集合）。

### 3. セッションの無効化は既定構成（MongoDB）では書いた方法で実装できない（要件 5.5）

「store API（`all` / `destroy`）だけを使う。Redis 構成でも動く」と書いたが**実際は逆**。`connect-mongo` の `all()` は `unserialize(session.session)` の配列を返すだけで**セッション ID を返さない**ので、`destroy(sid)` に渡す ID が無く選択的な破棄ができない。GROWI は Redis の URL が無ければ connect-mongo を使うので、**既定構成がまさに動かない側**。しかも `all` の有無で「対応」と判定すると connect-mongo でも真になり、対応と申告したうえで 1 件も破棄しない黙った未達になる。

保存先ごとに経路を分けた（MongoDB は `sessions` を直接扱う / Redis は store API / それ以外は警告して続行）。セッションと利用者の対応が `session.passport.user` に依存することも明記（「構造に依存しない」は成立しない）。

### 4. 救済の一意フィールドが 1 つ漏れていた（要件 4.1 / 4.8）

`users` の一意索引は 3 つ（`username` / `email` / `slackMemberId`）だが、救済は `username` の付け替えと `email` の除去だけを扱っていた。同じ Slack ワークスペースを両インスタンスで使っていれば `slackMemberId` の衝突は普通に起きる。Mongoose 経由（`uniqueValidator`）で再投入するので検証エラーになり、**移行先に管理者が 1 人も残らない**。

`slackMemberId` を対象に加え、フィールド一覧は `detect-unique-conflicts.ts` の `USER_UNIQUE_FIELDS` を**単一の出所として参照する**形にした（索引が増えたときの取りこぼしも防げる）。

あわせて退避の取得方法も明記した。**`toObject()` を使ってはならない**——`users` の `toObject.transform` は `omitInsecureAttributes` を通し、**`password` と `apiToken` を落とす**。`IUser.password` は必須の `string` 宣言なので型検査は何も言わず、救済後に「同じパスワードでログインできる」が黙って壊れる。`_id` の文字列正規化（実体は ObjectId、アーカイブ側は 16 進文字列なので正規化しないと衝突判定が常に偽）と、トークン退避に `findTokenByUserId` を使わないこと（`tokenHash` と `user` を select しないので再投入に失敗する）も足した。

### 5. 保守モードの解除が救済の失敗を見ていなかった（要件 4.8）

解除の判断を「コレクションの失敗の有無」だけにしていた。設計は救済の再投入が失敗しうる前提でその方式を選んでいるのに（一意検証を通したいので Mongoose 経由）、「コレクションはすべて成功・救済だけ失敗」の組み合わせで**管理者が居ないまま通常運用へ戻り、完了として通知される**。要件 3.4 の警告を承知して続行した転送（種が食い違う）では、移行元のユーザーも旧パスワードで入れないので**誰も入れない**。

`rescueApplied` を結果に加え、解除の判断に含めた。`import()` が例外で抜けて失敗一覧が手に入らない場合の扱い（失敗ありとして残す／応答は成功で返して添付転送を止めない）も明記した。

### 6. 「取り込み中に保守モードが立っている」試験が原理的に失敗しえなかった（要件 2.4）

`isMaintenanceMode()` で確かめる形にしていたが、あれはメモリ上の値を返すだけなので、取り込み前に旗を立てた時点で真になり、設定コレクションを空にしても落ちない。**書き戻しの実装を丸ごと削っても緑のまま通る**＝何も守らない試験だった。DB 由来の値を読む形に変え、コミット前に書き戻しを外して赤くなることを確認する作法を添えた。

## 中程度（同時に反映）

- 失敗を仕込む方法の指定（閉じ括弧が無いだけの JSON では例外にならない。JSONStream は黙って止まる。ENOENT かトークン不正にする）。対の確認（仕込まなければ空）も追加。
- `pool: 'forks'` / `singleFork` はファイル内から指定できない。`vitest.workspace.mts` に専用プロジェクトを追加し既存の `exclude` に glob を足す作業が要ることを明記。
- `FORCED_MODE_COLLECTIONS` の型を 2 つに分けた。`pages` は「追加が不可」＝許される方法が 2 つあるので Map で表せず、除外から漏れて従来モードの組み合わせが 400 になっていた。
- 同時実行の拒否の応答コード（`import_already_in_progress`）を API 契約に追加し、押す側の失敗処理に枝が必要なことも明記。
- `importCollections` の署名に `innerFileStats` が届いていなかった（救済の算出に必要）。
- `g2g-transfer-preset` の依存の記述が表と本文で食い違っていた（引数で受け取る形に統一）。
- パスワードの種が **meta.json に平文で同梱されている**ことを記録し、要件 3.6 は点検の経路への制約で、同梱は既存挙動として受け入れると決着させた。

## 学び

**「観点を絞る」と収束は早まるが、絞った外側は点検されない。** 6 巡目は絞ったことで GO を出したが、時間と区間という 2 つの前提が観点の外にあった。またモデルの能力差がレビューの深さに直接出る（同じ資料・同じ指示でも、opus は sonnet が見なかった `transfer-key.ts` の TTL と `connect-mongo` の実装まで辿った）。**収束の判定は、最も能力の高いモデルで少なくとも 1 巡してから行うべきだった。**

# 敵対的レビュー 8 巡目（opus、2026-08-05）— 修正の適用範囲が狭かった

7 巡目の反映を検証させたところ、**現象の特定はすべて正しかったが、対処が現象を覆いきっていない**ものが 3 件出た（NO-GO）。指摘された癖は「観点」ではなく**修正の適用範囲**が絞られていたこと——変更した条件や値について「これを書く／読む経路は他にいくつあるか」を数えていなかった。

## 重大 3 件（着手前に直した）

### 1. 転送キーの延長が、いちばん長い区間を覆っていなかった

D10 で「要求のたびに `expireAt` を延ばす」と決めたが、**アーカイブの `POST /` は取り込みと v5 正規化をすべて 1 回の要求の中で終えてから応答する**（`routes/apiv3/g2g-transfer.ts:438-457` が `importCollections` を `await` してから `res.apiv3()`。middleware の延長は `:188-205` で到着時のみ）。つまり枠から外せたのは「エクスポート＋zip 生成＋送信」だけで、設計自身が「引っ越しは構造的に伸ばす」と書いた区間がそのまま残っていた。

**取り込みが走っている間ずっと延ばす**（開始時に 5 分間隔で `expireAt` を進め、`finally` で止める）形に変更。試験も「`expireAt` を過去へ寄せる」形をやめた——過去へ寄せた文書は TTL の掃除（約 60 秒周期）で消え、消えた文書は延長できないので掃除との競争になり、守りたい場面を一度も通らない。**寿命より長くかかる取り込みを作って区間を測る**形にした。

### 2. 保守モードの書き戻しが無条件 `true` で、従来モードの移行先を閉じ込めていた

7 巡目で「保守モードを**立てる**条件」を強制モード除外の集合に絞ったが、旗を DB に書く経路はもう 1 本ある——`ImportService` 側の書き戻しで、こちらは共通処理に無条件で置くと決めていた。しかも文言は一貫して「**true** を書き戻す」。

従来モードの既定の転送を辿ると、`configs` は必ず置き換えなので書き戻しが走って `true` が入り、**受信側は保護の条件を満たしていないので後始末を走らせない** → 旗を下ろす者が誰も居ない → 転送成功後も移行先が保守モードで固まる（要件 6.1 違反）。narrow した条件は経路を 1 本しか塞いでいなかった。

**書き戻す値を「設定の取り込みに入る直前の値」に変更**。これなら管理画面からの zip 取り込み（保守モードが必須なので必ず `true`）でも従来モード（`false`）でも正しく、条件分岐も要らない。

### 3. 1 つの条件が別々の関心（保護 / 救済 / 設定の復元）をまとめて駆動していた

保守モードと救済を同じ条件で起こしていたが、必要になる場面が違う。保護は「何かが置き換えられるとき」、救済は「`users` が空にされるとき」だけ。

従来モードで「`pages` を置き換え ＋ 他は追加」（`MODE_RESTRICTED_COLLECTION.pages` が置き換えを許すので選べる）を選ぶと条件が真になり、`users` は空でないのに救済が走る。Mongoose 経由なので**まだ存在する同じ管理者を入れ直そうとして `_id` と `username` で必ず失敗**し、`rescueApplied` が false になって保守モードが残り、**成功した転送が失敗として通知される**。

さらに「設定の復元」も同じ条件に巻き込まれていた。あれは既存の無条件の処理なので、条件を被せると従来モードで移行先のアップロード設定が移行元の値に置き換わる（要件 5.3 の退行）。

**3 つの関心の条件を分けた**。保護は強制モードを除いた置き換え対象集合が空でないとき、救済は `users` が置き換え対象に含まれるときだけ、設定の復元は条件に関わらず常に。

## 中程度 4 件（同時に反映）

- セッション無効化の記述が 3 か所（Allowed Dependencies / Technology Stack / Logical Data Model）で古い決定（「store API だけ」「構造に依存しない」）のまま残っていた。7 巡目で保存先ごとに分けたのに、その決定を書いた節以外を直していなかった。
- `invalidateSessionsExcept(store, keepUserIds)` の署名では MongoDB 経路が書けない（store から `sessions` へ到達する公開 API が無い）。`SessionAccess` としてコレクションへの到達手段も受け取る形にし、`session` フィールドが既定で文字列なので JSON として解析することも明記。判定関数も「`all` の有無」ではなく「セッション ID 付きで対象を選べるか」に改名。
- 受信側の「取り込み中」の旗を立てる位置が、流れ図（衝突検知の前）と本文（退避から）で食い違っていた。**退避の直前に立てて `finally` で必ず下ろす**に統一（検知より前だと早期の中断で下ろす経路が漏れ、以後すべての転送が永久に拒否される）。
- D10 により preflight が移行先の `transferkeys.expireAt` を書き換えるので、「preflight は読み取りだけ」という 2 か所の記述を「移行先のデータは変更しない（キーの寿命だけ延びる）」に直した。

## 取るに足らない 1 件

`USER_UNIQUE_FIELDS` は `detect-unique-conflicts.ts:103` で非公開なので、「単一の出所として参照する」には export が要る（実装時の判断で足りる）。

## 学び（7 巡目の学びの更新）

7 巡目は「観点を絞ると外側が点検されない」と書いたが、8 巡目で分かったのはもう一段手前の問題だった。**修正するとき、その条件や値に触る経路が他にいくつあるかを数えていない。** 同じ旗（`app:isMaintenanceMode`）を書く経路が 2 本、同じ条件で駆動される関心が 3 つ、同じ決定を書いた節が 4 か所——いずれも 1 つだけ直して残りを放置していた。次に直すときは「これを書く／読む経路は他にいくつあるか」を必ず数える。

# 敵対的レビュー 9 巡目（opus、2026-08-05）— 経路の棚卸しを文書に残した

8 巡目の反映は「現象の特定と対処の方向はどれも妥当」と評価されたが、**同じ癖が 3 か所に残っていた**（NO-GO）。いずれも「同じ状態に触る経路のうち 1 本しか直っていない」形。

## 重大 3 件

### 1. 同時実行の旗が、壊れる瞬間より後ろにあった

旗を「退避の直前」に置いたが、**壊れる瞬間は展開（unzip）**だった。受信ルートはハンドラ冒頭で `importService.unzip` を呼び（`routes/apiv3/g2g-transfer.ts:336`）、展開先は固定名の共有ディレクトリでファイル名はアーカイブの中身どおり。2 本目は**判定に到達する前に 1 本目が読んでいる最中の JSON を上書きする**。1 本目は例外を握って続行するので、別のアーカイブの中身が混ざったまま完了しうる——#10151 と同じ壊れ方。

さらに D5 がこの扉を開ける側に働く。管理画面からの zip 取り込みは「保守モードでなければ拒否」だが、引っ越しの最中はまさに保守モードなのでゲートを通る。

### 2. 保守モードの「解除」だけが転送前の値を見ていなかった

8 巡目で書き戻す値を「取り込み前の値」に直したのに、**同じ旗を書く 3 本目の経路（後始末の解除）は無条件のまま**だった。従来モードでは旗を立てないのに後始末の条件は「失敗の有無」だけなので、**移行先の管理者が自分で立てていた保守モードを勝手に下ろす**。引っ越しでも、転送前から保守モードだった移行先が開く。8 巡目に直した誤りと**向きが逆の同型**（あちらは無条件 true、こちらは無条件 false）。

後始末を**解除ではなく復元**に変更（立てる前に控えた値へ、自分が立てたときだけ戻す）。保護を起こさなかった転送では旗に一切触れない。あわせて「復元は添付転送より前に起きるので、移行先は添付が届かない状態で開く」ことを受け入れるリスクとして記録。

### 3. キーの延長が、今度はエクスポートの区間を覆っていなかった

8 巡目で取り込みの区間を覆ったが、**エクスポートと zip 生成の間も移行先へ要求が 1 本も届かない**（押す側は `growi-info` を 1 回問い、`export(collections)` を 1 回の `await` で完走させてから POST する。`service/g2g-transfer.ts:580-583` → `:615`）。書き出しは取り込みと同規模のデータを扱うので、取り込みが 30 分を超える規模なら書き出しも同程度かかる。ここで失効すると**アーカイブが 1 バイトも渡らずに終わる**。

延長の担い手を 2 つに分けた（押す側がエクスポート中、受信側が取り込み中）。受信側は `importCollections` に「キーを延ばす手段」を引数で渡す（`ImportService` に転送キーの概念を漏らさない）。

## 中程度 3 件

- **救済した管理者がログインできるかは移行元の設定で決まる**。`configs` は必ず置き換えられるので、転送後の `security:passport-local:isEnabled` は移行元の値になる。移行元が SSO 専用でローカル認証を切っていると、パスワードを保って救済した管理者も誰も入れないのに、`notLoginableAdminCount` は移行先のパスワードの有無しか数えないので捕まえられない。警告 `local_auth_disabled_at_source` を追加。

- 保守モードの middleware が付く場所の記述が不正確だった（apiv3 だけでなく apiv1・ページ・SSR の props も同じ値を読む）。結論は変わらないが訂正。

# 敵対的レビュー 10 巡目（opus、2026-08-05）— 棚卸しの表そのものを検証させた

9 巡目で追加した「状態ごとの経路の棚卸し」の表を検証させた。**状態 1（保守モードの旗）の書く 4 経路は実コードと完全一致**（表を作った効果が出て、この状態では初めて誤りが出なかった）。一方**状態 3（展開先のディレクトリ）は書く経路を 2 本、消す経路を 2 本落としており、落ちた 1 本が旗の位置の妥当性を直接崩していた**（NO-GO）。

## 重大 3 件

### 1. zip は multer が書く。旗をハンドラ冒頭に置いても間に合わない

壊れる瞬間は展開ではなく、その前の **multer による zip の受信**だった。受信ルートは `uploads.single('transferDataZipFile')` を挟み（`routes/apiv3/g2g-transfer.ts:295-298`）、保存先は `importService.baseDir`、名前は**アップロードされた名前そのまま**（`:111-127`。コメントも「同名は上書き」と書いている）。multer は middleware なのでハンドラの 1 行目より前に走る。

さらに**押す側の付ける名前は毎回同じ**だった。`` `${appTitle}-${Date.now}.growi.zip` `` の **`Date.now` に `()` が無く関数参照が文字列化される**（`service/g2g-transfer.ts:604-608`）。既定のサイト名は "GROWI" なので、別々の移行元からの 2 本でも名前が一致する。

1 本目は展開の直後に zip を再読みして版を照合するので、上書きされると**取り込む対象と違うアーカイブの meta を見て版を確かめる**ことになる。

旗を `uploads.single(...)` より前（キー検証の直後）へ移し、あわせて受信の一時ファイル名を要求ごとに一意にする（二重の守り）。表に multer の 2 経路と消す 2 経路を追記した。

### 2. 旗を 2 つ持つと、展開〜検知の間が無防備

「受信側の入口と `ImportService` の入口の 2 段構え」と書いていたが、2 つは別の状態なので守る区間が違う。`ImportService` 側が立つのは `import()` に入ったとき、つまり**受信側の展開・版の照合・衝突検知が全部終わった後**。衝突検知は大きな移行では分単位で居座るので、その間に管理画面から zip 取り込みを始めると通過して JSON を上書きする（あちらの「保守モードでなければ拒否」は、引っ越しの最中はまさに保守モードなので通る）。

**状態を 1 つにまとめ、両方の入口が展開の前に取る**形に変更（`ImportService` が「取り込みの作業が動いている」を 1 つ持ち、`import()` 自身も未取得なら取る）。守りたい区間は「共有ディレクトリに何かを書き始めた瞬間から取り込みが終わるまで」で、1 つの状態でしか表せない。

### 3. キーの延長が区間の先頭から始まっていなかった

受信側の延長を `importCollections` の引数として渡す形にしていたので、**1 回の要求の前半（zip のネットワーク受信・展開・版の照合・衝突検知）が覆えていなかった**。これらも同じ規模のデータを扱うので前半だけで寿命を超えうる。

**キーの検証の直後（要求の先頭）で延長を始め、応答の完了で止める**形に変更。副産物として `importCollections` にキーを延ばす手段を渡す必要が無くなり、`ImportService` に転送キーの関心が漏れなくなった（D10 が避けたかったことが最初から起きない形になった）。

## 中程度（同時に反映）

- **押す側の延長に `growi-info` を使ってはならない**。`answerGROWIInfo` は移行先のストレージへ書き込み試験のファイルを保存して**削除しない**（`file-uploader.ts:92-110` に TODO がある既存の取りこぼし）。5 分間隔で叩けばゴミが増え続ける。**延長専用の軽い口（`POST /keep-alive`、204 を返すだけ）を足した**。あわせて「preflight は移行先のデータを変更しない」の記述を「DB のデータは変更しない（キーの寿命は延び、既存の書き込み試験のファイルは残る）」に訂正。
- 棚卸しの表に、保守モードの**移行元の値が挿入される経路**（書き戻しをこの挿入より後に置くという順序の制約）と、読む経路の漏れ 4 つ（`/vault.git`・トップページ・管理 UI へ返す 2 つの API）を追記。
- 表の「キー発行〜転送開始の操作」の区間が「届く」になっていたのを「届かない（鍵を人が運ぶ間は要求が無い）」に訂正。

# 敵対的レビュー 11 巡目（opus、2026-08-05）— GO（重大ゼロ）

## 中程度 3 件（反映済み）

### 1. 10 巡目の決定が設計の 3 か所に届いていなかった

D9 の本文は「状態を 1 つにまとめ、両入口が `uploads.single` より前で取る」に直したのに、**流れ図・その説明文・別の箇条書きに 9 巡目の古い形（旗 2 つ・退避の直前・`preImport()` の前）が残っていた**。タスクは流れ図と箇条書きから作られるので、放置すると古い側が実装されて 10 巡目の修正が届かない——レビュアーが「これはタスク分解の**前に**直せ」と指定した理由。

流れ図の `Busy` を先頭（zip の受信より前）へ移し、「2 段構え」の説明を「1 つの状態を両入口が取る」に差し替え、古い箇条書きを「**解放するのは取った入口**（`import()` は自分が取ったときだけ返す）」に書き換えた。

### 2. 要求の先頭へ前倒しした取得を、異常終了で解放できていなかった

止め方が `try/finally` と `res` の `finish` のままだった。しかし G2G の受信は `uploads.single` より**前**の middleware で取るので、multer が失敗すると（`.zip` 以外の拒否・アップロード中の切断・multipart の破損）`next(err)` でハンドラを飛ばし、**ハンドラの `finally` は 1 度も走らない**。放置すると以後この移行先のあらゆる取り込みが永久に拒否され、しかも起こりやすい引き金が「大きなアーカイブのアップロード中に接続が切れる」——**切れた転送を再実行しようとすると必ず拒否される**という最悪の組み合わせになる。キーの延長も同様に止まらず、寿命が無期限に延びて「30 分で失効する」前提が崩れる。

**`res` の `close`（正常完了でも中断でも発火する）でも解放する**を D9 と D10 に追記。あわせて**管理画面側は同じ方式にしてはならない**ことも明記した（あちらは展開と取り込みの前に応答を返して非同期に続けるので、応答のイベントで解放すると取り込み中に状態が下りる。`try/finally` のままが正しい）。「入口ごとに解放の合図が違う」ことを設計に残した。

### 3. 点検の入力契約が、決めた警告 2 つを計算できなかった

- `local_auth_disabled_at_source`（9 巡目に追加）は**移行元の `security:passport-local:isEnabled`** を見ないと出せないのに、`evaluateTransferability` の `src` にその値が無かった。純関数と決めているので、引数に無い限り判定できない。→ `src` に `isLocalAuthEnabled` を追加。
- 要件 3.5 の条件は「ログインできる管理者が**居ない**」だが、移行先が申告するのは `notLoginableAdminCount`（ログインできない管理者の**数**）だけだった。管理者が 5 人居て 1 人が停止中でも 1 になるので「居ない」を判定できず、**偽の警告**になる（承知して進むボタンが日常化し、本当に危ないときの警告が効かなくなる）。→ `loginableAdminCount`（ログインできる管理者の数）に変え、条件を `=== 0` にした。警告の型からも `count` を落とした。

## 取るに足らない 3 件
