# Requirements Document

## Project Description (Input)

GROWI の GROWI-to-GROWI（G2G）転送が移行先 GROWI に対して何をするかを、2 つの preset として定義し直す。移行先を置き換える「引っ越し」を既定にし、従来の「既存データに追加する」を非既定で維持する。

### (a) 誰が困っているか

- G2G 転送で GROWI 間のデータ移行を行う管理者。G2G 転送は実質「GROWI の引っ越し」に使われるが、現在の実装は「移行先に追加する」ことを既定にしているため、初期セットアップ済みの移行先へ転送すると管理者アカウントが衝突して転送が完了しない。

### (b) 現状

- コレクション取り込みの既定モードは `insert`（移行先のデータを残したまま追加する）。移行先に同じ `username` / `email` を持つユーザーがいると、MongoDB の一意制約違反でそのドキュメントだけが取り込まれず、書き込みエラーを配列で受け取って処理が続行されるため、整合性の壊れたデータが生成されてグループ公開ページが閲覧不能になっていた（issue #10151）。
- その修正として spec `g2g-import-conflict-detection` が、取り込み開始前の衝突検知ゲート（衝突があれば 409 で中断し DB を変更しない）を実装済み（PR #11643、master 宛て、レビュー中）。壊れたデータを作ることは無くなった。
- ただしこれは安全網であって、管理者が達成したい結末（移行が完了し、アクセス権が保たれる）には届いていない。移行元と移行先を同じ人が管理している場合、その人の `username` / `email` はほぼ確実に衝突するため、**もっともありふれた移行シナリオが必ず止まる**。しかも衝突が判明するのはアーカイブ生成と送信を終えた後で、いちばん遅いタイミングになる。
- 一方で GROWI は既に一部を「引っ越し」として扱っている。`configs` は置き換えが強制されており、ファイルアップロード設定だけは移行先の値を退避して戻している。
- しかし `users` は置き換えが禁止されている（取り込み方法の選択肢が `insert` / `upsert` に限られている）。移行先の users を空にすると、そこで転送が失敗した場合に誰もログインできないインスタンスが残るためと考えられる。

### (c) どう変えたいか

移行先にあったデータは破棄して構わないシチュエーションが圧倒的に多く、保持したいことの方が稀である。この前提に立って、転送の意味を「移行先を移行元の状態に置き換える」ことを既定とする。置き換えなら移行元の識別子がそのまま入るため、ユーザー・グループ・グループ関係・ページの対応が整合し、アクセス権は構造的に保たれる（ID の再マッピングは不要になる）。

`users` を置き換えられない理由（ログイン手段の喪失）は、ロールバックではなく**移行先の管理者アカウントの救済**で解く。

### 決まっている仕様（spec 化に先立って合意済み）

- **モードは preset 2 つ。引っ越しからは選択肢を取り除く**: 画面の先頭で 1 回だけ選ぶ。引っ越しを選んだら、転送対象コレクションの選択も取り込み方法の選択も提示せず、転送可能なコレクションすべてを置き換える。従来モードは今の自由度（対象の選択と方法の選択）をそのまま残し、新しい規則を適用しない。
  - この形にした理由: 「これは置き換えるがこれは置き換えない」「このコレクションはあれと一緒でないとだめ」という条件を積むと、規則の数だけ操作者に理解を要求することになる。引っ越し側の自由度をなくせば、依存するコレクションを一緒に選ばせる規則も、混在の判定も操作者から見えなくなる（システムが常に満たす）。失うのは「引っ越しで一部だけ移す」ことだけで、それが必要なら従来モードを使う。
  - 混在の判定は、取り込み方法がシステム側で強制されるコレクション（設定は置き換えのみ、ページは追加が不可）を対象から除く。除かないと、従来モードの通常の転送（設定は置き換え・ユーザーは追加）が混在と判定されて止まる。
- **受信側に「モード」という概念を持たせない**: 受信側は「そのコレクションが置き換えられるか」だけを見て判断する。これは coding-style の「モード名で分岐せず宣言されたメタデータで判断する」「実行する側は対象集合を引数で受け取る」に従うもの（実現方法は design で決める）。
- **管理者の救済**: 移行先の管理者のドキュメントと、その管理者が発行していたアクセストークンを退避し、移行元のユーザーを取り込んだ後に再投入する。パスワード・管理者権限・識別子を保つ。`username` は移行元に存在しない名前へ付け替え、衝突する `email` は外す。付け替えは操作者に通知する。前提として、パスワードの種（`PASSWORD_SEED`）は移行先プロセスの環境変数であり、設定の置き換えでは変わらないため、移行先の管理者のパスワードは転送後も有効。
- **取り込み中の保護は既存の保守モードで行い、設定の取り込み後に立て直す**: 保守モードの旗（`app:isMaintenanceMode`）は設定コレクションの中にあり、そのコレクションは転送で必ず置き換えられるため、旗を立てても取り込みの途中で消える。そこで、設定の取り込みが終わった直後に旗を立て直す。保護が外れるのは設定の挿入が終わるまでの一瞬だけになる。判定の仕組み（`isMaintenanceMode()` と middleware）は変更しない。
  - 立て直す処理は取り込みの共通処理に置く。G2G の受信側からは「設定の取り込みが終わった瞬間」が分からない（全コレクションを同時に取り込んでいるため）。共通処理に置くと、管理画面からの zip 取り込みでも同じ保護が効き、「保守モードを先に立てろと要求しておきながら設定の取り込みでその旗を消す」という既存の不具合も直る。
  - 転送中は保守モードが立つため、「保守モードなら実行してよい」という合図（手動取り込み・v5 正規化）も立つ。取り込み中に別の取り込みを開始できないようにする（下記 2.7）。
- **モードに関係なく必要な修正 3 件**: (1) 検知ゲートが置き換え対象コレクションでは 409 を返さない、(2) 転送キーを G2G の転送対象から外す、(3) パスワードの種の不一致を転送前に警告する（現状は取り込み前の検証が GROWI のバージョンだけを見ており、アーカイブに種が書き出されているのに照合していない）。

### 関連

- 既存 spec `g2g-import-conflict-detection`（implementation-complete、PR #11643 レビュー中）。本 spec は衝突検知ゲートの役割を「事前提示のエンジン」と「従来モードの番人」に位置づけ直す。
- issue #10151

## Introduction

このドキュメントは、G2G 転送が移行先 GROWI に対して何をするかについての要件を定義する。転送の意味を 2 つの preset として定めたうえで、**引っ越し**（移行先を移行元の状態に置き換える。既定）を選んだときに何が起きるかを、操作者から観察できる結末として書く。前提と決定は上の「Project Description」にある。

引っ越しの結末は 2 つある。**移行元でグループに属していたユーザーが、移行後も同じグループ公開ページを閲覧できること**（移行元の識別子がそのまま入るので、一意制約の衝突は原理的に発生しない）。そして**移行先の管理者が転送後も移行先へログインできること**。後者は救済によって成立するが、救済されたアカウントは移行元のグループに属さないので、グループ公開ページは見えない。**日常のアクセスは移行元のアカウントで行う前提の、緊急用の管理者**である。

加えて、転送を始める前に操作者が知るべきことを提示する。移行先で削除されるデータの量と、転送後にログインできなくなる条件である。これらは重い処理を終えた後ではなく、アーカイブを作る前に提示される。

## Boundary Context

- **In scope**:
  - 転送方法を 2 つの preset（引っ越し / 既存データに追加する）から 1 回選ぶ形にし、置き換えと追加が混在する組み合わせを作れないようにする。
  - 引っ越しモードで、転送対象コレクションについて移行先の既存データを取り除いてから取り込み、移行元のアクセス権の対応関係を保ったまま転送を完了させる。
  - 引っ越しモードで、移行先の管理者アカウントを救済し、転送後もその管理者が移行先へログインできる状態を保つ。
  - 転送を開始する前に、削除されるデータの量とログインできなくなる条件を操作者へ提示し、明示的な確認を得る。
  - 置き換えても移行先に残るもの（転送キー・ファイルアップロード設定・サイト URL 設定）と、無効化されるもの（ログインセッション）を定める。
  - 従来モード（既存データに追加する）の挙動を維持する。
- **Out of scope**:
  - 移行元と移行先の識別子の再マッピング（引っ越しモードでは不要になるため）。
  - 手動 zip 取り込み画面の**取り込み方法・対象選択**の UI 変更（既存データに追加する能力はそちらにも既にある）。ただし設定コレクションの取り込みは保守モードを残す扱いに変わるので、**その予告を出すことだけは手動 zip 取り込み画面にも入れる**（2.9）。取り込みの共通処理を共有している以上、片方だけ予告が無い状態にはできない。
  - 従来モードに残る `externalaccounts` の複合一意制約の衝突検知（別途。引っ越しモードでは原理的に発生しない）。
  - ExternalUserGroup（外部連携グループ）系コレクションの衝突検知。
  - MongoDB の一意インデックス定義そのものの変更、および取り込み方法（insert / upsert / 置き換え）の意味の変更。
  - 移行先のファイルストレージに元からあった添付ファイルの削除。データベースの置き換えでは消えず、参照されない状態で残る。
- **Adjacent expectations**:
  - ページの閲覧可否判定は既存の仕組み（ページに設定されたグループと、ユーザーに紐づくグループ ID 集合の一致）に依存する。本 spec はこの判定を変更しない。「アクセス権が保たれる」という結末は、ユーザー・グループ・グループ関係の 3 者が整合して取り込まれた結果として成立する。
  - 転送の進捗と失敗は、既存の通知経路（転送元の管理者への WebSocket 通知）で伝わることを前提とする。
  - 衝突検知（spec `g2g-import-conflict-detection`）は、本 spec では 2 つの役割で使われる。転送前の提示のためにアーカイブと移行先を突き合わせる仕組みとして、および従来モードで壊れたデータを作らせない番人として。
  - パスワードの種（`PASSWORD_SEED`）は移行先プロセスの環境変数であり、設定の置き換えでは変わらない。救済された管理者のパスワードが転送後も有効であることは、この性質に依存する。

## Requirements

### Requirement 1: 転送方法の選択

**Objective:** G2G 転送を行う管理者として、転送が移行先に何をするかを 1 回の選択で決めたい。コレクションごとに取り込み方法を組み合わせる判断をせずに、意図どおりの移行を行うため。

#### Acceptance Criteria

1. When 操作者が G2G 転送の画面を開いた場合, the G2G Transfer System shall 「引っ越し（移行先のデータを置き換える）」と「既存データに追加する」の 2 つから 1 つを選ぶ形で転送方法を提示し、「引っ越し」を初期選択とする。
2. Where 「引っ越し」が選択されている場合, the G2G Transfer System shall 転送対象コレクションの選択とコレクションごとの取り込み方法の選択のいずれも操作者に提示せず、転送可能なコレクションのすべてを置き換えの対象とする。
3. The G2G Transfer System shall 置き換えられるコレクションと追加されるコレクションが混在する転送を、操作者が指定できないようにする。ただし取り込み方法がシステム側で強制されているコレクション（設定は置き換えのみ、ページは追加が不可）は、この判定の対象から除く。
4. Where 「既存データに追加する」が選択されている場合, the G2G Transfer System shall コレクションごとに取り込み方法を選べるようにする。ただし 1.3 を満たすため、**判定の対象になるコレクションでは置き換えを選択肢に出さない**。取り込み方法がシステム側で強制されているコレクション（設定・ページ）の選択肢は従来のまま変えない。
5. The G2G Transfer System shall 1.3 の判定を受信側でも行い、満たさない要求は取り込みを開始せずに拒否する。画面を通らない呼び出し（自動化スクリプトや改造したクライアントが口を直接叩く場合）に対する安全網であり、拒否したことと理由は 2.7 と同じく開始を試みた側へ届ける。**古い版の移行元からの転送はこの安全網の対象ではない**。取り込みは `meta.version` が移行先と完全に一致することを要求するので、版が違えば取り込み方法の指定によらず別の事由で止まる。

### Requirement 2: 引っ越しモードは移行先を置き換え、アクセス権を保って完了する

**Objective:** G2G 転送を行う管理者として、初期セットアップ済みの移行先であっても転送が完了してほしい。転送後に、移行元と同じユーザー・グループ・アクセス権で使い始めるため。

#### Acceptance Criteria

1. When 「引っ越し」で転送が実行された場合, the G2G Transfer System shall 転送対象の各コレクションについて、移行先の既存ドキュメントを取り除いた後に移行元のドキュメントを取り込む。
2. When 「引っ越し」で転送が完了した場合, the G2G Transfer System shall 移行元でグループ X に属していたユーザー U が、移行後も U のアカウントでグループ X 公開ページを閲覧できる状態にする。
3. Where 「引っ越し」で置き換えられるコレクションについて, the G2G Transfer System shall 一意制約の衝突を理由に転送を中断しない。
4. While 置き換えを実行している間, the G2G Transfer System shall 移行先の通常利用者に、置き換えが途中の状態のデータを提供しない。
5. If 「引っ越し」の取り込みが途中で失敗した場合, then the G2G Transfer System shall 失敗したことと移行先が中途の状態にあることを操作者へ通知する。
6. Where 「引っ越し」が選択されている場合, the G2G Transfer System shall ユーザー・ユーザーグループ・グループ関係・外部連携アカウントを常に同じ転送に含める（一部だけを転送対象から外せないようにする）。
7. If 取り込みが実行されている間に別の取り込みを開始しようとした場合, then the G2G Transfer System shall その開始を拒否し、拒否したことと「取り込みが実行中である」という理由を、開始を試みた側へ届ける。届かなければ操作者には理由の分からない失敗になり、拒否そのものが目的を果たさない。
8. When 「引っ越し」の取り込みが完了した場合, the G2G Transfer System shall 取り込みに失敗したコレクションが 1 つも無ければ移行先を通常の状態へ戻し、1 つ以上あれば通常利用者を通さない状態を保ったまま操作者へ通知する。**ただし 2.9 が優先する**——引っ越しは設定コレクションを必ず含むため、失敗が 1 つも無くても移行先は保守モードのまま残り、操作者が自分で解除する。前半が実際に効くのは、設定コレクションを含まない従来モードの取り込みだけになる。この前後関係は 9.3 の実装時に決着させた（実装後の検証で「一部しか満たされない」と判定されたのはこの文言の古さによるもので、挙動の欠陥ではない）。
9. When 設定コレクションが取り込まれた場合, the G2G Transfer System shall 取り込みの後も移行先を保守モードにしたままにし、操作者が自分で解除するまで通常利用者を入れない。設定コレクションの取り込みは移行先のあらゆる設定を移行元のもので置き換えるため、そのまま通常利用者へ提供してよい状態にはならない（転送では、さらに添付ファイルが 1 件も届いていない）。
10. When 操作者が取り込みまたは転送を開始しようとした場合, the G2G Transfer System shall 完了後に保守モードを操作者自身が解除する必要があることを、開始前に提示する。転送の場合は保守モードになるのが**移行先**であり、解除は移行先の管理画面から行うことを示す。

### Requirement 3: 転送を始める前に、失われるものと危険を提示する

**Objective:** G2G 転送を行う管理者として、何が削除され、誰がログインできなくなるのかを、転送を始める前に知りたい。重い処理を終えた後に中断されたり、転送後に初めて気づくのを避けるため。

#### Acceptance Criteria

1. Where 「引っ越し」が選択されている場合, when 操作者が転送を開始しようとした場合, the G2G Transfer System shall 移行先が現在保持しているユーザー・ユーザーグループ・ページの件数を提示し、それらが削除されることを示す。
2. Where 「引っ越し」が選択されている場合, the G2G Transfer System shall 操作者の明示的な確認を得るまで、アーカイブの生成も移行先への送信も開始しない。
3. If 操作者が確認を行わなかった場合, then the G2G Transfer System shall 移行先のデータを変更しない。
4. If 移行元と移行先でパスワードの種が異なる場合, then the G2G Transfer System shall 移行したユーザーが従来のパスワードでログインできなくなることを転送開始前に警告し、操作者が承知した場合に限り転送を続行する。
5. If 移行先にログインできる状態の管理者が居ない場合（管理者がパスワードを持たない、または管理者が有効な状態でない）, then the G2G Transfer System shall 転送後に管理者のログイン手段が残らないことを転送開始前に警告し、操作者が承知した場合に限り転送を続行する。
6. The G2G Transfer System shall パスワードの種そのものを移行元と移行先の間で送受信せず、一致するか否かの判定だけを行う。
7. If 移行先のセッションの保存方式がセッションの列挙に対応しない場合, then the G2G Transfer System shall 置き換えられたユーザーのセッションを無効にできないことを転送開始前に警告し、操作者が承知した場合に限り転送を続行する。

### Requirement 4: 移行先の管理者を救済する

**Objective:** G2G 転送を行う管理者として、移行先のユーザーが置き換えられても移行先へログインできる口を残してほしい。転送が途中で失敗しても、誰も入れない移行先が残らないようにするため。

#### Acceptance Criteria

1. When 「引っ越し」でユーザーが置き換えられた場合, the G2G Transfer System shall 移行先で管理者権限を持ち、かつログインできる状態にあったアカウントを転送後も残す。
2. When 管理者アカウントが救済された場合, the G2G Transfer System shall 救済前と同じパスワードでログインできる状態を保つ。
3. When 管理者アカウントが救済された場合 and 救済対象の識別子が移行元のユーザーの識別子と衝突しない場合, the G2G Transfer System shall 救済前と同じ識別子を保ち、転送前に確立されていたログインセッションが引き続き使える状態にする。
4. If 救済するアカウントの `username` が移行元のユーザーと衝突する場合, then the G2G Transfer System shall 移行元に存在しない `username` へ付け替えて救済する。
5. If 救済するアカウントの `email` が移行元のユーザーと衝突する場合, then the G2G Transfer System shall その `email` を持たない状態で救済する。
6. When 救済によって `username` が変わった場合, the G2G Transfer System shall 変更後の `username` を操作者へ通知する。
7. When 管理者アカウントが救済された場合, the G2G Transfer System shall 移行元のグループ関係を救済されたアカウントに付与しない。
8. If 「引っ越し」の取り込みが途中で失敗した場合 and 移行先に救済対象の管理者が存在していた場合, then the G2G Transfer System shall 移行先に管理者権限でログインできるアカウントが 1 つ以上残る状態を保つ。
9. When 管理者アカウントが救済された場合, the G2G Transfer System shall その管理者が転送前に発行していたアクセストークンを転送後も使える状態にする。
10. If 救済対象の識別子が移行元のユーザーの識別子と衝突する場合, then the G2G Transfer System shall 新しい識別子で救済し、転送前のセッションが失われることを操作者へ通知する。

### Requirement 5: 置き換えても残るもの、無効になるもの

**Objective:** G2G 転送を行う管理者として、置き換えによって転送そのものや移行先の環境設定が壊れないでほしい。転送を完走させ、移行先を移行先として使い続けるため。

#### Acceptance Criteria

1. While 転送が進行している間, the G2G Transfer System shall その転送に使われている転送キーを失わせない。これはコレクションの置き換えによる消失だけでなく、**時間の経過による失効**も含む（転送の所要時間がキーの寿命を超えても、進行中の転送の後続の要求が通ること）。
2. When 転送対象コレクションの取り込みが完了した場合, the G2G Transfer System shall 続く添付ファイルの転送を完走させる。
3. The G2G Transfer System shall 転送の前後で、移行先のファイルアップロード設定を変えない。
4. The G2G Transfer System shall 転送の前後で、移行先のサイト URL 設定を変えない。
5. When 「引っ越し」でユーザーが置き換えられた場合 and 移行先のセッションの保存方式がセッションの列挙に対応する場合, the G2G Transfer System shall 置き換えられたユーザーのログインセッションを無効にする（救済されたアカウントのセッションを除く）。
6. The G2G Transfer System shall 移行先の運用状態を持つコレクション（転送キー・移行スクリプトの適用記録・セッション・監査ログ・進行中ジョブの状態・添付ファイルの実体・共同編集の作業データ等）を転送対象に含めない。判断の基準は「GROWI のコンテンツではなく、その環境の運用状態を持つかどうか」とする。
7. The G2G Transfer System shall 転送対象に含めないコレクションの一覧を 1 か所で宣言し、転送を組み立てる側・受信して拒否する側・転送画面に選択肢を出す側のすべてがその宣言を参照する。ただしバックアップ用のエクスポート画面の選択肢は減らさない（そちらは転送とは別の目的を持つため）。
8. When 操作者が転送対象に宣言されたコレクションを選んだ場合, the G2G Transfer System shall そのコレクションを転送から除いて残りの転送を続行する（転送全体を失敗させない）。

### Requirement 6: 従来モードの挙動を変えない

**Objective:** 保守者として、既存データに追加する転送が従来どおり動いてほしい。既に出荷済みの能力と、そこに入れた安全網を失わないため。

#### Acceptance Criteria

1. Where 「既存データに追加する」が選択されている場合, the G2G Transfer System shall 転送対象コレクションの取り込み・添付ファイルの転送・進捗の完了通知について、従来の挙動を変えない。**ただし次の 4 点だけは意図的に従来と変える。**（前の 2 点は本 spec で決めたもの、後の 2 点は他の要件の帰結として従来モードにも及ぶもの。実装後の検証で洗い出した。）
   - **2.9 は従来モードにも適用する**（設定コレクションを取り込んだ移行先は保守モードで残り、操作者が解除する）。設定の置き換え自体は従来モードでも起きており、そこへ通常利用者を入れてよい理由が無いため。
   - **1.4 のとおり、判定の対象になるコレクションでは置き換えを選択肢に出さない**。今の画面は設定・利用者・ページ以外のコレクションで置き換えを選べるので、たとえば「グループだけを置き換えて他は追加する」指定が作れる。これは 1.3 が禁じたい混在そのもので、ユーザーとグループとグループ関係の整合が崩れた移行先を作る。**同じ能力は手動 zip 取り込み画面に残す**（本 spec の対象外）ので、製品から失われるわけではない。
   - **一部のコレクションの取り込みが失敗したとき、従来モードでも完了ではなく失敗として通知する**（要件 2.5 の帰結）。従来は移行先で起きた失敗が移行元に伝わらなかった。
   - **転送対象に含めないと宣言したコレクションは、従来モードでも転送から除かれる**（要件 5.6 / 5.8 の帰結）。従来は操作者が選べば転送キーや移行スクリプトの適用記録まで送られていた。
2. Where 「既存データに追加する」が選択され、置き換えられないコレクションに一意制約の衝突がある場合, the G2G Transfer System shall どのコレクションの取り込みも開始せず、衝突の内容を操作者へ通知する。
3. The G2G Transfer System shall 転送キーの保護とパスワードの種の警告を、選択された転送方法にかかわらず適用する。

### Requirement 7: 実データベース上で検証できる

**Objective:** 保守者として、置き換えと救済が実データベース上で検証されるようにしてほしい。モックでは表面化しない一意制約・関係解決・ログイン可否の挙動を担保するため。

#### Acceptance Criteria

1. The G2G Transfer System shall 引っ越しモードの置き換えと管理者の救済について、移行先に既存データを持つ実データベース上で検証できるようにする。
2. The G2G Transfer System shall 置き換えの後に「あるユーザーに紐づくグループ ID 集合」が移行元と同じ対応になること（＝グループ公開ページが当該ユーザーから到達可能であること）を実データベース上で検証できるようにする。
3. The G2G Transfer System shall 救済されたアカウントが救済前のパスワードでログインできることを実データベース上で検証できるようにする。
4. The G2G Transfer System shall 転送が進行している間に転送キーが失われないことを、コレクションの置き換えと時間の経過の両方について検証できるようにする（キーの寿命を超えた状態を作って後続の要求が通ることを確かめる）。
5. The G2G Transfer System shall 転送対象に含めないコレクションの宣言を、実データベースに存在するコレクションの一覧と突き合わせて検証できるようにする（新しいコレクションが増えたときに、宣言に加えるべきかを機械的に気づけるようにする）。
