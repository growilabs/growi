# Implementation Plan

> **2 段階で出す**。タスク 1〜6（**第 1 段**）は引っ越しモードが無くても効く既存不具合の修正で、**単独で出荷できる**（v8.0.1 に載せる想定）。移行先を破壊しない変更しか含まないので、確認も軽く済む。タスク 7〜11（**第 2 段**）が引っ越しモードの本体で、既定の意味を破壊的な置き換えに変えるため、独立したレビューと確認の期間を取る。
>
> **前提**: 衝突検知ゲート（spec `g2g-import-conflict-detection`、PR #11643）がマージ済みであること。第 1 段のタスク 6 はそのゲートの調整で、第 2 段はゲートの部品（アーカイブからの一意フィールド抽出）を公開して再利用する。
>
> **タスク 1 が両段の前提**。第 1 段の検証も設定コレクションを空にするため、worker を専有させる土台が無いと他の結合試験を壊す。
>
> **設計の要点**: 判断に使う状態と、その状態に触る経路は design.md の「状態ごとの経路の棚卸し」に表として残してある。保守モードの旗・転送キーの寿命・展開先のディレクトリを触るタスク（3, 4, 9）は、着手前にその表を読むこと。11 巡のレビューで繰り返し出た誤りは「同じ状態に触る経路のうち 1 本しか直さない」ことだった。

## 第 1 段: 引っ越しモードと独立に効く修正（v8.0.1）

- [x] 1. 置き換えを伴う結合試験を worker 専有で走らせる土台を作る
  - 設定コレクションは取り込み方法が置き換えに強制されるため、**第 1 段の検証もコレクションを丸ごと空にする**。試験用データベースは worker ごとの共有で、既存の G2G 結合試験は接頭辞つきの固定データを選んで消す方式なので、丸ごと空にする試験は同じ worker の他ファイルを壊す。
  - 専用ファイルに切り出すだけでは足りない。**専用のプロジェクトを 1 つ追加し、既存のプロジェクトの除外に同じ対象を足す**。
  - **実装時の訂正**: 分離は worker の専有（`singleFork`）では成立しなかった。1 つの worker に全ファイルが入ると、mongo のセットアップがファイルごとに in-memory サーバを停止するため、2 つ目以降のファイルが停止済みのサーバへ繋ぎに行く。**データベース名で分離する**（vitest の `provide` / `inject` で名前空間を渡す）。あわせて、新しいプロジェクトは `test:integ` に足さないと CI ではどのジョブからも実行されない。
  - Observable: 置き換えを伴う試験が専有の worker で走り、既存の結合試験と連続実行しても他ファイルが落ちない。
  - _Requirements: 7.1_

- [x] 2. 転送対象に含めないコレクションを宣言して除く
- [x] 2.1 その環境の運用状態を持つコレクションの宣言と判定を作る
  - 「GROWI のコンテンツではなく、その環境の運用状態を持つ」を基準として宣言のそばに書き、転送キー・移行スクリプトの適用記録・変更ストリームの再開位置・セッション・通信量の制限・監査ログとその同期状態・進行中ジョブの状態・送信失敗キュー・モデルカタログの控え・Vault の同期状態・添付ファイルの実体・共同編集の作業データを列挙する。
  - 実データベースのコレクション一覧から転送してよいものだけを返す判定を用意する。
  - 判断が分かれうるもの（`vault_instructions` / `growiplugins` / `vault_namespace_state` / `vault_user_views`）は、そのコレクションを使う機能のコードを読んで根拠を確認してから確定させる。**除外しすぎる誤りも同じ重さで扱う**（コンテンツを持つものを誤って入れると引っ越しでデータが移らない）。迷うものは「移す」側に倒す。
  - Observable: 宣言と判定の unit がグリーンで、実データベースの一覧を渡すと帳簿系が除かれた一覧が返る。
  - _Requirements: 5.6, 5.7_
  - _Boundary: non-transferable-collections_

- [x] 2.2 宣言と実データベースの差分を検出する試験を置く
  - 実データベースに存在するコレクションの一覧と宣言を突き合わせ、宣言にも「転送してよい」側にも現れない新しいコレクションを検出する。
  - 新しいコレクションが増えたときに人が判断できるだけの情報（コレクション名の一覧）を失敗メッセージに出す。
  - Observable: 実データベースに対して試験がグリーンで、宣言から 1 つ削ると赤くなることを確認済み。
  - _Requirements: 7.5_
  - _Boundary: non-transferable-collections_
  - _Depends: 2.1_

- [x] 2.3 押す側が送る前に除き、受信側は安全網として拒否する
  - 押す側のサーバ（転送を起動する前）で、操作者が選んだ対象から宣言のコレクションを除く。**クライアントの表示だけに頼らない**（画面を経由しない呼び出しでも効かせるため）。
  - 対になる取り込み方法の指定からも同じキーを除く（片方だけ絞ると、残った指定を後段の整合条件が誤判定する）。
  - 受信側は、宣言のコレクションが含まれた要求を取り込み開始前に拒否する（通常経路では到達しない安全網）。
  - Observable: 既定で全コレクションが選択された状態で転送しても、転送キーと移行スクリプトの適用記録が移行先で取り込みの前後とも変わらず、残りの転送は成功する。
  - _Requirements: 5.1, 5.6, 5.8, 6.3_
  - _Boundary: 押す側ルート, 受信ルート_
  - _Depends: 1, 2.1_

- [x] 2.4 G2G 画面に出す一覧を返す口を足し、クライアントの除外リストを消す
  - 押す側に「転送してよいコレクションの一覧」を返す口を足し、G2G の画面はそれを使う。クライアントは自前の除外リストを持たない。
  - **バックアップ用のエクスポート画面が使っている一覧の口は変更しない**。あちらは目的が違う（バックアップに含めて安全なもの全部）ので、選択肢を減らしてはならない。
  - Observable: G2G の画面に帳簿系のコレクションが出なくなり、バックアップ画面から選べるコレクションは減っていない。
  - _Requirements: 5.7_
  - _Boundary: 押す側ルート, G2GDataTransfer_
  - _Depends: 2.1_

- [x] 3. 転送キーが転送中に失効しないようにする
- [x] 3.1 受信側で、要求の先頭から応答の終わりまでキーの寿命を延ばす
  - キーの検証の直後に延長を始め、応答が閉じたときに止める（完了のイベントだけでは接続が切れたときに止まらず、寿命が無期限に延びる）。
  - 延長は一定間隔で寿命を現在時刻へ進める。無操作で失効するという意味は保つ。
  - 1 回の要求の中に zip のネットワーク受信・展開・版の照合・衝突検知・取り込み・v5 正規化が全部入るので、**取り込みの間だけ延ばす形にしない**。
  - Observable: 寿命より長くかかる取り込みを作っても（1 コレクションの取り込みを遅延させる）、その後の添付の受信が拒否されない。
  - _Requirements: 5.1, 5.2, 7.4_
  - _Boundary: 受信ルート_
  - _Depends: 1_

- [x] 3.2 押す側で、アーカイブを作っている間もキーの寿命を延ばす
  - エクスポートと zip 生成の間は移行先へ要求が 1 本も届かないので、一定間隔で移行先へ要求を出して寿命を延ばし、終わりに止める。
  - 延長には**移行先の状態を問う既存の口を使わない**（あれは移行先のストレージへ書き込み試験のファイルを残す）。寿命を延ばして応答するだけの軽い口を足す。
  - Observable: エクスポートがキーの寿命より長くかかっても、アーカイブの受信が拒否されない。
  - _Requirements: 5.1, 5.2, 7.4_
  - _Boundary: PusherService, 受信ルート_
  - _Depends: 3.1_

- [x] 4. 取り込みの共通処理の 3 点を直す
- [x] 4.1 設定の取り込みの後に、保守モードを立てる
  - 設定コレクションは必ず置き換えられるため旗が DB から消え、移行先は「他人の設定で動いていて、転送なら添付が 1 件も届いていない」状態になる。設定の取り込みの後に**常に `true`** を書き、以後のあらゆる再読込が閉じた状態を読むようにする。
  - **取り込みの共通処理は旗を下ろさない。** 下ろすのは操作者で、開始前に予告する（4.4）。
  - **設定の取り込みが失敗した場合も立てる**。空にした後に失敗すると DB に旗が無い状態で残る。
  - 書き込みの完了を待ってから取り込みの末尾の再読込へ進むことをコードで保証する（横で走らせない）。
  - Observable: 設定を含む取り込みの後、**DB 上の**旗が、取り込み前の値にもアーカイブの値にも関わらず `true` になる。設定の取り込みだけを失敗させても `true` になる。書き込みを外すと赤くなることを確認済み。
  - _Requirements: 2.4, 2.9, 6.1_
  - _Boundary: ImportService_
  - _Depends: 1_

- [x] 4.4 取り込み／転送の開始前に、保守モードで残ることを予告する
  - 管理画面の zip 取り込みと G2G の転送開始の両方で、開始前にモーダルを出す。「完了後にご自身で保守モードを解除してください」。
  - **転送側は保守モードになるのが移行先であることと、解除は移行先の管理画面から行うことを明記する**（操作者が見ているのは移行元の画面で、移行元には転送キーしか無い）。
  - 文言は英語のみ。他言語は後続タスク（本機能のゲートにしない）。
  - 第 2 段のタスク 10.2 が確認モーダルを入れるので、そちらが出たらこの予告はそこへ畳む。
  - Observable: 承知するまで取り込みも転送も始まらない。
  - _Requirements: 2.10_
  - _Boundary: ImportForm, G2GDataTransfer, admin locales_
  - _Depends: 4.1_

- [x] 4.2 取り込みの同時実行を拒否する
  - 「取り込みの作業が動いている」という状態を取り込みの共通処理に 1 つ持たせ、**G2G の受信と管理画面からの取り込みの両方が、zip を受け取る前にそれを取る**。守りたい区間は共有ディレクトリに何かを書き始めた瞬間から取り込みが終わるまで。
  - **状態を 2 つに分けない**。分けると受信側の展開・版の照合・衝突検知の間が無防備になる。進捗表示のための既存の状態も流用しない（取り込みループを抜けた直後に戻るので、v5 正規化の間が「取り込み中でない」と見える）。
  - 解放の合図は入口ごとに違う。G2G の受信は zip を受け取る処理より前で取るので応答が閉じたときにも解放する（そうしないと、アップロード中に接続が切れたときに以後すべての取り込みが永久に拒否される）。管理画面からの取り込みは応答を先に返して非同期に続けるので、そちらは従来どおり処理の終わりで解放する。
  - 受信の一時ファイル名を要求ごとに一意にする（押す側が付ける名前は現状すべての転送で同じなので、名前の衝突自体を消す）。
  - 拒否されたことが押す側に分かるよう、押す側の失敗処理に対応する枝を足す（足さないと汎用のエラーになる）。
  - Observable: 1 本目の取り込み中に 2 本目を送ると拒否され、1 本目の展開済みファイルが上書きされない。押す側には取り込み中である旨が届く（**アーカイブがまだ届き終わっていない状態で拒否が決まる場合でも**。小さなアーカイブでは送信が先に終わってしまうため、この条件を課さないと、実際には届かない実装でも試験が通る）。`.zip` 以外を送った後・アップロードを中断した後でも、次の取り込みが受け付けられる。
  - _Requirements: 2.7, 2.1_
  - _Boundary: ImportService, 受信ルート, PusherService_
  - _Depends: 1_

- [x] 4.3 取り込みに失敗したコレクション名を戻り値で返す
  - 現在はコレクション単位の例外を内部で握ってログとイベント通知だけを行い、呼び出し元が失敗を知る手段が無い。**エラーを握って続行する方針は変えず**、事実だけを返す。
  - 呼び出し元の最小限の型定義と、その型を使っている単体試験のモックを戻り値の形に追随させる（型検査の対象に試験ファイルも含まれるため）。
  - Observable: 特定のコレクションだけを失敗させると（存在しないファイル名を指すか、トークン自体が不正な JSON を置く）その名前が戻り値に載り、失敗を仕込まなければ空になる。
  - _Requirements: 2.8_
  - _Boundary: ImportService_

- [x] 5. 取り込みの失敗を移行元の管理者へ届ける
  - 移行元と移行先は別プロセスで、進捗の通知は移行元プロセスから出るため、**移行先で起きた失敗が移行元へ渡る経路は受信側の応答本体だけ**。
  - 押す側は現在この応答本体を読んでいないので、読んで通知に載せる。失敗したコレクションがあれば完了ではなく失敗として通知する。
  - 進捗の型に文字列を運ぶ余地が無いので、失敗の内容を載せられる形に広げる。
  - Observable: 一部のコレクションが失敗した転送で、移行元の管理者に届く通知が完了ではなく失敗になり、どのコレクションかが分かる。
  - _Requirements: 2.5, 2.8_
  - _Boundary: 受信ルート, PusherService_
  - _Depends: 4.3_

- [x] 6. 衝突検知が置き換え対象のコレクションで誤って止めないようにする
  - 取り込み設定から置き換え対象のコレクション名の集合を導く判定を作る（モード名を受け取らず、渡された設定だけを見る）。
  - 受信ルートでその集合を組み立てて検知へ渡し、含まれるコレクションを検知の対象から外す。置き換えられるコレクションは取り込み時に一意違反が起きないため。
  - Observable: グループを置き換えに指定した転送が、移行先に同名のグループがあっても中断されずに成功する。置き換えを含まない転送では従来どおり衝突で中断する。
  - _Requirements: 2.3, 6.2_
  - _Boundary: replace-target-collections, detect-unique-conflicts, 受信ルート_
  - _Depends: 1_

## 第 2 段: 引っ越しモード本体

- [x] 7. 判断の中核を純関数として作る
- [x] 7.1 (P) 転送計画の組み立てと取り込み方法の整合条件
  - 引っ越しでは転送可能なコレクションすべてを対象にし、すべてに置き換えを割り当てる（操作者に選択させない）。従来では操作者の選択をそのまま計画にする。
  - **ページとリビジョンには追加のオプションを必ず載せる**。受信側の取り込み設定の生成はキーの存在で判定し、無ければ例外を投げるため、載せないと引っ越しの転送が取り込み設定を作る段階で必ず失敗する。値は既存の既定値をそのまま使う。
  - 整合条件は「すべて置き換え」か「置き換えを含まない」のどちらかで、**取り込み方法がシステム側で強制されるコレクションは判定から外す**（設定は置き換えのみ、ページは追加が不可で許される方法が 2 つあるため、強制される方法の対応とは別の宣言に分ける）。判定は渡された対象の範囲だけを見る。
  - Observable: 組み立てた計画をそのまま受信側の取り込み設定の生成に通して例外が出ない。設定=置き換え＋ユーザー=追加（従来モードの通常の形）を整合と判定する。
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 2.1, 2.2, 2.6, 6.1_
  - _Boundary: g2g-transfer-preset_

- [x] 7.2 (P) 移行先の管理者の救済内容の算出
  - **アーカイブ側の一意フィールドと識別子の集合を返す公開関数を、衝突検知のモジュールに足す**（現在は抽出処理も一意フィールドの宣言も非公開で、公開されているのは衝突の判定だけ）。救済はこの集合を使って付け替え先を保証する。
  - 管理者権限を持ち、かつログインできる状態のユーザーだけを対象にする。
  - パスワードのハッシュ・管理者権限・識別子を保持し、移行元と衝突する `username` は付け替え、衝突する `email` と `slackMemberId` は外す（一意フィールドは 3 つある。対象の一覧は上で公開した宣言を単一の出所として参照する）。
  - その管理者が発行していたアクセストークンも救済の対象に含め、識別子を再割り当てした場合はトークンの参照も合わせる。
  - 識別子が移行元のユーザーと衝突する場合は新しい識別子で救済し、セッションが失われることを通知内容に含める。移行元のグループ関係は付与しない。
  - Observable: 4 分岐（付け替え・email 除去・`slackMemberId` 除去・識別子の再割り当て）の unit がグリーンで、出力がハッシュと管理者権限を保持している。
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 4.7, 4.9, 4.10_
  - _Boundary: rescue-admins, detect-unique-conflicts_
  - _Depends: 6_

- [x] 7.3 (P) 転送を止める事由と、承知を求める警告の算出
  - 既存の互換チェック（バージョン不一致・利用者数上限・アップロード設定・保存先の書き込み可否・総容量）を中断事由として移設する。挙動は変えない。
  - 警告は 4 つ。パスワードの種の不一致、移行先にログインできる管理者が居ないこと、セッションを無効化できない保存先であること、**移行元がローカル認証を無効にしていること**（設定は必ず置き換えられるので、救済した管理者もパスワードで入れなくなる）。
  - 判別可能な値を表示用の文字列に変換する関数を用意し、既存の呼び出し元が使っている文字列はそこを通して組み立てる。
  - Observable: 既存の中断事由が維持され、4 つの警告がそれぞれ条件どおりに出る。ログインできる管理者が 1 人でも居れば警告が出ない（数だけを見た偽陽性が起きない）。
  - _Requirements: 3.4, 3.5, 3.7, 6.3_
  - _Boundary: g2g-transfer-transferability, PusherService_

- [x] 8. 転送前の点検の経路を作る
- [x] 8.1 受信側が自分の状態を答える
  - 移行先の件数（ユーザー・ユーザーグループ・ページ）、パスワードの種の指紋、ログインできる管理者の数、セッションを選んで無効化できる保存先かどうかを、既存の状態を答える口に足す。
  - 種は**一方向のハッシュだけを送る**。値そのものは送らない。件数は数値のみで、ユーザー名やメールアドレスは返さない。
  - セッションを選べるかの判定と、後段で実際に破棄するときに使う手段を、**同じ判定から作る**（別々に作ると「対応している」と申告して 1 件も破棄しない状態になる）。

## Implementation Notes

第 2 段の実装中に見つかった、後続タスクが引き継ぐべき事実だけを書く。

- **9.3 / 10.3 は救済の結果をそのまま移行元へ返してはいけない**（7.2 のレビューで判明）。`AdminRescuePlan` は再投入のためのデータなので、移行先の管理者のパスワードのハッシュ・`apiToken`・アクセストークンの `tokenHash` を含む。design.md の `ImportCollectionsResult.rescue: AdminRescuePlan | null` を文字どおり実装して進捗通知に載せると、それらが移行元のサーバを経由して移行元の管理者のブラウザまで届く。通知に必要な値（`originalUsername` / `rescuedUsername` / `emailRemoved` / `slackMemberIdRemoved` / `idReassigned` / `notLoginable`）は別のフィールドに分かれているので、応答本体を組み立てる側でそれだけを取り出すこと。
- **引っ越しの転送は、成功しても移行先を保守モードのまま残す**（9.3 で確定。要件 2.9 / 2.10 / 6.1 がもともとそう定めている）。設定コレクションが必ず含まれるため。副作用として、要件 2.8 の「失敗が無ければ通常の状態へ戻す」は引っ越しでは到達しない（従来モードで設定を含まない転送でのみ効く）。2.8 と 2.9 の言い回しは spec の後始末で揃えること。
- **11.2 は「ページを置き換え ＋ 他は追加」で保守モードが立たないことを必ず確かめる**（9.3 のレビューで判明）。保護の条件から引く集合を `COLLECTIONS_EXCLUDED_FROM_COHERENCE` から `FORCED_MODE_COLLECTIONS` に変えても、9.3 時点の 171 試験は全部通る。区別できる試験を持っているのは 11.2 だけ。
- **10.3 は「取り込みが例外で抜けた」ことを完了通知で失敗として扱う**（9.3 で応答本体に印を足し、押す側の既存の失敗判定にその条件を 1 つ足してある）。文言と画面表示は 10.3 の担当。印を落とすと、失敗した取り込みが緑の成功として通知される（要件 2.5 違反）。
- **9.3 のセッション破棄まわりで知っておくこと**（9.2 のレビュー）。ストアの失敗は件数に混ぜず例外として外へ出る形にしてあるので、`finally` の中で受けて応答は成功のまま返すこと。途中で失敗するとそこまでに破棄した件数は例外と一緒に失われるので、ログの文言は件数が無い場合を想定して書く。また `connect-mongo` の暗号化（`crypto.secret`）を将来有効にすると全セッションが読めなくなり、この関数は「やり終えた、対象は無かった」を返す（要件 5.5 の黙った未達）。読めなかった件数をログの項目として分けて出しておくと、その状態が観測できる。
- **9.3 が移行先の管理者を読むときの読み方**（7.2 の実装メモ）。管理者は `lean()` か明示的な projection で読む（`toObject()` は `password` / `apiToken` を落とすため救済に使えない）。アクセストークンは `tokenHash` と `user` を含む projection で読む（`findTokenByUserId` は使えない）。
- **8.1 は `IDataGROWIInfo` に警告用の 3 フィールドを足すだけで足りる**（7.3 の実装）。判定側の型 `TransferabilityDestination` は `TransferabilityBlockerDestination` を継承する形になっており、`IDataGROWIInfo` がフィールドを満たせば構造的に代入できる。判定モジュール側の書き換えは要らない。あわせて `IDataGROWIInfo.fileUploadDisabled` は 7.3 でどこからも読まれない値になったので、8.1 で同じ型を触るときに廃止するか判定へ戻すかを決めること。
- **`IDataGROWIInfo.fileUploadDisabled` は 8.1 で廃止した**（OpenAPI の記述も削除）。`attachmentInfo.type === 'none'` と同じ事実を同じオブジェクトに二重に持っていただけで、読む側はもう居ない。バージョンが違う相手との組み合わせは、そもそもバージョン不一致が先頭の中断事由になって早く止まるので問題にならない。
- **セッションの手段は design.md の契約どおり**（8.1 で `SessionAccess` の記述を実装に合わせて更新済み）。9.2 は `resolveSessionAccess` が返す 3 種類を取りこぼしなく分岐すればよく、`canSelectSessions` を作り直す必要はない。
- **従来モードで混在を作れる状態は、9.1 のゲートだけでは塞げない**（9.1 のレビューで判明、2026-08-10 にユーザー判断）。`ImportCollectionItem` の選択肢は `configs` / `users` / `pages` しか制限しておらず、それ以外は置き換えも選べる。受信側のゲートだけを足すと、画面が提示した組み合わせをサーバが断る状態になる。**決定: 画面側でも塞ぐ（10.1 で従来モードから置き換えを外す）** うえで、受信側のゲートは古い版の移行元からの要求に対する安全網として残す。要件 1.4 / 1.5 / 6.1 をこの決定に合わせて更新済み。
- **断られた理由がどのコレクションのせいかは、まだ応答にもログにも出ない**（9.1 のレビューの指摘、未対応）。出すなら受信ルートではなく 7.1 の `g2g-transfer-preset.ts` 側に内訳を返す関数を足すこと（受信ルートに条件分岐を書かない、という 9.1 の約束を守るため）。取り込み方法は固定の列挙値なので、コレクション名と方法を出しても利用者のデータは漏れない。
- **確認モーダルは中断事由を出さないまま出荷する**（10.3 で確定）。design.md の Error Handling が「中断事由＝押す側が `growi_incompatible_to_transfer` で返して転送を開始しない」「警告＝確認モーダルで承知を求める」と書き分けており、実装はそのとおり。ただし操作者は「移行先のデータを全部消す」に同意してから断られる流れになる。改善するなら一番安いのは、確認モーダルを開く前に preflight の `blockers` が空でないかを見てその場で知らせる形（クライアント側だけで閉じる）。中断事由 5 種をモーダル本体に出すなら、値の補間（バージョン・バイト数・上限）が要るので 60〜100 行規模になる。**別タスクとして起票すること。**
- **g2g の結合試験は共有 MongoDB との接続がまとめて切れる形で間欠的に落ちる**（9.3・10.2 で実装者・レビュアー・統括役が独立に観測）。`MongoNetworkError: connection N to 172.18.0.2:27017 closed` がファイルの準備段階で出て、複数ファイルが試験を 1 件も実行せずに終わる。落ちるファイルはそのとき変更したファイルとは無関係で、直後の再実行は通る。**接続エラーとして現れるとは限らない**——11.1 のレビューでは、同じ切断が起きた実行で「応答は 200・失敗コレクションも空なのに、取り込んだはずのユーザーが DB に居ない」という assertion の失敗として現れた（同時刻に別ファイルが `MongoBulkWriteError: connection closed` で落ちていた）。取り込みの一括書き込みは書き込みエラーを集めて先へ進む作りなので、切断がこの形に化ける。第 2 段の変更を戻した基点では 8 回中 8 回成功しているので、ファイルが増えて worker への割り当てが変わり、`test/setup/mongo/index.ts` がファイルごとに接続を切る作りの危うさが表に出た、という見立てが今のところ最も説明が付く。**11 群でこれに当たったら、まず単独で走らせて切り分けること。**本 spec の範囲外なので別途追跡する。
- **転送方法を往復すると従来モードの選択が既定へ戻る**（10.1 のレビューで実測）。引っ越しでは対象選択の部品をそもそもマウントしないので、従来へ戻したときに再マウントされ、取り込み方法の初期化が走り直す。画面の表示も同時に戻るため、画面と送信内容が食い違うことはなく、戻り先は常に整合する既定値——つまり送信の誤りではなく操作感の問題。直すなら 10.2 以降で「選択を保持する」か「戻したことを操作者に示す」かを決める。
- **10.2 が読む点検の応答は、文言ではなく種類（判別可能な union）で返る**（8.2）。`POST /_api/v3/g2g-transfer/preflight` は `{ destinationCounts, blockers, warnings }` を返し、`blockers` / `warnings` は `type` を持つ値のまま。表示は `describeBlocker` / `describeWarning` を通すか、クライアント側で `type` に応じて翻訳する。10.3 の文言一覧には警告 4 種しか入っていないので、確認モーダルが中断事由も出すなら中断事由 5 種の鍵も足すこと。
- **結合試験でルータを app の直下に mount しない**（8.2 のレビューで判明）。`loginRequiredFactory` は `req.baseUrl` が `/_api/...` に一致するかで「未ログインを 302 で転送するか 403 を返すか」を変える。本番と同じ `/_api/v3` + `/g2g-transfer` の下に mount しないと、本番では起きない応答を固定してしまう。
- **中断事由の判定と警告の判定は入口が分かれている**（7.3 のレビューで確定）。`evaluateBlockers` は警告用の入力を持たない呼び出し元のためのもので、8.2 の点検の口は `evaluateTransferability` を呼ぶ。警告用の 4 入力は「未確認」を表す無難な値が存在しない（どれも警告が出ない側に倒れてしまう）ため、必須フィールドとして型で作れなくしてある。省略可能に戻さないこと。

- **応答本体の `rescue` は `rescueApplied` と必ず併せて読む**（最終ゲートの留保）。`{rescued: []}` は単体では「救済を計画したが再投入に失敗した」と「計画して成功したが対象が 0 人だった」の両方を意味する。`rescue` が null かどうかは「救済を計画したか」の合図で、従来モードと引っ越しの失敗を区別する唯一の手がかりでもある（従来モードも `rescueApplied: false` を返すため）。この応答を読む 3 人目が現れたときに誤読しやすい。
