# Brief: user-activities

## Problem

ユーザーページの「最近の活動」は、`GET /_api/v3/user-activities` が返す操作履歴の一覧を表示している。この API について、次の点を定めた仕様の文書が無い。

- 誰が、誰の履歴を取得できるか
- どのページへの操作を一覧に含めるか（閲覧者の閲覧権限との関係）
- 操作対象のページについて、どの項目を返すか
- 総件数を何の件数として返すか

仕様が無いため、この API を変更する人は「何を守れば正しいか」を実装から読み取るしかない。API を画面以外から直接呼ぶ利用者（アクセストークンなど）にとっても、応答に何が含まれるかの約束が無い。

## Current State

- 実装は `apps/app/src/server/routes/apiv3/user-activities.ts`（集計の組み立て）と `apps/app/src/server/service/activity/aggregate-user-activities.ts`（集計の実行）にある。
- 画面は `RecentActivity` コンポーネントと `useSWRxRecentActivity` がこの API を使う。
- 既存のテストは集計の形を確認するもので、「誰に何を返すか」を確認するテストは無い。
- `.kiro/specs` には、この API の応答を扱う spec が無い。`activity-log` は「何を記録するか」を担当し、読み出し側は範囲外である。
- GROWI の他の読み出し経路（検索、ページ一覧、`GET /users/:id/recent`）は、閲覧者が見られるページだけを返す。この API も同じ方針に揃える必要がある。

## Desired Outcome

- この API が返す内容は、**閲覧者が閲覧できるページについての情報だけ**である。閲覧できないページについては、パス・ID・公開範囲などページを特定できる情報を一切返さない。この判断はサーバー側で行い、画面側の表示制御に頼らない。
- 操作対象のページについて返す項目は、画面が必要とするものに限る。
- 総件数は、実際に一覧として返す対象の件数と一致する。ページ送りの表示が実際の件数とずれない。
- 上記が要件として文書になっており、権限ごとの応答を確認するテストがある。

## Approach

集計の中で、操作対象のページを結合するときに、閲覧者が閲覧できるページだけを残す。条件は既存の仕組み（PageQueryBuilder の `addConditionToFilteringByViewer` に相当する条件）と同じ情報源から作り、閲覧権限の規則を二重に定義しない。返すページの項目は、結合の時点で必要なものに絞る。

閲覧できないページへの操作履歴の扱いは、次の 2 案を design で実測して決める。

- **第 1 候補: 行ごと返さない。** 一覧にも総件数にも含めない。`GET /users/:id/recent` と同じ考え方で、「いつ何かを操作した」という事実も伝わらない。ただし、ページ送りと件数の計算より前にページの結合と絞り込みを行う必要があり、集計の負荷が上がる。
- **第 2 候補: 行は残し、ページの情報だけを返さない。** 結合はページ送りの後で済むので負荷は今と変わらない。操作の種類と日時は閲覧者に伝わる。

第 1 候補が望ましいが、採用は性能との兼ね合いで決める（ユーザー判断、2026-11-10）。design では、1 人のユーザーが保存期間内（既定 30 日）に持つ履歴の件数を想定して両案の応答時間を測り、第 1 候補の負荷が許容できるなら第 1 候補を採る。どちらの案でも「閲覧できないページを特定できる情報を返さない」という要件は満たす。要件は、どちらの案でも満たせるよう、観察できる結果で書く。

## Scope

- **In**:
  - `GET /_api/v3/user-activities` の応答の仕様（取得できる相手、含める履歴、ページについて返す項目、総件数の意味）
  - 閲覧権限による絞り込みをサーバー側で行うこと
  - 応答の変更に合わせた「最近の活動」画面の調整
  - 権限ごとの応答を確認するテスト
- **Out**:
  - contribution graph の API（`features/contribution-graph`。件数だけを返す）
  - 何を記録するか、保存期間の値（`activity-log` が担当）
  - 管理者向けの監査ログ画面とその API
  - 「最近の活動」画面の見た目の刷新

## Boundary Candidates

- 閲覧者が見られるページだけに絞る条件の組み立て（既存の閲覧権限の規則を再利用する部分）
- 集計の組み立て（絞り込み・ページ送り・件数・返す項目）
- 応答の型と、画面側の受け取り

## Out of Boundary

- 閲覧権限の規則そのものの変更（grant の種類や判定方法）
- 活動の記録の仕組み（`addActivity` や記録対象の判定）
- 他人の活動の件数を見せてよいかという contribution graph 側の判断

## Upstream / Downstream

- **Upstream**: activity の記録（`activity-log`）、ページの閲覧権限の判定（PageQueryBuilder）、activities を読む Prisma の集計
- **Downstream**: ユーザーページの「最近の活動」画面。この API を直接呼ぶ外部の利用者

## Existing Spec Touchpoints

- **Extends**: なし（新規 spec）
- **Adjacent**: `activity-log`（記録対象の制御）、`activity-log-snapshot` / `activity-log-snapshot-viewer`（監査ログの中身と表示）、`access-token-parser`（apiv3 の認証）。規約 `apps/app/.claude/rules/page-write-action-403-404.md`（apiv3 の応答でページの存在を伝えない方針）と整合させる。

## Constraints

- 閲覧権限の条件は既存の単一の情報源から作る。この API 専用の判定を新しく書かない。
- 集計は Prisma の `aggregateRaw` で実行されている。絞り込みは集計の中で行える形にする。
- 第 1 候補を採る場合の負荷を design で実測する。実測なしに方式を確定しない。
- 新しい索引が必要になった場合は migration で作る（Mongoose のスキーマでは作らない）。
- 画面に新しい文言を足す場合は、5 言語すべてをこの spec の中で訳す。
