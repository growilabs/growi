# attachment-search roadmap

添付ファイルの全文検索の、spec の一覧と、まだ着手していない拡張の候補。決めたことの中身と根拠は、各 spec が持つ。

## spec の一覧

| spec | 範囲 |
|---|---|
| [attachment-search-text-extractor](../attachment-search-text-extractor/) | 抽出サービス (`apps/attachment-text-extractor`) |
| [attachment-search-indexing](../attachment-search-indexing/) | apps/app のサーバ側 (抽出の呼び出し、Elasticsearch の索引、API) |
| [attachment-search-ui](../attachment-search-ui/) | apps/app のクライアント側 (検索結果、管理画面) |

## リリースまでの順番

日付は決めていない。順番と、次に進む条件だけを決めている。

前提: 機能を切り替えるスイッチは無い。管理者が抽出サービスの URI とトークンを設定したときだけ有効になり、既定は無効である。

### 1. 抽出サービスとサーバ側を master にマージする

- 対象: 抽出サービス (`attachment-search-text-extractor`) とサーバ側 (`attachment-search-indexing`)。画面は含めない。
- 進む条件: 全体の実装の検証とコードレビューを済ませ、人がレビューし、PR の説明に書いた「決めたいこと・残っていること」を確認する。

### 2. 無効のままリリースする

- マージの後の、次の通常のリリースに入れる。待つ理由は無い。
- 利用者から見える変化は無い。新しい API は、設定しない限り 503 などを返す。

### 3. 後続の作業に着手する

1 のマージの直後から始める。2 とは並行で進めてよい。

- (a) 画面 (`attachment-search-ui`): 設計を今の API に合わせ直し、タスクを作り、実装する。
  - 画面は、完成するまで master に入れない。この機能用のブランチで進め、完成したら 1 回でマージする。管理画面に半端な設定のページが出ると、使える機能のように見えるためである。画面をフラグで隠しながら小分けにマージする形は、隠すための仕組みが増えるので採らない。
- (b) 抽出サービスの配布: Docker image を公開する仕組み (`release-attachment-text-extractor.yml`) は入れた。残りは、最初の公開 (1.0.0) の後に、Docker Hub の `growilabs/attachment-text-extractor` に linux/amd64 と linux/arm64 の image と説明が出ていることを確かめること。
- (c) 運用者向けの文書: GROWI の公式ドキュメントに、抽出サービスの立て方と設定を書く。GROWI.cloud で使う場合は、その配備も行う。
- (d) 検索の速さ (`attachment-search-indexing` の task 10.8): 画面ができ、実際の使い方で測れるようになってから、詰めるか目標を見直すかを決める。
- (e) **重要: ページと添付をまとめた検索 (`facet=all`) の、あるべき動きを決め直す。** いまの 1 ページ目は、ページ検索をしてから、本文を見せてよいページの添付だけを検索する (見えない添付が結果に影響しないようにするため。そのぶん順に待つので遅い)。あるべき動きは、次の 2 つで変わりうる。(d) と一緒に決める。
  - 画面から検索する場合と、API を直接使う場合で、利用者が期待する結果と速さが違う。
  - ページと添付の両方を検索するか、ページだけか、添付だけか (`facet` の値) で、結果の並べ方と、何を待つべきかが違う。
- (f) レビューで見つかり、先送りにした項目。どれも 1 のマージの条件ではないが、4 までに扱うかどうかを決める。
  - サーバ側 (`attachment-search-indexing` の tasks.md に未完了のタスクとして載せてある)
    - 抽出の成功・失敗の件数と所要時間を、監視システムが収集できる形で公開する (Req 8.2。未実装。task 3.4)。1 のマージの条件にはしない (2026-11-18 の決定)。何を測るかは画面と運用の形が決まってから決め、4 のリリースまでに実装する
    - 抽出サービスの応答の大きさの上限と、呼び出し全体の制限時間を設ける (task 3.3)
    - 添付を持つページが 10,000 を超える環境でも、親ページの無い文書の掃除 (orphan sweep) が全ページを確かめるようにする (task 6.4)
    - 機能が無効のときに、不正な `facet` の値へ 400 を返してしまうのを、導入前と同じ動き (無視) に戻す (task 9.4)
  - 抽出サービス側 (`attachment-search-text-extractor`)
    - `/readyz` の結果を使い回す
    - ZIP の上限が、ファイル全体を読む fallback の経路で回避されてしまうのを直す
    - PDF / PPTX のページごとの繰り返しの中で、結果の大きさの上限を確かめる
    - 変換を行う子プロセスが、親プロセスの環境変数を読めることを文書に書く
    - 古い要件番号を指すコメントを取り除く (Python 版との互換のためのコードとテストは (g) で扱う)
  - 分かっている制限 (直すかどうかを決める)
    - 保存先のファイルが失われている添付が「20 件 + 対象の 5%」を超える環境では、それらの添付を片づける (添付を消す、ファイルを戻す) まで、添付の作り直しを最後まで走らせられない。作り直しは、読めないファイルを保存先の障害と区別できないので、失敗が続くと止まる (`attachment-search-indexing` の research.md 10.3)
- (g) 抽出サービスの、Python 版に由来する仕様を是正する。1 のマージの条件ではない。4 までに行うか、4 の後に回すかを決める。
  - いまの動き: 抽出サービスは、以前の実装 (Python) と同じ結果を返すことを方針にして書き直した。そのため、標準の仕様や Node の標準の動きと違う、Python とそのライブラリに固有の動きまで再現している。本番コード 118 ファイルのうち 47 ファイルが、コメントで Python 版の動きに合わせたことを述べている (2026-11-18 に数えた目安)。主な場所は次のとおり。
    - multipart とヘッダーの引数の読み方 (python-multipart、Starlette、`email.utils.unquote`)
    - 文字コードの判定と復号 (Python の codec の名前と、受け付けるバイトの範囲)
    - HTML からのテキストの取り出し (Python の `HTMLParser` の文法)
    - ZIP と OOXML の読み方 (CPython の `zipfile`、Python の空白と行の区切りの定義)
    - ipynb の JSON の読み方 (入れ子の上限、`NaN` と `Infinity`)
  - ほしい動き: Python に固有の動きを再現するのをやめ、標準の仕様どおりの動き (Node と、すでに使っているライブラリの標準の動き) にする。
  - 対象にする条件: **是正するとコードの量が減る箇所だけを対象にする。** 是正するとコードが増える箇所、同じ量にとどまる箇所は、いまのまま残す。
  - きっかけになった例: `header-params.ts` の `unquote` は、`\\` を `\` にしてから `\"` を `"` にするので、`\\"` を `\"` ではなく `"` と読む。Python の `email.utils.unquote` と同じ動きである。CodeQL がこれを指摘し (`js/double-escaping`、alert #1050)、Python 版と結果をそろえるために直さないと判断して閉じた。この箇所を是正したら、alert を開き直して、検出されなくなることを確かめる。
  - 着手するときに決めること:
    - 箇所ごとに、是正すると抽出結果と応答がどう変わるかを確かめ、変えると決めたものを `attachment-search-text-extractor` の research.md §5.4 と同じ形 (以前の動き、いまの動き、合わせない理由) で記録する
    - Python 版の動きを記録したテストのデータ (`header-param-oracle.json`、`multipart-oracle.json`、`python-baseline.json`) の扱い。Python 版は撤去したので作り直せない。是正した箇所の期待値だけを書き換えるか、データとそれを使うテストごと取り除くかを決める
    - すでに索引に入っているテキストと、是正の後の抽出結果が違う場合に、添付の作り直しを案内するかどうか
  - 関わる spec: `attachment-search-text-extractor` (応答や対応する形式の契約が変わる箇所は、要件と設計も直す)

### 4. 完成させ、使える形でリリースする

- 進む条件: (a)〜(c) がそろい、(d) の判断が済んでいる。
- 「有効化」はコードのスイッチを入れることではなく、利用者が抽出サービスを立てて設定すれば使えると案内できる状態のリリースを指す。GROWI.cloud で有効にするのは、運用側の別の作業になる。

## まだ着手していない拡張の候補

### 拡張子の表に無いテキストのファイルを、中身を見て抽出する

- いまの動き: 抽出サービスは、形式を拡張子と `mimeType` の表だけで決める。表に無い拡張子 (`.tf`、`.conf`、`.ini`、`.toml`、拡張子の無い `Dockerfile` など) は、中身がテキストでも `unsupported_format` になり、検索できない。
- ほしい動き: 表に無いファイルでも、中身がテキストだと判定できれば、テキストとして抽出して検索できるようにする (たとえば Terraform の `.tf`)。
- 着手するときに決めること:
  - 「テキストである」と判定する方法 (文字コードの判定の結果、制御文字の割合、先頭だけを見るか全体を見るか) と、バイナリを誤ってテキストとして索引に入れない条件
  - 判定をどちらで行うか (抽出サービスが行うのが自然である。apps/app はファイルの中身を見ない)
  - 大きさと文字数の上限 (テキスト系の形式の、いまの上限に合わせるか)
  - 応答の `mimeType` に何を返すか (`text/plain` に寄せるか)
- 関わる spec: `attachment-search-text-extractor` (形式の判定と、対応する形式の一覧の契約)、`attachment-search-indexing` (`unsupported` の扱いと失敗の記録)
