# Requirements Document

## Project Description (Input)
## 概要
- AI チャット欄にて "@/{page path 名}" を入力すると GROWI に保存されているページパスを検索して参照先ページとして指定できる機能を実装したい。
- 検索は既存の ElasticSearch の機能を使う。内部ロジックは SearchModal などが参考になると思う
- Claude Code に標準的に搭載されている機能が参考になる

## 挙動のイメージ
1. "@" の後に文字列を入力するとインクリメンタルサーチが行われ検索結果のページパス候補リストが表示される
2. ユーザーが候補リストの中でに任意のパスを選択するとチャット画面のテキストインプットに選択されたページパスが、rich text として表示される

### rich text
- 入力された他の文字列とは独立しており、clickable
- クリックすると対象のページに遷移できる
- 他の文字列と視覚的に区別できるようにする

## Introduction
本機能は、AI チャットの入力欄でユーザーが `@` に続けて文字列を入力すると、GROWI に保存されているページパスをインクリメンタルに検索し、候補リストから選択したページを「ページメンション」として入力欄に挿入できるようにする。挿入されたメンションは入力欄内の他のテキストとは独立した視覚的に区別できる要素（rich text）として表示され、クリックすると対象ページへ遷移できる。メッセージ送信時には、メンションは対象ページの**パス文字列**として AI に渡される。これにより、ユーザーは会話の中で特定のページを素早く参照先として指定できる。

## Boundary Context
- **In scope**:
  - AI チャット入力欄での `@` 起動によるページパスのインクリメンタル検索と候補リスト表示
  - 候補選択によるページメンション（rich text）の挿入、視覚的区別、クリックによるページ遷移
  - メンションを原子的な単位として扱う編集・削除挙動
  - メッセージ送信時にメンションを対象ページの**パス文字列**として AI に含めること
  - AI サイドバーのオープン時に入力欄へキャレットを付与すること（入力欄の実体が CodeMirror であることに起因して本 spec が所有する）
- **Out of scope**:
  - 参照先ページの**本文（コンテンツ）を AI のコンテキストとして付与する**こと。本機能で AI に渡されるのはパス文字列のみであり、本文取得・注入は行わない
  - ユーザーや他エンティティ（タグ等）に対するメンション
  - AI サーバ側の推論ロジックやプロンプト構築方法の変更（パス文字列を受け取ること以上の挙動）
- **Adjacent expectations**:
  - ページパス検索は既存の Elasticsearch ベースのページ検索機能に依拠する。候補として返るのはログインユーザーが閲覧権限を持つページのみであることを前提とする（既存検索 API の挙動に準拠し、本機能で独自の権限フィルタは新設しない）

## Requirements

### Requirement 1: メンション入力の起動とインクリメンタル検索
**Objective:** As an AI チャットの利用者, I want `@` に続けて文字列を入力するとページパスがインクリメンタルに検索される, so that 参照したいページを素早く見つけられる

#### Summary
チャット入力欄の語境界（行頭または空白の直後）で `@` を入力すると、その時点で検索モードが始まり候補パネルが即時に開く（クエリが空の間はページ名の入力を促すヒントを表示）。続けて文字列を入力・変更するたびに既存のページ検索を実行し、候補リストを逐次更新する。メールアドレスのように直前が非空白文字の `@` では検索モードを開始しない。クエリ中の空白入力、または起動した `@` 自体の削除があった場合は検索モードを終了し候補パネルを閉じる（このときすでに入力済みの文字列は通常テキストとして残り、メンションは確定しない）。

### Requirement 2: 候補リストの表示と操作
**Objective:** As an AI チャットの利用者, I want 候補リストをキーボードとマウスの両方で操作できる, so that 入力を中断せずに目的のページを選べる

#### Summary
候補リストは各候補についてページパス（および識別補助として作成者アバター）を表示し、上下キーで選択中項目を循環的に移動、Enter またはクリックで確定、Esc または候補リスト外クリックでメンションを挿入せずに閉じる。検索結果取得中はローディング表示、一致するページが無い場合はその旨を表示する。連続入力に対しては過剰な検索要求を抑制しつつ応答的に候補を更新する（debounce）。候補リストは標準的な ARIA コンボボックスパターンに準拠し、キーボードとスクリーンリーダーの双方で操作可能にする。

### Requirement 3: ページメンション（rich text）の挿入と視覚的区別
**Objective:** As an AI チャットの利用者, I want 選択したページが他のテキストと区別できる形で入力欄に挿入される, so that メッセージ内のどこを参照しているか一目で分かる

#### Summary
候補を確定すると、`@` 以降の検索文字列が選択したページを表すページメンション要素に置き換わり、直後に半角スペースが 1 つ挿入される（続けて `@` を入力すればすぐに次のメンションを開始できる）。メンション要素は他の入力テキストと視覚的に区別され、独立した 1 つのまとまり（原子的な単位）として保持される。1 つのメッセージ内に複数のページメンションを挿入できる。

### Requirement 4: メンションからのページ遷移
**Objective:** As an AI チャットの利用者, I want 入力欄のメンションをクリックすると対象ページへ遷移できる, so that 参照先の内容をその場で確認できる

#### Summary
入力欄内のページメンションをクリックすると対象ページへ遷移する。このクリック操作は、入力欄内での通常のテキスト編集操作と区別される。

### Requirement 5: メンションの編集・削除
**Objective:** As an AI チャットの利用者, I want メンションをひとまとまりとして編集・削除できる, so that 文字単位で崩れることなく参照を修正できる

#### Summary
ページメンションに対する削除操作（Backspace/Delete 等）は当該メンションを 1 単位として削除し、内部の 1 文字だけが消えることはない。確定済みメンションは文字単位で編集不可能な 1 個の要素として扱われ、キャレットはメンションの直前または直後の境界にのみ置かれる（内部の文字間には置かれない）。メンションの直前・直後に文字を入力しても、それは外側の通常テキストとして扱われ、メンション本体・参照先は変わらず検索モードも再起動しない。確定済みメンションの参照先を直接書き換える手段は提供されず、変更はメンションの削除と再入力（再検索・再選択）を通じてのみ行える。

### Requirement 6: メッセージ送信時の内容
**Objective:** As an AI チャットの利用者, I want メンションがパス文字列として AI に伝わる, so that AI がどのページを参照先として指定されたかを認識できる

#### Summary
メッセージ送信時、各ページメンションは対象ページの**パス文字列**として、メッセージ本文の該当位置にユーザーが選択した順序どおりに含められる。参照先ページの**本文（コンテンツ）は付与されない**（送信されるのはパス文字列のみで、本文取得・注入は行わない）。

### Requirement 7: 検索対象スコープ
**Objective:** As a GROWI の運用者, I want 候補に表示されるのが利用者の閲覧権限内のページに限られる, so that 権限のないページの存在や情報が漏えいしない

#### Summary
ページパス候補の取得には既存のページ検索機能を用い、独自の権限フィルタは新設しない。候補として提示されるのは、既存検索機能の権限挙動に準拠してログインユーザーが閲覧権限を持つページのみ。

### Requirement 8: オープン時のキャレット付与

**Objective:** As an AI チャットの利用者, I want AI サイドバーを開いた時点で入力欄にキャレットが当たっている, so that クリック直後にメッセージ（`@` メンションを含む）の入力を開始できる

#### Summary
AI サイドバーを開く操作（「新規チャット」または Recent Items からのスレッド選択）で入力欄にキャレットが移り、追加操作なしで入力を開始できる状態になる。表示中のスレッドを Recent Items から再選択した場合、入力欄の再マウントが発生しなくてもキャレットは入力欄に移る。一方、オープン以外の理由での再描画（応答のストリーミング、モデル選択、サーバ状態の解決など）では現在のフォーカス位置を変更しない（ユーザーの操作中にキャレットを奪わない）。
