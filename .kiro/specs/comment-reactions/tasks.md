# Implementation Plan

> **進め方**: 実装を伴う各サブタスクは、先に失敗するテストを書き(red)、実装して通す(green)。テストを書く、またはレビューするときは、`essential-test-design`(何を確かめるか)と `essential-test-patterns`(どう組むか)を先に参照する。
> 対象は主に `apps/app` 配下で、コマンドは `apps/app` で実行する。`packages/emoji-mart-data` と `packages/editor` を変えたタスクの後は、`apps/app` の型検査の前に `turbo run build --filter <package>` で `dist` を作り直す。
> `comment` スペックの本文(requirements.md / design.md / research.md)には、最終タスク(10)まで手を入れない(design.md「Amend Target」)。

- [x] 1. Foundation: 絵文字データ、データの保存先、インデックス、移行
- [x] 1.1 絵文字データのパッケージが、肌の色違いのグリフと別名の対応表を出力するようにする
  - 肌の色に対応する絵文字は、既定と `skin-tone-2`〜`6` の6件の肌の色のグリフを出力する。肌の色に対応しない絵文字は、これまでどおり1件
  - 同じ絵文字を表す別名から正規の名前を引ける対応表を、名前付きの出力として足す
  - 肌の色のグリフの並びの型を「先頭が必ずある」形にし、既存の利用者(本文のレンダラー、エディタの自動補完)が先頭のグリフを型の上でも安全に読めるようにする
  - 既存の先頭のグリフの値は変えない
  - このパッケージにはテストの仕組みが無いので、新しいパッケージの既定(Vitest)に沿って、テストの設定と `test` スクリプトを足す
  - 先に、生成物の先頭のグリフが拡張前と一致すること(拡張前の生成物を基準として固定する)、肌の色対応の絵文字が6件のグリフを持つこと、別名の対応表があることを確かめるテストを書く
  - 完了の状態: パッケージのビルドとテストが通り、`apps/app` と `packages/editor` の型検査と既存の絵文字の表示・自動補完のテストが通る
  - _Requirements: 4.1, 4.3, 4.5_

- [x] 1.2 リアクションの保存先を Prisma のモデルと拡張として用意する
  - 「Physical Data Model」の項目(コメント、ページ、利用者の ID、絵文字のキー、作成日時)を持つモデルを足す。コメント・ページ・利用者へのリレーションは1本も宣言せず、スカラーの項目だけにする。他のモデルには何も足さない
  - 一意性(コメント、利用者、絵文字の組)とページの索引を、migration と同じ名前で宣言する(実体は 1.3 の migration が作る)
  - 計算項目 `_id` / `__v` を足す Prisma 拡張を、アプリの Prisma Client の拡張の連鎖に加える。Mongoose のモデル・スキーマは作らない
  - 先に、本物の DB で、作成した行の `_id` が `id` と一致し `__v` が読めること、リアクションの付いた利用者を Prisma で消してもリアクションが原因の P2014 にならないこと(既存のリレーションが残る利用者は対象外)を確かめる結合テストを書く
  - 完了の状態: Prisma Client の生成と型検査が通り、モデルの結合テストが通る。移行できるコレクションの一覧の既存の結合テスト(スキーマの全モデルを分類済みか確かめる)は、1.4 で一覧に足すまで失敗する
  - _Requirements: 1.9, 2.4, 2.5_

- [x] 1.3 リアクションの一意インデックスとページのインデックスを作る migration を足す
  - 既存の最新の migration より後のタイムスタンプで、前例(監査ログの Elasticsearch 同期のコレクションに一意インデックスを足した migration)と同じ形にする。Mongoose のモデルは使わない
  - `up` では、同じ組の重複があれば最も古い1件を残して消してから、一意インデックスとページのインデックスを作る。コレクションが無くても、何度実行しても失敗しない
  - `down` では、コレクションとインデックスがあるときだけ2つのインデックスを消す
  - 先に、インデックスが 1.2 の宣言と同じ名前・キーで作られること、重複があるとき最も古い1件が残ること、2回の実行、コレクションが無いときの `down` を確かめる結合テストを書く
  - 完了の状態: migration の結合テストが通り、統合テストのテンプレート DB でインデックスが作られている(以降の結合テストが一意性に依存できる)
  - _Requirements: 2.4, 2.5, 10.2_
  - _Depends: 1.2_

- [x] 1.4 GROWI 間移行とアーカイブからのインポートでリアクションを運べるようにする
  - リアクションのコレクションを、移行できるコレクションの一覧に足す
  - インポート時に、文字列になったコメント・ページ・利用者の参照を ObjectId に戻す変換(不正な値はそのまま返す)を作り、コレクションごとの変換の生成に足す。G2G とファイルからのインポートの両方がこの生成を通る
  - 一意キーの衝突の検出の対象には加えない
  - 先に、変換の単体テスト(24 桁の16進文字列が ObjectId になる、不正な値はそのまま、生成がこの変換を返す)と、移行できるコレクションの一覧の既存の結合テストがリアクションを含めて通ること、エクスポート形式(JSON 文字列化)のデータを文書の変換と生成した変換で取り込んだとき参照が ObjectId・作成日時が Date になり、Prisma の参照の ID での検索(コメント ID 群での取得)で読めることを確かめる結合テストを書く
  - 完了の状態: 変換の単体テストと、移行・インポートの結合テストが通る
  - _Requirements: 10.1, 10.2, 10.3_
  - _Depends: 1.2_

- [x] 2. Core: リアクションの中核(キー、集計、書き込みの規則)
- [x] 2.1 (P) リアクションのキーの検証・正規化・変換・グリフの解決を作る
  - キーの形式(`unicode:<shortcode>` と、肌の色 2〜6 の付いた形)、その型、検証の失敗の種類を定義する。受け付ける名前空間は `unicode` だけ
  - 正規化は、存在の判定・肌の色の対応の判定・別名の解決を絵文字データのパッケージだけを根拠に行い、正規化済みのキーを通しても同じキーを返す(冪等)。正規化を通ったものだけがキーの型になる
  - ピッカーの選択(id と肌の色の番号。1 または指定なしは肌の色なし)からキーへの変換、Slack のリアクション名への変換、表示するグリフの解決(データから消えた絵文字は解決できないことを返す)を作る
  - サーバーとクライアントの両方から使う純粋関数にし、公開するものを barrel に絞る
  - 先に、別名の正規化、肌の色 2〜6 の受け付けと 1・7 の拒否、肌の色に非対応の絵文字への肌の色の拒否、存在しない絵文字、不正な形式、他の名前空間、ピッカーの選択の変換、Slack 名、グリフが肌の色の番号に対応する要素であること、ピッカーで選べる全絵文字(肌の色を含む)が正規化を通ることを確かめる単体テストを書く(ピッカーのデータは絵文字データのパッケージと抽出元が同じなので、その全件で確かめる)
  - 完了の状態: キーの単体テストが通り、型検査が通る
  - _Requirements: 3.3, 4.1, 4.2, 4.3, 4.4, 4.5, 4.6_
  - _Depends: 1.1_
  - _Boundary: reaction-key_

- [x] 2.2 リアクションの行をコメントごとのチップに集計する純粋関数を作る
  - チップと、リアクションした利用者(4項目、または利用者の情報が無いときの ID 文字列)の型を、`comment` のコードを型も含めて import せずに定義する
  - 絵文字ごとにチップを作り(肌の色が違えば別のチップ)、チップの並びは残っている行の最小の作成日時の昇順、チップ内の利用者も作成日時の昇順にする
  - 人数は行数で、利用者の文書が無い行も数え、その利用者は ID 文字列にする。自分のリアクションの印は、閲覧者と一致する行があるときだけ真(ゲストは常に偽)
  - 利用者の整形は引数で受け取った関数で行う
  - 先に、肌の色違いが別のチップになること、並び順(最初に付けた人が外して並びが変わる場合を含む)、自分のリアクションの印、文書の無い利用者が ID 文字列で人数に入ること、利用者が渡した整形関数の結果になることを確かめる単体テストを書く
  - 完了の状態: 集計の単体テストが通る
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.9, 1.10, 6.4, 11.4_
  - _Depends: 2.1_
  - _Boundary: summarizeReactions_

- [x] 2.3 指定したコメント群のチップを読むローダーを作る
  - リアクションの行をコメント ID 群で作成日時の昇順に取得し、行の利用者 ID の重複を除いて利用者を別に取得し(リレーションの `include` は使わない)、集計に渡す
  - 利用者の取得では、整形関数が読む計算項目 `_id` を必ず選ぶ
  - 結果には、リアクションの無いコメントも空の配列で含める
  - 先に、本物の DB と拡張を適用した Prisma Client で、利用者の要素が4項目だけを持ち `_id` が利用者の ID と一致すること、存在しない利用者 ID のリアクションがあっても失敗せず ID 文字列で数えること、リアクションの無いコメントが空の配列になることを確かめる結合テストを書く
  - 完了の状態: ローダーの結合テストが通り、ローダーとチップの型がリアクションの中核のサーバーの公開口から使える
  - _Requirements: 1.9, 1.10, 6.1, 6.4, 11.1, 11.4_
  - _Depends: 1.2, 2.2_

- [x] 2.4 追加・解除の業務規則(冪等、種類数の上限)を持つサービスを作る
  - 1コメントあたりの絵文字の種類数の上限(20)を定数として定義する
  - 追加は、そのコメントの絵文字の種類数が上限以上で、かつ追加する絵文字がまだ無いときだけ上限超過を返す。既にある絵文字の追加と解除は上限に関係なく通す
  - 既に付いている絵文字の追加は「既に付いている」、付いていない絵文字の解除は「付いていない」を返し、エラーにしない。同時の二重追加による一意インデックスの重複エラーは「既に付いている」に読み替える
  - 投稿者本人かどうかは判定しない
  - 先に、追加・解除、2回目の要求で行が増減しないこと、同時の二重追加で行が1つになること、上限で新しい絵文字が拒否され既存の絵文字は追加・解除できること、自分のコメントにも付けられることを確かめる結合テストを書く
  - 完了の状態: サービスの結合テストが通る
  - _Requirements: 2.4, 2.5, 2.6, 2.7, 2.8, 7.1, 7.2, 7.3_
  - _Depends: 1.3, 2.1_

- [x] 3.1 コメントの応答の1件にリアクションの項目を足し、整形が詰めるようにする

  - 旧 API の応答の型と出力にはリアクションの項目を入れない
  - 先に、渡したチップ(空の配列と `null` を含む)がそのまま入ること、旧 API の整形の結果にリアクションの項目のキーが無いことを確かめる単体テストを書く
  - 応答の1件を組み立てているテストの fixture とモック(コメント・インラインコメントの部品のテスト、インラインコメントの組み直しのテストなど)に、リアクションの項目を足す
  - 一覧のルートは、3.3 でローダーを取り込むまで、空の配列を渡して型を合わせる
  - 完了の状態: 整形の単体テスト、旧 API の既存の結合テスト、既存のクライアントのテストが通り、型検査が通る

- [x] 3.3 コメント一覧の応答の各コメントにリアクションを載せる

  - ローダーが失敗したときは、ログを残して全コメントのリアクションを `null` にして返す。コメント自体の取得の失敗は従来どおり 500
  - 公開仕様の一覧の1件の記述に、リアクションの項目(チップの各項目と `null` の意味)を足す
  - 先に、各コメントにリアクションが載ること(無ければ空の配列)、要求者によって自分のリアクションの印が変わること、リアクションした利用者が投稿者の整形(4項目)で整形され `_id` が利用者の ID と一致すること、アクセストークンでも同じに返ること、共有リンク経由でインラインコメントのリアクションも返ること、取り込みを失敗させたときにコメントが返りリアクションが `null` になること、存在しない利用者のリアクションがあってもページのリアクションが `null` にならず ID 文字列で数えられ投稿者の欠落と同じ形であること、旧 API の応答にリアクションが無いことを確かめる結合テストを書く
  - 完了の状態: 一覧の結合テストが通り、公開仕様の生成と検証が通る

  - ローダーが失敗したときはログを残してリアクションを `null` にする
  - 先に、一覧の該当する1件と同じ内容になること、別ページの ID の組では「無い」になること、取り込みの失敗で `null` になることを確かめる結合テストを書く

  - 完了の状態: 保存口の結合テストと activity の既存のテストが通り、2つの action が型と監査ログの分類に現れる

- [x] 5. Core: リアクションの書き込み API

  - 完了の状態: 認可と検証の結合テストが通る(正常系の応答は 5.2 で確定する)

## Implementation Notes

- 2.4 の実装:サービスは、ローダーと同じく依存を先頭に取る関数 `addReaction({ prisma }, target, userId, emoji)` / `removeReaction(...)` として公開している(design.md の Service Interface も同じ形。route タスクはこの形で呼ぶ)。種類数の上限の判定は同時の別種追加で 1〜2 件超過しうる(許容)。結合テストは、`MONGO_URI` の有無にかかわらず、`beforeAll` でインデックスの migration を実行して一意インデックスを作るので、インメモリ DB でも外部 DB でも実行できる。
- 3.1:ICommentListItem.reactions を、loadReactionChips の戻り値に合わせて readonly ReactionChip[] | null とした。
- 3.3:Prisma のデリゲートのメソッド(例: `prisma.commentreactions.findMany`)を `vi.spyOn` して `vi.restoreAllMocks()` すると、そのメソッドが `undefined` になり後続のテストが落ちる。リアクションの取り込みの失敗は、生のコレクションに `emoji` の無い行を入れて再現した。「取り込んで、失敗したらログを残して `null`」の処理(`loadReactionChipsOrNull`)は、3.4 で `features/comment/server/service/load-reaction-chips-or-null.ts` に移し、一覧(`list.ts`)と1件(`getCommentListItem`)の両方から使っている。
- 3.4:`getCommentListItem({ prisma }, { commentId, pageId, viewerId })` は `ICommentListItem | null`(`null` は「無い」)を返す。3.5 の route と PUT の route はこの null を 404 に変換する。
- 5.1:PUT の要求・応答の型は、`interfaces/` ではなく `features/comment-reaction/dto/update-comment-reaction.ts`(barrel は `dto/index.ts`)に置き、名前は既存の `GetCommentResponseBody` に合わせて `UpdateCommentReactionRequestBody` / `UpdateCommentReactionResponseBody` とした。応答が `ICommentListItem` を含み、層 1 の `interfaces` から `comment` を import できない(`comment/interfaces` → `comment-reaction/interfaces` と循環もする)ため。8.x のクライアントはこの型を使う。`notFoundOrForbidden()` は `features/comment/server/routes/not-found-or-forbidden.ts` に共通化し、一覧・単体・PUT から使っている。
