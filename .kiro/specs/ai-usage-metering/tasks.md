# Implementation Plan

- [x] 1. モデルカタログに単価を持たせる
- [x] 1.1 models.dev の単価と段階料金をカタログに取り込む
  - 選択肢に残す各モデルについて、100 万トークンあたりの入力・出力・キャッシュ読み取り・キャッシュ書き込みの単価を取り込む。0 以上の有限の数だけを採り、それ以外や欠けた項目は「不明」として持たない。
  - 入力トークン数で単価が変わる段階料金（種類が context のものだけ）を、境目の小さい順に取り込む。
  - 単価の形が壊れていても、そのモデルは選択肢に残す。
  - 保存済みのリフレッシュ済みカタログを読み込むときは、単価のない古い要素も、単価の部分だけ壊れた要素も受け入れる（単価を取り除いて受け入れ、カタログ全体は捨てない）。
  - 完了の状態: カタログ生成のテストで、4 つの単価と段階料金が取り込まれること、単価が一部欠けた・まったくないモデルも選択肢に残ること、古い形と単価の壊れた要素を読み込めることが通る。
  - _Requirements: 1.1, 1.3, 1.4, 1.6_

- [x] 1.2 同梱カタログを単価付きで作り直す
  - 同梱カタログの生成コマンドを実行し、単価付きのカタログに作り直す。リリース前の生成と実行中のリフレッシュが同じ取り込み処理を通ることを確かめる。
  - カタログの形を `{id, name}` だけで固定している既存のテスト（同梱カタログの読み込み、リフレッシュ）を、単価を含む形に直す。
  - 完了の状態: 作り直した同梱カタログに単価が入っており、カタログ関連の既存テストがすべて通る。
  - _Requirements: 1.2_

- [x] 1.3 (P) 採用しているカタログの種類と中身の取得日時を返す

  - 保存済みカタログの読み込みに失敗したら同梱カタログを返し、例外を投げない。
  - プロバイダとモデル ID からカタログの要素を引く関数を作る。カタログを持たないプロバイダ（Azure OpenAI）では「なし」を返す。
  - 完了の状態: リフレッシュ済みが採用されるとき・同梱が新しいとき・保存済みがないとき・読み込みに失敗したときの 4 通りで、種類と取得日時が正しく返るテストが通る。既存の比較の振る舞い（同じ日時ならリフレッシュ済みを選ぶ）も変わらない。
  - _Requirements: 3.1, 4.2, 6.3_

- [x] 3. 使用量の計算と記録
- [x] 3.1 呼び出し 1 回分の使用量の型と、足し合わせる処理を作る
  - 入力・出力の合計と、推論・キャッシュ読み取り・キャッシュ書き込みのトークン数を持つ型を用意する。プロバイダが返さなかった項目は 0 ではなく「値なし」として持つ。
  - 利用した機能（チャット・suggest-path・タイトル生成）を表す型も、ここで用意する（記録のコレクションと記録の処理の両方が使う）。
  - 複数の呼び出しを足し合わせるとき、ある項目がすべて「値なし」なら「値なし」のまま、1 つでも数があれば数の合計にする。
  - 完了の状態: 「値なし」を保ったまま合計できることを確かめるテストが通る。
  - _Requirements: 2.5_

- [x] 3.2 呼び出し 1 回の推定費用を計算する
  - キャッシュでない入力・キャッシュ読み取り・キャッシュ書き込み・出力に、それぞれの単価を掛けて合計する。キャッシュの単価がなければ通常の入力単価を使う。推論トークンは出力に含まれるので足さない。
  - その回の入力トークン数が段階の境目を超えていれば、その回のトークン全体に、超えた段階のうち境目がいちばん大きい段階の単価を使う。段階の中で欠けている項目は基本の単価で補わない。
  - 使う段階の入力か出力の単価が分からなければ「不明」を返す。
  - 完了の状態: キャッシュの単価の使い分け、キャッシュの単価がないとき、段階料金の選び方、欠けた単価で「不明」になることを確かめるテストが通る。
  - _Requirements: 3.2, 3.3, 3.4, 3.7_
  - _Depends: 1.1_

- [x] 3.3 (P) 使用量の記録のコレクションを作り、1 件書き込めるようにする
  - 記録のコレクションを作る。項目は、ユーザー、機能、プロバイダ、モデル、呼び出し回数、各トークン数、推定費用、重み付き消費量、使った基準モデル、記録時刻とする。値のない項目は省略せず null を書く。
  - 記録時刻に 90 日で消える TTL インデックスを付ける。インデックスは Mongoose が作り、書き込みと集計は Prisma から行う既存の形に合わせる。Prisma のスキーマとクライアントも更新する。
  - Prisma への登録は、記録のモデルのファイルを直接読む（機能の入口を経由すると読み込みが循環する）。
  - このコレクションを、G2G の転送で移さないコレクションに加える。
  - 完了の状態: 結合テストで、1 件書き込めること、記録時刻に 90 日の TTL インデックスができることが確かめられ、G2G の分類漏れを検査する既存のテストも通る。
  - _Requirements: 2.4, 2.9, 3.5_
  - _Boundary: AiUsageLogModel_
  - _Depends: 3.1_

- [x] 3.4 1 件の記録を作って保存する
  - 採用しているカタログを 1 回読み、使ったモデルと基準モデルの単価を引く。呼び出しごとに推定費用を出して合計し、1 回でも「不明」があれば推定費用も重み付き消費量も「不明」にする。
  - 重み付き消費量は、推定費用の合計を基準モデルの基本の出力単価（1 トークンあたり）で割って出す。基準モデルが指定なし・カタログにない・出力単価が不明か 0 のときは「不明」にする。
  - カタログの読み込みや書き込みに失敗しても例外を外へ出さず、エラーログを残す。
  - 完了の状態: 倍率の計算、「不明」になる各条件、一部の呼び出しだけ費用が出せないときの扱い、保存の失敗で例外が出ないことを確かめるテストが通る。
  - _Depends: 1.3, 2_
  - _Requirements: 2.4, 2.8, 3.1, 3.4, 3.5, 3.6, 3.7_

- [x] 3.5 1 回の応答の間の呼び出しをまとめる集計器を作る
  - 呼び出しが終わるたびに使用量を受け取り、閉じたときに 1 件の記録として保存する。保存は待たない。何度閉じても 1 件しか書かない。
  - 失敗として閉じても、それまでに集めた分を記録する。集めた呼び出しが 0 件で失敗として閉じたら、ユーザー・機能・モデルを添えて警告ログを出す。
  - 閉じた後に届いた呼び出しは、それぞれ 1 件として記録する。
  - 完了の状態: 複数の呼び出しが 1 件になること、失敗でも記録されること、0 件の失敗で警告ログが出ること、閉じた後の呼び出しが漏れないことを確かめるテストが通る。
  - _Requirements: 2.1, 2.2, 2.6, 2.7, 2.10_

- [x] 3.6 (P) 基準モデルの設定を起動時に検証する

  - 完了の状態: 不正な形式とカタログにないモデルで警告ログが出て、正しい設定と未設定では出ないことを確かめるテストが通る。起動処理へのつなぎ込みは 4.4 で行う。

- [x] 4.3 公開 API のルートを作る
  - 認証なしの GET を受ける。入力の検証より前に、パスが正しい書き方と完全に一致しなければ 404、メソッドが GET でなければ 405（許すメソッドを応答に添える）を返し、集計しない。
  - 開始時刻は 1〜10 個で、タイムゾーン付きの ISO 8601 とする。1 個なら文字列、2 個以上なら配列で届くので両方を受ける。形式の誤り・現在より後・90 日より前・個数の誤りは 400 にし、集計しない。
  - 応答をキャッシュさせない指定を付ける。このルートから静的にたどれる範囲に AI のパッケージを入れない。
  - 完了の状態: 入力の誤りの各パターンで 400 になり集計が呼ばれないこと、正しくない書き方のパスで 404・GET 以外で 405 になること、応答にユーザー ID や推定費用が含まれないことを確かめるテストが通る。
  - _Requirements: 4.4, 4.5, 4.8_

- [x] 4.4 公開 API をサーバーに組み込む
  - 公開 API を、メンテナンスモードの判定より前にあるルーター（healthcheck と同じ）に載せる。AI の準備の検査も通さない。
  - 機能の入口に、外へ出すものだけを置く: Prisma 拡張、ルーター、集計器、1 回ごとに記録する処理、停止理由を読む処理と停止理由の定数、起動時の検証、型。AI の呼び出し側（5 章）とリフレッシュ（6 章）はこの入口から読む。
  - サーバーの起動処理から、基準モデルの検証（3.6）を動的 import で読み込んで呼ぶ（起動処理に静的な import を増やさない）。
  - OpenAPI の生成対象に新しいルートを足す。認可の一覧の記録（参考の記録で、CI の検査ではない）には、新しいルートの行だけを書き足す（生成し直すと無関係な行まで変わるため）。
  - 完了の状態: 結合テストで、メンテナンスモード中・AI が無効なとき・認証なしのどれでも 200 を返すこと、リフレッシュ後にカタログの取得日時が変わることが確かめられる。OpenAPI の生成が通り、認可の一覧の記録に新しいルートの行がある。サーバーの起動時に基準モデルの検証が呼ばれる。
  - _Requirements: 4.4, 4.6, 4.11, 4.2, 6.3, 5.4_

- [x] 4.5 公開 API の回数制限とセッションを設定する
  - 回数制限の既定値に、この API を同じ送信元から 1 分 5 回までとする設定を足す。超えたら既存の仕組みが 429 を返す。
  - 固定 ID を使うパスの一覧と、ID を選ぶ処理を、テストからも呼べる関数として切り出す。結合テストは既存の前例と同じく Crowi を模擬してミドルウェアの並びを組み、セッションの ID を作る処理には切り出した本物の関数を入れる（模擬の関数に差し替えると、固定 ID を選ぶ処理を確かめられない）。
  - 4.4 の結合テストが通り続けるように、テストのケースごとに回数制限の記録を消す（または送信元をケースごとに変える）。
  - healthcheck と同じく、このパスには固定のセッション ID を使い、何度問い合わせられてもセッションが 1 件で済むようにする。固定 ID を使うパスは一覧として宣言し、healthcheck の処理もその一覧から引く形にする。
  - 完了の状態: 本物のミドルウェアの並び（セッション・CSRF 対策・ログイン処理を含む）を通す結合テストで、6 回目が 429 になること、書き方を変えたパスや HEAD でも集計が呼ばれないこと、Cookie なしで何度送ってもセッションが 1 件のままであることが確かめられる。
  - _Requirements: 4.10_

- [x] 4.6 公開 API が AI のパッケージを読み込まないことを検査する

  - 既存の起動時の検査（サーバーの起動点から AI のパッケージに届かないこと）が通り続けることを確かめる。
  - 完了の状態: 検査が通り、わざと AI のパッケージを import すると失敗すること（確かめた後に元へ戻す）を確認している。

- [x] 5. AI の呼び出しに使用量の記録を組み込む
- [x] 5.1 モデルを包んで、呼び出しが終わるたびに使用量を渡す
  - AI SDK の言語モデルのミドルウェアでモデルを包み、generate の結果と stream の終わりの使用量を受け取って、使用量の型に変換して渡す。変換では、値のない項目を「値なし」にする。
  - 渡した先で例外が起きても捕まえてエラーログに残し、LLM の応答はそのまま流す。包めない種類のモデルは包まずに返し、警告ログを出す。
  - 完了の状態: 実物の Mastra のエージェントとメモリ、模擬モデルを使うテストで、stream・generate・2 ステップ目がエラーのとき（1 ステップ目の分が渡る）に使用量が渡ることが確かめられる。
  - _Requirements: 2.1, 2.2, 2.5, 2.6, 2.8_

- [x] 5.2 リクエストの集計器につないでモデルを包む
  - リクエストの文脈に集計器があればそこへ、なければ 1 回ごとに記録する処理へ使用量を渡す形で、モデルを包む。チャットと suggest-path のリクエストの文脈の型に、集計器（suggest-path はモデルキーも）を足す。
  - ユーザーは包む時点ではなく記録する直前に文脈から読む。ユーザーがなければエラーログだけ残し、LLM の呼び出しは失敗させない。
  - 包む処理はモデルのキャッシュの後に、リクエストごとに行う。キャッシュには包む前のモデルを置く。
  - 完了の状態: 1 つのエージェントに別々のユーザーの 2 つのリクエストを同時に流しても、使用量がそれぞれの集計器にだけ入ること、文脈にユーザーがなくても LLM の呼び出しが成功することを確かめるテストが通る。
  - _Requirements: 2.1, 2.2, 2.8, 2.10_

- 1.3: `findCatalogEntry` は壊れた更新済みカタログの要素で例外を出し得る（`resolveEffectiveCatalog` だけが例外を出さない）。3.4 で呼ぶときは try/catch で囲む。

- 4.3: ルートのモジュールは `setup(): Router` を export する（入口で分かりやすい名前に付け替える）。OpenAPI のタグ `AiUsage` を `definition-apiv3.cjs` の x-tagGroups「Public API」に足す（4.4）。`lint:route-guard` は `src/server/routes` しか見ないので、`node tools/lint/route-top-level-guard.cjs src/features/ai-usage/server/routes` も実行する。
- 4.4: 起動時の `warnIfUsageBaseModelInvalid` は設計の「await import」ではなく、待たずに呼んで `.catch` で警告に残す形にした（`asyncAfterExpressServerReady` は呼び出し側で await されないため）。`utils/prisma.ts` はモデルのファイルを直接読む（入口経由にすると循環するため、入口は Prisma 拡張を出さない）。worktree では `pnpm run pre:styles-bulk-export` で `bulk-export.generated.ts`（gitignore 対象）を生成すると typecheck が通る。
- 4.5: 書き方を変えたパス（大文字小文字・末尾スラッシュ）は 404 だが Cookie なしだと 1 回ごとにセッションを作り、書き方ごとに別の回数制限の枠になる（設計 L861 が受け入れ済み）。回数制限は req.ip で数えるので、TRUST_PROXY の設定次第で枠を他人に使い切られる／すり抜けられる（`ai-usage-growi-cloud` に引き継ぐ）。既存の不具合: `config-generator.ts` は `API_RATE_LIMIT_*_USERS_PER_IP` 未設定だと倍率が NaN になる（この spec の範囲外）。
- 5.1: `withUsageMetering(model, onCall)` は v3 モデルだけ包み、それ以外は同じ参照を返して警告する。`onCall` の結果は待たない（非同期の記録関数を渡してよい）。Mastra の再試行では、失敗した試行は何も渡さず、成功した再試行がそれぞれ 1 回分として渡る。`finish` の前に失敗した呼び出しは報告されない（前のステップ分は渡済み）。
- 5.2: `meterModelForRequest(requestContext, feature, model)` は `Pick<RequestContext<MastraRequestContextShape>, "get">` を受ける（suggest-path の文脈は完全な型に代入できないため）。`usage-metering/index.ts` はまだ `meterModelForRequest` を出していない → 5.3 で足す。`modelKey` と `usageMeter` は共通の型 `MastraRequestContextShape` にあり suggest-path は交差型で受け継ぐ。5.4 で suggest-path が `modelKey` を置くときに、共通の型と suggest-path の型の JSDoc（チャット専用の書き方）を一般的な書き方に直す。design L202 の文言は 8 で実態に合わせる。
- 5.3: クライアントが切断しても `execute` は `abortSignal` なしで最後まで読むので、全呼び出しが completed で記録される。
- 5.4: 実際の Mastra は中断された `generate` を拒否せず出力なしで返すので、エンジンは `controller.signal.aborted` で failed を決めている（outcome は記録に保存されず、0 件のときの警告だけを変える）。構造化出力は `structuredOutput.model` を指定したときだけ別モデルが動く（今は指定なしで、1 ステップ 1 回の報告）。将来指定するなら、その別モデルは包まれず使用量が記録されない。
- 5.5: タイトル生成は `meterModelPerCall`（チャットの集計器を読まず、呼び出しごとに `thread-title` で 1 件記録する）で包む。設定は `mastra-modules/memory/title-generation.ts` に分けてある（`memory/index.ts` は import しただけで Mongo に繋ぐためテストから読めない）。design の Memory の項とファイル一覧（`title-generation.ts`、`meterModelPerCall`）は 8 で実態に合わせる。
