# Requirements Document

## Project Description (Input)

**Parent**: umbrella spec `ai-usage`（[roadmap.md](../ai-usage/roadmap.md)）。前提の訂正・決定事項（D1〜D14）・未決の論点は umbrella の roadmap を一次情報源とする。

GROWI AI Agent の利用量を記録し、外から読めるようにする計測の中核。GROWI.cloud が Hosted（GROWI.cloud 発行の API キーで動かす形態）の原価を守るための材料を提供する。セルフホストの管理者が自分の GROWI の AI 利用量を監視する用途にも使える。

出典: 社内 wiki「/Projects/GROWI/GROWI.cloud/会議室/20260911 GROWI AI Agent オプションサービススペック検討」（https://growi.weseek.co.jp/6aa3b4807dde6add1a2c9a47）の §6.3 項 1・2・5・7、§6.4-a〜d・h、§7.1。

### 誰が困っているか

- **GROWI.cloud の運営**: Hosted では、組織に属する複数の GrowiApp の消費量を集計し、上限を超えたら止める必要がある。ところが GROWI 本体は、消費量を外から読める形で持っていない。モデルによってトークン単価が最大 100 倍違うので、生のトークン数を合計するだけでは原価を守れない。
- **GROWI の管理者（GROWI.cloud・セルフホスト共通）**: 自分の GROWI が AI をどれだけ使っているかを確かめる手段がない。

### 現状

- Mastra の `stream.usage`（入力・出力・推論・キャッシュのトークン数）はリクエストごとに計算されているが、ログに出すだけで永続化も集計もしていない（`post-message.ts`）。
- suggest-path のエージェントとスレッドタイトルの自動生成も LLM を呼んでいるが、使用量はどこにも残らない。
- モデルカタログ（models.dev 由来）は id と name だけを取り込み、単価（cost）は捨てている（`build-model-catalog.ts`）。
- カタログの自動リフレッシュは AI が有効なときしか動かない。そのため、GROWI.cloud が「カタログが古い」という理由で AI を止めると、カタログが新しくならず、いつまでも復旧しない。

### 何を変えるか

1. モデルカタログに、models.dev の cost（input / output / cache_read / cache_write）を取り込む。リリース前の取り込みとランタイムのリフレッシュの両方の経路に反映する。
2. LLM を呼ぶたびに使用量を記録する。対象は post-message・suggest-path・スレッドタイトル生成の 3 か所。記録時点のカタログ単価で「基準モデルに対する倍率」（weightedUnits）を計算し、確定させて保存する。基準モデルは env で指定する。記録は TTL で自動削除する。
3. GrowiApp 単位の消費量（倍率の合計）とカタログの鮮度を返す API を用意する。合計の開始時刻は呼び出し側が指定する。
4. GROWI.cloud が「カタログが古い」という理由で AI を止めている間も、カタログのリフレッシュを動かす。

### 確定済みの要件判断（ユーザー確認済み、2026-10-09）

1. **集計の区切りは呼び出し側が決める**: 公開 API は「指定された開始時刻以降の合計」を返す。GROWI 本体は時間／月次の区切りやタイムゾーンを持たない。次回リセット時刻を出す GROWI.cloud と、区切りが食い違わないようにするためである。
2. **公開 API は認証なし**: 設計書 §6.4-h どおり。返すのはこの GrowiApp 自身の集計値とカタログ鮮度だけで、ユーザー単位の内訳・ドル建ての値・契約情報は含めない。
3. **倍率が分からない使用量は推測で埋めない**: 次のどれかに当たるときは、生のトークン数だけを記録し、倍率は「不明」とする。公開 API は、倍率の合計とは別に「倍率が不明な分の生トークン数」を返す。扱いは呼び出し側（GROWI.cloud）が決める。
   - 基準モデルの env が設定されていない（セルフホストの既定）
   - 使ったモデルの単価がカタログにない
   - 基準モデルの単価がカタログにない
4. **停止中のカタログリフレッシュは停止理由で切り替える**: GROWI.cloud が注入する停止理由が「カタログが古い」のときだけ、AI が無効でもリフレッシュを動かす。停止理由がない普通の AI 無効（セルフホストの既定）では、今までどおり外部と通信しない。
5. **公開 API は送信元ごとの回数制限で守る**（2026-10-10）: 認証なしの API なので、短い時間に大量に呼ばれて集計が何度も走らないよう、送信元ごとに一定時間あたりの回数を絞る。GROWI.cloud の問い合わせ（下書きでは 5 分ごと）が収まる範囲で、小さな上限にする。
6. **公開 API はメンテナンスモード中も応答する**（2026-10-10）: GROWI.cloud は、組織内の 1 つの app でも応答しないと、その組織の判定をまるごと見送る。1 つの app のメンテナンスで組織全体の停止・再開の判定が止まらないようにする。
7. **定期リフレッシュの取得時刻を GROWI ごとにばらす**（2026-10-10）: 定期リフレッシュは既定で毎日 04:00 に動くので、AI を有効にした GROWI がすべて同じ時刻に models.dev へアクセスする。Hosted で AI を有効にする app が増えると、外部サービスへの一斉アクセスになる。models.dev に拒否されて取得に失敗し続けると、カタログが古いと判定されて AI が止まる原因にもなる。
8. **段階料金も反映する**（2026-10-10）: models.dev には、1 回の呼び出しの入力が一定のトークン数を超えると単価が上がるモデルがある（OpenAI・Google・Anthropic の一部）。基本の単価だけで計算すると、長い入力の呼び出しを少なく数えてしまうので、段階料金も取り込み、呼び出し 1 回ごとに単価を選ぶ。
9. **起動時のリフレッシュを既定で ON にする**（2026-10-10）: 起動した時点でカタログが古いことがある。上限超過などで止まっていた app を再開したとき、新しいリリースに上げたとき、「カタログが古い」で止まったときのどれも当てはまる。今は起動時のリフレッシュが既定で OFF なので、次に取得するのは翌日の定期リフレッシュになり、その間に「カタログが古い」で止められうる。そこで、リフレッシュが許されている GROWI は、起動するたびにすぐ取得する。起動の時刻は GROWI ごとにばらばらなので、ずらさない（ずらすのは、全 GROWI が同じ時刻に動く定期リフレッシュだけ）。外部と通信させたくない環境は、設定で OFF にできる。

## Introduction

本機能は、GROWI の AI 機能（GROWI AI Agent のチャット、suggest-path、スレッドタイトルの自動生成）が LLM を呼んだときの使用量を記録し、GrowiApp 単位の集計値として外部から読めるようにする。

記録には、生のトークン数に加えて「基準モデルに対する倍率」（以下、**重み付き消費量**）を持たせる。重み付き消費量は、その呼び出しの推定費用を、基準モデルの出力 1 トークン分の費用で割った値である。モデルの単価差を反映するので、どのモデルを使っても実際の費用にほぼ比例して増える。推定費用は、記録した時点のモデルカタログの単価で計算し、そのあとカタログが更新されても計算し直さない。

本書で使う用語は次のとおり。

- **基準モデル**: GROWI.cloud が env で指定するモデル。重み付き消費量の物差しになる。
- **停止理由**: GROWI.cloud が `AI_ENABLED=false` とあわせて env で注入する、AI を止めた理由のコード。
- **実効カタログ**: 同梱カタログとリフレッシュ済みカタログのうち、新しい方として採用されているカタログ（既存の振る舞い）。

## Boundary Context

- **In scope**:
  - モデルカタログへの単価の取り込み
  - LLM 呼び出しごとの使用量の記録、重み付き消費量の計算、古い記録の自動削除
  - 消費量とカタログ鮮度を返す公開 API
  - 「カタログが古い」という理由で止まっている間のカタログリフレッシュ
  - 基準モデルと停止理由の env の定義
- **Out of scope**:
  - 停止理由やゲージの画面表示、GROWI.cloud のゲージ API の呼び出し（`ai-usage-growi-cloud`）
  - ユーザー単位の上限判定（`ai-usage-fair-use`）
  - 組織単位の合計、上限の判定、`AI_ENABLED` による停止指示（GROWI.cloud 側）
  - 長期の利用傾向を分析するための集計
- **Adjacent expectations**:
  - GROWI.cloud は、公開 API に集計の開始時刻を渡し、返ってきた値を組織単位で合計して判定する。
  - `ai-usage-fair-use` は、この機能の記録をユーザー単位・生のトークン数で合計する。そのため、記録はユーザーと生のトークン数を必ず持つ。
  - AI を止める・再開する操作は、既存の `AI_ENABLED` と `AI_USES_ONLY_ENV_VARS_FOR_SOME_OPTIONS` の注入で行う（umbrella の D1）。この機能は止める・再開する判断に関わらない。

## Requirements

### Requirement 1: モデルカタログの単価

**Objective:** As GROWI.cloud の運営, I want モデルごとの単価がカタログに入っていること, so that モデルの単価差を反映した消費量を計算できる

#### Acceptance Criteria

1. When モデルカタログを models.dev から生成する, the モデルカタログ shall 各モデルについて、models.dev が持つ 100 万トークンあたりの単価（入力・出力・キャッシュ読み取り・キャッシュ書き込み）を取り込む。
2. The モデルカタログ shall リリース前に同梱カタログを生成する経路と、実行中にリフレッシュする経路のどちらでも、同じ単価を取り込む。
3. If models.dev があるモデルの単価を持たない（一部の項目だけ欠ける場合を含む）, then the モデルカタログ shall そのモデルを選択肢から外さずに残し、欠けている単価を「不明」として保持する。
4. If 以前のバージョンで保存されたリフレッシュ済みカタログが単価を持たない, then the モデルカタログ shall そのカタログを不正なものとして捨てず、単価を「不明」として扱う。
5. The モデルカタログ shall 単価（ドル建て）を管理画面・一般ユーザー向けの画面・API の応答に出さない。
6. Where models.dev があるモデルについて、入力トークン数に応じた段階的な単価を持つ, the モデルカタログ shall 段階ごとの境目（入力トークン数）と、その段階の単価も取り込む。

### Requirement 2: 使用量の記録

**Objective:** As GROWI.cloud の運営と GROWI の管理者, I want AI が LLM を呼ぶたびに使用量が漏れなく記録されること, so that 実際に使った量をあとから集計できる

#### Acceptance Criteria

1. When GROWI AI Agent のチャットが 1 回の応答を終える, the AI 利用量計測 shall その応答のために行ったすべてのステップ（ツール呼び出しを挟んだ複数回の LLM 呼び出しを含む）の使用量の合計を、1 件の記録として残す。
2. When suggest-path のエージェントが 1 回の提案を終える, the AI 利用量計測 shall その提案のために行ったすべてのステップの使用量の合計を、1 件の記録として残す。
3. When チャットのスレッドタイトルを自動生成する, the AI 利用量計測 shall その生成の使用量を 1 件の記録として残す。
4. The AI 利用量計測 shall 各記録に、利用したユーザー、利用した機能（チャット・suggest-path・タイトル生成のどれか）、プロバイダ、モデル、入力・出力・推論・キャッシュ読み取り・キャッシュ書き込みの各トークン数、記録時刻を含める。
5. If プロバイダがトークン数の一部の項目（推論・キャッシュ読み取り・キャッシュ書き込みなど）を返さない, then the AI 利用量計測 shall その項目を 0 ではなく「値なし」として記録する。
6. If 応答の途中でクライアントが切断した、または応答の途中でエラーになった, then the AI 利用量計測 shall それまでにプロバイダが報告した使用量を記録する。
7. If 前項の場合にプロバイダが使用量を報告しなかった, then the AI 利用量計測 shall 使用量を記録できなかったことを、ユーザー・機能・モデルを添えて警告ログに残す。
8. If 使用量の記録に失敗した, then the AI 利用量計測 shall ユーザーへの応答を変えず（エラーにも遅延にもせず）、失敗をエラーログに残す。
9. The AI 利用量計測 shall 記録を、記録時刻から 90 日たったら自動的に削除する。
10. The AI 利用量計測 shall Owned・Hosted・セルフホストの区別なく、AI 機能が LLM を呼んだときは常に記録する。

### Requirement 3: 重み付き消費量

**Objective:** As GROWI.cloud の運営, I want 使用量が基準モデルに対する倍率で記録されること, so that 顧客がどのモデルを選んでも費用にほぼ比例した消費量で上限を判定できる

#### Acceptance Criteria

1. Where 基準モデルが env で指定されている, when 使用量を記録する, the AI 利用量計測 shall その時点の実効カタログの単価で呼び出しの推定費用を計算し、それを基準モデルの出力 1 トークン分の費用で割った値を、重み付き消費量として記録に含める。
2. When 推定費用を計算する, the AI 利用量計測 shall キャッシュから読み取った入力トークンにはキャッシュ読み取りの単価を、キャッシュに書き込んだ入力トークンにはキャッシュ書き込みの単価を、それ以外の入力トークンには通常の入力単価を、出力トークンには出力単価を使う。
3. If 使ったモデルにキャッシュ読み取りまたはキャッシュ書き込みの単価がない, then the AI 利用量計測 shall その分のトークンに通常の入力単価を使う。
4. If 基準モデルが指定されていない、使ったモデルの入力または出力の単価が不明、または基準モデルの出力単価が不明, then the AI 利用量計測 shall 重み付き消費量を「不明」として、生のトークン数だけを記録する。
5. The AI 利用量計測 shall 重み付き消費量を記録した時点で確定させ、そのあとカタログや基準モデルが変わっても、記録済みの値を計算し直さない。
6. The AI 利用量計測 shall 推定費用（ドル建て）を監査のために記録に残すが、API の応答や画面には出さない。
7. When 推定費用を計算する, the AI 利用量計測 shall LLM の呼び出し 1 回ごとに単価を選び、その回の入力トークン数が段階の境目を超えていれば、その回のトークン全体にその段階の単価を使う。1 回の応答が複数の呼び出しからなるときは、呼び出しごとの推定費用を合計する。

### Requirement 4: 消費量とカタログ鮮度の公開 API

**Objective:** As GROWI.cloud の運営, I want 各 GrowiApp の消費量とカタログ鮮度を外から読めること, so that 組織単位で合計し、上限超過とカタログの古さを判定できる

#### Acceptance Criteria

1. When 1 つ以上の集計開始時刻を指定した問い合わせを受ける, the AI 利用量計測 shall 開始時刻ごとに、その時刻から現在までに記録された重み付き消費量の合計と、重み付き消費量が「不明」だった記録の生トークン数の合計を返す。
2. The AI 利用量計測 shall 応答に、カタログの鮮度として「実効カタログの中身を最後に models.dev から取得した日時」と、それが同梱カタログかリフレッシュ済みカタログかの区別を含める。取得日時は、リフレッシュ済みカタログならリフレッシュで取得した日時、同梱カタログならその同梱カタログを生成した日時とする。
3. Where GROWI.cloud 上の GrowiApp ID が設定されている, the AI 利用量計測 shall 応答にその ID を含める。
4. The AI 利用量計測 shall この API に認証を求めない。
5. The AI 利用量計測 shall 応答に、この GrowiApp 全体の合計値とカタログ鮮度だけを含め、ユーザー単位の内訳、ユーザーを識別できる情報、推定費用（ドル建て）を含めない。
6. While AI 機能が無効になっている, the AI 利用量計測 shall この API に通常どおり応答する。
7. The AI 利用量計測 shall AI を一度も使っていない GROWI がこの API に応答するとき、AI 機能本体を読み込まず、そのメモリ使用量を増やさない。
8. If 集計開始時刻の形式が不正、現在より後、または記録の保持期間（90 日）より前, then the AI 利用量計測 shall 集計を行わずに、入力が不正であることを示すエラーを返す。
9. The AI 利用量計測 shall 時間や月の区切り、タイムゾーンを独自に持たず、指定された開始時刻だけに従って集計する。
10. If 同じ送信元からのリクエストが一定時間あたりの上限を超えた, then the AI 利用量計測 shall 集計を行わずに、リクエストが多すぎることを示すエラーを返す。
11. While GROWI がメンテナンスモードである, the AI 利用量計測 shall この API に通常どおり応答する。

### Requirement 5: 基準モデルと停止理由の設定

**Objective:** As GROWI.cloud の運営, I want 基準モデルと停止理由を env で GROWI に渡せること, so that GROWI.cloud の判断を GROWI 本体のコードを変えずに反映できる

#### Acceptance Criteria

1. The AI 利用量計測 shall 基準モデルを、プロバイダとモデル ID の組として env から受け取る。
2. The AI 利用量計測 shall 停止理由を、GROWI.cloud が定めるコード値として env から受け取る。
3. The AI 利用量計測 shall 基準モデルと停止理由を、管理画面から表示・変更できる設定にしない。
4. If 基準モデルの env の形式が不正、またはカタログにないモデルを指している, then the AI 利用量計測 shall 起動時に警告ログを残し、基準モデルが指定されていないときと同じに扱う。

### Requirement 6: カタログリフレッシュの契機

**Objective:** As GROWI.cloud の運営, I want 「カタログが古い」という理由で止めた GrowiApp のカタログが自動で新しくなること, so that 止めた GrowiApp が人手を介さずに復旧できる

#### Acceptance Criteria

1. While AI 機能が無効で、かつ停止理由が「カタログが古い」を示している, the モデルカタログ shall AI 機能が有効なときと同じ契機（起動時と、設定されたスケジュール）でカタログをリフレッシュする。
2. While AI 機能が無効で、かつ停止理由が設定されていない、または「カタログが古い」以外を示している, the モデルカタログ shall カタログのリフレッシュのために外部と通信しない。
3. When リフレッシュが成功する（停止中か否かを問わない）, the AI 利用量計測 shall 公開 API が返すカタログの取得日時を、そのリフレッシュで取得した日時に更新する。
4. When 定期リフレッシュのスケジュール時刻になる, the モデルカタログ shall すぐには取得せず、GROWI ごとに異なる時間だけ遅らせてから models.dev へアクセスし、多数の GROWI のアクセスが同じ時刻に集中しないようにする。
5. The モデルカタログ shall 前項の遅れを、次の定期リフレッシュの時刻を越えない範囲に収める。
6. When 管理者が管理画面から手動でリフレッシュする, the モデルカタログ shall 遅らせずにすぐ取得する。
7. When リフレッシュが許されている状態（AI 機能が有効、または停止理由が「カタログが古い」）で GROWI が起動する, the モデルカタログ shall 起動時リフレッシュの設定が OFF にされていない限り（既定は ON）、遅らせずにすぐカタログをリフレッシュする。
