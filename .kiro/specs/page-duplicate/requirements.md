# Requirements Document

## Project Description (Input)

**誰が困っているか**

- 配下を含むページの複製を使う GROWI の利用者。とくに、配下のページ数や版の数が多いツリーを複製する人。
- 複製が途中で止まった範囲で、複製・移動・ページ名変更をしようとする、同じ GROWI の他の利用者。
- 上記の問い合わせを受ける運用者（GROWI.cloud を含む）。

**現在の状況**

- GROWI.cloud の顧客環境（v8.0.9）で、配下83ページ・1505版のツリーの複製が途中で止まった。先頭ページだけが作られ、配下は1ページも複製されなかった。
- 進行中を表す操作記録（PageOperation）が残り続け、その範囲の複製・移動・ページ名変更が約3週間すべて拒否された。複製は応答が返らずロードバランサーの 502 になり、利用者には理由が分からなかった。応答が返らない不具合は PR #12284 で修正済み。
- 本番データでの再現計測で、配下の複製処理（`PageService.duplicateDescendants`）が対象ページの最新版だけでなく全版の本文を一度に読み込み、複製中にメモリが約 300MB 増えることを確認した。最新版だけを読み込めば約 20MB で済む。コンテナのメモリ上限が 768M の環境だと、平常時の使用量によってはこの増加で上限を超え、プロセスが強制終了されうる。これが、複製が止まった原因の有力候補である（本番での強制終了は未確認）。旧形式（v4）のページを複製する経路も、同じく全版を読み込む。
- 操作記録は期限を持つが、操作中かどうかの判定は期限を見ない。止まった操作の記録は、次の再起動（v8.0.11 以降の起動時の掃除）まで残る。先頭ページだけの不完全な写しは、誰にも知らされず残る。
- 複製の処理は、約5900行ある `PageService` の中に、作成・移動・削除などの処理と混在している。

**何を変えるか**

1. 配下の複製で、各ページの最新版だけを写す。
2. 写しの本文をアプリのプロセスに読み込まずに作る（MongoDB の中で写す方向で design する）。最新版だけを読み込む方式でも、アプリに載る量は「本文の最大の大きさ × 一度に扱う件数」で決まり、本文は MongoDB の1ドキュメントの上限（16MB）近くまで入りうるため、上限を保証できない。一度に扱う件数（現在は `BULK_REINDEX_SIZE` の100件単位）は、アプリのメモリではなく DB への負荷とのかね合いで見直すかどうかを決める。
3. 複製の拒否と失敗の扱いを整理する。応答を先に返し、配下の処理は裏で走らせて待たない今の方式は維持する。そのうえで、配下の複製が途中で止まったときに、システムが自動で回復できるようにする。
4. 複製の処理を `PageService` から別のモジュールに切り出し、筋の良い実装にする。

**決まっている仕様（spec 化に先立って合意済み）**

- **回復の結末**: 途中で止まった複製の、作りかけの写しは消さずに残す。続きのやり直しもしない。残った操作記録だけを片付けて、以降の操作が拒否されないようにする。
- **本人への通知**: 複製を実行した本人に、アプリ内通知でどういう結末になったかを知らせる。
- **回復までの時間**: 再起動を待たず、止まってから数分以内に回復する。

**対象範囲**

- 対象はページの複製だけとする。操作記録の仕組みは移動・削除・元に戻す操作と共通だが、それらの整理はこの spec では行わない。共通の仕組みを変える場合は、他の操作に後から広げられる形にする。

## Introduction

このドキュメントは、配下を含むページの複製について、利用者と運用者から観察できる挙動を定める。

狙いは3つある。1つ目は、複製が途中で止まりにくくすることで、複製中に増える GROWI のプロセスのメモリを、本文の大きさ・版の数・ツリーの大きさに左右されない量に抑える。2つ目は、それでも止まったときに、同じ範囲の操作が拒否され続ける状態を数分以内に自動で解くこと。3つ目は、何が起きたかを複製した本人に知らせることである。

止まった複製は、続きをやり直さず、作りかけの写しをそのまま残す。写しを使い続けるか、消して複製し直すかは、通知を受けた本人が決める。

## Boundary Context

- **In scope**:
  - 配下を含む複製で、写しの本文を元ページの最新版にそろえること。
  - 複製中の GROWI のプロセスのメモリの増加を、本文の大きさ・版の数・ページ数によらない量に抑えること。旧形式（v4）のページの複製も含む。
  - 複製が例外で失敗した場合と、複製を実行していたプロセスが止まった・終了した場合の、自動での回復と本人への通知。
  - 複製の処理を、他のページ操作から独立して扱える形に切り出すこと。切り出し方は design で決める。
- **Out of scope**:
  - 移動・削除・元に戻す操作の、拒否・失敗・回復の扱い。
  - 途中で止まった複製の続きのやり直しと、作りかけの写しの自動削除。
  - 管理者が止まった操作を一覧・操作する画面。
  - 複製の権限の規則（複製先で公開範囲が合わない場合の拒否、読めない配下ページを複製するかどうかの選択肢）の変更。
  - 複製が正常に終わったときの通知の追加。
- **Adjacent expectations**:
  - 拒否の理由を応答で返す仕組み（`grant_not_assignable` / `operation_in_progress`）は PR #12284 で導入済みのものを使う。
  - 一度に処理する単位の大きさを今の100件から変えるかどうかは、design の調査で、データベースへの負荷とのかね合いで決める。要件2は、単位の大きさによらず GROWI のプロセスのメモリが増えないことを求める。
  - 複製中の本文の写しにかかる負荷は、データベース側が受け持つ。
  - 起動時に残った操作記録を掃除する既存の仕組み（v8.0.11 以降）は残す。

## Requirements

### Requirement 1: 写しの本文

**Objective:** As a 複製する利用者, I want 写しの本文が元ページの最新の内容になっていること, so that 複製した直後から写しを元ページと同じ内容として使える

#### Acceptance Criteria

1. When 利用者が配下を含めてページを複製した場合, the ページ複製機能 shall 先頭ページと各配下ページの写しの本文を、複製を始めた時点での元ページの最新版の本文と同じにする。
2. The ページ複製機能 shall 写しの本文を、元ページの過去の版から取らない。版の並び順や件数によって、どの版が写るかが変わってはならない。
3. The ページ複製機能 shall 1.1 と 1.2 を、旧形式（v4）のページを複製する場合にも満たす。

### Requirement 2: 複製中のメモリ使用量

**Objective:** As a GROWI の運用者, I want 大きなツリーを複製してもメモリが急に増えないこと, so that メモリ上限の小さいコンテナでも複製でプロセスが落ちない

#### Acceptance Criteria

1. The ページ複製機能 shall 複製中に増える GROWI のプロセスのメモリの量が、配下ページの本文の大きさ、版の数、配下ページの総数のいずれによっても増えないようにする。
2. When 本文が1ページあたり MongoDB の1ドキュメントに入る最大級の大きさ（約 16MB）のページを、一度に処理する単位を満たす数だけ含むツリーを複製した場合, the ページ複製機能 shall 2.1 を満たす。
3. When 配下83ページ・1505版（全版の本文の合計 約57MB）の規模のツリーを複製した場合, the ページ複製機能 shall 複製中の GROWI のプロセスのメモリの増加を、現在の全版を読み込む実装（約 300MB）と比べて計測し、その値を設計書に記録する。
4. The ページ複製機能 shall 2.1 と 2.2 を、旧形式（v4）のページを複製する場合にも満たす。

### Requirement 3: 進行中の複製と重なる操作

**Objective:** As a 同じ GROWI の他の利用者, I want 複製の途中で重なる操作をしたときに理由が分かること, so that 待てばよいのか、別の問題なのかを判断できる

#### Acceptance Criteria

1. While 配下の複製が進行中である, the ページ複製機能 shall 複製元と複製先に重なる範囲の複製・移動・ページ名変更を拒否し、別の操作が進行中であることを理由として示す。
2. When 配下の複製が完了した場合, the ページ複製機能 shall 3.1 の拒否をやめ、その範囲の操作を受け付ける。
3. When 配下の複製が途中で止まり、Requirement 4 の回復が終わった場合, the ページ複製機能 shall 3.1 の拒否をやめ、その範囲の操作を受け付ける。

### Requirement 4: 途中で止まった複製の自動回復

**Objective:** As a 複製した利用者と同じ GROWI の他の利用者, I want 複製が途中で止まっても、その範囲の操作がすぐに使えるようになること, so that 再起動や運用者の手作業を待たずに作業を続けられる

#### Acceptance Criteria

1. If 配下の複製が例外で失敗した場合, the ページ複製機能 shall その複製の操作記録を片付け、作りかけの写しは消さずに残す。
2. If 複製を実行していたプロセスが、配下の複製の途中で止まった、または終了した場合, the ページ複製機能 shall 止まってから15分以内に、その複製の操作記録を片付け、作りかけの写しは消さずに残す。
3. If 複製を実行していたプロセスが終了し、すぐに再起動した場合, the ページ複製機能 shall 再起動してから5分以内に 4.2 の回復を行う。
4. While 配下の複製が処理を進めている, the ページ複製機能 shall その複製を止まったものとして扱わない。処理に時間がかかっているだけの複製を、4.2 の回復の対象にしてはならない。
5. When 4.1 または 4.2 の回復を行った場合, the ページ複製機能 shall 残した写しのページを、ページツリーから親をたどって到達できる状態にし、各ページの配下ページ数の表示を実際の数と一致させる。
6. The ページ複製機能 shall 途中で止まった複製の続きを自動でやり直さない。
7. The ページ複製機能 shall 1つの止まった複製について、回復を1回だけ行う。複数のプロセスが同時に同じ複製を回復しようとしても、結果と通知が重複してはならない。

### Requirement 5: 複製した本人への通知

**Objective:** As a 複製した利用者, I want 複製が途中で止まったことと、その結果どうなっているかを知らされること, so that 作りかけの写しを使うか、消して複製し直すかを判断できる

#### Acceptance Criteria

1. When Requirement 4 の回復を行った場合, the ページ複製機能 shall 複製を実行した本人に、アプリ内通知で複製が途中で止まったことを知らせる。
2. The ページ複製機能 shall 5.1 の通知に、複製元のパス、複製先のパス、写しが作られたページ数と複製元の配下のページ数を含める。
3. The ページ複製機能 shall 5.1 の通知から、残った写しのページへ移動できるようにする。
4. The ページ複製機能 shall 5.1 の通知で、写しが不完全であること、その写しは消すか別の名前で複製し直せることを伝える。
5. The ページ複製機能 shall 5.1 の通知を、複製を実行した本人以外には送らない。
6. The ページ複製機能 shall 5.1 の通知の文言を、GROWI が対応するすべての言語で用意する。

### Requirement 6: 既存の挙動の維持

**Objective:** As a 複製する利用者, I want 処理の作り直しで複製の結果が変わらないこと, so that これまでどおりに複製を使える

#### Acceptance Criteria

1. The ページ複製機能 shall 複製の要求に対して、配下の複製の完了を待たずに応答を返す今の方式を維持する。
2. The ページ複製機能 shall 複製の要求の受け付け方（指定できる項目と、その意味）と、拒否・失敗のときの応答を変えない。
3. The ページ複製機能 shall 正常に完了した複製について、写されるページの範囲、各写しの公開範囲、タグの引き継ぎ、写しの作成者を今と同じにする。「自分が閲覧可能なページのみを複製する」を選んだ場合の挙動も含む。
4. The ページ複製機能 shall 「リンクを知っている人のみ」のページを配下の複製の対象にしない今の挙動を維持する。
