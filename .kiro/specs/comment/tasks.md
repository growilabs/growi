# Implementation Plan

> **進め方**: 実装を伴う各サブタスクは、先に失敗するテストを書き(red)、実装して通す(green)。テストを書く、またはレビューするときは、`essential-test-design`(何を確かめるか)と `essential-test-patterns`(どう組むか)を先に参照する。
> 対象は `apps/app` 配下。コマンドは `apps/app` で実行する。

- [x] 1. Foundation: 共有の型、整形、件数の集計
- [x] 1.1 コメント1件の応答の型と、行から応答への整形を作る
  - 応答の型は、旧 API の項目(別名の `page` / `revision` / `replyTo`、安全化した `creator`、`commentPosition` など)の上位集合に、インライン用の項目(`isInline`、引用文字列、前後の文脈、おおよその位置、アンカー起点の版、解決の状態)を足したものにする。型は単独で定義し、`as` で食い違いを隠さない
  - リクエストのクエリ(ページ、版、共有リンク)と、応答の本体(`comments` の配列)の型も同じ場所に置く
  - 整形は、行を受け取って応答の1件を返す純粋関数にする。投稿者があれば安全化(メールなどを除く)し、なければ投稿者の ID を入れる
  - 整形の入力となる行の型(投稿者を含む行。`CommentListRow`)は、整形と同じ場所で定義して export する。2.1 の取得サービスがこれを import する(依存の向きは「整形 → サービス」)
  - 先に、通常コメントの行とインラインコメントの行で、別名の項目、安全化された投稿者、投稿者が無いときの ID を確かめるテストを書く
  - 完了の状態: 整形の単体テストが通り、型検査が通る
  - _Requirements: 1.2, 1.3, 1.7_
  - _Boundary: ICommentListItem, toCommentListItem, CommentListRow_

- [x] 1.2 旧 API の応答の整形を共有の整形に置き換え、非推奨を明示する
  - 旧 API の応答の組み立てを、1.1 の整形に置き換える。出力(項目、値、並び順)は変えない
  - 旧 API の公開仕様の記述に `deprecated` を付け、置き換え先として新しいコメント一覧 API を案内する文を足す
  - 旧 API がインラインコメントを返さないこと(取得メソッドの固定の除外)には触れない
  - 既存の旧 API の結合テスト(共有リンクの認可、インラインコメントを返さないこと)が変更なしで通ることを確かめる
  - 完了の状態: 旧 API の既存の結合テストがすべて通り、旧 API の公開仕様の生成と検証が通って `deprecated` が付いている
  - _Requirements: 5.1, 5.2, 5.3_
  - _Depends: 1.1_
  - _Boundary: comments.get(apiv1)_

- [x] 1.3 コメント件数の集計を、インラインコメントと返信も含めて数えるようにする
  - 件数の集計から、インラインコメントの除外を外す。返信も1件、解決済みのインラインコメントも1件として数える
  - 一覧の取得メソッド(旧 API が使う側)の除外は変えない
  - 先に、通常コメント、インラインコメント、返信、解決済みを含むページで、合計が返ることを確かめる結合テストを書く。既存の「インラインを数えない」前提のテストは、新しい数え方に書き換える。`isInline` の補完の移行テスト(補完の前後で件数の集計を確かめている部分)の期待値も、インラインを数える新しい数え方に合わせて書き換える
  - 完了の状態: 件数の結合テストが通り、旧 API が使う取得メソッドのテストは変わらず通る
  - _Requirements: 7.1, 7.2, 7.3, 7.6_
  - _Boundary: countCommentByPageId_

- [x] 1.4 ページのコメント件数の更新が、書き込みの完了を待つようにする
  - 件数を更新する関数(`Page.updateCommentCount`)が、保存値の書き込みを `await` して結果を返す形に直す。いまはコールバック方式で、完了を待たずに戻り、失敗の例外も呼び出し元に届かない
  - 通常コメントの追加と削除のコメントイベントの購読、通常コメントのルートも、同じ関数を使うので、同じ競争が一緒に解消される
  - 先に、関数の完了後すぐに保存値が合計と一致することを確かめる結合テストを書く(待ち合わせなし)
  - 完了の状態: 結合テストが通り、通常コメントの追加と削除の既存のテストも通る
  - _Requirements: 7.4_
  - _Boundary: Page.updateCommentCount_

- [x] 2. Core: コメント一覧 API(サーバー)
- [x] 2.1 版の範囲を決めて、コメントを取得するサービスを作る
  - ページを指定して、通常コメント、インラインコメント、返信、解決済みを区別せずに、作成日時の新しい順で取得する
  - 版が指定されたら、その版をページ付きで取得し、存在しない、または別ページの版なら「版が見つからない」を返す
  - 次の版(同じページで、指定した版より作成日時が後で最も古い版)があれば、その作成日時より前に作成されたコメントだけを返す。次の版が無ければ(最新の版)絞り込まない
  - 先に、全種類が返ること、新しい順、版の指定で範囲が変わること、最新の版で全件、別ページの版と存在しない版、返信が親と同じ規則で絞られること、を確かめる結合テストを書く
  - 完了の状態: サービスの結合テストがすべて通る
  - _Requirements: 1.1, 1.4, 1.5, 1.6, 2.1, 2.2, 2.3, 2.4_
  - _Depends: 1.1_
  - _Boundary: listComments_

- [x] 2.2 コメント一覧のルートを作る(入力の検証、認証、閲覧権限、応答)
  - ページ(必須)と版(任意)と共有リンク(任意)の ID を、文字列かつ有効な ID であることまで検証する。不正なら 400
  - ミドルウェアの順は、アクセストークンの解析 → 入力の検証 → 共有リンクの判定 → ログイン(ゲストを許可する版)とする。旧 API と同じ理由で、検証を共有リンクの判定より前に置く
  - 共有リンクでないときは、ページの閲覧権限を確認し、見えない場合と存在しない場合を区別せず 404(`notfound_or_forbidden`)を返す。版が見つからない場合も同じ 404
  - 成功時は、コメントを1件ずつ整形して `{ comments }` で返す。予期しない失敗は、内部の詳細を含まない 500 を返す
  - 先に、ログイン済みの利用者、アクセストークン、未認証(ゲスト閲覧の許可あり、なし)、見えないページと存在しないページが同じ応答になること、不正な ID が 400 になることを確かめる結合テストを書く
  - 完了の状態: ルートの結合テストが通る(共有リンク経由の分岐は 2.3 で扱う)
  - _Requirements: 1.8, 3.1, 3.2, 3.5, 3.6, 3.7, 3.9_

  - _Boundary: list route_

## Implementation Notes

- 1.1: `ICommentCreator`(整形後の投稿者の型)には実行時にある `_id` / `__v` が無く、`name` が null を許す。`Ref<IUser>`(`_id` 必須)や `IInlineComment.creator` にはそのまま代入できないため、4.3 / 4.4 / 4.5 で投稿者の型も合わせて広げる。`_id` を `as` なしで載せるには `CommentListRow` を拡張済み prisma クライアントの結果型から作る方法がある。
- 1.1: 投稿者の安全化は `serializeUserSecurely` を使わず `toCreator` で自前実装(Prisma の行は `IUser` に合わない)。`isEmailPublished` が真なら `email`(null 含む)を残す、旧 API と同じ挙動。
