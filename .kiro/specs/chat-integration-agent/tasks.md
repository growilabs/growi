# Implementation Plan

設計は `design.md`、決めた理由は `research.md` にある。この spec は amend spec なので、最後のタスク（7）で対象の spec へ書き戻し、このディレクトリを削除する（`.claude/rules/spec-lifecycle.md`）。

進め方の注意:

- 1（protocol）が終わると、2〜3（proxy）と 4〜5（app）は互いを知らずに並行して進められる。ただし `pnpm install` と build・test を同時に走らせない（`.claude/rules/devcontainer.md`）
- app の chat-integration の試験は `MONGO_URI='mongodb://mongo:27017/growi_test_chat?replicaSet=rs0'` を付けて 1 ファイルずつ回す。proxy の結合試験は PostgreSQL が要る
- 振る舞いを変えるタスクは、先に失敗する試験を書いてから直す

- [ ] 1. protocol: コマンドの語彙と 2 つの新しい口
- [ ] 1.1 コマンドの語彙を `search`・`create-page`・`agent` に入れ替える
  - `keep` はこのタスクでは消さない（proxy と app が使うのをやめた後、6.1 で消す）。1 が終われば、proxy と app を並行して進められる
  - コマンドの名前ごとの表を持つ proxy と app の箇所に、型検査が通るだけの `agent` の行を足す（中身は 3.1・5.3 で作る）。このタスクは protocol・proxy・app にまたがる
  - `agent` を、書き込みを伴い・対象が 1 つの GROWI に定まり・DM を専用の欄だけで判定するコマンドとして宣言する。ほかのコマンドは、DM を「すべてのチャンネル」の決まりに従わせる
  - `agent` の依頼（呼びかけを外した文章と会話の鍵、それぞれの長さの上限）、「受け付けた」の応答、「AI が使えない」「処理中」のエラーを足し、依頼と応答の parser を合わせる
  - 完了の条件: protocol の試験で、`agent` の依頼と応答が往復し、長さの上限を超えた依頼が拒まれる。protocol・proxy・app の型検査が通り、既存の試験は変更なしで通る
  - _Requirements: 11.6, 15.1, 15.4, 15.12, 15.13_
- [ ] 1.2 DM であることを伝え、`agent` の DM の許可を判定できるようにする
  - チャンネルの参照に「DM である」の欄を、権限の設定に「DM で許す」の欄を、どちらも省略できる欄として足し、parser を合わせる（省略は「DM ではない」「許さない」と読む。proxy が値を入れるのは 2.2）
  - 権限の判定に、「DM で、専用の欄で判定するコマンドなら、その欄が真のときだけ許す」決まりを足す。判定はコマンドの名前で分岐せず、コマンドの性質だけを見る
  - 完了の条件: 判定の試験で、`agent` は「すべてのチャンネル」を許していても DM の欄が偽なら DM で断られ、ほかのコマンドは今までどおり「すべてのチャンネル」で DM も許される。protocol・proxy・app の型検査が通る
  - _Requirements: 11.7_
- [ ] 1.3 答えを送る口を足す
  - GROWI から proxy への向きの口として、答え（文章と出典、作ったページと要約した範囲、失敗とその理由）の本文と、結果（届けた・届けられなかった・知らない依頼・配達中）を定義し、parser を足す
  - 答えの本文の長さと出典の件数に上限を設ける
  - 完了の条件: 口の表に行があり、本文と結果が parser で往復し、上限を超えた本文が拒まれる
  - _Requirements: 5.8, 5.12, 15.6, 15.7, 15.19_
- [ ] 1.4 会話を求める口を足す
  - GROWI から proxy への向きで、元の依頼の番号だけを送り、発言の一覧と範囲・「まだ古い発言がある」、または読めなかった理由と取れる操作を返す口を定義し、parser を足す
  - 完了の条件: 口の表に行があり、成功と 6 種類の失敗の結果が parser で往復する
  - _Requirements: 5.7, 5.13, 5.14, 5.15, 5.16, 5.17_

- [ ] 2. proxy: 受け取り・保存・読み取りの土台
- [ ] 2.1 答えを待つ依頼の記録と、DM の許可の保存先を用意する
  - 答えを待つ依頼の表（連携・依頼の番号・installation・宛先・配達の状態と取った時刻・期限）と、権限の表の「DM で許す」の欄を、migration で足す
  - 依頼の記録を読み書きする repository を作り、期限切れの掃除の一覧と、連携の解除で消す順序に加える
  - 設定の受け取りで「DM で許す」を保存し、判定に渡す
  - 完了の条件: migration を適用した状態で、保存の往復の結合試験と、掃除の一覧の試験（表の数）が通り、連携を解除すると依頼の記録も消える
  - _Requirements: 11.7, 15.7_
- [ ] 2.2 スレッドの根元と、bot への呼びかけを外した文章を、イベントからコマンドまで通す
  - イベントに、実際にスレッドの中にあったときの根元・答えを置くスレッドの根元・DM であること・bot 自身への呼びかけだけを外した文章を載せ、コマンドの呼び出しまで運ぶ（聞き返しの記録に残る形は省略できる欄にする）
  - 答えを置く根元は、DM のスレッドの外の発言なら発言そのもの、返信の階層の無い Teams の DM では無し、とする
  - 語の形で呼びかけを推測していた処理を取り除き、既存のコマンドの引数も新しい文章から取る
  - 本人に宛てた返事の宛先（origin）にも、2 つの根元と場所の種類（チャンネルか DM か）を足す
  - 完了の条件: 4 サービスで、bot への呼びかけだけが外れて先頭のほかの利用者への言及が残り、Slack の DM（AI アプリの画面が無効）で依頼の発言が答えを置く根元になる試験が通る。既存のコマンドの試験と、本人に宛てた返事・聞き返しの試験は変更なしで通る
  - _Requirements: 15.8, 15.14, 15.17_
- [ ] 2.3 スレッドの中へ投稿する操作を足す
  - 本人にだけ見えるメッセージをスレッドの中に出す、スレッドの中にふつうに投稿する、の 2 つの操作を足す。どちらもイベントの処理の外から、installation を指定して呼べる
  - 完了の条件: 代役のサービスを使った結合試験で、スレッドの根元が各サービスの投稿に渡る
  - _Requirements: 15.8_
- [ ] 2.4 処理中の表示と、Slack の AI アプリの画面の設定を足す
  - 処理中の表示を出す操作を足す。対応しないサービスでは何もしない
  - 運用者の設定で Slack の AI アプリの画面を有効にできるようにする（既定は無効）
  - 完了の条件: AI アプリの画面が有効・無効の両方で、既存の「DM へ届け直す」と「DM での聞き返し」の結合試験が通り、有効なときだけ処理中の表示が Slack に送られる
  - _Requirements: 15.16_
- [ ] 2.5 会話を読む
  - スレッドの中の依頼ならそのスレッドを、そうでなければその場所の直近を、200 件まで 1 回で読み、古い順に返す。bot 自身の発言と依頼の発言は除く
  - Slack では、頻度の制限で断られた読み取りをやり直さずにすぐ「頻度の制限」として返す。ほかの 3 サービスのアダプタが自前でやり直すかを最初に確かめ、やり直すなら同じく外す
  - 完了の条件: 代役のサービスを使った結合試験で、スレッドの読み取り・直近の読み取り・「まだ古い発言がある」・bot が参加していない・頻度の制限（429 で待たずに返る）が確かめられる
  - _Requirements: 5.7, 5.13, 5.15, 5.16, 5.17_
- [ ] 2.6 (P) 能力表に `agent` の行を足す
  - スレッドの中への答え、続けられる場所（Slack は画面の設定で切り替わる。Discord と Teams は無し）、会話の要約と読める範囲の限り、返事の無いメッセージのスレッドへの本人だけのメッセージ（Slack は未確認）、AI アプリの画面の自由な文章、の行を足す
  - 完了の条件: 能力の報告に新しい行がサービスごとの段階で出る試験が通る
  - _Requirements: 1.20, 15.9_
  - _Boundary: CapabilityTable_
  - _Depends: 2.4_

- [ ] 3. proxy: `agent` の流れ
- [ ] 3.1 コマンドの組から `keep` を外し、`agent` を足す
  - `agent` の性質を宣言し、`keep` の処理と、`keep` 専用の時間範囲の入力・履歴の読み取り・範囲の解析を取り除く。proxy は protocol の `keep` の型を使わなくなる
  - 完了の条件: `@GROWI agent …` が `agent` のコマンドとして解釈され、`keep` が知らないコマンドとして扱われる試験が通る
  - _Requirements: 15.1, 15.13_
- [ ] 3.2 `agent` の依頼を受け付ける
  - 試験用の偽の GROWI を、`agent` に「受け付けた」・紐付けが要る・エラーを返せるように広げる
  - GROWI を選び（複数なら選ばせる）、依頼の記録を保存してから GROWI へ送り、リアクションで受け付けを示す。AI アプリの画面では処理中の表示も出す
  - GROWI が「受け付けた」と返したら終わる。紐付けが要る・エラーなら記録を消して今のコマンドと同じく本人に返す。10 秒以内に返事が無ければ、記録を残して「答えが後から届くことがある」と返す
  - 完了の条件: 偽の GROWI を使った試験で、3 種類の返事と時間切れのそれぞれで、記録の有無と本人に届く文面が上のとおりになる
  - _Requirements: 15.1, 15.3, 15.4, 15.5, 15.12, 15.16_
  - _Depends: 2.1, 2.2, 2.4_
- [ ] 3.3 (P) 答えを投稿の文面にする
  - 文章の答え（出典の一覧、チャンネルでの答えなら続けられる場所の案内）、ページを作った答え（リンク・発言の件数と最初と最後の日時・範囲が限られたこと）、失敗の答え（理由ごとの文。会話を読めなかったときは理由と取れる操作）の文面を作る純粋関数
  - 完了の条件: 答えの種類・場所・能力の組み合わせごとの文面の試験が通り、続きの案内はチャンネルでの答えにだけ、続けられる場所のあるサービスでだけ付く
  - _Requirements: 5.12, 5.13, 5.14, 5.15, 5.16, 5.17, 15.9_
  - _Boundary: AgentAnswerMessage_
- [ ] 3.4 あとから届いた答えを届ける
  - 依頼の記録から宛先を引き、配達中の印を付けてから届ける。記録が無ければ「知らない依頼」、届け終えていればその結果、まだ新しい配達中なら「配達中」を返す。配達中の印は 2 分で取り直せる
  - チャンネルの依頼には本人に宛てた返事の決まりで届け、スレッドの中の依頼ならそのスレッドに出す。DM の依頼は、依頼のスレッドの中にふつうに投稿する
  - 完了の条件: 結合試験で、記録どおりの場所と本人に届き、同じ答えが 2 つ同時に届いても 1 回しか届かず、配達中のまま止まった記録が 2 分後の送り直しで届き直し、時間切れにした依頼の答えも届く
  - _Requirements: 15.7, 15.8, 15.11_
  - _Depends: 2.1, 2.2, 2.3, 2.6, 3.3_
- [ ] 3.5 2 つの口の受け口をつなぐ
  - 試験用の偽の GROWI を、2 つの口を署名つきで呼べるように広げる
  - 署名の検査を通った答えと会話の求めを、それぞれの流れに渡す受け口を足す。会話の求めは依頼の記録から場所とスレッドを引いて読み、0 件なら「発言が無い」を返す
  - 完了の条件: 偽の GROWI から署名つきで呼ぶ結合試験で、両方の口が結果を返し、DM のスレッドの外での要約の依頼がその DM の直近を読む
  - _Requirements: 5.7, 5.14, 15.7, 15.19_
  - _Depends: 2.5, 3.4_
- [ ] 3.6 Slack の AI アプリの画面の文章を `agent` に振り分ける
  - AI アプリの画面では、答えとして解釈できる聞き返しへの答えを先に扱い、それ以外は先頭の語にかかわらず `agent` の依頼にする。答えにならない文章が来たら聞き返しを捨てる。ふつうの DM の振り分けは変えない
  - 完了の条件: 「search for …」が AI アプリの画面では `agent` に、ふつうの DM では `search` になり、GROWI の選択が残っていても別の文章で新しい依頼が始まる試験が通る
  - _Requirements: 15.15_
  - _Depends: 2.2, 2.4, 3.2_
- [ ] 3.7 proxy の配線と導入ドキュメント
  - 新しい流れ・受け口・repository・設定を起動時の配線に加える
  - Slack の導入ドキュメントに、AI アプリの画面に要る設定・権限・イベントと、有効にしたときの DM の変化を書く。Teams の導入ドキュメントには、1 対 1 の会話に要る導入の範囲の節を用意する（中身は 6.3 の実機の確認で確定する）
  - 完了の条件: 起動の配線の試験が通り、Slack の導入ドキュメントに上の内容があり、Teams の節がある
  - _Requirements: 1.21_

- [ ] 4. app: 書き留めと送り手を 1 つにする
- [ ] 4.1 通知の書き留めを、種類つきの書き留めに広げる
  - 通知の送り手を書き留めの共通の場所へ移し、取る・送り直す・諦めるの仕組みを、種類ごとの「1 件の送り方」の表を受け取る形にする。通知 1 件の送り方は今の動きのまま移す
  - 書き留めに種類と答えの欄を足し、通知の欄の必須を通知の行に限り、答えの行に限った「連携と依頼の番号」の一意の索引を張る。既存の行に種類を補う migration を足す
  - 移した定期処理を、起動時の配線（`server/crowi/index.ts`）から起動する
  - 完了の条件: 既存の通知の試験が、移した場所で変更なしに通り、migration の後の既存の行が通知として送られ、移した後も定期処理が起動する
  - _Requirements: 15.11_
- [ ] 4.2 書き留めた直後に送り始め、定期処理を 5 分にする
  - 書き留めたら、プロセスの中で同時に 1 つだけ走る送り手を起こす（走っている間に呼ばれたら、終わった後に 1 回だけ走り直す）。失敗は書き留めの呼び出し元へ伝えない
  - 取った時刻を 1 件ごとの現在時刻にし、取り直しの時間を 4 分に、定期処理を 5 分に 1 回にする。要件 2.9 の試験の時間の上限を合わせる
  - 完了の条件: 書き留めた通知が定期処理を待たずに送られ、続けて書き留めても送り手が重ならず、止まった送信が 10 分以内に取り直される試験が通る
  - _Requirements: 2.10, 2.11_
- [ ] 4.3 (P) proxy への 2 つの呼び出しと、口ごとの打ち切り時間
  - 答えを送る呼び出しと、会話を求める呼び出しを足す。署名つきの呼び出しに、口ごとの打ち切り時間（通知は 15 秒、ほかは 10 秒）を付ける
  - 完了の条件: 応答しない proxy に対して呼び出しが打ち切り時間で失敗として返る試験と、2 つの呼び出しの往復の試験が通る
  - _Requirements: 5.7, 15.6_
  - _Boundary: ProxyClient_
- [ ] 4.4 答え 1 件の送り方
  - 答えの行を送り、届けた・届けられなかった・知らない依頼なら終わり、配達中・HTTP の失敗・打ち切りなら送り直しにする。送れた行からは答えの本文を消し、諦めた答えの行は 7 日で消える
  - 完了の条件: 結果ごとの判定と、送れた行の本文が消えること、5 回目の失敗で諦めて理由が残ることの試験が通る
  - _Requirements: 15.6, 15.11_
  - _Depends: 4.1, 4.3_

- [ ] 5. app: `agent` の処理
- [ ] 5.1 GROWI の AI の結果の形を、実際のライブラリで確かめる
  - 道具が開いたページを `generate` の結果から取り出す方法と、打ち切られた `generate` が例外にならずに返ることを、インストール済みの Mastra で確かめる
  - 完了の条件: 2 つの振る舞いを固定する小さな試験があり、確かめた結果が research.md に書いてある。結果が設計と違えば、5.4 に進む前に設計を直す
  - _Requirements: 15.2, 15.10_
- [ ] 5.2 実行中の依頼の記録と、DM の許可の保存先
  - 依頼の行（連携と番号で一意、利用者ごとに実行中は 1 つ、24 時間で消える）と、その索引を作る migration を足す
  - 権限の保存に「DM で許す」の欄を足し、保存時の検査と、読み出し・proxy への送信に載せる
  - 完了の条件: 同じ利用者の 2 件目の実行中の行と、同じ番号の 2 行目が索引で拒まれ、「DM で許す」が保存と読み出しで往復する試験が通る
  - _Requirements: 11.7, 15.12_
- [ ] 5.3 `agent` を受け付け、app の `keep` とヘルプを直す
  - 権限の判定・紐付け・AI が使えるか・実行中の行の挿入の順に関門を調べ、通れば「受け付けた」を返して、応答の後で実行を始める。実行役は引数で受け取る形にし、本物の実行役は 5.6 でつなぐ（このタスクの試験では差し替えた実行役を使う）。同じ番号の再送は「受け付けた」を返して二重に実行しない
  - `keep` の処理と会話のページの組み立てを取り除く。app は protocol の `keep` の型を使わなくなる。ヘルプは、AI が使えないときに `agent` を含めない
  - 完了の条件: 紐付けなし・AI が使えない・同じ利用者の 2 件目・同じ番号の再送（実行は 1 回）・権限なしの試験が通り、AI が使えない GROWI で `search` と `create-page` の既存の試験が通る
  - _Requirements: 11.6, 14.6, 15.3, 15.4, 15.12, 15.20_
  - _Depends: 5.2_
- [ ] 5.4 GROWI の AI を呼ぶ入口を作る
  - 依頼の種類の判断（質問か要約か、パスの指定）・質問への答え（会話の記録つき、出典の一覧つき）・会話の要約（題名と本文）の 3 つを、紐付けた利用者として呼ぶ入口を作る。会話の id は、連携・利用者・会話の鍵から計算する
  - AI の部品は、この入口の中だけで、実行時に読み込む。読み込み役と型は別のファイルに置く
  - 完了の条件: 会話の id の計算の試験（同じ入力は同じ id、どれかが違えば別の id）と、起動時に AI の部品を読み込まないことの試験が通り、偽の AI を使った試験で 3 つの入口がそれぞれの形の結果を返す
  - _Requirements: 15.2, 15.14, 15.18_
- [ ] 5.5 要約のページを作る
