# Requirements Document

## Project Description (Input)

### 誰が困っているか

GROWI.cloud のように、多くの GROWI（テナント）が 1 つのデータベースを共有する環境の運用者。チャット連携を使っていないテナントも含め、すべてのテナントが通知の定期処理のための問い合わせを毎分データベースへ送っており、その負荷がテナント数に比例して共有のデータベースにかかり続けている。

### 今どうなっているか

- 通知の定期処理は、チャット連携を使っているかに関係なく、すべての GROWI のプロセスで起動時に始まり、1 分ごとに 2 回データベースへ問い合わせる（送信待ちの通知を取る問い合わせと、保持期間を過ぎた解除済みの連携を探す問い合わせ）。
- 解除済みの連携は 45 日残してから消すが、その掃除も通知と同じく毎分走っている。

### 何を変えるか

1. チャット連携が 1 つも無い GROWI では、通知の定期処理の問い合わせを飛ばす。「連携があるか」の答えは一定時間覚えておき、その確認自体も毎回は行わない。
2. 解除済みの連携の掃除を通知の定期処理から切り離し、1 日 1 回にする。

詳しい背景と、この spec が変える既存の spec は `brief.md` の「Amend target」にある。

## Introduction

この spec は、完了済みの `chat-integration`（umbrella）の要件 2・9 に受け入れ条件を足す amend spec である。番号は umbrella の `requirements.md` の続き番号で、既存の番号は振り直さない。要件 2 には 2.7〜2.9 を、要件 9 には 9.8 を足す。2.10・2.11 は空けてある（`research.md`「取り下げた ID」）。

通知の定期処理の間隔は 1 分のまま変えない。間隔を延ばす変更は、通知を書き留めた直後に送る経路と一緒に `chat-integration-agent` で作る（`research.md` の「先に間隔を延ばす」の Decision）。

ここに書く時間の上限は、すべて「テストで時刻を指定して確かめられる」形にしている。

## Boundary Context

- **In scope**: 連携が無いときの問い合わせの省略と、その答えを覚えておく時間。新しく書き留めた通知を、覚えた答えのせいで待たせないこと。解除済みの連携の掃除の頻度。
- **Out of scope**:
  - 通知を書き留めた直後に送ること（`chat-integration-agent` の「答えをあとから送る口」と同じ経路で作る。umbrella の roadmap 順 7）。この spec の受け入れ条件は、定期処理が唯一の送り手であることを前提にしない。
  - 通知の定期処理の間隔の変更（1 分のまま）。`chat-integration-agent` で、書き留めた直後に送る経路と一緒に扱う。
  - 送り直しの回数と間隔、止まった送信とみなすまでの時間（5 分）の変更。
  - proxy とチャットサービス側の振る舞い、通信の契約。
- **Adjacent expectations**:
  - 要件 2.4（投稿できなかったことを記録する）と 2.5（通知が失敗してもページ操作は完了させる）は、この変更の後もそのまま満たす。
  - 複数のプロセスが同時に動いても、同じ通知を 2 回送らない（`chat-integration-app` の設計）。この性質は変えない。

## Requirements

### Requirement 2: GROWI からチャットへの通知（追加分）

**Objective:** As a 多くの GROWI が 1 つのデータベースを共有する環境の運用者, I want チャット連携を使っていない GROWI が通知のための問い合わせを出さないこと, so that テナントが増えても、使われていない機能のために共有のデータベースへ負荷がかかり続けない

#### Acceptance Criteria

7. While GROWI にチャット連携が 1 つも無い（解除済みで保持期間中のものも無い）, the GROWI application shall 通知の定期処理で、送信待ちの通知と掃除の対象を探す問い合わせを行わず、連携の有無を確かめる問い合わせを 1 プロセスあたり 10 分に 1 回以下に抑える
8. When ある GROWI のプロセスが通知を書き留めた, the GROWI application shall そのプロセスで次に動く通知の定期処理で、連携が無いと覚えている答えが残っていても、送信待ちの通知を探して送る処理を飛ばさない
9. If 通知を書き留めたプロセスが、その通知を送る前に止まった, then the GROWI application shall ほかのプロセスで、連携の有無について覚えている答えの期限（10 分）が切れた後に最初に動く通知の定期処理で、送信待ちの通知を探して送る（定期処理は 1 分に 1 回なので、書き留めてからおよそ 11 分以内）

### Requirement 9: chat-integration proxy と GROWI の紐付け（追加分）

**Objective:** As a 多くの GROWI が 1 つのデータベースを共有する環境の運用者, I want 解除済みの連携の掃除が、その期限に見合った頻度でだけ走ること, so that 45 日の保持期間を守るために毎分の問い合わせを払わずに済む

#### Acceptance Criteria

8. When 紐付けを解除してから保持期間（45 日）が過ぎた, the GROWI application shall その連携と、それに属するチャット利用者の紐付けを、保持期間が過ぎてから 1 日と 1 時間以内に消し、この掃除のための問い合わせは通知の定期処理とは別に 1 日 1 回だけ行う
