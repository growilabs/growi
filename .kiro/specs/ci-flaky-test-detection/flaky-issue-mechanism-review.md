# flaky test 対応の仕組みが機能していない理由

調査日: 2026-09-14
対象: growilabs/growi の #11720（flaky-ci-routine ダッシュボード）と、そこに並ぶ flaky test 追跡 issue 群

## 前提として分かったこと

flaky test を見つける仕組み（detect-flaky-ci）と、原因を調べる仕組み（investigate-flaky-test）は、どちらもきちんと動いていました。ほぼ全ての issue に、実際に原因調査のコメントが最低1回はついています。「調査する力が足りない」ことが問題ではありません。

問題は、調査が終わった後にあります。

## 問題1: 同じ原因から出た失敗が、テストの数だけ別々の issue として数えられる

この仕組みは、失敗したテストの名前ごとに1件の issue を作ります。そのため、1つの原因が複数のテストを巻き込むと、原因は1つなのに issue は複数できます。

今回確認できた実例:

- `AdminCodeEditor.spec.tsx` の4つのテストが、それぞれ別の issue（#11849, #11890, #11891, #11892）になっていましたが、失敗ログを見ると原因は1つで、`@codemirror/state` というライブラリが二重に読み込まれてしまう不具合でした。
- `growi-plugin.integ.ts` の3つのテストも、それぞれ別 issue（#11708, #11709, #11710）でしたが、原因は1つの外部ダウンロード失敗でした。しかも issue 本文自体に「#11708 の道連れで落ちている」と書いてあり、原因が1つであることは調査した時点で分かっていました。

見かけ上「31件の未解決 issue」がありましたが、9件は今回の調査で重複と確認できてクローズしました。原因の数で数え直すと、残りはもっと少なくなります。

**なぜ問題か**: 見た目の件数が実際の原因の数より何倍にも膨らむため、「issue が減らない」「増え続けている」という印象を実態以上に強めてしまいます。

## 問題2: 調査が「人の判断待ち」で止まった後、誰も判断しに来ない

#11752（`migrate-mongo` の初期化がタイムアウトする不具合）を例に、実際に何が起きていたかを時系列で示します。

1. 8/28: 修正 PR が一度マージされ、issue はクローズされました。
2. 9/1: 別の巡回で「まだ直っていない」ことが見つかり、issue が再び開きました。
3. **9/3: 調査が実際に走り、原因もかなり具体的なところまで特定しました。ただし直す範囲が広いテスト基盤全体に及ぶため、「これは人に判断してほしい」と、仕組み自体の設計どおりに正しく立ち止まりました。**
4. **9/3 から 9/14（今回の調査時点）までの11日間、この issue には何のコメントもつきませんでした。**「また同じ失敗が起きました」という自動の記録だけは、その間も律儀に追加され続けていました。

この設計自体（難しい判断は人に投げて、自動では踏み込まない）は正しい判断です。問題は、**人に投げた後、その判断を実際に誰かが拾いに来る仕組みが存在しない**ことです。

## 問題3: 「変化がなければ何もしない」ループが、気づかれないまま回り続ける

flaky test の修正 PR の一つ（#11863。最終的に「タイムアウトを伸ばすだけ」という理由で却下されました）には、1時間おきに状況を確認する自動処理がついていました。実際の記録を見ると、2026-09-06 14:52 から 09-07 10:37 まで、少なくとも20回、休みなく1時間おきに動いていたことが分かりました。

この処理の中身は、次のような指示でした（実際の文面の要約です）。

> 前回確認したときから何も変わっていなければ、誰にも知らせず、どこにもコメントを残さず、ただもう1時間後の自分を作り直して終える。

対象の PR は却下されて終わるまで、この「何も変わっていない」確認と「黙って自分を作り直す」動きだけを繰り返していました。この PR に人が実際に手を動かして関わらない限り、このループが自分から誰かに声をかけることは、設計上ありません。

**なぜ問題か**: このループの存在自体、外から見えません。今回たまたま実行履歴の一覧を直接確認したことで見つかりましたが、そうしなければ「動いているのかどうかさえ分からない」状態でした。

## 3つの問題に共通する本質

この仕組みは、「何か変化が起きたら反応する」ようにできています。ところが、判断待ちで止まっている issue にとって、その「変化」を起こせるのは人間だけです。そして、人間に「判断待ちの issue がある」と知らせる手段が、この仕組みのどこにもありません。

つまり、**判断待ちで止まっていること自体が、どこにも見える形で残らない**のが根本の欠陥です。ダッシュボード（#11720）は「今どんな issue があるか」は一覧できますが、「どれが調査済みで人の判断待ちなのか」「どれがまだ一度も調べられていないのか」を区別できていません。

## isolate: false 案の検証結果（参考）

#11752 / #11821 の根本原因に対して、9/3 のコメントが候補に挙げていた「`isolate: false` の導入」を、今回実際に CI 上で検証しました。

- 1回目の設定の書き方では、Vitest の既知の制限（`poolOptions` と同じ理由）により実際には有効化されておらず、検証として成立していませんでした。
- CLI フラグで正しく有効化したところ、`crowi` インスタンスなどの共有状態がテストファイルをまたいで持ち越されてしまい、広い範囲のテストが壊れることを確認しました。

**結論: この案は NO-GO です。** 導入するには、共有状態を明示的に元へ戻す仕組みを別途実装する必要があり、それ自体がまとまった作業になります。検証結果は #11752 に記録済みです。

## 対策として考えられること（提案）

1. **重複をまとめる仕組みを、人手ではなく機械的に行えるようにする。** 同じ実行・同じコミットから複数のテストが同時に落ちた場合は、最初から1つの issue にまとめる（あるいは既存の issue に「まとめ済み」の印をつける）。
2. **「調査は終わったが人の判断待ちのまま止まっている」issue を、別枠で一覧できるようにする。** 現状のラベル（`0️⃣ phase/new` → `1️⃣ phase/under-investigation`）だけでは、「まだ手つかず」と「調べたが止まっている」を区別できません。
3. **「変化がなければ黙って再武装する」ループに、上限か、定期的な人への報告を必ず入れる。** 今のままだと、却下されて終わるまで気づかれずに回り続けるループが今後も作られる可能性があります。
