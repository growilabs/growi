# Requirements Document

## Project Description (Input)
GROWI 管理者が、コンテナシェルを使わずに、管理画面のセキュリティ設定からパスワードハッシュ移行を完了できるようにする。

**背景:** `password-hash-upgrade` spec（実装済み）により、パスワードの保存方式は SHA-256 から scrypt へ置き換えられた。移行は遅延的に行われる — ユーザーの scrypt ハッシュは、そのユーザーが次にローカルパスワードを検証してログインしたときに初めて書き込まれ、それまでは旧形式の `password` フィールドが並存し続ける。この移行の最終段階、すなわち残存する旧形式ハッシュの削除（「クリーンアップ」）は、アプリケーションコンテナ内で実行する CLI スクリプトとしてしか存在しない。GROWI.cloud のようなマネージドホスティングでは、テナント管理者はシェルを持たないため、この最終段階に到達する手段がなく、旧形式ハッシュがデータベースに残り続ける。本機能は、その実行手段を設定画面から提供する。

**スコープ:**
- 全ユーザーにわたるパスワード保存状態を管理者に提示する。新形式のみを持つユーザー数、両形式を持つユーザー数、旧形式のみを持つユーザー数（「未移行」）、ローカルパスワードを持たないユーザー数。
- 取り消し不能であることへの明示的な同意を経たうえで、画面からクリーンアップ（移行済みユーザーに残存する旧形式ハッシュの削除）を実行できるようにし、監査アクティビティとして記録する。
- 他のユーザーが未移行のままでも、移行済みの全ユーザーに対してクリーンアップを実行する。現在の CLI は、アクティブな未移行ユーザーが 1 人でも存在すると処理全体を中断するが、この条件は実運用では解消しない。LDAP / OAuth / SAML でサインインするユーザーや、長命なセッションを保持するユーザーは、ローカルパスワードを検証しないため永久に移行しない。この中断条件は、本機能が救おうとしているまさにそのホスティング管理者に対して機能を到達不能にしており、しかも何も守っていない — クリーンアップは未移行ユーザーの資格情報に一切触れないからである。
- 未移行者を、単なる人数ではなく行動可能な形で、ページング付きの一覧として提示する。各行には最終ログインと外部アカウントの有無が必要である。最近ログインしているのに未移行であるユーザーは、消去法によりローカルパスワードでサインインしていないことになり、「ログインしてください」と促しても永久に解消しないからである。
- 旧形式ハッシュがどこにも残っていない状態になったら、成功を報告し続ける常設パネルを残すのではなく、画面からセクションごと消す。

**制約:**
- UI にハッシュアルゴリズム名や CLI スクリプト名を出さないこと。マネージドホスティングの管理者はスクリプトを実行できず、また旧アルゴリズムは宣伝すべき情報ではない。
- クリーンアップのロジックは既存の CLI スクリプトと新 API で共有し、両経路が食い違わないようにすること。

## Introduction

`password-hash-upgrade` は、ローカル認証のパスワード保存方式を、ソルトなしのレガシーダイジェスト（SHA-256 + `PASSWORD_SEED`）から、メモリハードな適応的 KDF（scrypt）へ移行した。移行は**遅延的**である。ユーザーの新形式資格情報は、そのユーザーが次にローカルパスワードをログイン時に検証されたときに初めて書き込まれ、旧形式の資格情報は管理者が削除するまで意図的にそのまま並存させられる。この削除こそが移行の最終段階であり、今日それはアプリケーションコンテナ内で実行する CLI 手順としてしか存在しない。

マネージドホスティング（GROWI.cloud 等）の管理者はコンテナシェルを持たない。したがって彼らにとってこの最終段階は存在しない。そのインスタンスには旧形式の資格情報が残り続ける — アップグレードが解消しようとしたまさにその露出が残る。本機能は、この最終段階を管理画面のセキュリティ設定に置き、すべての管理者が到達できるようにする。

保存される 2 つのフィールドの有無から 4 つの資格情報状態が定まる。本書を通じてこの用語を使う。

| 用語 | 意味 |
|---|---|
| **新形式のみ** | 新形式の資格情報のみを持つ。移行完了済みで、削除すべきものはない。 |
| **両形式** | 新形式と旧形式の両方の資格情報を持つ。移行は済んでいるが旧形式がまだ保存されている — クリーンアップが削除するのはこれである。 |
| **未移行** | 旧形式の資格情報のみを持つ。アップグレード以降、ローカルパスワードを検証されていない。 |
| **ローカルパスワードなし** | どちらも持たない。外部認証のみのアカウントや未有効化アカウントでは正常な状態。 |

本機能は、`password-hash-upgrade` から継承した規則をひとつ改訂する。同 spec の Requirement 3.4 は、アクティブな未移行ユーザーが存在する場合にクリーンアップ全体を中断する。しかしこの条件は実運用では解消しない。LDAP・OAuth・SAML でサインインするユーザー、あるいは単に長命なセッションを保持しているだけのユーザーは、ローカルパスワードを検証されることがないため移行しないまま、なお ACTIVE として数えられる。したがってこの中断条件は、本機能が救おうとしているまさにそのインスタンスでクリーンアップを恒久的に封じており、しかも何も守っていない。クリーンアップはそもそも未移行ユーザーの資格情報に触れないからである。下記の Requirement 3 がこれを置き換える。

## Boundary Context

- **In scope**: 管理画面セキュリティ設定での資格情報状態の分布の提示。取り消し不能であることへの同意を経たクリーンアップの実行と、その監査記録。未移行ユーザーの一覧と、管理者が行動するために必要な手がかりの提示。移行が何も残さなくなった時点でのパネルの消去。そしてクリーンアップの中断規則の改訂（削除できるものは削除する）。
- **Out of scope**: パスワードのハッシュ方式と遅延移行の発火条件（`password-hash-upgrade` が所有）。画面から特定ユーザーの移行を発火・強制すること。画面からパスワードリセットメールを送信すること。ダウングレード準備および再アップグレード準備の手順（CLI のまま）。外部認証プロバイダ。そして永久に移行しないユーザーを削除・凍結するなどして解消すること。
- **Adjacent expectations**:
  - `password-hash-upgrade` がハッシュ化と遅延移行を所有する。本機能は、同一ユーザーについて同 feature が既に置き換え済みの旧形式資格情報のみを削除する。
  - 本機能は **`password-hash-upgrade` Requirement 3.4 を改訂する**。ACTIVE な未移行ユーザーに対する中断は下記 Requirement 3 で置き換えられ、この改訂は管理画面経路だけでなく CLI 経路にも適用される。両者が食い違うことはない。
  - 未移行ユーザーが本機能によって解消されることはない。完全に移行済みのインスタンスに到達するには、本機能の外側で管理者が行動する必要がありうる — 当人にローカルパスワードでサインインしてもらう、パスワードをリセットしてもらう、あるいはアカウントを削除する。本機能はそうしたユーザーを可視化し、なぜ詰まっているかを説明するところまでを担い、解消はしない。
  - 旧形式の資格情報が 1 件でも存在する限り `PASSWORD_SEED` は設定されたままでなければならない（`password-hash-upgrade` に基づく）。
  - 監査記録はインスタンス既存のアクティビティログの挙動に従う。本機能は記録を 1 件追加するだけであり、仕組みを定義しない。

## Requirements

### Requirement 1: 資格情報の保存状態の可視化

**Objective:** GROWI 管理者（コンテナシェルを持たないマネージドホスティング上の管理者を含む）として、インスタンス全体でパスワード資格情報がどう保存されているかを見たい。そうすることで、移行が完了しているのか、何が残っているのかを判断できる。

#### Acceptance Criteria

1. When 管理者がセキュリティ設定画面を開く, the パスワードハッシュ移行パネル shall 各資格情報状態（新形式のみ・両形式・未移行・ローカルパスワードなし）のユーザー数を表示する。
2. The パスワードハッシュ移行パネル shall 未移行の人数のうち何人が ACTIVE で何人がそうでないかを報告する。管理者は ACTIVE なユーザーにはサインインを依頼できるが、凍結済み・招待中・未有効化のユーザーには強制できないためである。
3. If 資格情報状態の集計を取得できない, then the パスワードハッシュ移行パネル shall その失敗を提示する。移行完了済みインスタンスと区別がつかないゼロ件表示を出してはならない。
4. When クリーンアップが完了する, the パスワードハッシュ移行パネル shall 管理者が画面を再読み込みすることなく更新後の集計を提示する。
5. If 管理者権限を持たない利用者から資格情報状態の集計が要求される, then the パスワードハッシュクリーンアップ機能 shall その要求を拒否し、いかなる集計も開示しない。

### Requirement 2: 管理画面からのクリーンアップ実行

**Objective:** コンテナシェルを持たない GROWI 管理者として、残存する旧形式の資格情報を設定画面から削除したい。そうすることで、他に完了手段のない移行を完了できる。

#### Acceptance Criteria

1. When 管理者がクリーンアップを確定する, the パスワードハッシュクリーンアップ機能 shall 両形式を持つ全ユーザーから旧形式の資格情報を削除し、それ以外のユーザーの保存済み資格情報は一切変更しない。
2. The パスワードハッシュ移行パネル shall 削除が取り消せないことを管理者が明示的に承諾するまで、クリーンアップを開始させない。
3. When 管理者がクリーンアップを開始する, the パスワードハッシュ移行パネル shall 承諾を受け付ける前に、旧形式の資格情報を削除されたユーザーは移行前のビルド上では既存のパスワードでサインインできなくなり、そこで新しいパスワードを設定し直す必要があることを提示する。
4. When クリーンアップが終了する, the パスワードハッシュクリーンアップ機能 shall 旧形式の資格情報を削除されたユーザーが何人かを報告する。
5. If クリーンアップが完了しない, then the パスワードハッシュクリーンアップ機能 shall その失敗を管理者に報告し、パネルは実際に保存されている内容を反映し続ける。
6. When クリーンアップが実行される, the パスワードハッシュクリーンアップ機能 shall それを監査アクティビティログに、実行した管理者に帰属させて記録する。
7. If 管理者権限を持たない利用者からクリーンアップが要求される, then the パスワードハッシュクリーンアップ機能 shall その要求を拒否し、保存済み資格情報を一切変更しない。
8. While 両形式のユーザーが 1 人もいない, the パスワードハッシュ移行パネル shall クリーンアップ操作を提供しない。削除すべきものが存在しないためである。
9. When 削除可能なものが既にすべて削除済みのデータに対してクリーンアップが実行される, the パスワードハッシュクリーンアップ機能 shall 失敗を報告するのではなく、正常に完了し対象 0 件であったことを報告する。

### Requirement 3: 未移行ユーザーが残っていてもクリーンアップは実行される

**Objective:** 一部のユーザーが外部プロバイダ経由でしかサインインしないインスタンスの GROWI 管理者として、安全に削除できるものはすべて削除してほしい。そうすることで、永久に移行しないユーザーによって移行が無期限に止められずに済む。

> `password-hash-upgrade` Requirement 3.4 を改訂する。

#### Acceptance Criteria

1. While 1 人以上のユーザーが未移行である, when 管理者がクリーンアップを確定する, the パスワードハッシュクリーンアップ機能 shall それでもなお両形式を持つ全ユーザーから旧形式の資格情報を削除する。
2. The パスワードハッシュクリーンアップ機能 shall 未移行ユーザーからは決して資格情報を削除しない。いかなるユーザーも使用可能な資格情報を失わないためである。
3. When クリーンアップが CLI から実行される, the パスワードハッシュクリーンアップ機能 shall 受入基準 1 および 2 を同一に適用する。これにより CLI 手順は、ACTIVE な未移行ユーザーが存在することを理由に実行を拒否しなくなる。
4. While 1 人以上のユーザーが未移行である, the パスワードハッシュ移行パネル shall それらのユーザーがクリーンアップの影響を受けないこと、およびその資格情報が旧形式のまま残ることを提示する。
5. The パスワードハッシュ移行パネル shall 外部プロバイダ経由でのみ認証するユーザーや長命なセッションを保持するユーザーは、GROWI を使い続けるだけでは移行しないことを説明する。そうすることで、管理者が未移行の人数がゼロになるのを無期限に待ち続けずに済む。

### Requirement 4: 未移行者の特定

**Objective:** GROWI 管理者として、誰が未移行なのか、そしてその理由を示す手がかりを見たい。そうすることで、人数を知らされるだけでなく実際に行動できる。

#### Acceptance Criteria

1. When 管理者が未移行ユーザーの表示を要求する, the パスワードハッシュクリーンアップ機能 shall 未移行ユーザーを 1 ページずつ、未移行ユーザーの総数とともに提示する。そうすることで管理者が集合全体を辿れる。
2. The パスワードハッシュクリーンアップ機能 shall 一覧の各ユーザーについて、ユーザー名・メールアドレス・最終サインイン日時・外部認証アカウントの有無を提示する。
3. The パスワードハッシュクリーンアップ機能 shall 一覧を最終サインインの新しい順に並べ、一度もサインインしていないユーザーを末尾に置く。未移行のまま最近サインインしているという事実こそが、そのユーザーがローカルパスワードで認証しておらず、サインインを促しても永久に解消しないことを示す手がかりだからである。
4. The パスワードハッシュ移行パネル shall 一覧中の ACTIVE でないユーザーに印を付ける。管理者は凍結済みや未有効化のアカウントにサインインを促せないためである。
5. The パスワードハッシュクリーンアップ機能 shall 管理者が表示を要求するまで一覧を取得しない。そうすることで、未移行ユーザーが多いインスタンスでもセキュリティ設定画面を開く費用が集計の表示以上にならない。
6. If 一覧を取得できない, then the パスワードハッシュ移行パネル shall その失敗を提示する。「未移行者はいない」と区別がつかない空の一覧を出してはならない。
7. If 対応可能な上限を超えるページサイズが要求される, then the パスワードハッシュクリーンアップ機能 shall その上限を超える件数を返さない。単一の要求を際限なく大きくできないようにするためである。
8. If 管理者権限を持たない利用者から一覧が要求される, then the パスワードハッシュクリーンアップ機能 shall その要求を拒否し、いかなるユーザー情報も開示しない。

### Requirement 5: 提示すべきものがある間だけパネルを出す

**Objective:** 移行が完了したインスタンスの GROWI 管理者として、一度きりの作業を報告する常設パネルは要らない。そうすることで、設定画面には対応が必要なものだけが並ぶ。

#### Acceptance Criteria

1. While いかなる状態でも旧形式の資格情報を持つユーザーが存在しない, the パスワードハッシュ移行パネル shall セキュリティ設定画面に現れない。
2. While 資格情報状態の集計がまだ取得されていない, the パスワードハッシュ移行パネル shall 現れない。そうすることで、既に移行が完了しているインスタンスで、消える直前のパネルが一瞬表示されることがない。
3. While 1 人以上のユーザーが旧形式の資格情報を持つ, the パスワードハッシュ移行パネル shall 現れる（両形式のユーザーが 1 人もおらずクリーンアップに削除すべきものがない場合を含む）。かつその場合には、旧形式の資格情報は残っているがまだ削除できるものがないことを提示する。

### Requirement 6: 画面が管理者に伝えてよい内容

**Objective:** マネージドホスティング上の GROWI 管理者として、自分が実際に取れる行動だけを画面に説明してほしい。そうすることで、自分には使えない手順へ誘導されず、また置き換えられた保存方式の詳細が宣伝されずに済む。

#### Acceptance Criteria

1. The パスワードハッシュ移行パネル shall 旧形式・新形式いずれについても、資格情報に用いる暗号アルゴリズム名を出さない。
2. The パスワードハッシュ移行パネル shall いかなる CLI 手順へも管理者を誘導しない。マネージドホスティング上の管理者にはそれを実行する手段がないためである。
3. The パスワードハッシュ移行パネル shall この変更を、置き換えられる保存方式の観点ではなく、管理者とそのユーザーが観測する内容の観点で、パスワード保存の強化として説明する。
4. The パスワードハッシュ移行パネル shall GROWI 管理画面が対応する全言語で、自身のすべての文言を提示する。

### Requirement 7: 2 つの経路が一致する

**Objective:** GROWI メンテナとして、管理画面のクリーンアップと既存の CLI のクリーンアップが削除対象について一致していてほしい。そうすることで、運用者がどちらの経路を選んだかによってインスタンスが異なる状態に残されることがない。

#### Acceptance Criteria

1. When クリーンアップが管理画面から実行される, the パスワードハッシュクリーンアップ機能 shall 同一の保存データに対して CLI のクリーンアップが削除するのとまったく同じ集合の資格情報を削除する。
2. When クリーンアップがいずれかの経路から実行される, the パスワードハッシュクリーンアップ機能 shall 影響を受けたユーザー数を同一の計数規則で報告する。そうすることで両経路の報告が比較可能になる。
