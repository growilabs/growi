# Research & Design Decisions — plantuml

## 問題の原因（調査で確定）

問い合わせ: GROWI v3.3.8 から v7 系へ移行した後、一部の PlantUML 図だけが空表示になる（構文エラーは出ない）。同じページの他の図は描画される。ネームスペース名やクラス名を変えると描画される。Redmine #187170。

- 原因は文字数や文字種の制限ではない。図を PlantUML サーバーへ送る GET の URL が長すぎて拒否されている。
- 移行後に表に出た主な原因は、v7 系の GROWI が各図の先頭に約14,000字のテーマを付けるようになり、URL が約2倍に膨らんだこと。v3.3.8 はテーマを付けていなかった。
- 名前を変えると描画されるのは、単調な名前ほど deflate の圧縮が効いて URL が短くなるから（文字数が減るからではない）。

## 実測

### テーマの軽量化（2026-08、問い合わせの図・ライトテーマ）
`plantuml-encoder` で「テーマ＋図」を符号化して測った。

| 条件 | エンコード後 | URL 全体 | 8192 以内か |
|---|---|---|---|
| テーマ無し | 3,652 | 3,690 | 以内 |
| 現行テーマ | 8,280 | **8,318** | **超過**（失敗の実態） |
| ミニファイ後 | 6,844 | **6,882** | 以内 |

- テーマの生の長さは 14,581 → 11,331（22%減）。URL 全体は 17%減（1,436字）。
- deflate は空白やインデントを既に圧縮するので、効いているのはコメントの削除。空白を消すだけではほぼ縮まない。
- 8192 はリクエスト行とすべてのヘッダの合計。自前サーバーで Cookie が乗ると余裕が減る。公開 plantuml.com へは GROWI の Cookie は乗らない。
- ただし公開 plantuml.com で実際に GET が通る長さは 8192 より短い（下の「軽量化の効果と GET の上限」を参照）。Chrome 相当のヘッダでは確実に通るのは 7,022 まで（測る時刻によって 7,042 まで通った）で、6,882 との差は約140字しかない。2026-08 の表の「ミニファイ後」のテーマの生の長さ（11,331）は現在のライトのテーマと同じなので、6,882 は今のコードでの値である。
- **結論**: ミニファイだけで、問い合わせの図は GET のまま描画できる見込み。ただし問い合わせの図そのものでは、まだ 200 を確かめていない（下の「未実施: 問い合わせの図そのものでの確認」を参照）。

### 公開 plantuml.com の応答（2026-11-12）

| リクエスト | 応答 |
|---|---|
| `POST /plantuml/svg`（本文に図、`text/plain; charset=UTF-8`） | 302。本文は空で、見本の図「Bob -> Alice : hello」の URL へリダイレクトする |
| 末尾 `/` 付き、`plantuml.com`（www なし）への POST | 302 で同じ見本の図へ、または 301 で www 付きへ |
| 同じ図の GET | 200。送った図が描画される |
| 構文エラーの図の GET | 400、`image/svg+xml`、`Access-Control-Allow-Origin: *`（エラーを描いた SVG） |
| URL 約10,000字の GET | 400、`text/html`（Tomcat のエラーページ）、CORS ヘッダ無し |

- 公開 plantuml.com は POST の本文を無視する。サーバーは Cloudflare の後ろにあり、公式ドキュメントに POST の説明は無い。理由は分からないが、POST は使えないものとして扱う。
- URL が上限を超えたときは、画像でない応答が返る。そのため `<img>` は onError になる。

### 軽量化の効果と GET の上限（2026-11-12、合成図で実測）
問い合わせの図は手元に無いので、代わりに作った図（以下「合成図」）で測った。合成図は、乱数の種を固定してランダムな名前を並べたクラス図（3 ネームスペース × 6 クラス、各クラスにフィールド 3 つ・メソッド 2 つ、関連 17 本）。テーマ無しのエンコード後の長さが 3,540 で、問い合わせの図（3,652）に近い大きさにした。URL 全体の長さは、`plantuml-encoder` の `encode()` の結果に `https://www.plantuml.com/plantuml/svg/`（38字）を付けた長さ（`<img>` の `src.length` と同じ）。

**軽量化の前後（URL 全体の長さ）**

| 条件 | ライト | ダーク |
|---|---|---|
| テーマ無し | 3,578 | 3,578 |
| 軽量化前（commit `a5c9e8c25b` の親のテーマ） | 8,298 | 8,298 |
| 軽量化後（現在のテーマ） | 6,850 | 6,854 |

- 軽量化で URL 全体は 1,448字（17%）短くなった。問い合わせの図で 2026-08 に測った値（1,436字、17%）とほぼ同じ。

**公開 plantuml.com へ送った結果**

| 送った図 | 応答 |
|---|---|
| 合成図・軽量化後・ライト（6,850） | 200、`image/svg+xml`、`Access-Control-Allow-Origin: *`。図が描画された |
| 合成図・軽量化後・ダーク（6,854） | 200、`image/svg+xml`、`Access-Control-Allow-Origin: *`。図が描画された |
| 合成図・軽量化前・ライト（8,298） | 400、`text/html`、CORS ヘッダ無し（下の失敗時の応答と同じ） |

**GET が失敗し始める長さ**

合成図に、ランダムな名前のフィールドを持つクラスを1つ足して長さを変え、二分探索で調べた。どの図も構文は正しい。エンコード後の長さは常に4の倍数なので、4字刻みで調べた。

| リクエストのヘッダ | 成功した最大の長さ | 失敗した最小の長さ |
|---|---|---|
| 最小限（curl の既定。ヘッダは約50バイト） | 7,474 | 7,478 |
| 最小限＋300バイトの詰め物ヘッダ | 7,262 | 7,266 |
| Chrome が `<img>` で送るのと同じくらいの大きさ（約540バイト） | **7,022**（1回目は 7,042） | **7,026**（1回目は 7,046） |

- 境目は、測る時刻によって20字ほど動いた。Chrome 相当のヘッダでは、1回目の二分探索で 7,042 が成功・7,046 が失敗だったが、数分後に送り直すと 7,042 も 7,026 も失敗し、7,022 以下は成功した。最小限のヘッダの 7,474 は3回送って3回とも成功し、7,478 は2回とも失敗した。中継サーバーが足すヘッダの大きさが、リクエストごとに少し変わるためと見られる。
- 失敗したときの応答は、どの長さでも 400、`text/html;charset=utf-8`、CORS ヘッダ無し。本文は Tomcat のエラーページで、メッセージは「Request header is too large」（`Http11InputBuffer` の例外）。上限の正体は Tomcat の `maxHttpHeaderSize`（リクエスト行とヘッダの合計、既定 8192）で確定した。
- 8192 より 700字ほど手前で失敗するのは、途中にある Cloudflare と中継サーバー（応答に `x-ez-proxy-out` ヘッダが付く）が、ヘッダを足してから Tomcat へ渡すためと見られる。ブラウザが送るヘッダが大きいほど、通る URL は短くなる（300バイト足すと 212字、約490バイト足すと 432〜452字短くなった。ヘッダの増え方とぴったり比例はしない）。
- 「Chrome と同じくらい」のヘッダは、Chrome がクロスサイトの画像を読むときに送るヘッダ（`sec-ch-ua`、`accept`、`sec-fetch-*`、`accept-language` など）を真似て作った。User-Agent は Chrome と同じ長さの汎用の文字列に置き換え、Referer はオリジンだけ（`https://growi.example.com/`）にした。実際の大きさは、ブラウザの種類、言語設定、GROWI のドメイン名の長さで数十〜百数十バイト前後する。実ブラウザでは確かめていない。
- 公開 plantuml.com の応答は Cookie（`ezoictest`、SameSite の指定無し）を設定する。Chrome は SameSite の指定が無い Cookie を別サイトの `<img>` に付けないが、付けるブラウザでは上限がさらに 25字ほど下がる（未確認）。
- 1行に数千字のコメントを書いた図を送ると、長さに関係なく（6,850字でも）200・本文が空の `text/plain` が返った。原因は調べていない。画像ではないので `<img>` は onError になると見られる。この形の図は測定に使っていない。

**GET の URL 長の目安値: `PLANTUML_GET_URL_LIKELY_TOO_LONG = 6800`**（`src.length`、つまり URL 全体の長さで比べる。エンコード後の長さでいうと 6,762）

- Chrome 相当のヘッダで失敗し始めるのは 7,026〜7,046。目安値はそれより少し低くした。境目は時刻によっても20字ほど動き、ヘッダが大きい環境（言語設定が多い、ドメイン名が長い、Cookie が付くなど）では、さらに下がるからである。目安値を高くしすぎると、そうした環境で上限を超えた図に「描画できなかった」という一般的なメッセージが出て、問い合わせと同じ分かりにくさが残る。
- 目安値は、失敗した後にどのメッセージを出すかを選ぶためだけに使い、リクエストは止めない。そのため低めにしても、描ける図が描けなくなることはない。低めにして起きうるのは、6,800〜7,026 の図がサーバーの停止など別の理由で失敗したときに「URL 長の上限を超えた可能性が高い」と出ることだけである。上限ぎりぎりの大きさの図なので、分割・簡略化の案内も的外れにはならない。
- 自前の Tomcat（中継無し、既定 8192）では、通る長さは公開 plantuml.com より長い見込み（測っていない）。そこで 6,800 以上の図が失敗したときも、URL 長の上限が原因である可能性が高いので、この目安値のままでよい。

### 未実施: 問い合わせの図そのものでの確認
- 問い合わせの図は顧客の Wiki の内容で、手元に無い。そのため、問い合わせの図での軽量化前後の長さ（ライト・ダーク）と、軽量化後の図が公開 plantuml.com で 200 になることは確かめていない。上の数値はすべて合成図のもの。2026-08 の表は問い合わせの図のライトだけの値で、ダークの値と 200 の確認は無い。
- 図のコピーを持つ人が確かめる手順:
  1. 図のソースを、リポジトリの外のファイルに置く（リポジトリには入れない）。
  2. テーマ（軽量化前は commit `a5c9e8c25b` の親、軽量化後は現在の `carbon-gray-{light,dark}.puml.ts`）と図を改行1つでつなぎ（テーマが先）、`plantuml-encoder` の `encode()` に通し、先頭に `https://www.plantuml.com/plantuml/svg/` を付けた長さを、ライト・ダークそれぞれで測る。
  3. 軽量化後の URL を Chrome で開き、図が表示されるか確かめる。7,022 以下なら通る見込み、7,026 以上なら上限を超えることがある。
  4. research.md には、長さの数値と表示されたかどうかだけを書く。

### plantuml-server の POST の仕様（ソースと実機で確認、2026-08）
- `UmlDiagramService.doPost()` が本文の生のテキストを読み、リダイレクトせずに画像を返す（PR #74 で 2018-04 に追加）。設定は要らない。公式の Docker イメージ（`plantuml/plantuml-server:jetty`）でもそのまま POST が使える。POST 先は `/svg`。
- 本文は生のテキスト（deflate＋base64 は GET のときだけ）。
- `doPost` は文字コードを決めていない。`Content-Type: text/plain; charset=UTF-8` を付けないと ISO-8859-1 として読まれ、日本語が文字化けする。
- `DiagramResponse.sendDiagram()` の先頭で `Access-Control-Allow-Origin: *` を付ける。図も構文エラーの画像も、ブラウザから読める。
- 構文エラーは 400 と、エラーを描いた画像。
- 自前サーバーでの PoC: URL が 17,929字になる図で、GET は 414、同じ図の POST は 200（正しい SVG）。

## Decisions

### 送信方式は送信先で決める
- **決定**: 既定では、公開 plantuml.com（`*.plantuml.com` を含む）には GET、それ以外には POST で送る。`PLANTUML_HTTP_METHOD=get` を指定すれば常に GET にする。POST を強制する値は用意しない。
- **理由**: 本来はすべて POST にしたいが、公開 plantuml.com は POST を受け付けない。方式の選び方を管理者に任せる（既定 GET の opt-in）と、自前サーバーの環境でも、管理者が気付いて設定するまで大きい図が描けないままになる。
- **影響**: 自前サーバーの環境は、アップデートしただけで POST に切り替わる（下の「リスク」を参照）。

### GROWI サーバーで中継しない（ブラウザから直接 POST する）
- **決定**: POST も GET と同じく、閲覧者のブラウザから PlantUML サーバーへ直接送る。
- **理由**:
  - 中継すると、PlantUML サーバーへ送る主体が「ブラウザ」から「GROWI サーバー」に変わる。ブラウザからは届くが GROWI サーバーからは届かない送信先（例: `PLANTUML_URI=http://localhost:8080/...`）が壊れる。
  - 中継をやめると、そのために要る仕組みがまとめて要らなくなる。GROWI の新しい API、認証と共有リンクの扱い、SSRF 対策、本文サイズの検査、サーバー側キャッシュ（`lru-cache`）、エディタのプレビューでキャッシュが汚れる問題への対策がそれにあたる。
  - 直接 POST を退ける理由として挙がっていたものは、どれも当たらない。CORS は plantuml-server が許可ヘッダを付ける。サーバーをブラウザに見せる点は今の GET も同じ。サニタイズは `<img>` で表示すれば要らない。
- **失うもの**: サーバー側のキャッシュ。閲覧中のメモで同じ図の送り直しは防げる。

### リダイレクトは追わずに検出する
- **決定**: `fetch` に `redirect: 'manual'` を指定し、`res.type === 'opaqueredirect'` なら「POST が使えない」とする。
- **理由**: `'follow'` だと、POST 非対応のサーバーが返す見本の図を黙って表示してしまう。`'error'` だと、接続失敗や CORS 失敗と同じ例外になり区別できない。

### 構文エラーの SVG は図として表示する
- **決定**: `image/svg+xml` の応答は、ステータスが 400 でも図として表示する。
- **理由**: PlantUML は構文エラーを画像に描いて返す。書いた人が誤りに気付ける、PlantUML 本来の見せ方なので、エラー表示に置き換えない。

### SVG は blob URL でなく data URL で表示する
- **決定**: POST で受け取った SVG は、blob URL ではなく `data:image/svg+xml;base64,…` の data URL にして `<img>` の `src` に入れる。
- **理由**: blob URL は、それを作ったページ（GROWI）と同じ生成元になる。利用者が図を右クリックして「画像を新しいタブで開く」を選ぶと、SVG 内のスクリプトが GROWI の生成元・権限で動く。従来の GET では SVG は PlantUML サーバーの生成元から読まれるので、この差は POST にしたことで生まれる。data URL の文書は生成元がどのサイトにも属さないので、新しいタブで開かれても GROWI の権限は使えない。主なブラウザは、さらにトップレベルの遷移そのものを止める（止め方はブラウザによって違うので、これには頼らない）。
- **前提条件**: PlantUML サーバーが悪意ある SVG を返すこと（管理者が選んだサーバーの侵害、古い PlantUML の出力からの XSS など）と、利用者が新しいタブで開くことが要る。そのため重さは Important とした。
- **代償**: 閲覧中のメモに base64 の文字列を持つ（Blob より約 1.3 倍）。メモは最大 50 件なので許容する。ブラウザによっては「新しいタブで開く」が使えなくなる。blob URL の生成と解放の処理は要らなくなる。data URL の長さにはブラウザごとの上限があり、巨大な図で超えると `<img>` の onError になり、「描画できなかった」と表示される（表示が壊れることはない）。
- **出どころ**: 実装後の最終検証（kiro-validate-impl）の指摘。

### GET の失敗は onError で検知し、長さで止めない
- **決定**: GET の失敗は `<img>` の onError で検知する。URL 長の目安値は、失敗後のメッセージを選ぶためだけに使う。
- **理由**: URL の上限はサーバーごとに違う（Tomcat 既定 8192、上限を上げた自前サーバーなど）。長さでリクエストを止めると、描ける図まで消える。onError は実際の失敗だけを捕まえる。

### POST を勧める案内は出さない
- **決定**: GET で失敗したときに「自前サーバーと POST で解決できる」と案内する機能は作らない。
- **理由**: 送信先で方式を選ぶようにしたので、自前サーバーの環境は既定で POST になる。この案内が当てはまるのは「自前サーバーなのに GET を明示した」環境だけで、そうした管理者は事情を分かって選んでいる。

### ライト・ダークともにテーマを付ける（撤廃しない）
- **決定**: GET でも POST でも、すべての図にライト用・ダーク用のテーマを付ける。URL を縮めるためにテーマを外すことはしない。
- **理由**: テーマは、図の見た目を洗練させることと、ダークモードで図が白く浮かずに読めるようにすることが目的で、URL の長さの問題とは別に必要な機能である。
- **検討した案**: テーマを付けるのをやめる（撤廃する）案が検討された。テーマを無くすと問い合わせの図は公開 plantuml.com でも描画でき、テーマ無しの方が見やすいという意見もあった。しかし、ダークモードで白い図が浮くことと、URL 長の上限という根本の問題を避けるだけの対症療法であることから採らなかった。要求は「ダークモード対応は維持（CSS の軽量化は検討してよい）」「図の種類に応じて CSS を変えない」「GET の上限超過時に分かりやすいエラーを出す」と決まった。
- **出どころ**: Redmine #188245（spec 作成）の説明欄に転記された Slack のやり取り、および決定事項として最初に記録した commit `4bbdf399`（`.kiro/specs/plantuml-lighten-theme/requirements.md`、翌日の commit で統合されて削除）。

### テーマはミニファイで軽くし、定義は消さない
- **決定**: コメント行・行頭の空白・空行だけを消す。配色・skinparam・`<style>` の定義は消さない。
- **理由**: 非 UML 図種（board/gantt/json/mindmap/salt/wbs/wire/yaml）の配色は `<style>` でしか付けられない。消すとダークモードでその図種が読めなくなる（全体の既定文字色は無く、背景は透明）。しかも定義を消しても deflate が既に圧縮しているため、ほとんど縮まない。`sequenceDiagram` と `timingDiagram` は UML 図なので、どの場合も残す。
- 図の種類ごとにテーマを切り替えることはしない（図種が増えるたびに保守が要るため）。

### POST の失敗を GET でやり直さない
- **決定**: POST で描画できなかったときに、自動で GET で送り直すことはしない。
- **理由**: 失敗のたびにリクエストが2回になり、POST 非対応や CORS の設定漏れといった本当の原因が見えにくくなる。管理者が原因を知って `PLANTUML_HTTP_METHOD=get` を選べるよう、エラーメッセージで案内する。

### Changeset は作らない
`@growi/app` は `.changeset/config.json` の ignore 対象で、かつ private。changeset を足しても何も bump されず、changesets/action がリリース PR の作成で止まり、publish まで進まなくなる（commit `1d0a0d9f7a` 参照）。app のリリースノートは release-drafter が作る。

## リスク

### 自前サーバーの環境は、アップデートだけで POST に切り替わる
`<img>` の GET は、サーバー側に何も求めない。一方、ブラウザからの `fetch` の POST には、次の条件が要る。どれかが欠けると、今まで描けていた図が「POST に対応していないか、接続できない」のエラーになる。

- **CORS の許可ヘッダ**: plantuml-server は図の応答に付ける。ただし、手前の認証プロキシや nginx がエラーを返す場合や、plantuml-server 以外の互換サーバーでは付かないことがある。
- **POST 対応**: plantuml-server は 2018 年以降対応している。それ以外の互換サーバーは実装による。
- **混在コンテンツ**: GROWI が https で `PLANTUML_URI` が http の場合、ブラウザは http への `fetch` を止める。ただし `<img>` の http も、Chrome などの現行のブラウザは https へ自動で切り替え、https が無ければ失敗する。そのため GET でも既に描画できていない可能性が高く、差は小さい（実ブラウザでは未確認）。

対処:
- エラーメッセージで、管理者が `PLANTUML_HTTP_METHOD=get` を設定すれば元に戻せることを案内する。
- リリースノートで、自前サーバーの環境は POST に切り替わることと、戻し方を知らせる（spec の範囲外の作業）。
- POST が失敗したときに、自動で GET でやり直すことはしない（「Decisions」の「POST の失敗を GET でやり直さない」を参照）。
