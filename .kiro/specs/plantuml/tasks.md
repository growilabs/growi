# Implementation Plan

> タスク 1〜2（テーマの軽量化とエラー表示）は、それだけで問い合わせの図を GET のまま描けるようにする見込みのまとまりで、単独の PR として出せる。タスク 3（送信方式の選択と POST）はその後に続ける。

- [ ] 1. テーマの軽量化
- [x] 1.1 テーマをミニファイする
  - ライト・ダーク・共通の3つのテーマ資産から、行頭が `'`／`''` の PlantUML コメント行、行頭の空白、空行を取り除く。`'` が行頭にない行（文字列リテラル）は残す
  - 配色・skinparam・`<style>` の定義は1つも消さない（非 UML 図種の `<style>` も、`sequenceDiagram`・`timingDiagram` も残す）
  - 回避策の理由を書いたコメント（`ParticipantPadding`／`Padding` を skinparam で書かない理由 #11258・plantuml/plantuml#2622、`sequenceDiagram` の `Padding`／`Margin` の注記）は、消す前にファイル先頭の TSDoc へ移す
  - 完了条件: テーマ文字列からコメント行と空行が消え、配色定義が残り、理由のコメントが TSDoc にある
  - _Requirements: 5.3, 5.4, 5.5, 5.6_

- [ ] 1.2 軽量化の効果を実測し、GET の URL 長の目安値を決める
  - 実測用に `plantuml-encoder` を apps/app の devDependencies に追加する（今は他パッケージの間接依存にしか無く、直接 import できない）
  - 問い合わせで報告された図について、軽量化の前後でテーマ付きソースを GET 用 URL にしたときの長さを、ライト・ダーク両方で測る
  - ⚠️ 問い合わせの図は顧客の Wiki の内容なので、リポジトリには入れない。実測は手元のコピーで行い、research.md には長さの数値だけを残す
  - 公開 plantuml.com へ実際に送り、軽量化後の図が 200 で描画されることを確かめる。基準にする図は、200 が返る正しい図にする（構文エラーの図は長さに関係なく 400 になるので基準にならない）
  - 長さを変えた正しい図を送り、GET が失敗し始める URL 全体の長さを確かめ、GET の URL 長の目安値を決める
  - 完了条件: 前後の URL の長さ、200 の確認結果、決めた目安値と根拠が research.md に記録されている
  - _Requirements: 5.7, 6.2_
  - _Depends: 1.1_
  - 状況: 合成図での実測（前後の URL 長、200 の確認、失敗しきい値、目安値 6800）は research.md に記録済み。問い合わせの図そのものでの前後の長さと 200 の確認は、図が手元に無く未実施（図のコピーを持つ人が research.md の手順で確かめる）

- [ ] 1.3 （1.2 で問い合わせの図が上限に収まらなかった場合だけ）追加で削る
  - 未使用の色の段階を整理するか、非 UML 図種の `<style>` 定義を消すかを検討する
  - `<style>` 定義を消す場合は、その図種のダーク配色が失われるので、ダーク用の既定色を補う対策と組にする
  - テーマが参照する変数に、定義の無いものが残っていない（PlantUML がエラーにならない）ことを確かめる
  - 完了条件: 問い合わせの図が公開 plantuml.com で 200 になる
  - _Requirements: 5.3, 5.4, 5.6_
  - _Depends: 1.2_

- [ ] 2. 描画失敗のエラー表示（GET）
- [x] 2.1 (P) GET の URL 長の目安値を定数にする
  - 1.2 で決めた値を、方式の型・判定関数と同じ置き場所に定数として置く。リクエストを止める用途には使わず、メッセージを選ぶためだけに使う
  - 完了条件: Viewer から import できる
  - _Requirements: 6.2_
  - _Boundary: http-method_
  - _Depends: 1.2_

- [x] 2.2 (P) GET のエラーメッセージを5ロケールに追加する
  - `plantuml` 名前空間に「URL 長の上限を超えた可能性が高い（図を分割・簡略化する）」と「描画できなかった（サーバーに接続できない、またはサーバーのエラー）」の2件を、en_US・ja_JP・fr_FR・ko_KR・zh_CN のすべてに訳して追加する
  - 完了条件: 5ロケールすべてで同じキーが引け、i18n の検査（lint）が通る
  - _Requirements: 6.2, 6.4, 6.7_
  - _Boundary: locales_

- [x] 2.3 Viewer で GET の失敗を検知してエラーを表示する
  - `onLoad` と `onError` を分け、失敗したら画像の代わりにエラーメッセージを図の位置に表示する。`src` の長さが目安値以上なら「URL 長の上限」、そうでなければ「描画できなかった」のメッセージにする
  - 失敗時に、理由・方式・URL の長さをコンソールに警告として出す
  - 成功・失敗のどちらでも描画中ステータスを完了にする
  - 完了条件: Viewer のテストで、成功で画像、失敗で長さに応じたメッセージ、どちらでも描画中ステータスが完了、警告の出力、1つの図の失敗が他の図に影響しないことを確かめている
  - _Requirements: 4.1, 6.1, 6.2, 6.4, 6.5, 6.6, 7.1, 9.1_
  - _Depends: 2.1, 2.2_

- [x] 2.4 テーマと URL 長の回帰テストを追加する
  - ミニファイ後のテーマについて、コメント行と空行が無いこと、配色定義（非 UML の `<style>` を含む）が残っていること、テーマ付きソースが短くなっていることをライト・ダーク両方で確かめる
  - `skinparam ParticipantPadding`／`skinparam Padding` がテーマに戻っていないことを固定する
  - 長い図と通常の図をそれぞれ用意し、軽量化後のテーマを付けて `plantuml-encoder` で GET 用 URL にしたとき、1.2 で確かめた上限より短いことをライト・ダーク両方で固定する。今後テーマを変えて URL が上限を超えたら、このテストが落ちるようにする
  - 長い図は、問い合わせの図と同じくらいの大きさになるように作った架空の図にする（顧客の図は使わない）
  - 完了条件: テストが通る
  - _Requirements: 5.4, 5.5, 5.6, 5.7_
  - _Depends: 1.2_

- [ ] 3. 送信方式の選択と POST 描画
- [x] 3.1 送信先から送信方式を決める判定関数を作る
  - 設定値が `get`（大文字・小文字は区別しない）なら GET、送信先が空か解析できなければ GET、ホスト名が `plantuml.com` か `*.plantuml.com` なら GET、それ以外は POST を返す。`get` 以外の設定値は無視する
  - ホスト名は完全一致か `.plantuml.com` で終わるかで比べる
  - 完了条件: `plantuml.com.example.org` を POST と判定するケースを含め、判定の各ケースを `it.each` で固定したテストが通る
  - _Requirements: 1.1, 1.2, 1.3, 2.1, 2.2_
  - _Boundary: http-method_

- [ ] 3.2 送信方式の設定を追加し、画面まで渡す
  - 環境変数 `PLANTUML_HTTP_METHOD` で設定できる構成項目を追加する（既定値なし）
  - サーバー側でページの設定を作るときに判定関数を呼び、決まった方式をレンダラ設定に入れる。共有リンクのページにも同じ値が渡る
  - レンダラ設定の既定値に GET を入れ、レンダラ設定を作るテストやモックを更新する
  - 完了条件: 未設定・`get` 指定・自前の送信先のそれぞれで、レンダラ設定に期待どおりの方式が入る
  - _Requirements: 1.1, 1.2, 2.1, 2.3_
  - _Depends: 3.1_

- [ ] 3.3 remark プラグインを方式で分岐させる
  - プラグインに方式を渡し、レンダラの登録3か所（通常表示・簡易表示・プレビュー）から渡す
  - GET は今のまま。POST はテーマを付けたソースを属性に持つ `<plantuml>` 要素を作り、`src` は付けない
  - サニタイズの許可リストにソース用の属性を足す。送信先が空ならどちらの方式でも要素を作らない
  - 完了条件: プラグインのテストで、GET の出力が今と同じであること、POST の要素の形、どちらの方式でもライト・ダークに応じたテーマが付いていること、許可リスト、送信先が空のときに要素を作らないことを確かめている
  - _Requirements: 1.4, 3.1, 5.1, 5.2, 5.3, 9.1, 9.2_
  - _Depends: 3.2_

- [ ] 3.4 (P) ブラウザから PlantUML サーバーへ POST する取得処理を作る
  - テーマ付きソースを本文に入れて、送信先の `/svg` へ POST する。`Content-Type: text/plain; charset=UTF-8` だけを付け、リダイレクトは追わず、Cookie は送らない
  - SVG の応答はステータスが 200 でも 400 でも成功として返す。例外とリダイレクトは「POST が使えない」、それ以外は「描画できなかった」として返す
  - 閲覧中のメモで同じソースの送信を1回にまとめる。件数に上限を設けて古いものから捨て、失敗はメモに残さない
  - 完了条件: `fetch` をモックしたテストで、応答の分類、送信内容（ヘッダ・リダイレクト・Cookie）、送信の重複排除、上限での追い出し、失敗をメモに残さないことを確かめている
  - _Requirements: 3.1, 3.2, 3.3, 3.5, 6.3, 8.1, 8.2_
  - _Boundary: fetch-plantuml-svg_

- [ ] 3.5 Viewer に POST の描画を追加する
  - ソースがあれば、レンダラ設定の送信先へ取得処理で送り、受け取った SVG から blob URL を作って `<img>` で表示する。アンマウント時やソース変更時に blob URL を解放し、古いソースの結果は捨てる
  - 送信先は要素の属性からは取らない
  - 取得に失敗したら、理由に応じたエラーメッセージを表示する。理由・方式・ソースの長さ・応答ステータスをコンソールに警告として出し、描画中ステータスを完了にする
  - 「POST に対応していないか、接続できない（管理者は `PLANTUML_HTTP_METHOD=get` で戻せる）」のメッセージを5ロケールに訳して追加する
  - 完了条件: Viewer のテストで、POST の成功表示、blob URL の解放、失敗理由ごとのメッセージ、取得失敗でも描画中ステータスが完了になること、送信先にレンダラ設定の値を使うことを確かめている。i18n の検査が通る
  - _Requirements: 3.4, 4.1, 6.1, 6.3, 6.4, 6.5, 6.6, 6.7, 7.1, 7.2_
  - _Depends: 3.3, 3.4_

- [ ] 4. 実環境での確認
- [ ] 4.1 ライト・ダークの見た目を確認する
  - 公開 plantuml.com の既定構成で、主要な図種（class・sequence・activity・component・state・note）と非 UML 図種（gantt・mindmap・json など）が、ライト・ダークの両方で崩れず読めることを確かめる
  - 完了条件: 図種ごとの確認結果（スクリーンショットかチェックリスト）が残っている
  - _Requirements: 5.1, 5.2, 5.3, 5.4_
  - _Depends: 1.1_

- [ ] 4.2 実ブラウザで両方の方式を確認する
  - 公開 plantuml.com の場合:
    - GET で描画される。大きすぎる図は「URL 長の上限」のエラーになる
    - 構文エラーの図（400＋SVG）が `<img>` でエラー画像として表示されるか、onError になるかを確かめ、research.md に記録する
  - 自前の plantuml-server の場合（`plantuml/plantuml-server:jetty` を docker で起動）:
    - 未設定で POST になり、GET では URL が長すぎる図が描画される
    - 日本語が文字化けしない。構文エラーのときにエラー画像が出る
    - `PLANTUML_HTTP_METHOD=get` で GET に戻る
    - CORS の許可ヘッダを付けない設定のプロキシを手前に置くと「POST に対応していないか、接続できない」のエラーになる
    - 送信先が閲覧者の PC やプライベートネットワーク上（`localhost`、社内 IP など）にある場合、ブラウザの「公開サイトからローカル・プライベートネットワークへの通信」の制限で、`<img>` と `fetch` の扱いが違うかどうかを確かめる
  - 完了条件: 確認結果が research.md に記録されている
  - _Requirements: 1.1, 1.2, 2.1, 3.1, 3.2, 3.3, 3.5, 6.2, 6.3, 9.1_
  - _Depends: 2.3, 3.5_
