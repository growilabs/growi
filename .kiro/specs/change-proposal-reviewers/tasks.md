# Implementation Plan

> 本計画の語（閲覧できるページの操作、判断の対象、閲覧できないページの操作、承認者である人、判断の記録、見える段階）は requirements.md の「本要件で使う言い方」と design.md の用語と同じ。
>
> **進め方**: 各実装タスクは、先にテストを書いて失敗を確かめてから実装する（RED → GREEN）。テストの書き方は、`essential-test-design` と `essential-test-patterns` のスキルに従う。
>
> **テストの要件番号**: この spec のテストの名前やコメントに要件の番号を書くときは、core の番号と区別できる形（例: `Reviewers Req 2.5`）にする。core に戻すとき（10.1）に、この形を grep して、新しい番号に書き換える。
>
> **この spec は amend spec である**: 最後のタスク（10）で、内容を `change-proposal-core` に戻し、この spec を削除する。要件の番号は、そのとき core の番号（14 の続き）に付け直す。
>
> **公開の順序**: 承認者の機能は、viewer の承認画面と承認待ちの一覧、ai-agent の承認者の指定の入口ができるまで、機能の切り替え（1.4）を無効のままにする。それまでは、承認者を指定して作る入口と、承認者の追加が、受け付けられない。

  - 作成の入力で、承認者（ユーザー・グループ・混在・依頼した人自身）と変更の目的を受け、存在しない承認者・上限・文字数を検証し、重複を 1 つにまとめて保存する。承認者の指定が無ければ、依頼した人だけが承認者になる

  - 後続・見直しは、元の承認者を引き継ぎ、作成のときに指定し直せる。依頼した人以外を含む承認者がいる提案は、自動反映の方針にかかわらず、作成直後に何も反映せず、すべて承認待ちにする
  - 承認者を指定しない作成と、承認者を持たない既存の提案、取り消しの Change Proposal の動きが変わらないことを、テストで確かめている

- [ ] 5. 通知と activity の記録
- [x] 5.1 承認者への通知と、依頼した人への結果の通知を作る
  - 承認者への通知: 新しく承認者になった個人のユーザー（依頼した人と、追加した人を除く）に送る。中身は、受け取る人が閲覧できるページの分だけで作る。判断の対象が 0 件の人には送らない。グループの所属者には送らない
  - 結果の通知: 1 回の求めにつき 1 件を、依頼した人に送る。中身は、依頼した人に返す操作の結果と、コメントから作る。そのような操作が 0 件で、全体の却下も無ければ送らない。全体の却下を記録した求めは、操作が無くても送る。依頼した人自身の承認では送らない
  - どちらの通知にも、その求めの activity の ID を渡す。通知の一覧に、判断した人が出る
  - 反映のあとのまとめた通知（既存）の宛先と中身が変わらないことと、通知の中身に閲覧できないページのパス・タイトル・件数が入らないことを、結合テストで確かめている
  - _Requirements: 4.11, 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 6.7_
  - _Depends: 1.5, 4.1_
  - _Boundary: review-notifier_
- [x] 5.2 承認・却下・放棄・承認者の追加と削除の activity を記録する

  - 応答を送る前に、同期的に記録する（`activity-recording` の規則）。承認者の ip と endpoint は、承認の activity に残す（承認がきっかけで動く反映の activity には渡さない。それは 6.2 の担当）
  - 監査ログを無効にしていても記録されること、経路が保存されること、操作者と `username` が保たれることを、結合テストで確かめている
  - _Requirements: 6.8, 6.9, 6.10_

- 6.3: **7.1 の実装者へ**: `POST /:id/reviews` の振り分け: `reject` でキーなし → `rejectAll`、`reject` でキーあり → `rejectOperations`、`abstain` → `abstain`。`abstain` にキーが無い求めと、キーが空の配列の求めは、route が 400 `validation_failed` で断る（design の route 表）。サービスに空の配列を渡すと、何も記録せずに成功を返す。次のエラーコードは、HTTP の応答に変える処理を足すまで `respondWithServiceError` の既定の分岐で 500 になる: `comment-too-long`、`requester-cannot-review`、`user-not-allowed`。何も記録しなかった求め（対象が 0 件）は activity を決着させない（ミドルウェアの後始末で捨てられ、応答は 200）。空の文字列のコメント `''` は、そのまま保存され、通知にも入る。省略と同じに扱うかは、7.1 の route の検証で決める。`isWithinCodePoints` は `normalize-create-input.ts` から import している（共通の util への移動は後の整理）。記録を足したあと、前の記録を消す処理で衝突以外の例外が出ると、記録は保存されたまま 500 になり、activity も通知も出ない（design の手順 6 が許している範囲。読み出す側は最新の 1 件だけを使う）。
