# Brief: change-proposal-reviewers

**Type**: amend spec（完了済みの `change-proposal-core` の契約を変える一時的な spec。最後のタスクで内容を core に戻し、この spec を削除する。規則: [spec-lifecycle](../../../.claude/rules/spec-lifecycle.md)）

**Revalidation Triggers への影響**: core が「依頼した人だけが承認・飛ばす・破棄できる」「承認待ちは依頼した人にしか返さない」を前提にしている箇所（core の 4.6、9.2、9.4 と、viewer・ai-agent がそれに依存する表示）。これらは、この spec が承認者を導入すると前提が崩れる。

## Problem

今の Change Proposal は、承認できるのが依頼した本人だけで、承認待ちは本人以外に見えない。そのため、次のような使い方ができない。

- ユーザーAが AI に作らせた Change Proposal を、ユーザーBに確認して承認してもらう。
- ユーザーグループの人たちが手分けして承認する。
- 依頼した人が不在の間、承認待ちが溜まり続ける。

AI が頻繁に Change Proposal を作るようになると、本人だけが承認する前提では、レビューが 1 人に集中する。

## Current State

- モデルに持つ人は依頼した人（`requester`）だけで、宛先・レビュアー・担当者に当たる項目は無い（core の `CreateProposalInput`）。
- 承認・飛ばす・破棄・ページごとの通知の指定の変更ができるのは依頼した人だけ。他のユーザーには「見つからない」と同じ応答を返す（core の 4.6、7.15）。
- 承認待ちの Change Proposal は、依頼した人以外には返さない（core の 9.2、viewer の要件）。反映済みのものは、見る人が閲覧できるページの分だけを返す。
- 閲覧できるかどうかはページ単位で決まる。GROWI では、閲覧できるページは編集もできる。
- 反映するときは、依頼した人の権限をその時点で確かめ、作るリビジョンの作者も依頼した人にする（core の 3.6、3.10）。

## Desired Outcome

- Change Proposal に、承認者を指定できる。承認者は、複数のユーザー、複数のユーザーグループ、その混在のどれでもよい。依頼した人自身を承認者に含めてもよい。指定が無いときは、今までどおり依頼した人だけが承認する。
- 承認者は、承認待ちの Change Proposal を見て、自分が閲覧できるページの操作を承認できる。グループが承認者のときは、そのグループの誰か 1 人が承認すれば、そのページの操作は反映される。
- 承認者は、別の承認者（ユーザー・グループ）を追加できる。
- 承認待ちは、依頼した人と承認者だけに見える。反映済みの見え方は今までと同じ。
- 承認者に指定された人へ通知が届き、人間が気付ける。
- 見る人が閲覧できないページの存在・件数は、どの画面・通知・応答からも分からない（今までと同じ）。

## Approach

- Change Proposal に承認者の一覧（ユーザーとユーザーグループ）を持たせる。誰が承認者かは、操作の時点で決める（グループの所属が変わったら、そのときの所属で判定する）。
- 承認・飛ばす・破棄の権限を「依頼した人だけ」から「依頼した人または承認者」に広げる。ただし、反映するときの権限の確認と、作るリビジョンの作者は変えない（依頼した人の権限で確認し、依頼した人が作者になる）。承認者に指定されたことで、書き込める範囲が増えないようにする。
- 承認者が操作できる範囲は、承認者自身が閲覧できるページの操作に限る。
- 承認者を指定した Change Proposal は、承認者に通知する。

## Scope

- **In**:
  - 承認者の保存（ユーザー・グループ・混在・依頼した人自身）と、指定が無いときの既定
  - 承認者による承認・飛ばす・破棄と、承認者の追加
  - 承認待ちの Change Proposal を、依頼した人と承認者に返すこと（見える操作の絞り込みを含む）
  - 承認者への通知
  - 作成の API で承認者を指定できること
  - 上記の 5 言語の文言（core が持つ共通の表示名の範囲）
- **Out**:
  - 承認・承認者の追加の画面（`change-proposal-viewer` に別に足す）
  - AI チャットで承認者を選ぶ画面と指定の道具（`change-proposal-ai-agent`、必要なら別に判断する）
  - 全員の承認を要求する形（グループ全員の承認、承認数の閾値）
  - 承認者の削除（未決。requirements.md の「決まっていないこと」を参照）
  - 導線（サイドバーなど）の変更（viewer の導線の判断は、この spec の要件が決まった後に行う）
  - 差分の塊ごとの承認

## Constraints

- 見る人が閲覧できないページの存在・件数・パスを、応答・通知・エラーのどこにも出さない。承認者であっても、閲覧できるページの操作だけを扱う。
- 閲覧できるかどうかの判定には、GROWI の既存の判定を使い、新しい規則は作らない。グループの扱い（グループの階層や外部連携のグループを含む）も、既存のページの閲覧範囲（グループ指定）と同じ規則に合わせる。
- 読み取り専用ユーザーとゲストは、承認者になれても承認できない（今の core の 9.9 と同じ）。
- 既存の Change Proposal（承認者の指定が無いもの）の振る舞いは変えない。
- 反映するときの権限の確認と作者は依頼した人のまま（承認者の権限で書き込まない）。
