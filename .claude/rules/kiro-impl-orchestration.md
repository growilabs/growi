# kiro-impl Orchestration Policy

How the cc-sdd implementation workflow (`/kiro-impl`) distributes work across models in
this repository. This layers on top of the `kiro-impl` skill
(`.claude/skills/kiro-impl/SKILL.md`) — it does **not** replace that skill's TDD gate
(RED → GREEN) or its per-task reviewer / debug loop, and deliberately does not restate
them.

"Opus / Fable / Sonnet tier" is written by tier on purpose, not pinned to a version id,
so it survives model releases.

## Why this is a rule and not steering

Both reasons were learned from watching this policy get skipped during real `/kiro-impl`
runs:

- **`.kiro/steering/` is not auto-loaded.** `CLAUDE.md` describes steering as project
  memory in prose, but the only things that actually enter a session's context are
  `.claude/rules/*.md` and `@`-imported files. A policy that has to be honored on every
  run cannot live somewhere that depends on a skill remembering to read it.
- **`.claude/skills/kiro-impl/SKILL.md` is generated by cc-sdd** — its entire history is
  a single `upgrade cc-sdd` commit. Encoding this policy by editing that file would be
  overwritten, without any merge conflict to warn us, on the next upgrade. **Do not move
  these hooks into the skill.** They belong here, where the repository owns them and
  upgrades cannot touch them.

## 1. This policy outranks the skill's argument-derived default

`SKILL.md` Step 2 determines mode from the argument list: task numbers → manual mode, no
task numbers → autonomous mode. **That is the default, not the decision.** Where the
sections below direct otherwise, they win.

Precedence, highest first:

1. An explicit user request for a specific mode or model
2. This policy
3. The skill's argument-derived default

## 2. On a strong main-loop model, orchestrate first

When the session's main-loop model is an **Opus** or **Fable** tier model and
`/kiro-impl` is invoked, treat orchestration — not typing implementation — as the
primary duty:

- Run `kiro-impl` in **autonomous mode** (a fresh implementer subagent per task) rather
  than implementing in the main context, **even when the argument list would otherwise
  select manual mode** — passing task numbers does not by itself mean the work is typed
  in the main context — unless the user explicitly asked for manual mode.
- Spend the strong main-loop model on planning, task dispatch, review synthesis, and
  GO/NO-GO judgement — the work that benefits most from the stronger model — and delegate
  the mechanical implementation to subagents.

On a lighter main-loop model, in-context (manual-mode) implementation is fine; this rule
does not force subagent dispatch there.

## 3. Match the implementer subagent's model to task difficulty

Choose each implementer subagent's model from the task's difficulty (consistent with the
tiers in `.claude/rules/performance.md`):

- **Opus** — architectural tasks, tricky debugging, subtle correctness, anything where a
  wrong shape is expensive to unwind.
- **Sonnet** — straightforward, mechanical, well-specified tasks.

## 4. Final review runs adversarially on Opus

After all tasks are implemented, the feature-level review/validation gate
(`/kiro-validate-impl`, applying the `kiro-review` protocol) must run on an **Opus** tier
model, as a **fresh** subagent — never the implementer reviewing its own work. This sits
on top of the per-task reviewer, not instead of it: the per-task gate catches local
defects; this final adversarial pass is where a strong, independent model looks at the
whole feature.

## 5. State the plan before dispatching

Before the first subagent dispatch of a `/kiro-impl` run, output this block:

```
Orchestration plan
- Mode: <autonomous|manual> (<argument default | policy override | user request>)
- Implementer model: <per-task assignment, e.g. 1.1 Sonnet / 1.2 Opus>
- Final review model: <model>
```

It is the visible evidence that the policy was applied: **a run that reaches a dispatch
without having produced this block skipped the policy** — stop and apply it rather than
continuing.

Pass the assigned model explicitly on every Agent dispatch. The skill's dispatch steps
name no model, so an implicit one silently falls back to the host default and §3 / §4
never take effect.

## Out of scope here: TDD

cc-sdd already enforces RED → GREEN itself, so this policy adds nothing about it and
neither should any other repo document: `templates/implementer-prompt.md` requires the
implementer to capture the pre-implementation failing output as `RED_PHASE_OUTPUT`, and
`templates/reviewer-prompt.md` rejects a behavioral task whose `RED_PHASE_OUTPUT` is
missing or empty. For how to *write* the tests well, `.claude/rules/testing.md` (always
loaded) points to the `essential-test-design` and `essential-test-patterns` skills.
