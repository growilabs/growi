# 閉域ネットワークでの運用

GROWI 本体をインターネットに公開できない組織でも、この chat-integration proxy を
DMZ（社内ネットワークとインターネットの間に置く区画）に 1 つだけ立てることで、
チャット連携を使える（要件 13.1）。この文書は、その構成の図・必要な通信・
proxy と GROWI の役割分担、そして **proxy が乗っ取られた場合に閉域内の GROWI が
受ける影響と、要件 10 の署名がそれをどう抑えるか**（要件 13.5）をまとめる。

サービスごとの事前準備（Slack/Discord/Teams/Mattermost のアプリ登録など）は
`setup-slack.md`・`setup-discord.md`・`setup-teams.md`・`setup-mattermost.md` を
参照。ここでは閉域という配置そのものに関わる内容だけを扱う。

## 1. 構成図

```
                          インターネット
                                |
                  (Teams だけ、Azure Bot Service からの
                   HTTPS 接続を 1 本だけ受ける)
                                |
   ==============  DMZ  ========|===========================
   |                            v                           |
   |   +--------------------------------------------+       |
   |   |      chat-integration proxy (この app)      |       |
   |   |  - Slack   : Socket Mode でこちらから接続   |       |
   |   |  - Discord : Gateway でこちらから接続       |       |
   |   |  - Mattermost: WebSocket でこちらから接続    |       |
   |   |  - Teams   : Azure Bot Service からの POST  |       |
   |   |              を webhook で受ける            |       |
   |   +--------------------------------------------+       |
   |             |                          ^                |
   |    HTTP(S)  |  proxy から GROWI へ     | GROWI は公開   |
   |    (署名つき|  接続しに行く            | しない          |
   |     リクエスト)                        |                |
   ================================|=========================
                                    v
   ==============  閉域ネットワーク（社内網）===================
   |                                                          |
   |   +----------------------+                               |
   |   |  GROWI application   |                                |
   |   |  (公開しない)        |                                |
   |   +----------------------+                               |
   |                                                          |
   ============================================================

   [PostgreSQL（proxy が使う DB）は DMZ・閉域内網のどちらに置くかが
    未決の論点。3 節参照。図では位置を固定しない]
```

要点:

- **GROWI は一切公開しない。** proxy から GROWI へ接続しに行く形（決定 7）を
  Gen 1 から引き継いでいるので、GROWI 側に穴を開ける必要が無い。
- **proxy が DMZ に立つ唯一の公開対象。** 4 サービスのうち Teams だけが
  「外から proxy へ接続してくる」形（Bot Framework が proxy の webhook
  エンドポイントへ POST してくる）で、残り 3 サービス（Slack・Discord・
  Mattermost）は proxy 側から接続しに行く形なので、外から proxy への穴は要らない。
  この事実は `GET /health` の応答でも確認できる（後述）。
- **proxy は PostgreSQL を必要とする。** DB をどこに置くかは運用者が判断する
  未決の論点として 3 節に残す。

## 2. 必要な通信

| 経路 | 方向 | 必要性 | 備考 |
|---|---|---|---|
| proxy → GROWI | proxy から GROWI（社内網内） | 必須 | 通知の投稿・コマンドの実行・鍵の登録などはすべてこの向き。GROWI 側に穴は不要 |
| proxy → Slack | proxy から Slack（インターネット） | 必須 | Socket Mode。外部からの穴は不要 |
| proxy → Discord | proxy から Discord（インターネット） | 必須 | Gateway 接続。外部からの穴は不要 |
| proxy → Mattermost | proxy から Mattermost | 必須 | Mattermost が閉域内にある場合、その閉域内で完結する |
| Teams（Azure Bot Service）→ proxy | インターネットから proxy への webhook | 必須（どの配置でも） | 4 サービス中 Teams だけがこの向き。閉域構成だからではなく、Teams というサービスの性質上どの配置でも必要——閉域構成が変えるのは「どこで・どの接続元に絞って開けるか」だけ。詳細は `setup-teams.md` §4 |
| proxy ↔ PostgreSQL | proxy から DB | 必須 | proxy 自身のテーブル用 `DATABASE_URL` と、Chat SDK のテーブル用 `CHAT_SDK_DATABASE_URL` の2本を接続先として指定（既定では同じホストを指す）。配置は 3 節で扱う未決の論点 |

各サービスについて「外から proxy へ届く経路が必要か」は、実装が持つ
`REQUIRES_INBOUND_REACHABILITY`（`src/capabilities/platform-capabilities.ts`）
という宣言がそのまま真実であり、この文書はその値を書き写したものにすぎない。
**動いている proxy 自身に必ず確認すること**: `GET /health` を叩くと、外から穴を
開ける必要があるサービスとその開けるパスが `inboundExposure` として実際に返る
（値がドキュメントより後から変わっても、確認先はここになる）。今のところ
値を持つのは Teams だけで、Slack・Discord・Mattermost は空である。

**GROWI 側の宛先許可も忘れずに設定する。** proxy は GROWI へ送るすべての
リクエストの前に、名前解決したアドレスが私的アドレス帯でないかを検証する
（`judgeGrowiUri`）。閉域内の GROWI のアドレスはほぼ確実に私的アドレス帯に
入るため、`GROWI_ALLOWED_DESTINATIONS` 環境変数でそのホスト名を明示的に
許可しない限り、proxy から GROWI への通信はすべて拒否される。同じ設定で、
閉域内の自前認証局・自己署名証明書を信頼させる CA 証明書のパスも
ホスト名ごとに指定できる。

## 3. proxy と GROWI の役割分担

| 役割 | 担当 |
|---|---|
| チャットサービスへの接続を維持する（Socket Mode / Gateway / WebSocket / webhook 受信） | proxy |
| 届いたイベントをコマンドとして解釈する | proxy |
| **GROWI へ送るリクエストに署名する**（proxy 自身の秘密鍵で） | proxy |
| **proxy から届いたリクエストの署名を検証する**（proxy の公開鍵で） | GROWI |
| ページの検索・作成の実行と、その**権限判定**（読めるか・作れるか） | GROWI（proxy の言い分を信用せず、GROWI 自身が判定する） |
| 通知の宛先チャンネルが、署名から特定した関係の installation に属するかの検査 | proxy |
| 非公開ページの本文を通知に含めるかどうかの判断 | GROWI |

proxy の公開鍵は、ペアリング（proxy と GROWI を結びつける手続き）の時点で
GROWI 側に登録され、GROWI はそれを使って以降のすべてのリクエストの署名を
検証する。この署名の検証は GROWI 側で行われるからこそ意味を持つ
（4 節で扱う理由により、proxy 側の判定は侵害時には防御にならない）。

**PostgreSQL の配置は、この構成では運用者の判断に委ねられている。**
proxy は installation・関係・鍵などの状態を PostgreSQL に持つため、DB への
到達経路が要る。DB を DMZ に置くか、DMZ から閉域内の DB への経路を開けるかは
どちらもあり得る構成で、この spec は**どちらか一方を推奨しない**——DMZ に
置けば閉域内への穴が 1 つ減るが DMZ 自体に永続データが乗り、閉域内に置けば
逆に DMZ から閉域内への恒常的な経路が要る。運用者が自組織のセキュリティ方針
に照らして選ぶ論点として明示するに留める。

## 4. proxy が侵害された場合に GROWI が受ける影響と、署名の検証がどう抑えるか

**ここが最も誤解しやすい点なので、防げるものと防げないものを混ぜずに書く。**
署名の検証（要件 10）が止められるのは、鍵を持たない第三者だけである。
**鍵を持っている本人（＝乗っ取られた proxy 自身）は止められない。**
この区別を曖昧にすると、閉域に置くという判断が誤った前提の上で下される。

### 4.1 要件 10 の署名が防ぐもの・防がないもの

以下は umbrella の design.md「Security Considerations」の表をそのまま載せる。

| 出来事 | 要件 10 の署名で防げるか |
|---|---|
| 経路上の第三者がリクエストを書き換える | **防げる**（`@method` / `content-type` / `content-digest` を署名対象に含める。本体には `relationId` と `op` が入り、`content-digest` が覆う） |
| 第三者が署名を**別の口へ流用する** | **防げる**（受ける側が本体の `op` と自分がどの口で受けたかを突き合わせる） |
| 第三者が署名を**別の GROWI へ流用する** | **防げる**（鍵は関係ごとなので、別の関係では検証が落ちる） |
| 第三者が過去のリクエストをそのまま再送する | **防げる**（`expires` と nonce） |
| **相手側の DB が漏れて、そこから自分になりすまされる** | **防げる**。相手が持つのは公開鍵だけで、秘密鍵は通信路にも相手の DB にも出ない（要件 10.6）。Gen 1 は平文の共有秘密を両側に置いていたのでこれが成立していなかった |
| **chat-integration proxy 自身が侵害される** | **防げない。** 攻撃者は proxy の秘密鍵をそのまま使い、GROWI から見て完全に正しいリクエストを作れる。要件 10.1〜10.4 と 10.6 はすべて素通りする |

### 4.2 proxy が乗っ取られたときに実際にできること

閉域構成では proxy が DMZ に立つため、ここを具体的に把握しておく必要がある。

- **紐付いている利用者の名前でページを作れる。** 作成者はその利用者に
  紐付いた GROWI ユーザーとして記録される
- **紐付いている利用者の閲覧権限で検索できる。** その人が読めるページの
  パス・タイトル・URL・更新日時が得られる
- **通知として任意の文面を、紐づく workspace のチャンネルへ投稿できる**

**逆に、できないこと** — GROWI の管理者になること、GROWI の権限判定を回避
すること、紐付いていない利用者になりすますこと。いずれも **GROWI 側が
独立に判定する**ため。（チャンネル単位のコマンド権限がどこまで効くかは
別の性質を持つため、4.3 で切り分けて扱う）

### 4.3 「どちら側が判定するか」が防御になるかを決める

**proxy 側で判定するものは、proxy が侵害された時点で防御にならない。**
攻撃者は自分が持っている検査を飛ばすだけでよい。したがって、防御として
数えてよいのは **GROWI 側で判定するもの**に限られる。これが umbrella の
design.md が示すもう 1 つの表の要点であり、以下はその表をそのまま載せる。

| 仕組み | 判定する側 | 侵害時に防御になるか |
|---|---|---|
| 署名の検証（要件 10.1–10.4, 10.6） | GROWI | **ならない**（攻撃者が秘密鍵ごと持っているため） |
| **チャンネル単位のコマンド権限（要件 11）** | GROWI と proxy の両方 | **どこでも不許可にしてあるコマンドについてだけ、なる**——`CommandEnvelope.channel`（そのコマンドがどのチャンネルから呼ばれたか）を書いているのは proxy 自身なので、GROWI にはそれを裏付ける手立てが無い。1 つでもチャンネルを許可した瞬間、乗っ取った攻撃者はそのチャンネルを名乗るだけで通ってしまう。「許可したチャンネルの範囲に被害が収まる」わけではない。書き込みを伴うコマンド（`create-page` / `keep`）の既定値はどのチャンネルでも不許可なので、まだ何も許可していない組織はこの経路で守られる |
| ページの閲覧・作成の権限（要件 3.6 / 4.5） | GROWI | **なる** |
| 契約面の狭さ | — | **なる**（そもそも呼べる操作が限られている） |

### 4.4 逆向き（1 台の GROWI が乗っ取られた場合）

公式運用の proxy には多数の GROWI が紐づくため、この逆向きも現実的な観点
である。攻撃者は自分の関係の範囲でしか動けない——通知の宛先チャンネルが
その関係の installation に属することを proxy 側が確かめるため、他の GROWI
の関係にも、その workspace の他のチャンネルにも触れられない。

## 5. GROWI 全体のレート制限との関係

閉域構成では、proxy が DMZ に固定 IP を持つ形で 1 台だけ立つのが普通であり、
**1 つの workspace の通信はすべてその 1 つの IP アドレスから GROWI へ届く**。
GROWI 側のレート制限（design.md によれば既定 IP・パス・メソッドごとに
1 分 2500 回）を運用者が絞ると、この送り元の集中により**チャット連携全体が
同じ制限に引っかかって止まりうる**。仕組みの詳細と運用者が確認すべき点は
`rate-limit-notes.md` にまとめる。

## まとめ

- 構成図・必要な通信・役割分担は 1〜3 節のとおりで、GROWI は公開しない。
- 署名の検証は「乗っ取られていない第三者」を防ぐものであり、「乗っ取られた
  proxy 自身」は防げない。この区別を混同しないこと（4.1）。
- 乗っ取られたときに実際にできること・できないことは 4.2 のとおりで、
  GROWI 側の独立した権限判定が最後の防御線になる。
- PostgreSQL の配置（3 節）と、レート制限の設定（5 節）は運用者が自組織の
  方針に照らして判断する論点として残っている。
