# GROWI の全体レート制限との関係

GROWI application は `features/rate-limiter`（`apps/app/src/features/rate-limiter/`）
で全 API にレート制限を掛けている。仕組みを実物のコードで確認した内容は次のとおり。

- **判定の単位は「利用者ごと」と「IP アドレスごと」の両方。** ログイン中の
  利用者がいれば利用者単位でも数え、それとは別に IP アドレス単位でも数える
  （どちらか一方でも超えれば 429 を返す）。
- **エンドポイントごとに個別の上限を宣言できる。** `API_RATE_LIMIT_<番号>_ENDPOINT`
  ／`_METHODS`／`_MAX_REQUESTS`／`_USERS_PER_IP` の組で 1 エンドポイント分を
  宣言する（`config-generator.ts`）。宣言が無いエンドポイントには既定値が
  適用される。
- **既定値は「1 分あたり 500 回」（`DEFAULT_MAX_REQUESTS`）に、IP アドレス単位
  では「利用者換算 5 人ぶん」の掛け算（`DEFAULT_USERS_PER_IP_PROSPECTION`）が
  掛かる。** つまり、個別設定の無いエンドポイントで 1 つの IP アドレスが
  実際に許されるのは 1 分あたり 500 × 5 = **2500 回**である。design.md が
  「既定は IP・パス・メソッドごとに 1 分 2500 回」と書いているのはこの掛け算後
  の値を指す。

## 通常は問題にならない

複数のチームメンバーが GROWI をブラウザから直接使う通常の利用では、
アクセス元の IP アドレスが利用者ごとに分散するため、既定値の
「1 分 2500 回」に単独の送信元が到達することはまずない。

## chat-integration proxy 経由では事情が異なる

**1 つの workspace（Slack のワークスペース、Discord のサーバーなど）から
GROWI への通信は、すべて proxy という 1 つの送り元から来る。** 通知の投稿・
コマンドの実行・鍵の登録といった proxy → GROWI のリクエストは、実際に
チャットで操作した利用者が何人いても、GROWI から見れば同じ IP アドレスから
届く。閉域ネットワークで proxy を 1 台だけ立てる構成（`closed-network-deployment.md`
参照）ではこの集中がとくに顕著になる——proxy が DMZ の固定 IP を持つ
構成が普通だからである。proxy はログイン済みの GROWI セッションを持たない
ため、proxy からの通信は利用者単位ではなく**常に IP アドレス単位でのみ**
数えられる。

## 運用者が注意すべきこと

**GROWI 側のレート制限を既定値より絞ると、チャット連携全体が同じ制限に
引っかかって止まりうる。** `API_RATE_LIMIT_*` でエンドポイントごとに
`_MAX_REQUESTS` や `_USERS_PER_IP` を既定より小さい値に絞ると、proxy からの
通信も同じ IP・パス・メソッドの組として数えられるため、chat-integration
proxy が使う経路が意図せず詰まる可能性がある。

**エンドポイントごとに個別の上限を宣言する仕組み自体はあるので**、
proxy が使う GROWI 側のエンドポイントに対してだけ、他より高い
`_MAX_REQUESTS` / `_USERS_PER_IP` を明示的に宣言することは、この仕組みの
範囲でできる。ただし**そのエンドポイントを個別に指定して運用者が設定する
場合の話であり、proxy 経由の通信だけを自動的に見分けて優遇する既定の仕組みは
無い**——何も設定しなければ、proxy からの通信も他の通信と同じ既定値
（1 分 2500 回／IP）で数えられる。レート制限を既定値から変更する場合は、
chat-integration proxy が実際に呼ぶ GROWI 側のエンドポイントを確認したうえで、
それらに対してだけ個別の上限を宣言するか、全体の値を十分な余裕を残した
ままにするかを検討すること。
